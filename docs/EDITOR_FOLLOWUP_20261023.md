추가·이름 편집·완결편 원복 재압축 수정은 이제 구현됐다.

기존 격추 자금·EXP·드랍 파츠, 개조 비용, 지형 효과, 무장 추가·인라인 편집,
미사용 5종 구성, 모바일 크롭, 반복재생·음악 선택·조건 고정 피해는 이미 구현된
범위다. ‘조건 고정 피해’를 실전 전체 피해 공식으로 부르지 않는다.
미리보기를 켠 채 같은 무기의 수치를 바꾼 경우도 다음 재생·정상 반복 재생에
최신 편집본을 전달하도록 보완했다. 입력 중에는 재시작하지 않고 기체·파일럿·
숨김 상태를 보존한다. 관련 프로토콜과 합성 iframe 검증 범위는
[무기 미리보기 문서](WEAPON_PREVIEW.md)를 따른다.
사용자가 제외한 α 등급, 천지인 입력 화면, 크리스 레벨 소실 추가 조사,
세이브 파츠 장착 칸 강제 확장은 이번 구현 목록에 넣지 않는다.

### 현재 전투에서 사용하는 아군 증원

사용자의 정정에 따라 단순 격납고 입수는 1차 완료 기준이 아니다. 지도에서
조건을 만족하면 지정 파일럿·기체가 현재 전투에 아군으로 등장하여 수동 조작되고,
전투 후 보유되는 흐름을 구현한다. F의 원래 CA01 출격과 CA02 생성의 actor
인수 및 수동 입력 분기가 일치함을 확인했다. 이 근거를 완결편까지 확장하지 않는다.

설정 계약은 `enabled/pilotId/unitId/level/triggerX/triggerY/x/y`다. 발동 칸과
등장 희망 칸은 서로 다르며, 구 prototype의 적 템플릿·턴·보상 설정을 이 계약으로
해석하지 않는다. 현재 ROM의 표와 지도 문맥을 저장/정규화 경로에 전달하고,
재읽기에서 지도·후보·좌표를 검사한다. native AQ03 설치/제거는 인증된 증원
이벤트의 존재에 종속되며 사용자 JSON에 별도 native 활성화 권한을 두지 않는다.

F 제4화 「포세이달의 습격」(physical34/slot54)은 정확한 본문·공통 코드·기체 속성 서명으로 활성화했다.
원래 초기 배치 완료 flag241 가드를 보존하므로 이후 남는 원래 증원3쌍과
새1쌍을 위해 파일럿/기체/actor 각각4칸을 요구한다. 기존 본문에서 조작하는
파일럿20명과 기체19는 제외하며, 구조상 일반 후보 중322파일럿/309기체가
선택 가능하다. 일반 후보라는 이유만으로 다른 맵에서도 안전하다고 하지 않는다.

실제 F a를 읽어 람바 랄(#2)+건담(#1), 레벨25, 발동(4,5), 등장(11,15)을
제품 export 경로로 적용하고 새 inspector로 재열어 값을 확인했다. 증원 해제 후
TSR와 해제된 시나리오 본문이 원본과 정확히 같고 AQ03도 제거된다. 압축 표현이
달라 전체 BIN 해시는 원본과 다르다. 출력 크기는 그대로이며 새 BIN 파일은
저장하지 않았다. 이는 게임 실행 검증을 뜻하지 않는다.
실제 로컬 브라우저에서도 해당 시나리오의 이벤트 목록에 새 증원 항목이 나오고,
켜기·레벨 변경 후1280/740/430px에서 입력값과 조작부가 유지되며 가로 넘침 및
페이지 오류가 없음을 확인했다. 확인 안내창을 정상 수락한 뒤 검사했다.

후속 profile은 원래 CA02의 좌표·보상 byte와 C7 초기 레벨 bits만 제외한
제어 흐름 해시를 검사한다. 기존 제품에서 쓰기가 허용된 배치·보상·초기 레벨은
증원과 함께 변경할 수 있다. 이 profile만으로 읽기 전용 배치를 쓰기 가능으로
확대하지는 않는다. 기존 턴·사건 조건·시점 및 승패 wrapper와 신규 증원의
동시 적용은 계속 제한한다. 별도 대사 wrapper는 정규화한 원본으로 검사한다.
다른 실제 맵·완결편 연결은 남아 있다.

추가 지원: 제30·31화 「콜로니의 반역」(physical27/slot27, map17,28×38).
초기완료flag241 이후 원래8턴 적10기의 자리를 남기기 위해 각각11칸을 검사한다.
일반 후보에서파일럿331명·기체310종을 선택할 수 있다. 실제 제품 export→재열기→
해제 원복을 확인했고,1280/740/430px UI에서 항목·입력값·가로 폭도 확인했다.
CA02 좌표·보상만 제외한 제어 해시를 사용하며 원래8/10턴 조건은 고정한다.
압축 여유가 작아 다른 편집을 함께 넣을 때 최종 저장 용량 검사는 계속 필요하다.

아래 codec·AQ02 기록은 활성화 이전의 조사 경과다.

실제 F 본문 52개를 대조하니 24바이트 기본 목적 전체를 가정하는 초기 compiler는
body0 외 실제 맵에 맞지 않았다. 기존 `inspectPendingObjectiveHook`가 인식하는
실제 맵 20개의 대기 경로를 재사용하는 compiler를 추가했다. 승리·패배와 원래
플래그 분기를 먼저 실행하고, 대기할 때만 증원 조건을 검사한다. 원래 root8와
결과 처리 코드는 옮기지 않는다. body34의 40바이트 목적 구조를 반영한 회귀는
통과했으며, 이는 아직 맵별 후속 생성 용량을 증명한 결과가 아니다.

후속 SP03 순수 codec은 실제 body34에서 15,530→15,802바이트이며, 재압축은
원래 9,163바이트 슬롯 안의9,023바이트에 들어갔다. 압축 해제→codec 원복도
원래 본문과 일치했다. 원본 BIN 크기·수정 시간을 보존했고 새 BIN은 만들지 않았다.
이는 선택한 한 본문의 저장 적합성 증거이며 생산 normalizer는 아직 해당 신규
이벤트를 거부한다. 별도 목적·제한 턴 편집과 동일 pending 위치를 함께 사용할
때는 한쪽을 조용히 덮어쓰지 않고 충돌 사유를 반환하도록 연결했다.

AQ03/SP04 후속 구현은 파일럿·기체·actor의 필요한 빈칸 수를 각각 검사한다.
실행 코드는250바이트로 기존256바이트 영역에 들어가며, 이전 AQ01/AQ02 설치는
정확히 인식·원복하되 새 증원의 실행 근거로 인정하지 않는다. 편집 JSON에는
이 예약량을 임의로 낮추는 항목을 두지 않는다. 실제 body34 순수 codec을 예약량
24/23/58로 구성하면 본문15,788바이트·압축9,016바이트이고 원래9,163바이트
슬롯에 들어간다. 이 수치는 압축 적합성 실험의 인수이며 맵 사용 권한을 뜻하지
않는다. 남은 조건은 원래 사건의 반복 횟수·도달 경계와 기체 ID 삭제 참조다.

AQ03 native-only 적용본은 실제 F 승인 입력을 메모리에서 수정하여 에디터로
다시 열었고, 버전3 식별 및 원복 후 전체 SHA 일치를 확인했다. 변경 sector는
2/372 두 곳, 출력 크기는578,512,032바이트로 같았다. 새 BIN 파일과 에뮬레이터
실행은 만들지 않았다. 구 helper가 붙은 이미지를 새 증원 실행 근거로 오인하지
않도록 정규화 이전 설치 버전도 함께 검사한다. 이 검사는 증원 이벤트 자체의
활성화나 실제 전투 실행 검증을 대신하지 않는다.

## 무기 탭의 전투화면

- 미리보기 ON일 때도 기본 OFF 정책과 같은 iframe의 숨김/재개를 유지한다.
- 무기 상세 폭이 560px 이상이면 플레이어가 오른쪽 열 전체 높이를 차지한다. 수치·지형·타임라인·사용 기체가 플레이어의 위아래로 쌓여 영상 높이를 나누지 않는다.
- 좁은 화면은 전투화면을 위에 두고, 선택한 표시 비율과 설정/재생 조작부의 높이를 기준으로 가용 높이의 70%까지 배정한다. 나머지 편집/트랙/기체는 기존 페이지 탐색으로 접근한다.
- 삽입 플레이어의 반복 설명과 소스 링크는 단독 플레이어에서 제공한다. 기체·파일럿 선택과 재생·정지·소리·반복 조작은 유지한다.
- 전체 화면 모드는 320×224 프레임을 비율 유지하여 표시한다.
- 후속 요청에 따라 모바일은 기본적으로 ‘전투만’ 모드를 쓴다. HUD 아래 y=32부터 대사 프레임 위 y=160까지, 가로 전체 320×128(5:2)을 표시한다. 좌우 기체나 무기 효과를 자르거나 세로로 늘리지 않는다. ‘전투만 / 전체 화면’ 버튼으로 즉시 바꿀 수 있고 화면 변경 때문에 다시 부팅하지 않는다.
- 전투 계산·프레임 버퍼는 그대로 유지하고 화면 배치만 바꾼다. 타임라인의 픽셀 판독과 저장 화면 표본도 전체 프레임 기준을 유지한다. 초기 모바일 판정은 iframe 자체 폭이 아니라 부모 에디터 폭을 사용하므로 데스크톱의 좁은 미리보기 열이 자동 크롭되지 않는다.

실제 완결편 v0.3a를 열어 웹포트 재생 중 1440×1000, 1024×768, 740×540, 430×780, 390×844, 375×667에서 페이지 전환을 검사했다. 페이지 가로 넘침/편집 영역 세로 넘침/콘솔 오류는 없었다. 전체 모드에서 1024px의 원본 프레임 표시는 약 351×246, 430px에서는 약 323×226이다. 이전 보존 캡처의 약 158×110 / 128×90보다 크게 표시한다. 이 비교는 웹 UI의 표시 크기이며 실게임 성능이나 전체 무기 재생 검증이 아니다.

로컬 서버는 WebAssembly 공유 메모리에 필요한 COOP/COEP 응답을 포함하도록 실행했다. 테스트는 백그라운드 브라우저에서 진행했으며 새 게임 이미지/세이브 파일을 만들거나 원본 파일을 바꾸지 않았다.

## 추가 조사: 자동 AI 추천

Google 공식 Gemini API는 API 키와 연결된 프로젝트를 요구하며, 무료 등급도 호출 한도가 있다. 무료 등급은 익명·무인증 호출을 뜻하지 않는다. 공용 키를 정적 페이지에 넣어 모든 사용자가 쓰는 구현은 현재의 정적 배포 구조에 맞지 않는다. Google 검색의 AI 응답 화면을 비공식 API처럼 자동 수집하는 경로도 제품에 추가하지 않았다.

현재 프롬프트 복사→외부 도구에서 실행→JSON 붙여넣기·검증은 유지한다. 추후 자동화를 선택한다면 사용자별 키 또는 별도 인증/서버 설계를 먼저 결정해야 한다. 이번 요청으로 계정·서버·원격 호출은 추가하지 않았다.

근거: [Gemini API 키](https://ai.google.dev/gemini-api/docs/api-key), [호출 한도](https://ai.google.dev/gemini-api/docs/rate-limits).

이름 조사에서는 신규 세이브 이름을 legacy 표로 인코딩하면 실제 글꼴에서 빈 셀을 고를 수 있음을 확인했다. 새 이름 입력은 현행 글꼴 코드로 쓰고, 기존 기본 이름의 정확한 일치를 먼저 처리해 원래 이름 판독을 보존한다. 무기 코덱은 그대로다. 실제 BCR 복사본의 체크섬·이름 필드와 승인 ROM 글꼴 참조를 확인했으며 게임 내 이름 표시를 새로 시험한 것은 아니다.

기존 배포 기능을 신규 구현으로 세지 않는다. 신규 증원·범용 이야기 편집·없는 글리프 삽입은 조사 결과만으로 활성화하지 않았다.

## 관련 검사와 기존 전체 계약 검사의 구분

무장 구성·직렬화, 이름, 삽입 미리보기, 레이아웃 및 크롭은 각각 관련 검사를 실행했다. 전체 테스트가 모두 통과했다고 표현하지 않는다. 별도로 실행한 frontend-contract/runtime-loader/worker 묶음은 61통과·3실패·31취소였다. 남은 실패는 하드코딩된 옛 캐시 리비전 기대값, 기존 글꼴 미리보기 fixture, 철회된 Final v0.1을 사용하는 전환 fixture의 대기로 이어졌다. 공개 릴리스 허용 범위를 넓혀 이 검사를 통과시키지 않는다. 상세 출력은 저장소 밖의 로컬 검사 로그에 둔다.

최종 `scripts/verify_repo.py`는 exit 0, `537 files; release policy is fail-closed`로 통과했다. 최종 음악·피해 4건과 6개 화면 크기의 16개 페이지를 실제 웹포트로 확인했다. 크롭 전환 전후 프레임 663→691, 준비시간 3802ms 동일로 전투가 재시작되지 않았음을 확인했다. 무장 JSON/worker의 버전 0/1 호환 검사 23건, 이름 관련 검사 41건(사적 승인 TSR fixture 포함), 음악·피해 관련 Node 검사 27건도 각각 통과했다. 이 숫자는 중복 없는 전체 테스트 합계가 아니다.

## 후속 사용자 지시: 전 기체·파일럿 합류 로직과 기능화

현재 대사·화자 편집을 먼저 마무리한 뒤 F/완결편 전체의 합류를 조사한다.
이데온 한 사례의 제한으로 전체 합류 기능을 중단하지 않는다. 로스터에
파일럿·기체를 넣는 native 함수의 호출부부터 역으로 추적하여 다음을
하나의 합류 이벤트 묶음으로 연결한다.

1. 파일럿/기체 생성·교체·보조 파일럿 연결의 호출 위치와 명령 경계.
2. 시나리오/root/분기/플래그/선행 사건 등 실행 조건과 재실행 여부.
3. 앞뒤 B1 대사·초상화·이동/등장 연출과 복귀 경로.
4. 이후 검색·퇴각·재합류·중복 생성·스토리 분기의 의존 관계.
5. 로스터 수용량·인계 복원 시점·세이브 재개를 포함한 적용 조건.

카미유/Z 건담, 에반게리온, 고쇼군, 건버스터, 윙제로 커스텀처럼 분기나
후반 획득이 있는 사례도 조사 대상이다. 사용자 예시를 실제 수록/합류
사실로 단정하지 않고 각 게임의 자료에서 먼저 식별한다.

조사 결과는 단순 목록에 그치지 않고 공통 생성/조건/대사 절차와 개별
예외로 분류하여 합류 시점 변경·분기 조건 편집·조기 추가 중 구현 가능한
범위를 제품 UI→검증→저장→재열기로 연결한다. 초기 레벨 편집은 이 요청의
완료를 대신하지 않는다. 미해석 경계와 검증된 호출부를 구분하여 전수
조사 범위/누락을 수치로 기록한다.


## 기존 대사의 화자 편집 연결 (완료)

기존 B1 descriptor의 파일럿 9비트만 변경하고 표정 low2와 나머지 비트를
보존한다. 후보는 선택한 디스크의 TSR 파일럿 머리부와 실제 FACE.BIN 전체
표정 프레임 범위에서 얻는다. 동적 주인공·별칭·잘못된 그림은 후보에 넣지 않는다.
공유 owner를 통해 이어진 모든 대사 구간은 같은 화자로 원자적으로 변경한다.
없는 표정을 요구하거나 공유 호출을 서로 다른 화자로 지정하는 요청은 거부한다.
본문·페이지·화자는 서로 독립적으로 유지·원복하며 SRWDIA04가 원본 descriptor와
수정 위치를 보존한다. 이 작업은 새 이벤트 생성이나 합류 시점 이동의 완료가 아니다.

core/model/저장 경로를 연결했다. helper·descriptor·모델 집중 검사 14건과 기존
core 10건 통과. 압축 carrier 내부로 화자 후보를 넘기던 누락을 고친 뒤 실제 F와
완결편에서 화자·대사 페이지·신규 글리프(힣)·합류 초기 레벨을 동시에 수정하여
메모리 내 BIN 저장→재열기→원복을 확인했다. F 1:11858의 #76→#2,
완결편 3:10391의 #72→#2를 사용했으며 원복 후 scope와 TSR 원본이 일치했다.
출력 길이는 각각 578,512,032 / 521,680,656바이트로 원본과 같고 원본 파일은
변경하지 않았다. 화자 변경은 초상화의 파일럿 선택이며 본문에 적힌 이름은 자동으로
바꾸지 않는다. 이후 실제 완결편 브라우저에서 #72→#71 화자 변경·초상화·
JSON 저장/원복/재적용을 확인했다. 1280·1024·430·320 폭에서 오류 및 가로 넘침은
없었다. 화자 변경과 새 발화 추가의 지원 범위는 아래처럼 구분한다.

### 기존 발화 뒤에 다른 화자의 발화 추가

원래 다음 명령도 B1이라고 확인한 연속 발화 경계에서만, 기존 발화 전체 뒤에
`화자·본문` 최대 4개를 추가한다. 원래 표정 슬롯과 다른 descriptor 비트를
보존하고 실제 FACE 후보에서 해당 표정을 표시할 수 있는 파일럿만 받는다.
각 추가 발화는 종결자를 제외한 107바이트까지이며 공유 호출에는 같은 목록을
원자적으로 적용한다. 미해석 중간 참조·signed16 범위·작업 공간·최종 압축 공간은
writer가 확인한다. SRWDIA05 기록으로 원래 호출·복귀점·본문을 보존한다.

UI의 ‘발화 ＋’로 추가하고 ‘기존 발화 / 추가 발화’를 고르면 같은 화자·초상화·
본문 입력칸에서 편집한다. 잘못된 입력은 초안으로 남겨 화면 이동을 막으며,
잘못된 추가 발화를 삭제하거나 원본복원할 수 있다. JSON에는 구조화된 추가
발화가 포함되고, 공유 호출의 서로 다른 목록·화자 불일치·동시 글리프 용량 초과는
적용 전에 거부한다. 이것은 임의의 위치에 새 이벤트나 조건·플래그를 만드는 기능은 아니다.

실제 승인 F의 `7:11108`, 완결편의 `14:10376`에서 화자를 람바 랄로 변경하고,
기존 3페이지·다른 화자의 새 발화 `힣`·새 글리프·로스터 초기 Lv33을 함께
메모리 내 BIN으로 저장·재열기했다. 새 발화와 기존 편집이 함께 보존되고,
사용 중인 글리프 삭제는 거부됐으며 원복 후 scope와 압축 전 원본 바이트가
정확히 일치했다. 원본 파일과 출력 길이를 보존했고 디스크 파일을 새로 쓰지 않았다.
실제 완결편 브라우저에서도 공유 4구간의 뒤에 람바 랄의 `힣`을 추가하여
JSON 저장→원본복원(변경·새 글리프 0)→JSON 재적용을 확인했다.
수동 AI 요청문에도 실제 표정 호환 화자 목록과 추가 발화 형식을 전달하고,
응답의 화자 ID를 검증한다. 이 연결에 로그인 없는 외부 자동 호출을 추가하지 않았다.


### 로스터 생성과 이야기 합류의 구분

전체 명령 catalog를 추가했고 core view/model에 조건·보조 파일럿 묶음·관련 대사·
동일 파일럿의 다른 생성 지점을 전달한다. 실제 자료에서 기존 C7 목록 F86개와
완결편382개가 모두 보존되며, 완결편은 C1.0B 이후 명령 경계를 연결해 4개를
추가로 읽어 386개다. 생성 시간은 해당 조사 환경에서 F31ms/완결편85ms였다.
이 수를 스토리 합류 횟수로 표시하지 않는다. 완결편의 358개는 물리본문2의
초기 구성·인계 자료에 모여 있으며 서로 다른 초기레벨의 같은 기체도 포함한다.

초기 root부터 경로를 따라 도달한 C7는 F31개/완결편6개이며 나머지는 원본 hash로
고정된 native 경계에서 해석을 시작한 자료다. 그 이전 조건을 알아냈다고 주장하지
않는다. CA02 등장과 C1/C2 조회·생성·연결 등 추가 의미를 연결하는 작업은 계속
진행 중이다. UI의 기존 ‘합류 n곳’은 ‘로스터 생성 n곳 · 초기 구성·인계 포함’으로
고쳤다. 새로 읽은 4개의 편집 권한이나 조기 합류 기능을 아직 활성화하지 않았다.


## 사용자 후속 우선순위: 전투맵 좌표 습득을 1차로

전 시나리오 합류 이동의 조사 비용을 줄이기 위해 사용자 요청에 따라 1차 구현을
**전투맵에서 특정 XY에 도착하면 기체를 지급하는 이벤트**로 우선한다. 전투 전후
시나리오 합류·원래 스토리의 조건 조정은 2차로 남긴다. 이전 전체 목표를 완료했다고
처리하지 않으며, 기존 기능과 진행 중인 대사 작업은 보존한다.

기체 종류 ID와 로스터 인스턴스는 구별한다. 원본 F에도 같은 unit205를 서로 다른
pilot153/154로 생성하는 C7가 있으므로 같은 기체 종류가 여러 대 존재하는 것은
원본 데이터에도 있다. 단, 특정 기체 종류를 검색하는 후속 명령이 어느 개체를
고르는지까지 모든 스크립트에서 무해하다고 일반화하지 않는다.

1차 기본 설계는 파일럿을 새로 생성하지 않는 기체 지급이며, 실제 맵 등장과
보유 로스터 등록의 차이 및 클리어 후 보존을 확인한다. 좌표 조건, 획득 1회 처리,
중간 저장 재개, 기체 슬롯 여유와 변형 파생 슬롯을 확인하는 경로가 필요하다.
기존 지역 조건과 C2 기체 생성 명령을 우선 재사용한다. UI는 맵 선택→좌표 지정→
지급 기체 선택으로 묶고, 전투 전후 스토리 편집 UI는 이 단계에서 늘리지 않는다.

현재 `editor-scenario-unit-pickup.mjs`에 좌표 조건 15바이트와 기체 지급 11바이트,
대기/완료 루프를 합친 34바이트 프로그램을 구현했다. 도착 전에는 지급하지 않고,
칸 부족으로 생성이 실패하면 대기하며, 성공하면 생성 명령으로 돌아가지 않는다.
집중 검사에서는 대기 및 완료 지점의 명령 포인터를 재개해 이 동작을 확인했다.
이 검사는 실제 세이브 파일이 그 포인터를 보존한다는 증거가 아니다. 실제 이동 후
호출되는 이벤트 연결·세이브 보존 계약·writer/UI 연결은 아직 미완성이다.
현재 좌표 프로그램은 검증된 F 지도 context만 받으며, 완결편 좌표 지원을
가정하여 열지 않았다. 지급 효과 자체는 두 게임의 생성 명령을 사용한다.

기본 작전목적 24바이트를 대기/완료 양쪽에 복제해 승리·패배 검사를 유지하는
74바이트 합성기도 추가했다. 그러나 F 공통 스크립트의 root8 호출은 매번 시작
주소를 재등록하므로, 이 연결에서는 완료 PC만으로 1회 지급을 보장할 수 없다는
반증을 찾았다. 해당 합성기를 제품 writer에 설치하지 않았다. 별도의 보존 상태
계약을 찾고 있으며, 합성 검사 통과를 실제 1회 지급 기능 완성으로 간주하지 않는다.

### 사용자 정정: 현재 전투에서 사용할 아군 증원 우선

사용자는 격납고 지급만으로는 현재 전투에서 쓸 수 없음을 지적했다. 이에 1차
우선순위를 **조건 충족 시 파일럿이 탄 아군 기체를 지정 좌표에 즉시 증원**하는
기능으로 정정한다. 격납고 지급 모듈을 이 요구의 완료로 대체하지 않는다.
맵 개체·파일럿·기체 할당, 중복 파일럿 처리, 등장 좌표, 1회 실행 상태 및 저장
연결이 필요하다. 기존 CA02의 할당 실패 FF 처리 위험을 해결해야 하며,
일반적인 기체 ID 중복 허용을 파일럿 ID 중복 허용으로 확대하지 않는다.

즉시 증원용 100바이트 프로그램을 추가했다. 새 파일럿의 보유 여부→발동 좌표→
파일럿/기체 빈칸→AQ02의 맵 개체 빈칸·배치 가능성→한 기 CA02→기존 기본
승리/패배 판정 순서다. 제어 흐름 검사에서는 각 실패 시 생성하지 않고 원래
목적 판정으로 돌아가며, 파일럿이 남아 있는 동안 root8 시작 주소가 재설정되어도
재생성하지 않는다. 파일럿 삭제 및 조작 가능성 계약이 모두 끝난 것으로 부르지 않는다.

AQ02 native 코드의 이미지 접합·정상화도 연결했다. 현재 exact code SHA는
`fc2791dd0b6327229f67f8a751208e722930068e5659050175438b2832c0224b`이며,
실제 F a에서 섹터2·372만 변경하고 에디터가 재열 때 원래 IP/EXEC로 정확히
환원해 기존 immutable-disc 검사를 수행한다. EXEC/IP 허용 마스크를 늘리지
않았다. 이미지 전체 원복 SHA가 승인 F a와 같고 재적용은 변경0섹터였다.
이 확인은 실제 맵 증원 실행이나 증원 UI 완료를 뜻하지 않는다.

### 주인공 얼굴 변경 후 이름이 일본어로 돌아가는 제보

사용자는 원본 패치 수정은 보류하고 기존 세이브 이름 변경으로 대응하라고 정정했다.
얼굴 선택을 마친 뒤 저장한 파일에서 주인공·애인 이름을 현재 ROM 문자표에 있는
한글로 변경하고 게임에서 다시 불러오는 경로를 안내한다. 이 대응을 새 게임의
얼굴 변경 코드 자체를 수정한 것으로 표시하지 않는다. 이 제보 때문에 승인 패치나
천지인 입력 화면을 수정하지 않는다.

### 여러 맵 저장 및 완결편 실행 코드 연결

#### 완결편 지도 문맥 연결 후속

`editor-scenario-region-context.mjs`는 F/완결편의 지도·시나리오 크기를 각각
검사하고 완결편의 지도 연결도 생성한다. 실제 v0.3a에서 87개 연결을 읽었고,
물리 본문9/선택106의 맵30·30×52를 확인했다. 지도 값 편집은 기존 허용
마스크를 유지하며 지도 불변 바이트와 별칭은 계속 identity에 포함한다.
다른 게임의 지도나 한 목록에 섞인 게임 문맥은 거부한다.

이는 완결편의 위치 조건/증원 실행 허가가 아니다. `regionContextOf`는 F의
원본 조회에만 적용하며 문맥 자체의 gameId까지 일치해야 한다. 완결편
목적 조건의 `regionCriteriaEditable`은 실제 입력에서도 false를 유지했다.
지도 문맥/기존 RG01 JSON·출력·재열기 집중 검사 10개가 통과했다.
사적 실제 입력 결과는 `final-map-context.json`에 기록했다.

기존 NR03 연구의 336바이트 조회 helper는 시나리오에, 별도 dispatcher는
IP의 256바이트 영역에 두던 구조다. 현재 AQ03도 같은 IP 영역을 사용하므로
두 구현을 단순 중첩할 수 없다. NR03 문서의 실제 3회 조회는 이전 helper의
증거이며 새 336바이트 helper의 실제 실행 증거와 혼동하지 않는다.
통합 dispatcher 또는 별도의 검증된 조회 경로 연결은 계속 미구현이다.
현재 로컬 검색에서는 과거 NR03 helper 소스를 찾지 못했다. 문서의 설계와
해시만으로 해당 구현을 재사용했다고 주장하지 않는다.

새 `editor-final-region-snapshot.mjs`는 원 C0.0F를 감싸는 176바이트 SH-2
wrapper를 생성한다. actor1184B와 목록257B를 stack에 복사하고 원 함수를
호출한 뒤 두 영역을 복원한다. VM 결과/판정은 유지하며 입력 r0..7과 SR을
원 함수에 전달하고 복귀 시 r8..15/PR/SR을 보존한다. 자체 stack은1480B이며
원 함수가 추가 사용하는 stack까지 포함한 값은 아니다. 코드 SHA-256은
`3f7164a42da6fba72bc61dbdaebc3c70d653e89c576047375e475794cf6c364d`다.

새 테스트는 작성한 SH-2 명령을 실행하되 원 함수는 모든 actor/list 바이트를
변경하는 명시적 대역이다. 배치 주소3개×내용4개×반환값2개=24조합에서
복원·호출규약·결과 보존을 확인했다. 원 C0.0F 실행 검사와 구분한다.
현재 image writer에 설치하지 않는다. 런타임 포인터 전체 범위·stack 및
코드 비중첩 검사, 실제 원 함수와의 통합, AQ03와의 dispatcher 공유 및
시나리오 저장·정상화 연결이 남아 있다. 이 precondition들을 충족하기 전에는
완결편 증원 UI를 활성화하지 않는다.

후속 주소 검사판은364바이트다. actor/list 전체 범위의 RAM 이탈·주소 wrap,
actor 정렬 오류, 두 원본 영역의 겹침, wrapper 코드 및 자체 stack과의 겹침을
복사 전에 거부한다. 거부 시 원 함수와 VM 판정은 건드리지 않고 `0xF000`을
반환한다. 연결 dispatcher는 이를 원본 조회로 fallback해서는 안 되며 증원을
보류해야 한다. 주소0x20288000에서 코드 SHA는
`03cedc36035e1ff879b11df744e7cb0f1391dfb63e680def3dec9c417b96733f`다.
코드 범위 literal을 포함하므로 다른 주소의 코드는 별도로 재생성한다.
위176바이트/SHA는 주소 검사 추가 전 기록이다. 원 함수가 추가 사용하는
stack 범위 확인과 전체 dispatcher 연결은 여전히 남아 있다.

#### 증원 대상 검색

증원 선택에 파일럿·기체 공용 이름/번호 검색을 추가했다. 공백과 전각 숫자를
정규화하며 검색에서 벗어난 현재 선택은 `현재`로 남긴다. 사용 불가 대상은
비활성 상태와 기존 사유를 유지한다. 검색은 편집값이나 JSON에 포함되지 않으며
잘못 입력 중인 숫자와 아직 반영하지 못한 선택도 유지한다. 원자적 JSON 적용,
복원 및 입력 유지 검사를 포함한 관련 UI 검사 4개가 통과했다.

실제 F의 두 지원 맵을 함께 켜서 JSON 직렬화·적용→제품 export→재열기를
확인했다. 한 맵만 해제하면 다른 맵의 증원과 공용 AQ03이 남고, 마지막 맵을
해제하면 AQ03이 제거되며 두 해제 본문은 원래 데이터와 일치한다.
근거: 사적 `story-font/reinforcement-two-maps.json`.

완결편용 native-query 정보는 `spawnCapacityInfo(gameId)`로 구분한다. 이미지
adapter의 EXEC 크기·dispatch 위치 및 코어 출처 정상화도 게임별 정보에 연결했다.
실제 완결편0.3a를 메모리에서 적용→에디터 재열기→정상화하여 전체 원본 SHA
일치를 확인했다. 변경 sector는2/385, 파일 크기는521,680,656바이트로 유지된다.
새 BIN 파일·에뮬레이터 실행은 만들지 않았다. 이 결과는 native 의존성만의 검증이며
완결편 증원 이벤트 활성화를 뜻하지 않는다. Final C0.0F의 actor/list 변경 때문에
F의 좌표 발동 코드를 그대로 사용하지 않는다.
