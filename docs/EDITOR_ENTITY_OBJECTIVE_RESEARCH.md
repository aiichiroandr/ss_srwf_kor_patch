# 특정 대상·영역 목적 조건: 실행 명령 조사

2026-10-10 조사. 이 문서는 읽기 전용 연구 결과다. `SRWFOB01`·`SRWFOB02`, 조건 인코딩, 개인 BIN 출처 마스크와 UI의 지원 범위를 변경하지 않는다. 현재 조건 조합의 구현·출력 근거는 [EDITOR_OBJECTIVE_COVERAGE.md](EDITOR_OBJECTIVE_COVERAGE.md)에 있다.

## 먼저 확정한 의미

`C0.0E`는 고유한 등장 개체의 생존 이력을 확인하는 명령이 아니다. 파일럿 식별값 또는 기체 **종류 번호**와 일치하는 현재 게임 상태의 개체를 세며, 없으면 거짓을 만든다. 같은 종류가 두 대 있으면 2를 반환한다. 미등장, 철수, 상태 필터, 변형 때문에 없어지는 경우를 격추와 구별하지 않는다.

두 게임에서 이 조회 자체의 쓰기는 VM 결과 `+20`, 판정 바이트 `+37`, 임시 스택뿐이다. 다만 파일럿 조회에는 등록되지 않은 번호의 캐시 범위를 벗어나는 읽기가 있다. 다음 구현의 가장 좁은 후보는 **유효한 기체 종류 번호 1 이상에 대한 현재 존재/부재 판정**이다. 에뮬레이터 실행과 판정 시점·저장 재개를 검증하기 전에는 제품 기능으로 열지 않는다.

`C0.0F`의 사각형 조회는 완결편에서 관계 개체의 좌표와 임시 목록을 갱신한다. `C0.20`의 직교 인접 조회는 두 게임 모두 관계 개체의 좌표를 갱신한다. 따라서 이를 일반 조건의 순수 조회처럼 삽입하지 않는다.

## 자료와 좌표계

입력은 최신 승인 F v0.5 a와 F완결편 v0.3 c에서 추출한 실제 `EXEC0`와 `SCEDATA.BIN`이다. 완결편 SCEDATA는 MODE2 Form 1으로 읽었으며, 과거 MODE1 오추출본은 쓰지 않았다.

| 자료 | SHA-256 |
| --- | --- |
| F EXEC0 | `308fe51501cd70091fe1a9983101d6cd98b9fdc7d8857e4bac9e2bff3e9974f1` |
| 완결편 EXEC0 | `2b17a510e9eb4758ada3aa954577222b848d15b573c56f63610e1cdc1d3320c0` |
| F SCEDATA | `26a3c66a55987323b2c47dd5214f9a2267c724d53f48ca79b16ebc538b091671` |
| 완결편 SCEDATA | `8902db80ae5aeecc11902adcfc5fc0ebe7bcfb216eb63e5ea01da23fc8081b6b` |
| 재사용한 scedis 문법표 | `2bb7c473ea6e11789a070725aedaba7403667bc1d713e30970526997f381fa71` |

아래 `root8`·명령 위치는 **SCEDATA 압축 해제 본문 상대 바이트 위치**다. 네이티브 함수·전역 포인터는 **SH-2 RAM 주소**다. 출격·기체·파일럿 표의 번호는 런타임 캐시 위치와 TSR 레코드 번호를 구분한다. 물리 본문 번호를 플레이 화수로 부르지 않는다.

`readScenarioArchive`, `readScenarioDeployments`, `buildEditorRows`를 재사용했다. 선언된 root8에서 기존 `scedis.decode(..., fallback=False)`의 정적 후속과 분기를 따라갔고, 다음 물리 unique root를 벗어난 곳은 별도 경계로 기록했다. 미지 명령은 건너뛰지 않는다. 해당 조회의 길이는 각 게임의 **현재 EXEC0**를 기존 `vmdis`로 실행하여 별도로 대조했다. 번역 목적 문구나 원시 바이트 검색을 쓰기 권한으로 삼지 않았다.

## C0.0E: 현재 대상 수 조회

| 계약 | F | 완결편 |
| --- | --- | --- |
| C0 공통 디스패치 | `0x06022244` | `0x06024184` |
| C0 하위표 | `0x060B2944` | `0x060B8EB8` |
| C0.0E 실제 함수 | `0x06022B9C` | `0x06024ADC` |
| 목록·개수 함수 | `0x06026C90` | `0x06028834` |
| VM 선택 문맥 | `0x060C06F0` | `0x060C6B60` |
| 판정 참 / 거짓 helper | `0x0601F41C` / `0x0601F430` | `0x06020984` / `0x06020998` |

총 길이는 **4바이트**: `C0 0E selector_hi selector_lo`. 서브명령 위치를 가리키는 VM 인수 커서에서 +1/+2를 읽어 unsigned BE16을 조립한다. 반환 `6003`은 메인 VM의 opcode 다음 커서에서 3바이트 전진하므로 전체 명령 4바이트와 맞는다.

선택값의 bit15가 모드이고 나머지는 **하위 9bit만** 남긴다.

| 선택값 | 실제 해석 | 신규 조건 정책 후보 |
| --- | --- | --- |
| `0000` | 진영 0·1·2 전체, 특정 파일럿 없음 | 파일럿 #0로 노출하지 않음 |
| `0001..01FF` | 파일럿 식별값 → 런타임 캐시 → 연결 보정 → 보정된 파일럿 ID로 집계 | 임의 번호 허용 보류 |
| `8000` | 기체 종류 #0이 아니라 진영 0·1·2 전체, 기체 모드의 상태 제외 적용 | 종류 #0로 노출하지 않음 |
| `8001..81FF` | 기체 종류 ID 1..511 집계 | 실제 TSR 기체 표에 있는 1 이상만 후보 |
| `FFFF` | bit15=1, 하위9bit=511 → 기체 종류 511 | 현재 개체·전체·종료 표시로 해석하지 않음 |

상위 나머지 비트는 버린다. 추후 편집값은 의미가 같은 여러 표현을 허용하지 않고 `8000 | 유효 ID`로 정규화해야 한다.

### 상태 필터와 수명

출격 표는 74칸 × 16바이트이며 표 포인터는 F `0x060B207C`, 완결편 `0x060B855C`다. 이번 실제 표 주소는 `0x20201AA0`이고 각 슬롯의 첫 byte는 X다. X=`FF`는 조회에서도 할당기에서도 빈 슬롯이다. 한 시점의 슬롯 번호를 저장해 두는 방법은 격추·제거 후 재할당 수명에 안전한 식별이 아니다.

각 조회는 actor+3의 `(byte >> 1) & 3`을 진영 번호로 삼아 마스크 7에 포함되는 0·1·2만 읽는다. 종류 번호만으로 아군/적군을 구별하는 조건은 아니다.

- 파일럿 모드: `BE32(actor+4) & 0x20000008`이 0인 대상만 센다. actor+2 → 30바이트 기체 캐시 → +15 파일럿 캐시 위치 → 12바이트 파일럿 캐시의 +0 ID를 비교한다.
- 기체 모드: `BE32(actor+4) & 0x60000008`이 0이고, 기체 캐시 +0의 unsigned BE16 ID가 같아야 한다. 그 뒤 일치 목록 중 **기체 캐시 +16이 FF가 아닌 것**은 개수에서 다시 뺀다.
- 따라서 `0x40000000` 상태는 파일럿 모드에서는 셀 수 있으나 기체 모드에서는 세지 않는다. +16 연결값이 있는 경우도 두 모드의 결과가 다르다.

이 수치 필터와 +16 연결 byte의 모든 게임 명칭을 격납·변형·격추·철수로 각각 확정하지 않았다. 이 문서의 시험에서 임의로 필드를 바꾼 것은 필터 분기의 시험이며 실제 게임의 격추·철수 사건을 재현한 시험이 아니다. **0명은 특정 개체의 격추 이력이라는 뜻이 아니다.** 출현하기 전에도 0이며, 동일 종류의 다른 기체가 남아 있으면 1 이상이다. 이름이 같은 다른 형식으로 변형했을 때도 선택한 종류의 수는 달라질 수 있다.

### 파일럿이 미등록인 경우

F의 파일럿 캐시 ID 검색 `0x0602A3E0`과 완결편 `0x0602D98C`는 128칸 × 12바이트를 읽고 못 찾으면 `FF`를 반환한다. 연결 보정 F `0x0602A194`에는 그 값을 받으면 캐시 +`255*12+3`을 읽는 경로가 있다. 완결편의 보정 `0x0602D734` 자체는 `0x0602D73A..73E`에서 FF를 먼저 걸러낸다. 그래도 C0.0E의 목록 함수에서는 보정된 위치의 ID를 읽는다.

완결편의 목록 함수 `0x0602894A..958`에는 FF 결과 / ID 0을 걸러 0을 반환하는 분기가 있지만, **FF 비교 분기의 지연 슬롯이 이미 캐시 ID를 읽는다**(`0x06028950`). F `0x06026DA6..DBC`에는 같은 반환 가드가 없다. 따라서 미출격·미등록 파일럿은 무조건 안전하게 0이라고 가정하지 않는다. 캐시 존재·연결 보정·제거 후 수명에 대한 검증이나 별도의 안전한 읽기 경로 없이 임의 파일럿 조건은 추가하지 않는다.

### 쓰기와 판정 플래그

처음 거짓 helper가 VM +37의 bit7을 **set**하고, 계산한 수를 VM +20 BE32에 쓴다. 결과가 0이 아니면 참 helper가 bit7을 **clear**한다. 참=1 bit가 아니다. 다른 bit는 보존한다.

기체/파일럿 목록 함수와 파일럿 연결 보정 함수, 진영 마스크 helper까지 실행한 경로에서는 게임 상태 쓰기가 없었다. C0.0E의 임시 출격 목록은 함수 스택 안에 있고, 전역 이벤트 목록이나 actor 좌표를 쓰지 않는다. 이후 `F0/F1`로 바로 판정하거나, +20을 `F2/F3/F4/F5`로 비교할 수 있다. 후속 조회가 이 값을 덮기 전 각 조건을 분기로 소비해야 한다.

## C0.0F: 직사각형 내 현재 대상 수

| 계약 | F | 완결편 |
| --- | --- | --- |
| 실제 함수 | `0x06022C80` | `0x06024BC0` |
| 길이·반환 | 8바이트 / `6007` | 8바이트 / `6007` |
| 형식 | `C0 0F selectorBE16 x1 y1 x2 y2` | 동일 |

selector는 **signed BE16**으로 목록 함수에 직접 전달하고 기체 모드 bit15/하위9bit 처리를 하지 않는다. `FFFC`=-4는 마스크 2, `FFFB`=-5는 마스크 1, `FFFD`=-3은 마스크 4다. 양수는 파일럿 보정 조회다. 이 명령에 `8185`를 넣어 종류 389를 조회할 수 있다고 가정하지 않는다.

X/Y는 unsigned byte이며 양 끝을 포함한다: `x1 <= X <= x2`, `y1 <= Y <= y2`. 한 칸은 두 끝을 같은 좌표로 정한다. 현재 범위 안의 수를 세는 동작이며 ‘한 번이라도 도달’ 플래그를 저장하지 않는다. 실제 맵 크기와 관계된 입력 검사는 명령 자체와 별도다.

F는 목록의 현재 X/Y를 읽고 +20·+37을 갱신한다. 완결편은 목록의 각 actor에 `0x060209E0`을 호출해 **관계 개체의 좌표를 원개체 좌표로 동기화**한 뒤 검사한다. 이 helper는 actor +4 관계 비트와 +5/+6 연결 슬롯을 따라가며 actor +0/+1 두 byte에 쓴다(`0x06020A0C`, `0x06020A1C`). 선택 개체만 바꾸는 함수가 아니다.

완결편은 또한 `*0x060BB298`의 +256 카운트를 0으로 만들고, 구역 안의 대상마다 2바이트 목록의 두 번째 byte에 actor 슬롯을 쓰며 첫 byte의 하위7bit를 지운다(`0x06024C38`, `0x06024CA2`, `0x06024CB0`, `0x06024CB2`). 이것은 부모 이벤트가 소비할 수 있는 전역 목록이다. 추가 조건이 기존 root8의 앞/사이에 실행되면 원래 좌표·목록과 소비 순서가 달라질 수 있다. 목록에 부작용이 없다고 주장하는 기호 실행은 이 helper들을 외부 호출로만 처리한 경우이므로 근거로 삼지 않는다. C0.0F의 추상 경로 열거는 목록 반복에서 loopcap/maxpaths에 닿았으며, 이를 전체 경로 검증 통과로 계산하지 않았다. 위 부작용과 포맷은 실제 함수의 분기·메모리 store와 원래 root8 사례를 대조한 정적 관측이다.

## 인접·관계 조회와 제외한 명령

`C0.20`은 6바이트 `C0 20 pilotA_BE16 pilotB_BE16`이며 함수는 F `0x06023DEC`, 완결편 `0x06025E98`다. 두 파일럿을 출격 개체로 찾고 좌표 동기화 helper(F `0x0601F478`, 완결편 `0x060209E0`)를 두 번 호출한다. 조회 함수 F `0x060271B0`, 완결편 `0x06028D74`는 B가 A의 위/오른쪽/아래/왼쪽이면 0/1/2/3, 인접하지 않거나 찾지 못하면 -1을 반환한다. +20에 그 값을 쓰고 -1이 아니면 참 플래그를 만든다. 임의 거리·영역 조회가 아니며 좌표 쓰기를 보존해야 한다.

`C0.1E`는 4바이트이며 F `0x06023A64`, 완결편 `0x06025AEC`다. 파일럿으로 개체를 찾은 후 actor+4 첫 byte의 bit6(`0x40000000`)을 읽어 참/거짓만 만든다. +20에 새 수를 쓰지 않는다. 비트의 게임 상태 명칭과 누락 대상/연결 수명 검증 없이 ‘생존’으로 명명하지 않는다.

`C0.12`는 5바이트다. 확인한 경로에서 기체 캐시 +22의 2바이트 값을 변경한다. `C0.08`도 외부 처리 호출이 있으므로 순수 존재 조회 후보에서 제외했다. 명령 길이를 확인한 것은 이 명령들의 조건 사용을 승인한 것이 아니다.

## 독립 재실행 시험과 한계

저장소 밖 `entity-c00e-concrete.py`는 기존 `vmsym`의 SH-2 실행·분기·지연 슬롯 해석을 재사용한다. 현재 EXEC0의 C0.0E 실제 함수에서 시작해 조회·캐시 보정·마스크·플래그 helper를 모두 inline 실행했다. 외부 함수 반환값을 ‘존재함’으로 임의 대체하지 않았다. 합성 RAM 읽기가 정의되지 않으면 실패하도록 했고, 쓰기 주소도 전부 수집했다.

각 게임 **128개** 경우를 독립 산식과 대조했다: 대상 0/1/2/74기, 같은 종류·같은 파일럿 여러 개체, 종류와 파일럿 모드 차이, selector 0/8000/8001/FFFF, 32개 상태 bit 각각, 진영 0..3, X=FF, 연결 byte +16의 FF/0/1. 정상 대상은 74, 동형 두 대는 2를 반환했다. 모든 경우 VM +20·+37 밖의 비스택 쓰기는 없고 기체·파일럿·actor RAM은 같았다.

미등록 파일럿 사례는 범위 밖 캐시 읽기를 **명시적으로 기록**하기 위해 그 영역을 0으로 둔 합성 입력이다. 그 결과를 실제 미등록 파일럿의 동작 보장으로 쓰지 않는다. 또한 합성 RAM에서 네이티브 바이트를 실행한 것은 에뮬레이터의 실제 게임 실행·격추·세이브 검증이 아니다.

사적 보고서는 `/private/tmp/srwf-scenario-research/`의 `entity-objective-root8-traversal.json`, `entity-objective-handlers-f.json`, `entity-objective-handlers-final.json`, `entity-c00e-concrete-f.json`, `entity-c00e-concrete-final.json`, `entity-objective-deployment-links.json`에 있다. 게임 파일·해제 본문·네이티브 명령 추출본은 저장소에 넣지 않았다.

## 기체 종류 조회의 연결값과 현재 집계 수명

### 기체 캐시 +16은 다른 기체 캐시와의 연결이다

기체 캐시 할당 함수는 +16을 `FF`로 초기화한다(완결편 store `0x0603113A`, F `0x0602D382`). 연결 함수 F `0x0602E524` / 완결편 `0x060325C4`는 현재 TSR root27 레코드 +7의 `kind=(byte & 0x78)>>3`, `form=byte & 7`을 읽는다. 현재 표에서 kind6은 단쿠가, kind8은 콤바트라V, kind9는 슈퍼건담·건담MkII·G디펜서다. 이 초기 연결 함수는 kind1..5와 kind7을 그대로 반환하므로, 모든 변형을 이 함수로 설명하지 않는다.

kind6/8의 구성 기체 검색은 네이티브 기체 캐시 ID 검색(F `0x0602D02C`, 완결편 `0x06030D5C`)을 사용한다. 구성 기체 캐시의 +16에 현재 합체 기체의 **캐시 인덱스**를 쓴다. 완결편의 store는 `0x0603277C` / `0x0603283E`이며, 슈퍼건담 경로는 `0x06032942` / `0x06032984`다. 첫 구성 기체의 +15 파일럿 캐시 인덱스도 합체 기체에 복사한다. actor 슬롯 번호를 저장하는 필드가 아니다.

반대 방향의 함수 F `0x0602E914` / 완결편 `0x060329B4`는 구성 기체의 +16을 FF로 돌리고, 합체 기체 +16을 첫 구성 기체의 캐시 인덱스로 연결한다. 슈퍼건담 경로의 실제 store는 완결편 `0x06032C5A`, `0x06032C62`, `0x06032C7E`다. 따라서 같은 캐시와 actor를 그대로 남겨 둬도 C0.0E의 종류 집계가 바뀔 수 있다.

저장소 밖 `entity-unit-lifecycle-native-link-proof.py`는 두 게임의 실제 연결·해제·C0.0E 함수 및 현재 TSR를 실행하여 각 게임 5개 경우를 확인했다. 모든 actor의 현재 캐시 포인터를 고정하여 **+16 필터 자체**를 분리한 시험이다. 연결·해제 함수의 비스택 쓰기는 해당 기체 캐시 +15/+16뿐이고, 각 조회의 비스택 쓰기는 VM +20/+37뿐이었다.

단쿠가·콤바트라·슈퍼건담의 연결 후 +16은 `[FF,0,...,0]`, 해제 후는 `[1,FF,...,FF]`였다. 이 합성 시험은 원래 게임 메뉴가 모든 actor 포인터를 그대로 두고 합체한다는 뜻이 아니다. 실제 게임은 현재 actor의 캐시 포인터도 바꿀 수 있다.

기존 SH-2 해석기는 서로 다른 길이의 스택 접근과 정렬된 스택 주소에 `OR 1`을 하는 표현을 완전히 해석하지 못했다. 이 사적 시험에서만 상수 스택 store를 byte 단위로 연결하고, 명시한 16바이트 정렬 스택에 한해 `SP+짝수 OR 1 = SP+다음byte`를 해석했다. 8KiB 합성 스택 scratch의 초기값은 0으로 명시했다. PR·레지스터 저장은 기호 값으로 보존하며, 그 밖의 미정의 RAM 읽기나 기호 값을 게임 RAM에 쓰는 경로는 실패한다. 초기 두 실패는 이 해석기 한계를 보완하기 전의 시험이며 게임 동작 반례로 계산하지 않는다. 재실행 보고서는 `entity-unit-lifecycle-native-link-proof-{f,final}.json`이다.

또 다른 현재 캐시 전환 경로인 완결편 `0x06055B40`는 `0x06055BFE`에서 이전 캐시 +16을 새 캐시 인덱스로, `0x06055C10`에서 actor +2를 새 캐시 인덱스로, `0x06055CEA`에서 새 캐시 +16을 FF로 쓴다. 그러므로 +16을 오직 합체 여부 또는 오직 격납 여부라고 부르는 것도 잘못이다. 이 경로의 메뉴 명칭·모든 호출 조건은 아직 실제 게임 관측으로 확정하지 않았다.

### actor 관계 비트와 제거 과정

완결편 좌표 부모 해석 함수 `0x06020A30`는 actor +4 첫 byte의 bit5(`0x20000000`)가 있으면 +6의 부모 actor 슬롯을 먼저 읽고, bit6(`0x40000000`)가 있으면 +5의 부모 슬롯을 따른다. 대상 슬롯은 0..73, X!=FF, actor +7 bit3=0인지 검사한다. 관계를 해석할 수 없으면 `0x06020AC6`에서 원래 actor의 bit6을 지우는 경로도 있다. 좌표 동기화 `0x060209E0`가 이 관계를 사용한다. 관계 필터가 있는 것은 확인했지만 모든 bit5 setter와 게임 메뉴 의미를 닫지는 않았다.

bit6을 설정하는 확인된 생성 경로는 완결편 `0x06027802`와 `0x06028026`이다. 함께 쓰는 actor +5에는 부모 슬롯을 둔다. bit5는 제거 helper `0x06029F94`에서도 소비된다: 모든 actor를 훑어 +6이 제거할 부모와 같고 bit5가 켜진 자식을 먼저 `0x06029E10`으로 제거한 뒤 부모를 제거한다. 이 두 관계를 모든 상황에서 ‘격납’, ‘보조 파일럿’ 등 하나의 게임 명칭으로 단정하지 않는다.

제거 함수 완결편 `0x06029E10`는 map 점유와 연결을 정리하고 actor의 16바이트를 비운 뒤, `0x06029F4E`에서 X를 FF로 만든다. 제거 원인이 격추인지 시나리오 철수인지와 관계없이 이후 집계에서는 사라진다. `C0.0A`는 완결편 `0x06024576`에서 actor +7 bit3(`BE32(+4)`의 `0x8`)을 먼저 켜고, 다음 정리 경로에서 파일럿·기체 캐시와 actor를 제거한다. `C0.15`에도 `0x06024658`의 같은 표시와 재귀 제거 경로가 있다. 따라서 이 bit가 켜진 때에는 슬롯이 아직 X!=FF여도 종류 조회가 제외한다. **이 bit를 HP=0으로 명명할 근거는 아니다.**

진영은 actor +3에서 `(byte>>1)&3`으로 읽으며 C0.0E의 고정 마스크7은 0·1·2만 포함한다. 진영3으로 바뀌거나 관계·정리 표시가 생겨도 조회 수는 달라질 수 있다. +3의 표시 비트와 +4..7의 조회 상태 word를 혼동하지 않는다.

### 원래 목적 코드의 실제 종류 조회 사례와 허용 번호

선언된 root8 시작부터 다음 물리 unique root 경계까지 기존 grammar의 명령·분기를 따라 조회를 확인했다. F 물리10/선택10은 root8 `2355..3073`의 명령3005에서 `C0.0E 813E`로 종류318 에바 초호기를 조회한다. F 물리21/선택21은 `2050..2269`의 명령2082에서 `8026`으로 종류38 콤바트라V를 조회한다. 완결편 물리54/선택151은 `5851..8827`의 명령6187에서 `8034`로 종류52 단쿠가를 조회한다. 합체 기체도 원래 목적 코드에서 이 집계 조회를 사용한다는 사례다.

이번 순회에서 관측된 unit-mode 명령은 F 2개, 완결편127개였다. F 물리7의 grammar frontier `81.11@3036`가 있으므로 F 전체의 완전한 명령 수라고 주장하지 않는다. 위 세 사례의 선언된 root8 순회에는 unknown 명령이 없었다. 자료는 사적 `entity-unit-lifecycle-root8-queries.json`이다.

현재 승인 TSR의 실제 종류 번호 상한은 **F367, 완결편447**이다(`entity-unit-lifecycle-tsr-record7.json`). 검증된 입력 표의 번호 집합 중 1 이상만 사용하고, ID0·selector0000/8000·표 밖 ID를 편집값으로 허용하지 않는다. 명령 자체는 요청 ID로 TSR를 인덱싱하지 않고 캐시 ID를 비교하므로, 이 범위의 종류가 현재 캐시에 없어도 파일럿 모드의 미등록 FF 보정 읽기를 하지 않는다. 9-bit라는 사실만으로 511까지 제품 허용 범위를 넓히지 않는다. 종류 번호는 입력 표와 연결된 종류이며 고유 등장 개체의 장기 식별자가 아니다.

### 게임 저장 근거와 한계

별도 F 실험의 [게임 저장 복원 관측](EDITOR_SCENARIO_F_RUNTIME_PROGRESS.md#게임-내-저장과-새-부팅-후-이어하기)은 기체·파일럿 표 전체가 같고 actor +3 한 byte만 관측 시점에 달라졌음을 확인했다. 실제 복원 PC `0x0609FBC6`은 원래 첫 word `0B1001E9`를 쓰고, 이후 `0x060489FA`가 +3의 bit6을 E9/A9로 점멸했다. 이는 actor +4의 `0x40000000` 관계 비트가 아니다. +3 bit6은 위 진영 추출에도 영향을 주지 않는다. 새 종류 조건이 모든 저장·변형·합체 경로에서 유지된다는 증거로 확대하지 않는다.

### 현재 의미와 다음 F 사적 시험

현재 확정한 표현은 **‘해당 기체 종류의 현재 집계 수가 0 / 0이 아님’**이다. 출현 전, 제거·철수, 다른 형식 전환, 합체 구성 연결, 관계·정리 상태, 제외 진영 모두 부재의 원인이 될 수 있다. 같은 종류 여러 개체를 하나씩 고유하게 추적하지 않으며, 과거에 격추되었는지도 저장하지 않는다.

F의 다음 사적 최소 후보는 이미 지원하는 물리0/선택0, root8 `1489..1513`이다. 가드는 없고 원래 승리1507·패배1510·E9대기1503을 유지할 수 있다. 선언된 root4 CA02@1226의 항목1229는 종류65 아톨∇ / 파일럿2 / 좌표(13,5)이며 현재 record+7은0이다. 새 이미지는 아직 생성하지 않았다. 물리번호를 실제 화수로 단정하지 않으며 이 배치가 실행되는 실제 경로, 조회 시점의 actor, C0.0E 반환·F3·원래 action·E9 재개·게임 저장은 새 출력 자체에서 확인해야 한다. 부모 작업자의 F 런타임 작업이 끝난 뒤 별도 사적 이미지와 고유 실행 디렉터리를 사용한다.

## 다른 파일럿 존재 조회 후보: C0.11의 판정 플래그

2026-10-10. 이 절은 기체 종류 OB03와 별개의 읽기 조사다. 제품 compiler·metadata·UI에 파일럿 opcode를 추가하지 않았다. 확인한 후보는 **`C0 11 pilotId_BE16`**의 판정 플래그이며, 전용 생존·격추 이력 명령으로 부르지 않는다.

명령표는 현재 EXEC의 main dispatcher에서 실제 하위 표를 따라 읽었다. F main `0x060B21BC`의 C0 entry는 `0x06022244`이고, `0x06022268`의 literal은 하위 표 `0x060B2944`다. 완결편 main `0x060B869C`의 C0 entry `0x06024184`는 `0x060241A8` literal로 `0x060B8EB8`을 읽는다. 근처에 있는 다른 dispatcher 표를 추정해서 쓰지 않는다. 해당 표의 0E 항목도 기존 확인된 `0x06022B9C` / `0x06024ADC`와 일치한다.

| 단계 | F | F완결편 |
|---|---|---|
| C0.11 실제 leaf | `0x06022E14` | `0x06024DC0` |
| 파일럿 ID → 현재 actor helper | `0x06024ABC` | `0x060273F8` |
| 128개 파일럿 캐시 ID 검색 | `0x0602A3E0` | `0x0602D98C` |
| 초기 FF 검색 실패 분기 | `0x06024ACE..AD0` | `0x0602740A..40C` |
| 연결 파일럿 보정 | `0x0602A194` | `0x0602D734` |
| 보정 cache index → actor 검색 | `0x06024B00` | `0x0602743C` |
| +20 결과 store | `0x06022E78` | `0x06024E24` |

leaf는 먼저 판정 플래그를 거짓으로 초기화하고 피연산자의 **unsigned BE16 전체**를 helper에 넘긴다. helper는 초기 파일럿 ID 검색이 FF이면 연결 보정 함수를 호출하지 않고 FF를 반환한다. 현재 C0.0E 파일럿 모드에서 문제였던 F의 FF 연결 보정 읽기를 이 경로에서는 먼저 차단한다. 이후 actor 검색 실패도 leaf가 FF로 확인한 뒤 캐시를 읽지 않는다.

actor 검색은 74칸을 순회하며 X=FF, actor +7 bit3, actor +2=FF를 제외한다. actor가 가리키는 기체 캐시 +15의 파일럿 캐시 위치와 보정 위치가 같으면 그 actor를 반환한다. 직접 일치하지 않으면 기체 캐시 +16이 FF가 아닌 경우 해당 연결 캐시 +15도 비교한다. 진영이나 actor +4의 관계 bit29/30을 C0.0E와 같은 방식으로 제외하지 않는다. 같은 파일럿 캐시를 참조하는 여러 actor 중 **첫 일치**를 반환하며 수를 세지 않는다.

leaf는 찾은 actor의 기체 캐시 +15가 가리키는 파일럿 캐시 **+6의 BE16**을 VM +20에 쓰고 판정 플래그를 참으로 바꾼다. +6 값은 이 조회의 존재 수가 아니다. 연결 기체 경로에서 요청한 파일럿 번호와 최종 +6을 읽은 캐시가 다른 합성 사례도 확인했다. 파일럿 캐시 생성 F `0x0602A2F4..A2FC` / 완결편 `0x0602D8A0..D8A8`는 +6을 `(level-1)*2`로 초기화하지만 그 값의 일반 게임 수치 이름을 이 조건 조사에서 확정하지 않는다.

**찾지 못하면 +20은 이전 값을 그대로 남긴다.** 존재/부재 후보는 C0.11 다음의 F0/F1으로 즉시 판정 플래그를 소비해야 한다. +20을 F2/F3으로 0과 비교하면 직전 다른 조회 값이 남아 잘못된 결과가 될 수 있다. 길이는 4바이트이고 leaf 반환값은 `6003`이다.

### 합성 RAM에서 실제 네이티브 바이트 실행

저장소 밖 `entity-c0011-concrete.py`는 기존 C0.0E probe와 `vmsym`을 재사용하고 위 검색·보정·actor·플래그 helper를 모두 inline 실행했다. F/완결편 각 15개, 총30개 경우가 독립 기대값과 일치했다. 일반 존재, 미등록, 등록됐으나 미출현, X=FF 제거, actor 기체 캐시 FF, 정리 bit3, 관계 bit29/30, 중복 actor, 파일럿 캐시127, actor73, IDFFFF 부재, 연결 기체의 다른 파일럿, 파일럿 보정 연결을 포함한다.

FF 파일럿 캐시 영역을 0으로 채우지 않고 미매핑해 해당 읽기가 있으면 실패하도록 했다. 모든 완료 경로의 비스택 쓰기는 VM +20/+37뿐이고 actor·기체·파일럿 표는 그대로였다. 부재 시 seed +20=`12345678` 유지도 명시적으로 확인했다. 결과는 `entity-c0011-concrete-f.json` / `entity-c0011-concrete-final.json`이며 EXEC SHA-256은 각각 `308fe51501cd70091fe1a9983101d6cd98b9fdc7d8857e4bac9e2bff3e9974f1` / `2b17a510e9eb4758ada3aa954577222b848d15b573c56f63610e1cdc1d3320c0`이다. 이것은 실제 바이트를 합성 상태로 실행한 것이며 에뮬레이터의 게임 사건·저장 복원 시험이 아니다.

### 기존 사례와 아직 남은 경계

기존 grammar로 현재 승인 본문의 root8 및 14개 선언 root를 각 다음 unique root 경계까지 재귀 추적했을 때 C0.11 원래 사용 사례는 찾지 못했다. 미해석 명령과 경계 밖 분기가 있으므로 전수 부재라고 하지 않는다. stale EXEC alias fallback은 사용하지 않고 unknown에서 멈췄다. 결과는 `entity-c0011-declared-roots.json`이다. 명령표와 실제 handler가 존재한다는 사실을 원래 작전 목적에 삽입해도 안전하다는 증거로 대신하지 않는다.

다른 실제 판정의 의미도 구분한다. 완결편 물리12/선택109의 root8 `2883..3262`에는 2947에서 파일럿56 엘피 플의 C0.1E, 2967에서 파일럿57 플 투의 C0.1E가 있고, 각각 F0 이후 별도의 C0.0E/F1로 현재 집계를 확인한다. C0.1E 자체는 관계 bit6 조회이며 존재 조회로 대신 쓸 수 없다. 물리59/선택156의 root8 `4981..10889`에서는 10451의 C0.27로 파일럿159 기와자 로와우 주변 맵 점유를 읽은 뒤 F1로 다른 사건으로 분기한다. 주변 칸 상태가 판정을 바꾸므로 이 명령도 파일럿 존재만을 뜻하지 않는다. C0.21은 완결편 `0x06025F40`에서 actor +3 bit7을 지우고 `0x06025F42`에서 전역 선택 actor 값을 쓰므로 순수 존재 조회 후보에서 제외한다. 기존 C0.0F/C0.20의 좌표·목록 부작용 제한도 유지한다.

파일럿 보정 helper의 +3 bit3 연결 경로는 128칸의 +8을 따라 보정한다. 순환하거나 역연결을 찾지 못하는 잘못된 합성 캐시에서는 종료를 보장할 수 없다. `entity-c0011-alias-cycle.py`의 두 게임 각각 ‘역연결 없음’/‘두 칸 순환’은 실제 helper 실행이 40,000-step cap에 도달하고 반환하지 않았다. 결과는 `entity-c0011-alias-cycle-f.json` / `entity-c0011-alias-cycle-final.json`이다. 고의로 잘못 만든 캐시의 정적 반복 경로를 재현한 것이며 실제 게임에서 그 상태가 생성되거나 에뮬레이터가 멈춘 증거는 아니다. 현재 보정 연결의 실제 생성·교체·제거·게임 저장 수명은 이 절에서 전수 증명하지 않았다. 번호가 다른 파일럿 캐시·연결 기체로 해석될 수 있고 중복 actor도 있으므로 고유 등장 개체 생존·격추 이력으로 부르지 않는다.

- **관찰:** C0.11은 초기 미등록 FF를 안전하게 걸러내고, 정상·연결 상태의 합성30개에서는 VM 결과/플래그 외 쓰기 없이 현재 조회 가능한 actor 유무를 판정했다.
- **가설:** 확인된 입력 표 번호와 검증한 캐시 연결 수명 안에서 ‘이 파일럿 번호가 현재 조회 가능한 개체에 연결됨/안 됨’ 조건을 F0/F1으로 만들 수 있다.
- **반증·제한:** +20은 개체 수가 아니고 부재 때 stale이다. 파일럿/기체 보정과 중복 때문에 고유 개체가 아니며, 잘못된 연결 순환과 실제 callback·게임 저장 재개는 미검증이다.
- **다음 최소 probe:** 아래 사적 실행 시험은 승인 원본에서 새로 만든 완결편 물리5/선택102의 파일럿80 실제 현재 연결과 유효159 초기 미등록 경로까지 확인했다. 남은 최소 범위는 등록됐으나 actor 없는 실제 상태, 파일럿/기체 보정 alias의 생성·교체·제거·저장 수명, F 자체의 실제 조회와 기존 callback·게임 저장 재개다. 이 경계를 확인하기 전에는 고유 개체 의미나 제품 파일럿 조건을 허용하지 않는다.

### 단일 실제 파일럿 조회 실행 근거

[사적 C0.11 실행 시험](EDITOR_PILOT_QUERY_RUNTIME.md)은 승인 원본에서 별도 OP11 이미지를 만들고 기존 GameSave33의 새 부팅 불러오기부터 실제 시마 조회→즉시F0→원래EC01/commonECFF→34화 완료를 관측했다. 파일럿80/actor73/기체·파일럿 캐시60의 한 정상 현재 연결 사례에서 세 표 전체6,560바이트·인자80바이트·보존 레지스터가 같고 VM+20/+37 외 변경이 없었다. 원래 제품 형식과 다른 magic은 fresh inspector가 거부한다. 이 한 존재 경로를 미등록/중복/alias/고유 인물 생존/격추 의미나 제품 지원으로 확대하지 않는다.

후속 사적 반례도 [같은 실행 문서](EDITOR_PILOT_QUERY_RUNTIME.md#실제-반례-현재-존재하는-파일럿의-없음-조건)에 분리했다. 같은 정상80 조회 뒤 F1은 실제 미분기하고 E9가 재개PC/인자 스택을 저장·반납했다. 현재128칸 캐시에 없는 유효159 조회는 초기 검색FF에서 보정/actor 탐색을 건너뛰고 +20의 이전2를 남기며 bit7=1을 반환했다. 바로 뒤 F0 미분기와 별도의 C0.11→F1 분기도 실제로 관측했다. 각각 세 표 전체·VM80·인자80·보존 레지스터를 대조했다. 이 경로 증거는 등록됐으나 actor 없음/중복/alias/고유 개체 의미나 제품 지원을 승인하지 않는다.
