이 문서는 로컬 구현과 정적·출력 검증의 기록이다. 게임 전체 플레이 안정성이나 미사용 연출의 정상 재생을 확인했다는 뜻이 아니다. 공개 릴리스·배포는 변경하지 않았다.

## 반영한 기능

- 롬·세이브 에디터 공통 최초 안내. ‘다시 보지 않기’ 기본 체크. 확인한 경우에만 브라우저 설정을 저장하며 취소하면 진입하지 않는다.
  - 문구: ‘에딧하면 게임 밸런스가 달라집니다. 모든 변경 조합의 정상 진행이 검증된 것은 아닙니다.’
  - 확인하지 않은 멈춤 현상을 확정해서 쓰지 않는다.
- 기체 종류별 기본 격추 자금 편집. 행운 등 게임의 후속 보정은 유지한다.
- 기체 종류별 파츠 장착 칸을 1~4칸으로 편집. 같은 바이트의 다른 비트는 보존한다.
- 개조 비용: 기체 5항목×10단, 무기 4비용형×11칸(10단+풀개조 보너스), 합계 94칸. 변경 목록·JSON 저장/불러오기·개별 복원·출력까지 연결했다.
- 기체 화면과 무기 화면에서 비용창을 연다. 무기 화면에서는 선택한 무기의 실제 비용형으로 연결하고 같은 표를 쓰는 무기 예시를 표시한다.
- 비용창은 페이지로 나눈다. 낮은 창에서는 표시 행 수를 줄인다. 입력 중에는 입력칸을 다시 만들지 않는다.
- 비용의 잘못된 값은 페이지·비용표를 바꿔도 유지하고 출력을 막는다.
- 지형 명중·방어 보정은 감소와 증가 양쪽을 허용한다. HP·EN 회복은 별도 범위를 쓴다.
- 지형의 잘못된 입력이 지형 선택 변경으로 사라지던 경로를 수정했다. 해당 지형으로 돌아가 수정·복원하기 전에는 출력을 막는다.
- 새 화면과 이전 워커/데이터 코어가 섞이는 상태를 실제 브라우저에서 관찰했다. 수정한 모듈·워커의 버전을 갱신했다. 지형 미반영 문의의 유일한 원인으로 단정하지는 않는다.
- 기체 무장 교체: 기존 각 칸의 무기 ID만 바꾸고, 개조 슬롯·조건 플래그·추가 투자·미해석 비트·항목 수·레코드 길이는 보존한다. 바뀐 무기가 탄약을 쓰면 다른 무장과 겹치지 않는 탄약 칸을 배정하고, 쓰지 않으면 0으로 바꾼다. 변경하지 않은 항목은 그대로 보존한다.
- 무장 추가: 선택 기체에서 비어 있는 개조 슬롯과 탄약 칸을 배정한다. 추가한 항목은 `×`로 취소할 수 있다. 원래 목록의 조건·추가 투자 비트를 유지하며 새 항목은 이벤트 제한 없이 만든다. 변형 기체의 개조 공유 규칙은 유지되므로 다른 형태와 같은 번호의 개조 슬롯을 쓸 수 있다.
- 추가 무장 JSON에는 기준 무장 수를 기록한다. 같은 결과 BIN을 다시 연 뒤 이미 적용된 JSON을 불러오면 중복 추가하지 않는다. 기준 목록 수가 다른 경우에는 추가 항목을 건너뛴다.
- 완결편 롱기누스의 창 #874는 에바 영호기 #232의 개조 슬롯 5·조건 플래그 83에 원래 연결되어 있다. ‘미연결’로 부르지 않는다. 조건 없는 다른 무장 칸에서 #874를 선택하는 교체는 가능하며, 전용 투척 연출의 완성 여부와는 별도다.
- 기체 화면은 데스크톱에서도 실제 공간에 따라 페이지를 나눈다. 무장 목록도 항목 전체를 페이지로 넘기고, 검색과 선택값은 페이지 이동 때 유지한다. 콜드부트·플레이 검사는 추가하지 않았다.

### 무장 교체의 확인 범위

`editor-loadout`, `editor-loadout-ui`, 기존 레코드·무장 연결·preset·layout·worker·개조 비용·지형 관련 기능 검사를 실행했다. F와 완결편의 합성 디스크에서 변경값의 JSON 저장/불러오기, 출력 섹터 체크섬, 독립 새 세션 재열기, 취소 시 원본 해시 복귀를 확인했다. 최신 한글판 a/b/c 여섯 개와 원본 두 개의 기존 불변 영역 해시를 먼저 대조한 뒤, 무기 번호 비트와 탄약 칸만 추가로 허용하는 프로파일을 만들었다. 이벤트·개조 슬롯·실행 코드의 쓰기 범위를 넓히지 않았다.

### 무장 칸 추가의 저장 방식과 확인 범위

기체 표만 압축 해제 TSR 끝으로 옮기고 원래 기체 표 영역은 0으로 채운다. 다른 표와 이름 문자열의 주소는 바꾸지 않는다. 기체 표의 상대 포인터·기존 별칭 관계를 유지하며 새 무장을 붙인다. 출처 검사에서는 허용된 추가 항목의 무기 번호·개조 슬롯·탄약 칸·제어 비트를 검사한 뒤, 기체 표를 원래 위치·길이로 환원하여 기존 불변 해시와 대조한다. 원래 영역의 외부 바이트, 추가 항목에 숨긴 조건 비트, 미허용 꼬리 데이터는 거부한다.

압축 해제 TSR 길이는 늘지만 **디스크의 TSR 할당 공간은 늘리지 않는다**. 필요한 경우 2바이트 근거리 참조까지 탐색하는 기존 압축기를 사용한다. 현재 F v0.5a 샘플은 194,002/202,752바이트, 완결편 v0.3c 샘플은 209,812/215,040바이트였다. 더 큰 변경 조합이 할당 공간을 넘으면 출력하지 않는다. 이 수치는 한 기체에 무기 하나를 추가한 샘플이며 모든 조합의 크기나 전체 플레이 안정성을 보증하지 않는다.

여섯 최신 한글판과 두 원본의 기존 해시를 대조하고, 추가한 표를 환원한 결과도 여덟 프로파일 모두 일치했다. F·완결편 합성 디스크에서는 새 세션 재열기, 재열기 후 추가, 빈 무장 목록에 첫 무기 추가, JSON 재적용, 잘못된 값과 변조 거부를 확인했다. 네이티브 콜드부트나 처음부터 게임을 진행하는 검사는 하지 않았다.

## 값의 범위와 근거

| 항목 | 현재 편집 범위 | 정적 근거 / 한계 |
|---|---:|---|
| 기본 격추 자금 | 0~65,535 | 기체 레코드 +20의 BE16. 영구 저장 자금의 상한과 다른 값이다. |
| 파츠 장착 칸 | 1~4 | 기체 +25의 bits4..5, 저장값+1. 세이브도 파츠 ID 네 칸을 갖는다. 5칸 이상은 기존 데이터 형식의 수치 조정으로 처리하지 않는다. |
| 기체 개조 비용 | 0~65,535 | root31/sub1, 항목별 u16×10. **0은 무료가 아니라 개조 불가로 판단하는 경로가 있다.** |
| F 무기 개조 비용 | 0~65,535 | root31/sub3, u16×11×4비용형. |
| 완결편 무기 개조 비용 | 0~655,350, 10단위 | 같은 표의 u16을 게임이 10배 한다. 풀개조 보너스 칸도 10배 한다. |
| 지형 명중·피해 감소 | -100~100% | 저장값=100−입력값, 즉 0~200. 양수는 감소, 음수는 증가. UI 설명에 방향을 표시한다. |
| 지형 HP·EN 회복 | 0~100% | 최대 HP·EN 기준 비율. EN 바이트 상위 제어 비트는 유지한다. |

위 금액 상한은 저장 표현과 계산 경로에서 확인한 범위다. 전체 플레이에서 안전하다고 확정한 수치가 아니다. u16보다 크게 저장하려면 표/게임 코드의 형식 변경이 필요하다. 모든 기체 비용을 최대로 했을 때 10단×5항목 합은 3,276,750, 완결편 무기 10단 합은 6,553,500으로 32비트 합산 범위와 게임 자금 상한 9,999,999 이내다.

완결편 건담 헤비암즈개 #280의 무기 풀개조 보너스는 표를 읽은 뒤 50,000으로 덮어쓰는 별도 경로가 있다. 이 원래 분기는 보존한다. 비용표 편집을 모든 예외 기체의 고정 비용까지 변경하는 기능으로 설명하지 않는다.

### 실행 코드 근거 (원본 EXEC, 로드 기준 0x06004000)

- 기체 기본 자금 읽기: F `0602C752..0602C768`, 완결편 `060303EC..06030402`. BE16을 work+0x17C에 복사한다.
- 완결편 격추 자금 가산: `06053E0C..06053E88`. u16 확대, 조건부 2배, 24비트 자금 읽기·가산·9,999,999 제한이 이어진다.
- 파츠 수: F `0602C798..0602C7B0`, 완결편 `06030432..0603044A`. 완결편 `06030498..060304C8`은 이 칸 수만큼 세이브의 파츠 ID를 읽어 효과를 적용한다.
- 완결편 기체 비용: `0607E8B0..0607EB5C`, root31/sub1. 한계반응·장갑·EN·HP·운동성의 표 순서이며 UI 메뉴 순서와 구분했다.
- 완결편 무기 비용: `06084366..060843AA`. 두 바이트를 unsigned로 조립한 뒤 ×10. 보너스 `06084498..060844D0`도 ×10. `060844D2..060844EC`에 #280 예외가 있다.
- 지형 방어 계산의 표 읽기: 완결편 `06051A1C..06051A56`, root34/sub3의 두 번째 바이트.
- 명중 계산의 표 읽기: `060520A6..060520C6`, 같은 표의 첫 번째 바이트.
- 회복 표 읽기: `0606E6CE..0606E6F4`, root34/sub4. 보정 계산에는 비행·상태에 따른 적용 분기가 있으므로 모든 상태에서 동일 효과를 보장한다고 설명하지 않는다.
- 지형정보 표시: `0606E95E..0606E980`은 전투 보정 표를 읽어 100을 빼서 표시한다. 에디터의 ‘감소’ 입력과 게임 부호를 혼동하지 않도록 설명했다.

확인한 완결편 v0.3a의 위 지형 읽기·표시 코드 범위는 원본과 같았다. 에디터 출력에서 `/0`, 얼굴·기체 이미지·전투 그래픽 파일이 동일함도 비교했다. 수정 BIN을 새로 실행해야 새 데이터가 읽힌다. 이전 메모리를 포함하는 세이브스테이트를 복원한 결과를 새 BIN 읽기의 증거로 삼지 않는다.

## 격추 드랍 파츠의 기존 기능

이미 구현되어 있다. root32의 48개 선택자와 최대 두 획득 후보, 확률 합계 100% 이하를 편집한다. 맵 초기 배치·증원에서 해당 드랍표를 선택해 원래 보상이 없는 등장 기체에도 연결할 수 있다. 같은 표를 공유하는 등장 기체에 함께 적용되며, 기존 파츠·확률 변경을 새 중복 기능으로 만들지 않았다. 레코드 길이와 후보 수는 유지한다. 생성 시 추첨한 보상을 이미 가진 기체는 세이브의 보상을 유지할 수 있다.

## 미사용 무기·기체 조사

### 롱기누스의 창

완결편 v0.3a에서 **무기 #874 / 공격력 5000**이 확인됐다. 에바 영호기 **기체 #232**의 다섯 번째 무장에 이미 연결돼 있고, 조건 플래그 **83**이 붙는다. ‘기체와 연결도 없는 새 무기를 복원해야 한다’고 볼 수 없다. 정상 시나리오에서 이 플래그가 설정되는지는 확정하지 않았다. 이후 원래 로더에 무기·기체·파일럿을 지정해 기체와 레이의 대사를 확인했지만, 원본 연출 번호는 0이며 전용 공격·피해·연출 완료는 확인하지 못했다. 상세 결과는 `WEAPON_PREVIEW.md`에 기록한다. 무기 헤더의 뒤쪽 참조 두 바이트가 0000인 것만으로 연출의 부재나 정상 동작을 단정하지도 않았다.

### 난무의 태도 및 다른 미사용 무기

완결편 기체 447레코드·무기 1407레코드의 이름·수치·소유 연결을 대조했다. ‘난무의 태도/乱舞の太刀’에 대응하는 이름 레코드는 현재 해석기로 식별하지 못했다. 이것은 D_ANIME의 이름 없는 연출까지 없다는 증거가 아니다. 무기 종류/연출 선택자와 연출 명령 해석은 별도 조사 대상이다.

이름과 양수 공격력이 있지만 확인한 기체 무장 목록에 연결되지 않은 일반 무기 16개는 연결 후보로 분류했다. 예: 아이언커터 #123, 드릴미사일 #125, 슈피겔토네이도 #1055, 검패천왕기염탄 #1178, 갓슬래시타이푼 #1272, 갓필드대시 #1274. 이 분류만으로 실제 시나리오 미사용·연출 정상 동작을 확정하지 않는다. 임의 기체에 연결할 때에는 탄약 칸·개조 슬롯·기체별 연출 의존성도 맞춰야 한다.

### S건담·Ex-S·서바인·즈와우스

원본 C_ROBOT에 남은 그림은 각각 이미지 번호 **305, 306, 308, 309**로 식별했다. 이 번호는 기체 ID가 아니다. 현재 기체 447레코드에서 해당 이름·정상 수치의 완성된 기체를 찾지 못했다. 기체 #305는 블랙윙H, #306은 도몬 캇슈, #308은 에어리즈, #309는 오레아나다. 이를 미사용 기체 ID로 잘못 연결하지 않는다.

추가로 실제 승인 F v0.5a와 완결편 v0.3c의 C_ROBOT을 기존 코덱으로 읽었다. 네 그림은 양쪽에서 각각 1,836 / 1,920 / 1,611 / 1,699바이트이며 각 자원의 하위 그림 5개가 해석된다. 현재 코어 파서로 F 367개·완결편 447개 기체 레코드를 모두 읽었을 때 이 네 그림을 참조하는 레코드는 0개다. 하위 그림의 해석 성공을 전투 동작·무장·변형 데이터가 완성됐다는 증거로 보지 않는다. 비공개 근거는 `weapon_preview_20261022/unused-unit-graphics-static.json`과 `unused-unit-graphic-references.json`에 기록했다.

남은 이미지를 정상 기체로 구성하려면 새 레코드 또는 확보한 더미 자리의 이름·수치·맵 아이콘·무장·변형·전투 그래픽 연결을 함께 설계해야 한다. ‘원래 완성된 스펙 복구’와 ‘남은 그래픽을 이용해 새 스펙을 제작’을 구분한다. 아래 새 구성 기능을 연결했으며 원래 스펙을 복구했다거나 정상 재생을 보장하는 표시는 하지 않는다.

### 남은 그래픽으로 새 기체 구성

기체 목록 아래 ‘＋ 기체 추가’에서 네 기체를 고른다. 확인된 18개 빈 더미
자리 중 첫 빈 자리에 만들며, 기존 실사용 기체를 덮어쓰거나 전체 ID 표의
크기를 늘리지 않는다. S·Ex-S는 건담 #1, 서바인·즈와우스는 단바인 #47의
열었을 때 기본 능력치·맵 아이콘·무장을 사용한다. 전투 그림은 위 네 실제
자원을 사용한다. 원래 완성된 스펙·변형·영입 이벤트를 복구한 기능이 아니다.

추가 직후 수치·지형·능력·무장을 고칠 수 있다. 같은 선택 메뉴의 ‘현재 추가
취소’는 이후 수정도 함께 버리고 원래 빈 자리로 되돌린다. 변경 목록과
편집값 JSON은 구성 지시와 수정값을 함께 저장한다. JSON은 적용 전 가상
행으로 비교하며 현재 세션을 바꾸지 않는다. 다른 기체가 차지한 자리와
알 수 없는 그림 지시는 거부한다. 같은 구성의 재적용은 중복 생성하지 않는다.
이미 저장된 구성 기체를 다시 수정한 JSON도 구성 전제 조건을 포함한다.

수정 BIN을 저장하고 다시 열면 그 기체가 ROM의 실제 레코드가 된다.
그때 전투 미리보기의 사용 기체와 세이브 에디터의 추가 목록에도 들어간다.
아직 저장하지 않은 새 기체는 원래 ROM을 시연하는 목록에 섞지 않는다.
세이브 파일에 자동 영입시키지는 않는다. 세이브 기체 추가는 따로 선택한다.

F·완결편 각각 합성 디스크의 화면 조작 → 추가·수치/무장 변경 → JSON
저장·비교·적용 → 실제 writer → 독립 새 세션 재열기를 확인했다. 두 경로의
출력 바이트도 일치했다. 추가 취소·이미 차지한 자리·오래된 계획·잘못된
그림 요청·기본 기체의 나중 무장 확장·재열기 뒤 JSON도 검사했다.
관련 최종 집중 검사는 45개 통과했다. 함께 넓힌 기존 변경 목록 검사는
48개 중 43개 통과·5개 실패였으며, 이전 `unit-growth-preset-tests.log`와
실패 이름 5개가 같았다. 전체 테스트 통과로 기록하지 않는다.

실제 부모 TSR 8종에서도 새 구성 행을 같은 writer에 넣고 출처 환원 해시가
기존 부모 핀과 일치함을 확인했다. 대표 F v0.5a·완결편 v0.3c에서 HP
43,210의 네 기체를 함께 구성한 TSR은 각각 194,155/202,752바이트,
209,930/215,040바이트로 기존 할당 공간에 들어갔다. 임의 모든 편집 조합의
압축 적합성이나 게임 전체 동작을 보장하는 값은 아니다.

실제 승인 완결편 v0.3a의 전체 해시를 검증해 네 기체의 그림·이름·수치
화면을 확인했다. 960×640과 390×844에서 추가 메뉴 문구를 표시하고
화면 전체 가로·세로 스크롤이 없음을 확인했다. 게임 실행은 추가하지 않았다.

`unused-unit-final-focused-tests.log`, `unused-unit-ui-integration-tests.log`,

## 무기 연출 미리보기: 기존 웹포트 재사용 평가

기존 로컬 `srwf-recomp`와 `srwf-web-port-publish/web-port`를 읽었다. 현재 포트는 게임 코드를 실행하고, 호스트 프레임을 Canvas2D `putImageData`로 표시한다. PixiJS로 연출을 다시 해석하는 구현이 아니다. 파일·패드·저장 메모리·오디오를 워커에서 처리하며, 초기 진입 프로토콜은 `boot`다. 임의 무기 하나를 지정해 재생하는 API는 없다.

**추론: 연출 정확도와 개발량에서는 기존 웹포트 재사용이 유리하다.** 새 PixiJS 구현은 D_ANIME 명령, 기체별 동작, 타이밍, 팔레트·효과·소리까지 다시 구현해야 한다. 이미 게임이 실행하는 연출은 원래 경로를 쓰는 편이 적은 중복 작업이다. 단, 실행 비용·초기 로딩이 더 가볍다는 뜻은 아니다. 조사한 런타임 WASM은 약 37.4MiB이며, 메모리·오디오·격리 환경도 필요하다.

이후 기존 런타임을 연결했다. 무기 상세 화면에서 기본 OFF인 스위치를 켜면 같은 단계에서 자동 재생한다. 원래 게임이 얼굴·대사·무기 자원을 읽기 전에 선택한 무기·기체·파일럿을 지정하고 일회용 저장 메모리에서 실행한다. 별도 창을 여는 경로는 제거했다. 실제 확인 범위·연출 번호 0인 롱기누스의 한계·지원 ROM·소스 및 라이선스는 [WEAPON_PREVIEW.md](WEAPON_PREVIEW.md)에 기록한다. 모든 미사용 연출의 복구나 PixiJS 재구현을 뜻하지 않는다.

## AI 추천 조작 평가

추천 방식은 **프롬프트 복사 → 사용자가 AI Studio에 입력 → JSON 붙여넣기 → 현재 에디터의 검증·변경 비교 → 선택 적용**이다. 이미 있는 편집값 JSON 형식과 from/to 충돌 검사를 재사용할 수 있다. AI가 레코드·허용 필드·원래 값·범위를 모른 채 직접 바이너리를 수정하게 하지 않는다. 추천 결과가 구조 검사를 통과해도 밸런스나 게임 진행의 타당성이 보장되는 것은 아니다.

Google AI 검색 화면을 자동으로 읽는 방식보다, Gemini의 문서화된 JSON Schema 출력을 사용하는 편이 형식 유지에 적합하다. 무료 사용은 현재 제공 모델·한도에 한정되므로 ‘무제한 무료’를 약속하지 않는다. 현재 저장소는 정적·동일 출처·외부 쓰기 없는 처리를 요구하므로 직접 API 호출·공용 API 키·ROM 업로드를 추가하지 않았다.

이후 편집 화면 아래에 **AI 추천**을 연결했다. 선택 항목·현재 검색 결과 또는 기체/파일럿/무기/지형/보상/개조 비용 전체 중 대상을 고른다. 요청문에는 현재 편집값·허용 범위·레코드 식별값·목록 편집의 선택지와 공간 제약만 담고, 파일·ROM 바이트·세이브·파일 경로·세션 토큰을 담지 않는다. 무장 추가·교체는 별도 체크로 포함하며 기본은 꺼져 있다. 실제 건담 한 항목의 기본 요청문은 3,521자였고, 전체 1,407개 무기 목록을 불필요하게 포함하지 않았다. 범위에 따라 길이는 달라진다.

받은 JSON은 기존 preset 파서에 더해 요청 대상·필드·identity·원래 값과 대조한다. 다른 대상, 만들어 낸 무기/능력 ID, 고정 항목, 잘못된 목록의 원래 값을 거부한다. 통과한 JSON은 기존 변경 비교 창으로 넘기며 바로 적용하지 않는다. 요청문 작성 뒤 직접 수정한 값은 충돌로 표시한다. AI 모델을 내장하거나 외부 서비스에 자동 질의하는 기능으로 부르지 않는다.

검사 근거:
