# 좌표 증원의 완료 플래그: 저장 범위와 초기화

2026-10-23. 현재 전투에서 사용할 아군 증원의 한 번 실행 조건을 위한 정적
조사다. 격납고 기체만 지급하는 기능으로 요청을 대체하지 않는다. 이 기록은
새 flag 예약이나 callback 설치 권한을 부여하지 않는다.

## 실제 입력과 네이티브 저장 계약

F는 현재 로컬 입력의 EXEC0 SHA-256
`308fe51501cd70091fe1a9983101d6cd98b9fdc7d8857e4bac9e2bff3e9974f1`,
공통 TSR root0 SHA-256
`b7175cfbe8e0dfef455cf8bf9eebd8798cf21fbffe9a0af08b78c340f3244c06`를
다시 읽었다. 이는 [기존 callback 근거](EDITOR_PHASE_CALLBACK_RESEARCH.md)의
네이티브/공통 스크립트와 같다. 아래의 D0 및 저장 구간은 원본 EXEC 구간과도
바이트가 일치했다. 전체 BIN이나 추출 게임 파일을 새로 저장하지 않았다.

| F 실행 위치 | 계약 |
| --- | --- |
| `0601FA18` | D0 subcommand를 읽어 `060B28E4` table을 직접 인덱스한다. |
| `0601FA40` → `0601FEC8` | D0.00: BE16 flag 번호의 비트를 켠다. |
| `0601FA74` → `0601FF1C` | D0.01: 같은 비트를 끈다. |
| `0601FAA8` → `0601FF70` | D0.02: 같은 비트를 조회하고 VM 조건 결과에 반영한다. |
| `0601FAF8` | D0.03: BE16 시작/끝 범위의 flag를 끈다. |
| `06030146..06030164` / `06030636..06030654` | 일반 저장 pack/unpack: GS+534부터 64바이트와 payload+1FD6부터 64바이트를 서로 복사한다. |
| `06031314..06031382` / `060317FE..06031814` | 전투 중간저장 pack/unpack: GS+534부터 64바이트와 payload+94부터 64바이트를 서로 복사한다. |

flag `id`의 저장 주소는 `GS + 0x534 + (id >> 3)`, 마스크는
`1 << (7 - (id & 7))`다. 특별한 256 경계 분기는 없다. 실제 다음 데이터
GS+574가 강화파츠 보유 카운터이므로, 저장 pack이 보존하는 flag 영역은
**0..511의 512비트**다. helper의 `id <= FBFF` 검사는 이 64바이트 영역을
보호하는 검사가 아니다. 이를 flag 상한 확장 허가로 사용하면 안 된다.
flag 511은 GS+573의 bit 1이며 실제 저장 대상이다.

D0.04..07의 field 시작/폭은 각각 unsigned byte다. helper
`06020DC4`/`06020E64`는 시작 byte 위치부터 네 바이트만 읽고 쓴다. 시작
번호가 최대255이므로 field 경로가 flag511에 접근할 수는 없다. 파일럿
스킬/정신기의 event gate도 byte 값에서100을 빼고, 기체 특수능력 gate도
byte를 소비한다. 이들 경로는 flag511의 소비자가 아니다. 다만 직접 bit
번호와 다른 네이티브 접근은 별도로 확인해야 한다.

## 공통 초기화에서 지우는 범위

아래 좌표는 압축 해제 **TSR root0 세그먼트 상대**다. root0 시작은 전체
압축 해제 TSR+A4다. 아래 marker와 실제 D0 길이/소비 규칙을 함께 대조했다.

| 게임 | 위치 | 지우는 flag 범위 |
| --- | --- | --- |
| F | `0204`, `020A` | 224..255, 480..511 |
| 완결편 | `020D`, `0213`, `0219` | 224..255, 400..415, 480..511 |

F의 다음 `0210`은 기존에 인증한 첫 맵 준비 root4 wrapper 호출이며,
완결편은 `022D`다. 그러므로 256..511 전체를 막연히 맵 로컬 영역으로
취급할 수 없다. 초기화 범위와 Continue의 진입 순서는 별개 계약이다.
위 표만으로 Continue 뒤 완료 flag가 언제나 유지된다고 주장하지 않는다.

공통 root0 및 모든 현재 SCEDATA 해제 본문에서 직접 D0.00/01/02와
E7.00/01 모양을 부정 전용으로 검색하면 상위480..511의 기존 번호 후보는
F494, 완결편494/507이다. 511 marker는 없었다. marker 검색은 잘못된
명령 경계의 가짜 후보를 추가할 수 있고, 간접 네이티브 참조의 부재를
증명하지 못한다. 따라서 이 목록은 **예약 후보를511로 좁히는 자료**이며
미사용 번호를 자동 할당하는 제품 근거는 아니다.

사적 경량 근거는 `weapon_preview_20261023/story-font/`의
`d0-once-flag-audit.mjs/json`이다. JSON에는 해시·좌표·marker 목록만 있다.
각 원본의 크기와 수정 시각은 조사 전후 같았다.

## 샤아 전용 자쿠 사례가 실제로 하는 일

완결편 물리 본문36 / selector133의 root8에서 +4860은 파일럿75가 정확히
XY(10,47)에 있는지 C0.0F로 조회한다. 성공 대사 뒤 +4905에서 flag341을
켜고 +4909의 원래 승리 처리를 실행한다. root0의 +9263은 flag341을 읽고,
+9512의 C2.04로 기체340을 만들며 기존 파일럿75의 하차/재배정을 이어간다.
즉 **전투 종료 시 좌표 조건으로 다음 처리에서 받는 기체**의 사례다.
이동 완료 즉시 새 아군 actor를 만드는 사례로 해석하지 않는다. 341은 위
공통 초기화 범위에 속하지 않으므로 단순히 `>=256`이라는 이유로 새
맵 한정 완료 표식으로 빌려 쓰면 안 된다.

## 현재 가능한 합성과 남은 설치 조건

[root8 callback 조사](EDITOR_PICKUP_CALLBACK_CONTRACT_20261023.md)에서 확인한
공통 wrapper는 매번 root8 시작을 다시 선택한다. pending/done PC 두 개만
만드는 방식은 다음 호출의 중복 증원을 막지 못한다.

새 파일럿 단일쌍을 만드는 경우에는 C1.0A의 **full roster ID 존재** 결과를
재호출 가드로 재사용할 수 있다. 성공 후 파일럿 캐시에 같은 ID가 남으므로
다음 호출과 저장 복원에서도 중복 생성을 건너뛸 수 있다. 이 방식은 기존
파일럿을 새 기체에 태우는 사건에는 적용되지 않는다. 같은 맵의 원래
삭제/전체 초기화가 그 파일럿을 제거할 수 있는 경우에도 독립 완료 표식이
필요하다.

제품 writer를 열기 전 남은 범위는 좁다. 511에 대한 다른 native/동적
소비자의 부재와 Continue의 초기화 순서를 닫거나, 삭제 없는 새 파일럿
단일쌍의 존재 가드 범위를 인증해야 한다. 아군 actor 할당과 파일럿/기체
캐시의 용량을 **변경 전에** 검사하고 실패 시 부분 생성이 없어야 한다.
현재의 C2.04 단독 effect는 이 actor 생성 계약의 대체물이 아니다.

## C0 dispatch 대조 정정

실제 F C0 handler는 `06022244`, subtable은 `060B2944`다. C0.0F는
cell `060B2980`의 `06022C80`으로 가고 전체8바이트다. 레벨 조회
`06022D68`은 C0.10이다. 앞선 잘못된 table 시작 추정을 제품에 적용하지
않았으며 기존 RG01/C0.0F compiler는 유지한다. 정확한 독립 대조는
[로스터 명령 근거](EDITOR_ROSTER_COMMAND_SEMANTICS_20261023.md)에 있다.
