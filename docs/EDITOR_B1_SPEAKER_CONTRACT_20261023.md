# B1 화자 선택과 VM 호출 계약 — 2026-10-23

이 문서는 기존 시나리오의 확인된 B1 발화에 **화자 파일럿을 바꾸는 제품 코어**와, 연속 B1 경계에 한정한 새 발화 코어와 아직 허용하지 않은 일반 VM 이벤트 삽입을 구분한다. 원본 F v0.5 c와 완결편 v0.3 a의 실행 코드·TSR·SCEDATA·FACE는 사용자 로컬 파일에서 메모리로만 읽었다. 게임 파일·추출 글리프·실제 세이브는 이 저장소에 추가하지 않았다.

## 확인한 packed descriptor

B1은 opcode, signed BE16 문구 상대 참조, packed BE16 descriptor의 5바이트다. 핸들러가 받는 VM 현재 포인터는 opcode 다음 byte, 즉 피연산자 커서다.

| 필드 | 의미와 근거 | 제품 변경 |
|---|---|---|
| descriptor bits 2..10 | `(word >>> 2) & 511`을 파일럿 번호로 사용한다. TSR root28의 그 레코드 첫 BE16 low9bit에서 FACE ID를 얻는다. | 검증된 실제 파일럿·FACE 후보에 한해 변경 |
| bits 0..1 | FACE subheader 선택 인덱스 0..3. UI flags bit3..4와 이미지 생성기의 첫 stack 인자로 전달된다. | 원문 유지. ‘분노/웃음’ 같은 표정 이름을 추측해 붙이지 않음 |
| bit15 | B1이 32비트 전역 값 0/1로 저장하고 B9.01이 동일 값의 하위16비트를 읽어 분기한다. | 원문 유지 |
| bits11..14 | 이번 B1 준비 경로에서 소비하지 않는다. 다른 의미가 없다는 전수 증명은 아니다. | 원문 유지 |

파일럿 번호와 FACE 번호는 서로 다른 값이다. 실자료에서 F 다바 #151의 FACE ID는 #152였다. 이름이나 레코드 번호로 FACE를 임의 매칭하지 않는다.

주요 네이티브 진입점은 다음과 같다. 주소는 런타임 SH-2 주소이며 디스크 offset이 아니다.

| 단계 | F | F완결편 |
|---|---|---|
| B1 핸들러 | `0601BA2C` | `0601BFC8` |
| descriptor 준비 | `0601C4DC` | `0601CAA8` |
| 파일럿 FACE 조회 | `0601C5F0` | `0601CBBC` |
| B9.01 분기 선택 | `0601BDEC` | `0601C388` |
| B1 전역 분기 값 | `060C37C4` (32비트) | `060C9C34` (32비트) |
| B9.01의 동일 값 읽기 | `060C37C6` (하위16비트) | `060C9C36` (하위16비트) |
| 현재 문구 포인터 | `060C37D0` | `060C9C40` |

B9.01 자체에는 범위 검사가 없지만, B1 경로에서는 descriptor bit15를 저장한 바로 그 값이므로 인덱스는 0 또는 1이다. `060C37C4`와 `060C37C6`를 서로 독립된 상태로 해석하면 이 계약을 놓친다. B9.01 반환은 이 경우 `5001` 또는 `5003`이다.

## 실제 FACE 변형 수와의 관계

F의 전달 경로는 B5 → `0601736C` → `060143E8` → `060141F0` → `06009D18`이다. 마지막 이미지 생성기는 원래 low2 값을 첫 stack 인자에서 local+20으로 읽는다. `06009E36`에서 해제 이미지의 첫 BE16을 subheader 수로 읽고 `06009E3C`에서 `index >= count`이면 종료한다. `06009E52/54/58`은 `index * 16`으로 subheader를 선택한다.

완결편의 대응 경로는 B5 → `06017800` → `06014860` → `060144EC` → `06009F40`이다. count 검사는 `0600A05E/64`, 16바이트 subheader 선택은 `0600A07A/7C/80`이다.

따라서 화자를 바꿀 때 원래 low2 값이 새 FACE의 실제 subheader 수 이상이면 그림이 출력되지 않을 수 있다. writer는 `speakerVariant < variantCount`를 요구한다. FACE의 `decoded[1]`만 count로 쓰려면 `decoded[0] === 0`까지 확인해야 한다. 제품 후보 생성은 core가 실제 파일럿 레코드와 FACE 압축 블록·모든 subheader를 검증해 제공한다. FACE 0, 머리부 없는 주인공 습득표와 검증하지 못한 동적 슬롯은 후보에 넣지 않는다.

## 제품 코어 API

`assets/editor-scenario-dialogue.mjs`는 다음 trusted 입력을 받는다.

```js
{
  speakerOptions: [
    {pilotId, faceId, variantCount, identity}
  ]
}
```

`pilotId`는 1..511 정수, `faceId`는 1..511 정수, `variantCount`는 1..64 정수이고 identity는 실제 자료 검증을 마친 호출자가 제공한다. 이 배열 자체는 사용자 JSON으로 가져오는 편집 권한이 아니다. core가 검증한 원래 TSR/FACE와 연결해야 한다. 파일럿 번호 중복과 잘못된 항목·접근자·희소 배열은 거부한다.

원본의 일반 대사는 `speakerOptions` 없이도 읽을 수 있다. 이 경우 화자 번호는 표시할 수 있지만 화자 변경은 허용하지 않는다. 읽은 행은 다음 필드를 추가로 제공한다.

- `speakerId`, `originalSpeakerId`: 현재 값과 원래 파일럿 번호.
- `speakerVariant`: 원문 low2 값. 편집하지 않는다.
- `speakerEditable`, `speakerReadOnlyReason`: 실제 후보와 공유 owner 계약에 따른 편집 가능 여부.
- `speakerIdentity`: owner 위치와 원래 descriptor 묶음의 식별자.

지원 요청은 기존 `{recordIndex, text}` 또는 `{recordIndex, pagesJson}`에 `speakerId`를 함께 주거나, `{recordIndex, speakerId}`만 주는 형태다. `text`와 `pagesJson`은 동시에 받지 않는다. `validateScenarioDialogueSpeaker(row, speakerId, options)`는 선택된 파일럿의 FACE 변형 호환성을 확인한다.

**공유 owner의 원래 descriptor가 모두 동일한 행**만 바꾼다. 여러 일반 글자 run이 같은 B1을 공유하면 새 화자를 모든 run에 표시하며, 같은 owner에 서로 다른 화자를 요청하면 거부한다. 쓰는 값은 `(old & 0xF803) | (speakerId << 2)`이므로 기존 문구 참조, low2, bit15, 미확정 bits11..14는 보존한다. 검증된 다른 이벤트 확장이 원래 B1 위치를 바꿨으면 화자 변경은 거부한다.

부분 수정은 이미 저장된 다른 필드를 보존한다. 예를 들어 화자만 바꾼 뒤 본문을 고치면 화자를 유지하고, 본문을 원래 값으로 되돌려도 바뀐 화자는 유지한다. 화자를 원래 번호로 되돌리면 본문·페이지 변경은 유지한다. `replace:true`와 빈 목록은 이 대사 metadata 전체를 원문으로 되돌린다.

## SRWDIA04 원복과 출처 검사

화자 편집이 없으면 기존 SRWDIA01/02/03 형식을 계속 출력한다. 화자 편집이 있는 출력만 SRWDIA04를 쓴다. 기존 32바이트 footer 구조는 유지한다.

v4의 각 typed entry 앞 4바이트는 종류 BE16과 화자 번호 BE16이다. 종류는 0=일반 본문, 1=페이지, 2=화자만, 3=본문+화자, 4=페이지+화자다. 종류0/1의 화자 번호는 0이어야 한다. 원문 run의 위치·원래 바이트·입력 UTF-8은 이전 형식을 따른다. 화자 전용 항목은 입력 본문 길이가 0이며 원문 본문은 그대로 남긴다.

8바이트 patch record의 마지막 BE16은 v4에서 0=문구 참조 원복, 1=descriptor 원복으로 구분한다. 이전 v1/v2/v3의 reserved 값0 규칙은 완화하지 않았다. 모든 patch는 위치별 정렬·비중첩, 본문 경계와 원래 원문 해시를 확인한다. 정규화는 원래 문구·descriptor를 복원한 뒤 원래 자료를 다시 해석하고 trusted 후보로 writer를 재실행하여 **모든 출력 바이트가 정확히 같아야** 성공한다. 따라서 화자를 바꾼 v4를 `speakerOptions` 없이 열어 새 권한을 만들어 내지 않는다. 외부 SCEDATA 출처 검사는 기존 원문 hash를 계속 확인해야 하며 이 모듈은 전역 mutable mask를 늘리지 않는다.

집중 회귀는 화자만 쓰기, 원문 불변, 비트 마스크, v4 재열기/원복, 짧은 본문·늘어난 본문·동일 화자 페이지와 합성, 부분수정 보존, 공유 run 일관성, 후보/변형 불일치와 metadata 변조 거부를 포함한다. 실제 F/완결편의 통합 압축·재열기 검사는 동일 trusted FACE 후보 생성 이후 core 통합 검사 한 번씩에 합쳐 수행한다.

## 새 발화 추가의 최소 경계와 네이티브 근거

B1의 native 반환은 `6000`이며, 길이5를 반환하는 명령이 아니다. 공통 보조 함수는 VM+68의 깊이를 늘리고 피연산자 커서+4, 즉 원래 opcode+5를 반환점으로 저장한 뒤 TSR root0/group2/entry3으로 이동한다. `04`는 그 주소를 복원하고 `F000`으로 interpreter fetch를 재개한다. B1 helper 자체에는 깊이16 검사가 없고 `03` VM call에는 검사가 있으므로 추가 `03` wrapper를 끼우면 원래보다 스택을 한 칸 더 사용한다.

후보 trampoline은 기존 B1 자리에 `01` signed16 점프를 두고, 본문 끝에서 ‘원래 B1 복제 → 새 B1 → 01 원래 다음 명령 복귀’를 실행하는 형태다. `01`은 호출 스택을 늘리지 않는다. 두 게임 각각 초기 VM 깊이 0/1/7/14의 4건에서 실제 SH-2 코드로 점프·B1·반환·다음 opcode fetch와 복귀 포인터 보존을 확인했다. 별도 descriptor 준비 검사는 게임별 실제 파일럿24명 × low2 4종 × bit15 2종 × 미확정 보존 비트 2종 = 384건으로 파일럿 추출·원래 TSR 상대포인터 FACE 조회·분기 선택이 맞았다. 캐시 마킹은 인수를 관측하는 hook으로 대체했고 실제 그림 출력까지 실행한 검사는 아니다.

원문에서 연속한 확인된 B1 쌍도 F589쌍, 완결편1220쌍이 있으며 완결편4쌍은 packed descriptor까지 같았다. 이는 실제 게임 형식이 연속 호출을 사용한다는 정적 근거이고, 임의 삽입 지점이 모두 안전하다는 근거는 아니다.

제품 코어의 최초 허용 범위는 **원래 다음 명령도 확인된 B1인 연속 발화 경계**다. 게임이 이미 순차 발화를 쓰는 경계에서만 원문 B1 복제와 새 B1을 실행하고 원래 다음 B1으로 복귀한다. 임의 B1 뒤의 공통 UI 닫힘 상태나 새로운 callback을 추측하지 않는다. 일반 글자 페이지 추가는 기존 B1 안의 F7을 쓰는 별도 기능이다. **기존 B1 화자 변경, 기존 발화 다음 페이지 추가, 연속 B1 사이의 새 발화, 일반 VM 이벤트 삽입, 새 화수·맵 전체 추가는 서로 다른 완료 항목이다.**

## 합성 carrier 통합 회귀

`editor-deployments.mjs`와 `editor-scenario-provenance.mjs`는 trusted `tables.speakerOptions`만 전달한다. 요청 options의 동명 배열로 후보 권한을 대체할 수 없다. 물리 압축을 담당하는 `repackScenarioBodies`도 동일 후보를 source/wanted 대사 정규화에 전달한다.

코어와 carrier 집중 회귀 11건은 F/완결편 합성 자료에서 화자만 변경 → 본문 변경 → 페이지+다른 화자 → 좌표 재수정 → 화자만 원복 → 본문 원복을 확인했다. 각 단계의 원래 decoded scope, 다른 배치·턴 제한 편집, 재압축 파일 길이는 유지됐다. 공유 owner 충돌은 압축 전 거부하며, alias 문구에서 일부 owner만 바꿔 다른 행의 화자가 섞이는 요청도 거부한다. 원복 patch 개수도 출력 전에 8192개 상한을 확인한다. 이 검사는 실제 전체 게임 실행이나 새 이벤트 삽입 성공을 주장하지 않는다.
