# 로컬 게임 데이터 에디터

정적 패치 사이트에는 세가 새턴판 **슈퍼로봇대전 F**와 **슈퍼로봇대전 F 완결편**의
정품 원본, 공개 패치 및 개인 수정 이미지를 편집하는 브라우저 에디터가 포함되어 있습니다. 파일과 수정 데이터는
사용자의 기기 안에서 처리합니다. 웹사이트로 전송하지 않습니다.

시나리오 화면은 확인된 기존 맵·배치·사건과 지원되는 작전 목적만 편집합니다. 일부 조건은 실제 게임 실행과 저장·재부팅 복원까지 확인했지만 모든 시나리오의 실행을 검증한 것은 아닙니다. 신규 이벤트·증원 추가, 완결편 위치 조건, 격추·도착 이력 조건은 공개 버전에서 지원하지 않습니다.

## 다른 Mac에서 로컬 실행

Node.js 24 이상과 Python 3이 필요합니다. 저장소를 받은 폴더에서 다음을 실행하세요.

```sh
git switch codex/editor-local-preview-20261015
python3 -m http.server 8844 --bind 127.0.0.1
```

브라우저에서 `http://127.0.0.1:8844/`를 열고 그 Mac에 있는 본인 게임 폴더를 선택하세요.
별도 npm 설치나 빌드는 필요하지 않습니다. 게임 이미지·추출 그림·음성·개인 세이브는
저장소에 포함되지 않습니다. 서버를 종료하려면 터미널에서 Control-C를 누릅니다.
이 브랜치는 개발 중인 로컬 미리보기이며 모든 무기 연출이 완성된 배포판은 아닙니다.

## 사용 방법

페이지는 **게임 폴더 열기 → 한글 패치 설정 → 선택적 편집 → BIN/CUE 저장**으로 진행합니다.
한글 패치와 에디터의 모드 전환은 없습니다. 편집을 건너뛰어도 같은 저장 화면을 사용합니다.

1. **게임 폴더 열기:** 정품 원본, 최신 승인 한글 패치본, 기존 개인 편집본이 든 폴더를 고릅니다.
   파일 구성·게임 헤더·전체 SHA-256과 편집 가능한 데이터 구조를 기기 안에서 검사합니다.
   F와 완결편은 파일에서 감지합니다. 구분할 수 없는 BIN이 여럿이면 임의로 고르지 않고 거부하며,
   잘못 고른 폴더는 열려 있던 편집 세션을 지우지 않습니다.
2. **한글 패치 설정:** 정확한 정품 원본을 열었으면 `한글 패치` 또는 `원본 유지`를 고릅니다.
   한글 패치를 선택한 경우에만 승인 버전과 폰트를 선택합니다. 원본 언어를 유지하면 한글 패치를
   적용하지 않고 원래 게임 데이터를 편집합니다. 기존 한글 패치본이나 개인 편집본은 파일의 언어와
   변경값을 유지합니다. 검증된 패치본·개인 편집본이면 이 설정 섹션을 생략하고, 편집 카드에 감지한 버전·폰트와 파일 종류를 표시합니다.
   보이는 단계 번호도 폴더 1 → 편집 2 → 저장 3으로 정리합니다. 다시 정품 원본을 열면 설정 섹션이 돌아옵니다.
   한글화 여부나 폰트를 바꾸려면 정품 원본이 필요합니다.
3. **게임 데이터 편집:** `F 에디터 열기` 또는 `F완결편 에디터 열기`를 누르면 편집 화면으로 갑니다.
   수정할 값이 없으면 밑줄 친 `편집 없이 저장으로 이동`을 누릅니다. 최신 승인 한글 패치 계열만
   편집할 수 있으며, 이전 승인 버전은 정품 원본에서 편집 없이 패치만 만들 수 있습니다.
4. **BIN/CUE 저장:** 편집 화면의 `저장으로 이동`도 같은 저장 화면으로 갑니다. `BIN/CUE 만들기`로
   결과를 만든 뒤 BIN과 CUE를 각각 다운로드하거나 `폴더에 저장`으로 기록합니다. 폴더 저장은
   입력 파일 덮어쓰기를 막고, 기록한 BIN 전체 해시와 CUE 내용을 다시 확인한 뒤 완료를 알립니다.
   다운로드 링크는 폴더 저장에 실패해도 유지됩니다. BIN과 CUE는 같은 폴더에 두세요.

`파일·설정으로`, `편집으로` 이동은 편집값을 지우지 않습니다. 값을 다시 수정하면
이전 결과 링크는 사라지고 새 결과를 만들 수 있습니다. 결과 BIN/CUE를 다시 열어 여러 번 이어서
편집할 수 있으며, 변경 내용 JSON 저장·불러오기도 그대로 지원합니다. 재불러온 BIN의 기존 변경값은
그대로 시작값이 되고, ‘이번 변경’은 현재 세션에서 새로 고친 값만 셉니다. 파일만으로 과거 편집 횟수나
모든 보정 이력을 복원할 수 있다고 주장하지 않습니다.

다른 파일을 열거나 한글화·폰트를 바꿔 원본에서 기반을 새로 만들 때, 저장하지 않은 수정이 있으면
먼저 버릴지 확인합니다. 변경 내용을 다른 기반으로 옮기려면 변경 내용 JSON으로 저장한 뒤 새 세션에
불러옵니다. 설정 선택만으로 세션을 지우거나 패치를 자동 적용하지 않습니다.

개인 BIN은 게임 헤더·전체 해시·TSR 구조만 같다고 무조건 열지 않습니다. 같은 브라우저가 검증한
출력 해시 기록 또는 정확한 원본/최신 승인 패치에 고정된 편집 범위·변경 불가 구간 검사를 통과해야
합니다. 원본 언어 편집본도 별도의 원본 검증 프로필을 사용하며 공개 승인 릴리스로 표시하지 않습니다.

### 로컬 개발판: 새 무기와 공격 연출 지정

이 절의 기능은 로컬 개발판 변경이며 공개 배포 완료를 뜻하지 않습니다.
무기 화면에서 사용 기체가 확인된 원본 무기를 선택하고 `무기 추가`를 누르면
해당 기체에 별도의 무기 항목을 만듭니다. 새 항목에는 이름 입력과 `공격 연출`
선택란이 표시됩니다. 연출 목록은 `기체 · 무기`로 원본을 구분합니다.
공격력·사거리·EN 등은 기존 수치 입력란에서 수정합니다.

연출 지정은 기존 공격 프로그램 전체를 복제합니다. 공격자의 그림 등 원본
연출에 포함된 자산도 함께 나타날 수 있으며, 공격자 외형 교체나 키프레임의
새 조합을 지원한다고 주장하지 않습니다. 연출 원본을 바꾸면 이전 원본에서
편집한 이동·시간값을 초기화합니다. 이름·연출 설정은 `무기 설정 적용`으로
반영하며, 적용 전 입력도 편집값 저장과 BIN 생성 전에 확인합니다.

새 무기의 이름·연출 원본 번호는 편집값 JSON과 개인 BIN에 함께 기록합니다.
BIN을 다시 열 때 전체 이미지의 변경 불가 구간 검증에 더해 이름의 실제 바이트,
상대 참조 주소와 남은 이름 공간을 검사합니다. 이 기록은 ACCEPTED 릴리스
인증을 대신하지 않습니다. 기체 항목·무기 레코드·연출·이름 공간에 여유가
없으면 추가를 거부하므로 무제한 추가 기능은 아닙니다.

게임 확인에는 새 출력으로 처음 부팅하거나 그 출력에서 만든 상태를 사용해야
합니다. 다른 출력의 세이브스테이트에는 옛 TSR/연출이 메모리에 남을 수 있어
새 디스크에서 읽은 결과라는 증거가 되지 않습니다. F v0.5 a에서는 아프로다이 A의 격투를 복제해 이름 ‘웨이브라이더어택’, 공격력 4100, 사거리 1~5, EN 100, 연출 원본 이글파이터 돌격으로 지정한 실제 UI 출력으로 새 부팅과 게임 내 이어하기를 확인했습니다. 실제 공격에서 푸른 돌진 연출, EN 100→0, 적 HP 5000→0을 확인했습니다. 완결편 v0.3 c에서는 초호기의 팔레트라이플을 같은 설정으로 복제한 UI 출력으로 새 부팅과 34화 완료 게임 저장 로드를 확인했습니다. 35화의 실제 반격에서 푸른 돌진 연출, EN 150→50, 적 HP 5300→0을 확인했습니다. 두 실행은 헤드리스이며 음성 포함 영상으로 기록했습니다. 공중 적응이 없는 격투를 원형으로 복제하면 공중 적을 공격할 수 없습니다. 연출 지정은 무기의 지형·사용 조건을 자동으로 바꾸지 않습니다. 이 사례는 모든 기체·연출 조합의 실게임 안전성을 증명하지 않습니다.

표준 2·3형태 변형에서는 연결된 기체의 기존 개조·탄수 칸도 피해서 새 무기의 번호를 배정합니다. Z건담의 1~6번 개조 칸을 보존하고 웨이브라이더의 새 무기는 7번부터 배정합니다. 재불러오기 때도 변형 형태 사이의 중복 번호를 거부합니다. 근거는 원본 실행 코드의 기체 레코드 +7 변형 방식·현재 형태 해독과 실제 Z건담→웨이브라이더 캐시 번호 변경입니다. 특수 합체·분리·폭주·사건에 의한 다른 연결을 이 규칙으로 추정하지 않습니다.

완결편의 웨이브라이더에서도 빔건을 원형으로 새 ‘웨이브라이더어택’을 만들고 위 수치와 이글파이터 연출을 지정한 실제 UI 출력을 확인했습니다. 새 부팅 후 게임 저장을 불러와 Z건담을 변형하고, 새 무기를 선택해 공격했습니다. 기체 그림에 푸른 돌진 연출이 재생되며 EN 153→53, 적 HP 5300→0으로 바뀌었습니다. 선택부터 공격까지 음성을 포함한 헤드리스 영상으로 기록했습니다.

무기 목록은 이름·연출 적용 뒤 새 데이터로 다시 만들며, 저장 성공 안내를 표시합니다. 데스크톱은 그림과 수치를 좌우로 배치합니다. 좁은 화면은 실제 남은 높이를 측정하고 미리보기 공간이 부족하면 수치를 다음 페이지로 나눕니다. 그림 크기는 미리보기 패널 경계 안에서 계산합니다. 웹의 참조 그림 반복은 게임의 실제 연출 재생 시간과 다릅니다.

### 목록과 화면 배치

모바일 기체 화면의 이동력·운동성·장갑·한계반응은 4열 한 줄로 표시하고 페이지를 나눌 때도 같은 묶음으로 유지합니다. 숫자 글자 크기는 유지하고 입력 여백과 되돌리기 단추 폭을 줄였습니다. 옆 ↶ 단추는 입력칸과 같은 40px 높이이며 **에디터를 열었을 때의 값**으로 되돌립니다. 수정본을 열었으면 그 수정본의 값이 기준입니다. 320·360·375·390·414px에서 최대값(이동력 255, 나머지 65535)과 변경 상태를 실측해 숫자·제목이 잘리지 않고 버튼 높이와 페이지 수가 변경 전후 유지되는 것을 확인했습니다.

설정·편집·저장 화면은 문서 세로·가로 스크롤 없이 현재 창 안에 들어가도록 배치합니다. 확인한 화면 크기와 레코드 표본은 아래 ‘레이아웃 측정’ 및
‘통합 에디터 변경’에 기록합니다. 이 측정 결과를 모든 레코드·오류 상태·브라우저 조합의 보증으로 확대하지 않습니다. 안쪽에서 스크롤되는 것은 목록과
읽기 창입니다(레코드 목록, 기체의 무기 목록, 무기의 사용 기체, 특수능력 편집 창의 목록, 도움말 카드, 패치노트 읽기 창).
설정의 세 카드가 나란히 놓일 때는 폭과 높이를 맞추며, 행의 높이는 가장 많은 내용을 가진 카드로 정합니다. 세로 화면에서는 카드마다 필요한 높이만 사용해 쌓습니다.

창 크기에 따라 배치가 셋입니다.

- **넓은 화면(폭 1100px 이상이고 높이 720px 이상):** 목록과 레코드의 모든 구역이 한 번에 보입니다.
- **중간(폭 761px 이상이지만 폭 1100px 미만이거나 높이 720px 미만):** 목록은 옆에 있고 레코드는 실제 남은 공간에 맞춰 페이지를 구성합니다. 구역 단추는 기록 막대 줄의 오른쪽에 있습니다.
- **좁은 화면(폭 760px 이하):** 목록 또는 편집 페이지가 보입니다. 가로로 든 휴대폰(폭 520px 이상, 높이 480px 이하)은 탭·저장 줄이 왼쪽 세로 줄로 가고 구역 단추가 기록 막대 줄로 올라가며,
  패치 화면의 세 카드는 데스크톱처럼 나란히 섭니다.

기체 능력치·기체 지형·특수능력, 파일럿 능력·성장·정신커맨드·특수능력, 무기 수치·무기 지형을 실제 높이로 잽니다. 함께 들어가는 항목은 한 페이지에 모으고,
다음 항목을 넣었을 때 넘치는 범위만 나눕니다. 구역 이름과 개수는 창 크기와 선택한 레코드에 따라 바뀌며, 기체 지형과 무기 지형은 서로 별도의 데이터로 다룹니다.
좁은 화면의 맨 앞에는 `목록`이 붙습니다.

각 탭은 `기록 막대`(이전 ‹ · 제목 · 다음 › · `n / 전체`), `목록`(검색칸과 스크롤되는 목록), `게임 화면`(선택한 레코드의 수치) 순서입니다.

- **목록:** 마우스 휠·트랙패드·터치로 스크롤되는 실제 스크롤 상자(`overflow-y: auto`, `overscroll-behavior: contain`)입니다. 무기 목록은 1,300줄이 넘어도

- **조건 검색:** 검색칸 옆 `조건`에서 현재 편집값의 지형 등급, 수치 범위, 정신커맨드·특수능력 보유 여부, 수정 여부를 조합합니다. 이름 검색과 모든 조건을 함께 만족하는 항목만 보이며, 최대 12개 조건을 사용할 수 있습니다. 기체·파일럿 지형과 무기 지형의 등급 저장 방식은 각각 처리합니다. 조건창은 실제 행 높이와 보이는 화면 높이로 측정하여 들어가는 행을 함께 표시하고, 넘칠 때만 페이지로 나눕니다.

  한 줄 범례(`A 120% · B 100% · C 80% · D 60% · - 0%`, 무기는 `A 100% · B 70% · C 40% · - 0%`)와 선택지의 읽어 주는 이름에 있습니다. 저장값은 4·3·2·1·0 정수
  그대로이고, 무기는 네 칸을 한 바이트로 묶어 저장합니다. 4를 넘는 저장값(파일럿 표 꼬리 블록)은 `?n`으로 보이고 고칠 수 없습니다.
- **무기 탭:** 이 탭은 게임 **전체 무기 데이터**이며 특정 기체의 무기 칸이 아닙니다(제목 `전체 무기 목록`과 설명 문구). 줄마다 사용 기체(`기체명 외 2대`, `사용 기체 없음`, `사용 기체 확인 불가`)를 보여 주고,
  고른 무기의 `사용 기체` 구역에 기체 단추(번호·슬롯)가 있어 누르면 그 기체로 이동합니다(검색이나 미사용 토글에 가려져 있으면 풀어 줍니다).
- **기체 탭:** `기체 무장` 구역이 그 기체의 무기를 저장된 순서와 슬롯 번호 그대로 보여 주고(게임 화면의 표시 순서는 확인하지 못했다고 적습니다), 항목을 누르면 무기로 이동합니다.
  목록 상태가 `inconsistent`·`unknown`이면 주의 문구와 함께 보여 주거나(개수만 어긋남) 보여 주지 않습니다.

- **파일럿 특수능력 편집 창:** 특수능력 제목 옆 `추가·삭제` 단추가 창을 엽니다. 창 위쪽에 `습득 시점 n개`와 `능력 종류 c/4`가
  항상 보이고, 현재 목록은 능력 계열별로 묶여 나옵니다. 아래의 `능력 · 단계 · 습득 Lv · 추가`로 더합니다(고를 수 있는 능력은 이 게임이 만드는
  번호 중 아직 갖지 않은 것이며, 지운 능력도 다시 고를 수 있습니다). 더할 수 없으면 단추를 막고 이유를 말합니다: 남은 자리 없음, 새 계열이 다섯 번째가 됨(같은 계열은 하나로 세며
  단독 능력은 각각 하나), 읽기 전용(이유: 미사용·주인공 자리·여러 ID 공유·머리부 없음·자리 없음 등), 습득 레벨이 1~99가 아님. 이미 한도를 넘는 목록이 있으면 경고로 알립니다.

  남은 자리·서로 다른 능력 수·한도·고를 수 있는 능력·잠금 이유는 모두 행이 주는 값(`skillCapacity`·`skillConsumers`·`skillConsumerLimit`·`addableSkills`·`skillEditable`/`skillEditReason`)이고, 창이 목록을 바꾸는 동안 같은 수를 다시 세는 규칙(칸 소비자 키, 계열 순서)은 저장 단계와 같다는 것을 시험이 고정합니다(아래 ‘화면과 코어의 계약’).

  신규 추가는 `추가할 능력 → 단계 → 습득 Lv → 추가`입니다. 일반 파일럿에서는 기존 정신커맨드와 능력 항목을 지우거나 교체하도록 요구하지 않습니다. 정신커맨드 6칸을 예약하며, 필요한 공간은 같은 편집 가능 구간의 검증된 패딩에서 확보합니다. 창을 닫기만 하면 아무것도 바뀌지 않습니다.
  `이번 추가 되돌리기`는 두 목록에 다른 수정이 없는 동안 추가 직전의 능력 목록을 복원하고 앞서 한 정신기·습득 레벨 수정은 유지합니다. 그 외의 `원래 목록으로 되돌리기`는 능력 목록을 레코드를 열었을 때로 돌립니다. 정신기 표지만 있는 자리 표시 파일럿에 능력을 넣으면 표지가 능력 쌍으로 바뀐다는 점(표지를

  어느 레코드의 어느 칸이 왜 안 되는지 한국어로 말합니다(영어 문장은 쓰지 않음).

폴더 카드의 상태 문구(에디터): 알아낸 종류를 칩이 그대로 말합니다. 정확히 공개 패치의 전체 SHA-256과 같은 BIN만 `공개 한글 패치본으로 확인`(초록 확인 표시, 설명에 `공개 패치 … 일치`)이고, 원본 폴더에서 만든 세션은 `정품 원본으로 확인`, 수치가 조정된 BIN은 `수치 조정된 BIN으로 확인`(회색 정보 표시, `수치가 조정된 BIN · 기반 v0.5 폰트 a · 공개 해시와 다름`)입니다. 게임·버전 카드의 `ACCEPTED`는 고른 공개 버전 자체의 상태이지 열린 파일의 상태가 아닙니다.
폴더에 사용자 CUE가 함께 있으면 그 세션에서 만드는 CUE의 트랙 구성으로만 쓰고, 승인 릴리스에 고정된 CUE 구성 표는 바꾸지 않습니다.

진행과 오류 표시: 폴더를 고르면 시작하는 확인(크기 확인, 전체 해시, 한글패치 적용, 편집 데이터 읽기)의 막대·단계 문구·`중단`은 **그 폴더를 고른 카드 안**(한글 패치의 원본 카드,
에디터의 폴더 카드)에 나옵니다. 고른 폴더를 거부한 이유도 같은 카드 안에 나옵니다(한글 패치의 정품 원본 확인 포함). 진행 막대는 한 번에 하나뿐이라 작업을 시작한 카드의 칸으로 옮겨 가고, 패치 카드는 실제 `패치 실행`·다운로드 만들기가 돌 때만 씁니다.
편집 화면에서는 수정본 만들기의 진행과 오류가 어둡게 가린 편집 화면 위의 가운데 패널로 나와 편집 화면의 크기가 변하지 않고, 반쯤 가려진 칸이 남지 않습니다(진행은 `중단`, 오류는 `닫기`로 닫습니다).
좁은 화면에서 수정본을 만든 뒤에는 아래 줄이 `수정 BIN 다운로드`·`CUE 다운로드` 두 링크가 되고(상태 문장은 화면 읽기 프로그램이 그대로 읽음), 값을 다시 고치면 링크가 사라지고 만들기 단추가 돌아옵니다. 카드는 행 높이로 고정되고 칸은 카드 안의 맨 아래에
붙어 있어 막대가 나타나도 카드가 움직이지 않습니다. 브라우저와 워커가 던지는 영어 예외 문장은 화면에 내지 않습니다. 편집 코어와 워커가 내는 모든 `EDITOR_*` 오류 코드는
`assets/app.mjs`의 안내문 표(`EDITOR_ERROR_COPY`)에서 한국어 제목·설명을 가져오고, 새 코드가 안내문 없이 들어오면 계약 시험이 실패합니다. 저장 공간을 넘는 오류는 필요한 크기·허용 크기·초과 크기를 숫자로 알립니다.

공개 기본값은 F v0.5와 완결편 v0.3입니다. 원본을 선택하면 최신 공개 패치(고른 폰트)를 적용한 뒤 편집합니다. 한글 패치 쪽이 이전 공개 버전을 고르고 있어도 에디터는 그 선택을 바꾸지 않고 같은 폰트의 최신 버전으로 따로 엽니다. 이미 패치된 BIN은 최신 공개 버전 기반일 때만 편집합니다. 이전 공개 패치와 그 기반 개인 수정본은 차단하며, 원본에서 최신 패치를 다시 만들어야 합니다. 개인 BIN을 최신 버전으로 자동 교체하지 않습니다. 개인 BIN의 해시를 공개 승인 해시라고 표시하지 않습니다.

화면 아래줄의 상태 표시(`변경값 n개 · …`)는 **단추**입니다. 누르면 에디터 위에 `바뀐 값` 창이 뜹니다(페이지 높이는 늘지 않고, 목록이 길면 창 안에서
스크롤됩니다. `✕`·Esc·창 밖 클릭으로 닫히고 키보드로 모두 쓸 수 있습니다). 창은 바뀐 레코드를 **기체 / 파일럿 / 무기**로 묶어 이름·번호와 바뀐 내용을
짧게 보여 줍니다(`HP 3000 → 3500`, `지형 육 B → A`, 무기는 바뀐 칸만 `지형 해 B → A`, `특수능력 2개 → 3개`). 항목을 누르면 창이 닫히고 그 탭으로 가서
그 레코드를 고르고(검색이나 미사용 토글에 가려져 있으면 풀고 목록을 그 줄까지 스크롤합니다) 바뀐 칸에 초점과 강조 테두리를 둡니다(특수능력 목록은
`추가·삭제` 단추, 조건 플래그 번호는 `플래그 칸`을 펼쳐서, 좁은 화면은 그 칸이 있는 구역으로 넘깁니다). 창이 열려 있는 동안 값이 바뀌면 목록도 바로 바뀌고,
바뀐 값이 없으면 `바뀐 값이 없습니다`만 보입니다. 목록과 저장 파일은 **같은 비교 함수**(`assets/editor-preset.mjs`의 `diffEditorRows`: 레코드를 열었을 때의 값
`original`·`originalSkillEntries`와 지금 값의 차이)에서 나옵니다.

같은 창 위쪽의 두 단추:

- **`변경 내용 저장`**: 바뀐 값만 담은 `.json` 파일을 만듭니다. 이름은 `srwf-<게임>-edits-<YYYYMMDD-HHMM>.json`(기기의 현지 시각, 예: `srwf-final-edits-20261007-2130.json`)입니다.
  데스크톱 Chrome·Edge는 저장 위치를 고르는 창(`showSaveFilePicker`)을 쓰고, 그 밖의 브라우저는 일반 다운로드로 받습니다(취소하면 아무것도 저장하지 않습니다).
  파일은 기기 밖으로 나가지 않습니다. 바뀐 값이 없으면 단추가 꺼져 있습니다.
- **`불러오기`**: `.json` 파일을 하나 고릅니다. 파일은 **믿지 않는 입력**으로 다룹니다: 8 MiB를 넘으면 읽지 않고 거부하고, JSON으로 읽은 뒤 구조 전체를 확인합니다(아래 규칙).
  문제가 있으면 파일 전체를 거부하고 이유를 한 문장으로 말하며, 열려 있는 세션은 그대로입니다. 통과하면 창이 요약으로 바뀝니다:
  `바로 적용`(지금 값이 파일의 원래 값과 같음) · `원래 값이 다름`(이 판에서 값이 달라진 곳, 펼쳐서 `여기 값 · 파일의 원래 값 → 바꿀 값`을 봅니다) · `이미 같은 값` · `건너뜀`(이유별 개수).
  단추는 **`모두 적용`**(원래 값이 다른 곳도 파일의 값으로), **`원래 값이 같은 것만 적용`**, **`취소`**입니다. 적용은 화면에서 직접 고친 것과 똑같이 **편집 중인 값만** 바꿉니다
  (`수정 n건`·목록의 수정 표시·입력칸이 함께 바뀝니다). BIN은 `개인 수정 BIN/CUE 만들기`를 눌러야 만들어집니다. 같은 게임의 다른 버전·폰트 세션에도 불러올 수 있고
  (새 패치에 내 수정을 옮기는 용도), 이때 `원래 값이 다름`이 새 패치가 바꾼 값을 알려 줍니다. 다른 게임의 파일은 거부합니다. 편집 데이터를 만드는 중(작업 중)에는 불러오기와 적용이 막힙니다.

파일 형식(`format`이 형식 표시, `version` 1):

```json
{
  "format": "srwf.editor-preset",
  "version": 1,
  "gameId": "srwf-final",
  "base": { "releaseId": "srwf-final-20261005-v0-3-c" },
  "createdAt": "2026-10-07T12:30:00.000Z",
  "units": [
    { "recordIndex": 12, "name": "", "fields": { "hp": { "from": 3000, "to": 3500 }, "air": { "from": 3, "to": 4 }, "ability1": { "from": 3, "to": 6 } } }
  ],
  "pilots": [
    { "recordIndex": 7, "name": "", "fields": { "atk": { "from": 120, "to": 140 } },
      "skills": { "from": [{ "id": 41, "level": 7 }, { "id": 60, "level": 3 }], "to": [{ "id": 41, "level": 7 }, { "id": 76, "level": 12 }] } }
  ],
  "weapons": [
    { "recordIndex": 3, "name": "", "fields": { "attack": { "from": 1500, "to": 1800 }, "terrain": { "from": 239, "to": 255 } } }
  ]
}
```

- 값은 편집 모델의 저장 정수 그대로입니다: 기체·파일럿 지형은 0~4(4=A … 0=E/-), 무기 지형은 네 칸을 묶은 한 바이트(`terrain`), 기체 특수능력은 `ability1`~`4`와 조건 플래그 번호
  `abilityValue1`~`4`. 필드 이름은 저장 요청과 같습니다(기체 18개, 파일럿 20개, 무기 7개).
- 레코드마다 **바뀐 칸만** `{ from, to }`로 담습니다(`from`은 저장한 세션이 열었을 때의 값). 특수능력 목록이 바뀐 파일럿은 `skills`에 바뀌기 전과 후의 **목록 전체**(순서 있는 `{ id, level }`)를 담습니다.
- `base`(저장한 세션의 기반 공개 릴리스)·`createdAt`·`name`(그 세션에서 읽은 이름)은 **사람이 보라고 둔 정보**일 뿐 맞춰 보지 않습니다. 레코드는 언제나 `recordIndex`로만 찾습니다.
  `name`은 사용자 자신의 이미지에서 읽은 글자이므로 공개 저장소에는 넣지 않습니다(위 예시처럼 비워 둡니다).

불러올 때 파일 전체를 거부하는 경우(`assets/editor-preset.mjs` `parsePreset`): 8 MiB 초과, JSON이 아님, `format`이 다름, `version`이 1이 아님(더 큰 수는 `더 새 에디터`),
알 수 없는 `gameId`, 열린 세션과 다른 게임, **모르는 키**(맨 위·`base`·레코드·`fields`·`{from,to}`·`skills`·스킬 항목 어디서나, `__proto__`·`constructor` 포함: 자기 속성만 읽습니다),
필수 키 누락, 1~65535가 아닌 레코드 번호, 한 표에 같은 레코드가 두 번, 표마다 4096개·스킬 목록 64개 초과, 바뀐 값이 없는 항목, 그리고 **저장 단계와 같은 범위 표**
(`assets/editor-fields.mjs`의 `EDITOR_FIELD_BOUNDS`: 편집 코어의 기록 함수가 같은 표로 검사합니다)를 벗어나거나 정수가 아니거나 `from`과 `to`가 같은 값, 0~255가 아니거나 번호가 겹치는 스킬 항목.

열린 세션에 맞춰 보며 **건너뛰는** 경우(`planPresetApplication`, 이유별로 셉니다): 세션에 없는 레코드, 여러 ID가 함께 쓰는 별칭 레코드, 읽기 전용 레코드(미사용·주인공 자리·머리부 없음 등),
**구조 능력 잠금**(`editor-locks.mjs`: 잠긴 능력 번호를 `from`이나 `to`에 담은 변경, 그리고 적용한 결과가 저장 단계의 잠금 검사 `findUnitAbilityLockViolation`에 걸리는 변경. 두 적용 방식을 모두 검사하며,
한 기체의 특수능력 칸 변경 중 하나라도 걸리면 그 기체의 특수능력 칸 변경을 모두 건너뜁니다), 저장 단계가 받지 않는 지형 값(바뀐 값은 0~4, 저장된 이상한 값은 그대로 둘 때만),
특수능력 목록을 바꿀 수 없는 파일럿, 이 게임이 만들지 않는 능력 번호, 1~99가 아닌 새 습득 레벨(저장된 쌍은 그대로 둘 수 있음), 자리 초과, 서로 다른 능력 4가지 초과,
조건부(레벨 100 이상) 항목을 빠뜨리거나 바꾸는 목록. 적용한 값은 BIN을 만들 때 저장 단계가 처음부터 다시 검사합니다.

## 편집할 수 있는 값

- **기체:** HP, EN, 장갑, 이동력, 운동성, 한계 반응, 특수능력 4슬롯과 보조 byte(단, 구조 능력 7가지는 잠겨 있습니다. 아래 ‘기체 구조 능력 잠금’), 지상·바다·공중·우주 적응도,
  **실드**(레코드 +9의 비트 4)와 **베어내기 가능**(비트 5)의 있음/없음. 행에는 `shield`·`parry`(참·거짓)로 실리고, 저장 요청도 참·거짓만 받습니다(0·1이나 글자는 `EDITOR_VALUE_OUT_OF_RANGE`).
  저장은 +9의 그 두 비트만 바꾸고 나머지 여섯 비트는 그대로 둡니다. 실드는 파일럿의 실드 방어(60~68)가, 베어내기 가능은 파일럿의 베어내기(69~77)와 공격 무기의 속성이 함께 있어야 쓰입니다(`docs/EDITOR_FACTS.md#unit-shield`, `#unit-parry`).
- **파일럿:** 격투·사격·명중·회피·기량·반응, 정신 포인트(SP), 초기 경험치, 성장 보정,
  지상·바다·공중·우주 적응도 (레코드 +17은 SP, +19는 기량, +21은 반응이다. 게임 상태창의 값과 대조해 확인했다.),
  **특수능력 목록의 추가·삭제·교체**(레코드의 원래 자리 안에서, 아래 ‘파일럿 특수능력 추가·삭제’),
  **정신커맨드 여섯 칸의 교체·습득 레벨·삭제·추가**(특수능력과 같은 자리를 나눠 씀, 아래 ‘정신커맨드 편집’)
- **무기:** 공격력, 명중·크리티컬 보정, 최소·최대 사거리, 지형 적응 수치, 소비 EN, 그리고 사용 조건 세 가지(`docs/EDITOR_FACTS.md#weapon-requirements`):
  **탄수**(+12, `ammo`): 이미 탄수가 있는 무기만 1~255로 바꿉니다. 0인 무기(EN을 쓰거나 제한 없음)는 화면에 ‘없음’으로만 보이고, 0↔다른 값은 거부합니다(`reason` `no-ammo-counter` / `ammo-counter-required`).
  **필요 기력**(+15, `requiredMorale`): 0~150(0 = 조건 없음). **필요 기능**(+16, `requiredSkill`): 없음, 뉴타입 L1~L9, 성전사 L1~L9, 단일 능력(F 78~81, 완결편 78~83) 중에서 고르며(`reason` `skill-not-allowed`), 저장 단계도 게임을 알 때만 이 목록으로 바꿉니다.
  원래 값이 이 범위 밖이면 그대로 둘 수만 있습니다. 행에는 이름(`requiredSkillName`, 이미지의 이름표에서 읽음)과 게임이 보는 조건(`requiredSkillRule`)도 실립니다.

파일럿 화면에는 파일럿별 정신커맨드와 습득 레벨도 표시합니다. 이 정보는 파일럿 기록의 (ID, 레벨) 쌍과
해당 승인 이미지의 이름표에서 읽으며, 읽는 규칙은 게임의 실행 코드와 같습니다. 일반 파일럿 목록은 +23에서 시작해
ID가 0인 첫 쌍에서 끝납니다(`00 01`도 `00 00`도 종료이며 레벨 byte는 보지 않습니다). 정신커맨드는 ID 1~30이
이름을 가지며 앞의 6쌍만 칸이 됩니다(게임의 스캔 범위는 1~31). ID 32 이상은 특수능력(F 32~81, 완결편 32~83)입니다.
레벨이 99를 넘는 항목은 습득 레벨이 아니라 이벤트 플래그(레벨−100)가 켜졌을 때 효과가 있는 항목입니다(완결편).
일곱 번째 이후의 정신커맨드 범위 쌍은 게임이 읽지 않으므로 특수능력이 아니라 행의 읽기 전용 `extraSpirits`로 따로 나눕니다(화면은 읽기 전용 안내로만 보여 줍니다).
`00 01 00 00`으로 끝나는 레코드는 원판 데이터에 정신기가 없다는 뜻이며(행의 `noSpiritInDisc`), 그 파일럿이 플레이 가능한지는 이 데이터만으로 알 수 없습니다. 화면은 이 경우 정신커맨드 칸에 ‘원판 데이터에 정신기 없음’만 보여 줍니다.
일반 파일럿은 +23부터의 쌍 블록을 쓰고, 필요한 확장은 검증된 공유 구간 안에서 재배치합니다. 주인공 습득표는 +0부터 시작하며 마지막 4바이트를 제외한 고정 범위만 씁니다(아래 두 절). 원작 파일럿 화면에 표시되는
정신 포인트는 파일럿 수치에 포함되며, 개별 정신커맨드의 소비 SP는 파일럿 기록에 들어 있지 않습니다.

### 파일럿 특수능력 추가·삭제 (2026-10-07)

선택 가능한 능력은 캐릭터의 원래 능력에 묶이지 않습니다. 같은 게임에서는 모든 일반 편집 가능 파일럿이 같은 능력 목록을 고릅니다.
F·완결편의 코우지는 정신기 6개 뒤에 능력 습득 항목 3개, 아무로는 18개를 저장합니다. 코우지의 베어내기 1·2단계는
서로 다른 두 항목이므로 그중 하나를 뉴타입으로 교체하면 베어내기·저력·뉴타입 세 계열이 됩니다. 원래 습득 과정은 바뀝니다.
두 파일럿 모두 동시에 적용되는 능력 종류 한도는 4가지입니다. 신규 능력은 기존 습득 항목과 정신커맨드 6칸을 유지한 채 추가합니다.

브라이트의 승인 레코드는 정신기 6개만으로 기존 자리가 꽉 차 있지만, 신규 추가는 같은 구간의 패딩을 모아 레코드를 늘립니다.
코우지도 기존 베어내기 1·2와 저력을 유지한 채 뉴타입을 추가할 수 있습니다. 기존 정신기나 능력을 비우는 선택지는 없습니다.
예약 공간은 구간 전체에서 공유하므로 다른 파일럿에 추가한 내용도 예산에 반영합니다. 예산 초과·검증 실패는 원자적으로 거부하고 기존 데이터를 보존합니다.

화면에서는 뉴타입·강화인간·성전사·실드 방어·베어내기를 계열별로 묶고, **능력 단계**와 **습득 Lv(파일럿 레벨)**를 별도 입력으로
보여 줍니다. 추가할 때도 계열을 한 번 고른 뒤 단계를 고릅니다. 처음부터 뉴타입 9단계를 주려면 `뉴타입 / 단계 9 / 습득 Lv 1`인
항목 하나면 됩니다. 점차 성장시키려면 각 단계의 습득 시점을 따로 추가합니다. 이 표시는 원본의 `(능력 ID, 습득 레벨)` 쌍을 묶어
보여 주는 것이며 자동 성장 공식을 새로 만들지 않습니다.

기존 항목의 단계는 그 자리에서 바꿀 수 있고, **교체**를 누르면 다른 계열과 습득 레벨로 바꿀 수 있습니다. 교체는 항목 수를 늘리지
않으므로 빈자리가 없는 목록에서도 됩니다. 같은 단계 중복과 능력 종류 4개 초과는 거부하며 이벤트 조건 항목은 교체·삭제·레벨 변경을
잠급니다. 상태 표시는 **습득 시점 수**와 게임에서 동시에 적용할 **능력 종류 수**를 구분합니다.

파일럿 기록은 길이가 25~79바이트로 제각각이고 길이 필드가 없는 채 서로 이어 붙어 있습니다(레코드 표에서 다음 레코드의 시작이 곧
끝입니다). 자기 레코드가 꽉 찬 경우에는 승인 레이아웃으로 고정한 연속 편집 가능 구간 안에서만 재배치합니다.
종료쌍 뒤의 검증된 0 패딩을 모으며, 목록 내용·불변 머리부·레코드 ID 연결을 보존하고 자기 위치 기준 포인터를 다시 씁니다.
별칭 공유 레코드·영웅 슬롯·미사용 레코드의 주소와 바이트는 고정합니다. 주인공 습득표 #308~311도 이동하지 않으며, 아래에 명시한 기존 목록 범위만 편집합니다. TSR 전체 길이와 다른 루트 시작점은 바꾸지 않습니다.
정신커맨드 6칸과 읽기 전용 추가 정신기 쌍을 예약하므로 특수능력 추가가 정신기 자리를 사용하지 않습니다.
이동한 개인 수정본은 승인 레이아웃으로 정규화한 뒤 기존 불변 해시와 구조 검증을 통과해야 다시 열립니다. 포인터 범위를 통째로 편집 가능하게 풀지 않습니다.
같은 목록을 보내면(손대지 않은 파일럿) 아무것도 쓰지 않습니다.

**행이 알려 주는 것**(화면은 이 값만 보고 만듭니다):

| 필드 | 뜻 |
|---|---|
| `skillEditable`, `skillEditReason` | 이 파일럿의 목록을 고칠 수 있는지. 고칠 수 없으면 이유 코드(아래 표), 고칠 수 있으면 `null` |
| `skillCapacity` | 지금의 정신커맨드 블록 뒤에 들어가는 최대 (ID, 레벨) 쌍 수. 종료 쌍 `00 00`이 레코드 안에 남아야 하므로 `⌊(남은 바이트 − 2) ÷ 2⌋`. 화면은 정신커맨드를 함께 고치므로 `pairCapacity`에서 편집 중인 정신커맨드 수를 빼서 셉니다 |
| `skillFree` | 정신커맨드 6칸 예약과 같은 구간 공유 예산을 반영한 신규 추가 여유. 정신커맨드를 지워 특수능력 공간으로 바꾸지 않습니다 |
| `specialAbilities` | 지금 목록(정신커맨드 제외), 항목은 `{id, level, name, eventFlag, familyId, rank, unresolved, ignoredByGame}` |
| `addableSkills` | 이 게임에서 쓸 수 있는 능력 `{id, name, familyId, rank, unresolved}` 중 이미 가진 것을 뺀 목록. 이름을 읽지 못한 번호도 번호로 고를 수 있고 `unresolved`가 켜집니다. 고칠 수 없는 행은 빈 목록입니다 |
| `skillConsumers`, `skillConsumerLimit` | 지금 목록이 쓰는 서로 다른 칸 소비자 수와 한도(4) |

고칠 수 없는 이유(`skillEditReason`): `alias-group`(번호 1: 여러 ID가 한 레코드를 공유), `hero-slot`(302·303: 게임이 시작할 때 다시 조립), `hero-head`(304~307: 여기서는 능력치만 복사하므로 실제 특수능력은 별도 습득표에서 편집), `nonstandard-tail`(확인된 주인공 습득표 이외의 머리 없는 목록), `unused-filler`(미사용 레코드), `no-capacity`(정신커맨드를 남겨야 하는 만큼 남기고 나면 능력 쌍이 하나도 들어가지 않음), 그리고 에디터가 쓸 수 있었을 모양이 아닌 목록: `unterminated-tail`(종료 쌍이 없거나 그 뒤에 0이 아닌 바이트),
`terminator-level`(종료 쌍의 레벨이 0이나 1이 아님), `skill-id`(게임이 읽지 않는 번호), `duplicate-skill`(같은 번호 두 번), `too-many-skills`(칸 소비자 5개 이상), `unknown-game`.

이 경계는 정확히 다음과 같고, 시험이 경계의 양쪽을 모두 고정합니다.
- 종료 쌍의 레벨은 0과 1(`00 00`, 표식 `00 01`)만 에디터가 쓸 수 있었던 모양입니다. 게임은 레벨과 무관하게 번호 0에서 목록을 끝내지만, 2 이상은 승인 표에 없고 에디터가 쓰지도 않으므로
  그 레코드는 잠기고 편집 범위가 없어서 불변 해시에 들어갑니다. 따라서 `00 02` 목록은 개인 수정본으로도 열리지 않습니다.
- 에디터가 쓰는 특수능력 번호는 F 33~81, 완결편 33~83입니다(게임의 목록 생성 코드는 32부터 읽지만 32는 이름 칸이 비어 있어 에디터가 쓰지 않습니다). 범위 바로 밖의 번호(F 82, 완결편 84, 그리고 32)가 하나만 있어도 그 행은 `skill-id`로 잠기고 편집 범위가 없습니다(완결편 전용 82·83을 함께 가진 기록 하나만으로는 이 경계를 확인할 수 없어서, 번호 하나짜리 기록으로도 확인합니다).
- 특수능력 뒤에 정신커맨드 번호(1~31, 게임이 읽는 경계는 31)가 오면 어느 목록으로도 보여 줄 수 없어서 표를 `EDITOR_TSR_STRUCTURE_UNSUPPORTED`로 거부합니다. 32는 정신커맨드 번호가 아니라 위와 같은 쓰지 않는 특수능력 번호여서 표를 거부하지 않고 잠긴 행(`skill-id`)이 될 뿐입니다.
- 쌍 목록은 레코드 풋프린트 밖을 읽지 않습니다. 풋프린트가 쌍 중간에서 끝나는 홀수 길이에서 마지막 바이트 하나(`00`이라도)는 종료 쌍이 아니고, 그 레코드는 `unterminated-tail`로 잠깁니다(다음 레코드의 첫 바이트를 종료 쌍의 레벨로 읽지 않습니다).
`no-capacity` 행은 수치를 그대로 고칠 수 있습니다(특수능력 목록에 쌍이 들어갈 자리가 없을 뿐입니다). `hero-head`도 실제 능력치는 편집하며 목록만 별도 원본으로 안내합니다. 나머지 이유(레코드 종류와 목록 모양)로 잠긴 행은 수치도 읽기 전용입니다.

**요청**: 기존 파일럿 편집 요청의 `specialAbilities`는 원하는 **최종 목록 전체**(순서 있는 `{id, level}` 배열)이고 길이는 달라도 됩니다(`skillCapacity` 이하).

**저장 단계의 검증**(어긴 요청은 이미지를 만들지 않고, 표는 원래 값 그대로 남습니다):

| 규칙 | 거부 코드와 `details.reason` |
|---|---|
| 번호는 F 33~81, 완결편 33~83(32·0·정신커맨드 범위·F의 82 이상은 거부) | `EDITOR_VALUE_OUT_OF_RANGE` `skill-id` (`skillId`, `minimum`, `maximum`) |
| 새로 넣거나 바꾼 습득 레벨은 1~99. 레벨 100 이상(이벤트 플래그)은 원래 있던 쌍을 그대로 두거나 지우는 것만 되고 새로 만들 수 없음 | `EDITOR_VALUE_OUT_OF_RANGE` `skill-level` |
| 번호와 레벨은 0~255의 정수 | `EDITOR_VALUE_OUT_OF_RANGE` `byte-value` |
| 같은 번호는 한 번만 | `EDITOR_EDIT_INVALID` `duplicate-skill` |
| 쌍 수는 `skillCapacity` 이하(256개를 넘는 목록은 읽지 않고 같은 이유로 거부) | `EDITOR_EDIT_INVALID` `capacity` (`capacity`, `requested`) |
| 서로 다른 칸 소비자는 4개 이하(계열은 하나, 단독 능력은 각각 하나) | `EDITOR_EDIT_INVALID` `too-many-skills` (`consumers`, `limit`) |
| 고칠 수 없는 행은 어떤 변경도 거부 | `EDITOR_EDIT_INVALID` `read-only` (`cause`는 위 이유 코드) |
| 목록이 배열이 아니거나, 비어 있는 칸(구멍)·접근자·원형(prototype)으로만 채워지는 칸이 있는 배열 | `EDITOR_EDIT_INVALID` `not-a-list` |

모든 거부의 `details`에는 `kind`(`pilot`), `field`(`specialAbilities`), `recordIndex`가 들어 있고, 워커는 정수와 이 `kind`·`field`·`reason`·`cause` 키의 짧은 토큰만 화면으로 보냅니다(자유 문장은 보내지 않습니다).

**요청을 읽는 방법**: 기체·파일럿·무기 편집 목록과 특수능력 목록은 모두 **빈틈없는 배열**(모든 칸이 그 배열 자신의 값)이어야 하고, 항목의 `recordIndex`·`fields`·값·`id`·`level`도 그 객체 자신의 값만 읽습니다. 구멍이 있는 배열은 `forEach`·`every`가 구멍을 건너뛰어 검증을 통과해도 `[구멍, {id: 78, level: 1}]`이 `03 01 | 00 00 | 4E 01`(종료 쌍 뒤에 쌍)로 쓰여 다시 열면 ‘끝 표시 없는 목록’으로 잠기는 레코드가 되었기 때문입니다. 검증은 요청의 사본을 읽고, 쓴 뒤에는 레코드를 다시 읽어(블록의 바이트와 해석한 특수능력 목록이 계획과 같은지) 어긋나면 `EDITOR_OUTPUT_INTERNAL`로 이미지를 만들지 않습니다.

**호출자가 정하는 문자열로 표를 찾는 방법**: 게임 번호, 레코드 종류, 이미지 해시, 필드 이름, 뱃지 이름처럼 호출자가 정하는 문자열로 표(일반 객체)를 찾을 때는 언제나 그 표 **자신의 항목**만 봅니다(`assets/editor-own.mjs`의 `ownEntry`).
`constructor`·`toString`·`__proto__` 같은 이름은 원형 사슬이 대신 답하므로, 예전에는 ‘게임 `constructor`’에 편집 범위가 계산되고 어떤 특수능력 번호든 쓰였으며(`range.min`이 없어서 비교가 모두 거짓), 모르는 뱃지는 ‘검증됨’을 약하게 만들지 않았습니다.
이제 모르는 이름은 모르는 게임·모르는 항목과 같은 거부를 받고(`editorDecodedMasks`는 `EDITOR_RELEASE_INVALID`, 쓰기는 잠금 `unknown-game`, 도움말은 `null`, 터레인 위치는 `RangeError`), 뱃지가 아닌 값은 ‘미확인’으로 가장 약하게 읽힙니다. 빌드할 때 상수 반복문이 정하는 조회는 호출자가 정하는 문자열이 아니므로 그대로입니다.
기체·파일럿·무기 수치의 범위 위반(`EDITOR_VALUE_OUT_OF_RANGE`)과 읽기 전용 변경(`EDITOR_EDIT_INVALID`)도 같은 모양의 `details`(`kind`, `recordIndex`, `field`, `minimum`, `maximum` 또는 `reason`·`cause`)를 갖습니다.

칸 소비자를 4개로 제한하는 것은 게임이 파일럿에게 능력 칸을 네 개만 만들고 다섯 번째 능력을 조용히 무시하기 때문입니다.
같은 계열(뉴타입·강화인간·성전사·실드 방어·베어내기의 각 9단계)은 가장 높게 얻은 단계 하나만 칸을 차지하고, 게임은 목록 순서대로 등록하므로 낮은 단계가 높은 단계 뒤에 오면 그 칸을 덮어쓰지 못하고 다음 빈 칸을 차지합니다.
그래서 에디터는 **계열마다 낮은 단계부터** 쓰며, 순서는 그 계열의 항목들이 이미 차지한 자리 안에서만 바꿉니다(다른 계열과 단독 능력의 순서는 요청한 그대로입니다). 근거는 [EDITOR_FACTS.md](EDITOR_FACTS.md)의 ‘pilot-skill-write’입니다.

### 정신기 6칸 보존과 신규 능력 공간 (2026-10-11)

일반 파일럿의 기존 정신기·특수능력을 그대로 유지한 채 새 능력을 추가합니다. 기존 설정을 제거하는 선택지는 없습니다.
같은 편집 가능 연속 구간에서 종료쌍 뒤의 검증된 0 패딩을 모으고, 실제 목록과 고정 머리부를 보존하여 자기 위치 기준 포인터를 다시 씁니다.
F·완결편 모두 TSR 전체 길이와 다른 루트 시작점, 잠긴 레코드의 주소·바이트를 고정합니다. 초기 승인 데이터에서 #2..301 구간의 여유는 F 132쌍 / 완결편 86쌍입니다.
추가할 때 정신기 6칸을 예약하며, 이미 예약된 정신기 공간은 다시 열어도 다른 파일럿에 기부하지 않습니다.
다른 파일럿의 추가·삭제·되돌리기와 편집값 불러오기도 같은 공유 예산으로 판단합니다. 과잉 사용·불변 헤더 변경·잠긴 포인터 이동은 거부합니다.
개인 수정본은 승인 레이아웃으로 정규화하여 기존 불변 해시와 구조 검증을 모두 통과해야 다시 열립니다. 승인 릴리스로 표시하지 않습니다.

검증은 F v0.5a·완결편 v0.3c의 브라이트·코우지에 뉴타입9@Lv1을 추가한 전체 BIN 저장·재열기, 다른 파일럿 의미값과 기체·무기 보존,
독립 전체 SHA와 무변경 입력 Blob 동일성 확인을 포함합니다. F의 manifest 고정 원본도 전체 BIN 저장·재열기를 통과했습니다. 완결편 원본의 해당 왕복은 아직 검증하지 않았습니다. 실제 게임 코드의 포인터 조회·목록 스캔·능력 등록은 Lv1/31/99로 실행했습니다.
별도 복제 상태의 에뮬레이터에서는 TSR 변경분만 주입하고 게임 자체가 descriptor를 다시 구성하여 능력창에 새 능력을 표시하는 것을 확인했습니다.
최종 제품 BIN은 두 게임 모두 저장 상태 없는 콜드 부팅으로 타이틀 도달을 확인했습니다. 완결편은 게임의 본체 RAM 메뉴에서 기존 33화 완료 세이브를 정상 로드해 인터미션에 도달했고, 재배치된 브라이트·코우지 주소를 게임이 직접 읽어 새 뉴타입 9를 등록하는 것을 추적했습니다. 이 검증은 전체 게임 진행이나 모든 파일럿의 검증을 뜻하지 않습니다.
공유 예산이 모두 사용된 상태에서 다른 파일럿의 능력 삭제와 신규 추가를 함께 담은 프리셋은 개별 용량 검사가 먼저 적용되어 보수적으로 거부될 수 있습니다.

- `hero-head`(304~307): 게임은 이 레코드의 머리 23바이트만 #303에 복사하고 목록은 #308·309에서 가져오므로, 여기에 쓴 정신커맨드는 #303의 것이 되지 않습니다. #302의 목록은 #310·311에서 가져오며 능력치 공급원은 미확인입니다. 이 머리 레코드의 목록을 다른 경로에서 읽는지도 미확인입니다.
- `no-spirit-block`(F에서 목록에 정신커맨드 쌍이 하나도 없는 레코드, 고칠 수 있는 행 중 152개): 이런 파일럿 가운데 게임에서 정신커맨드를 갖는 파일럿이 있는지, 있다면 F가 그 정신커맨드를 어디에서 읽는지는 **미확인**입니다. 그래서 이런 레코드에는 정신커맨드 블록을 새로 만들지 않습니다(특수능력 자리는 그대로 쓸 수 있습니다).
- `no-capacity`: 쌍이 하나도 들어가지 않는 레코드.

**남겨야 하는 칸**(`spiritMinimum`): F에서 정신커맨드가 있는 레코드는 하나 이상 남깁니다(모두 지우면 위의 ‘블록 없는 F 레코드’가 되는데, 그 경우를 게임이 어떻게 읽는지 미확인입니다). 주인공 습득표 #308~311은 항상 여섯 칸을 유지하며 교체·습득 레벨 변경만 합니다(`keeps-hero-spirit-slots`). 일곱 번째 정신커맨드 쌍이 있는 레코드(두 게임의 19번)도 여섯 칸을 모두 채워 둡니다. 칸을 지우면 게임이 읽지 않던 일곱 번째 쌍이 여섯 번째 칸이 되기 때문입니다(이 쌍은 그대로 둡니다).
**이벤트 조건**: 습득 레벨이 100 이상인 정신커맨드는 그 칸에 그대로 남습니다(바꾸기·지우기·옮기기 불가, 지우면 그 칸이 앞으로 옮겨지므로 앞의 칸도 지울 수 없습니다). 화면에는 ‘이벤트 조건’으로 잠겨 보입니다. 승인 이미지에는 이런 정신커맨드가 없고 규칙만 둡니다.
**원래 같은 정신커맨드가 두 번 있는 레코드**(완결편 230번)는 그 중복을 둔 채 다른 칸을 고칠 수 있지만 새 중복은 만들 수 없습니다.

**행 필드**(코어가 행마다 보냅니다):

| 필드 | 뜻 |
|---|---|
| `spirits` | 여섯 칸의 지금 목록 `{id, level, name, eventFlag, unresolved}`(자리표시 없음, 일곱 번째 이후 쌍은 `extraSpirits`) |
| `spiritEditable`, `spiritEditReason` | 칸을 고칠 수 있는지, 없으면 이유 코드 |
| `spiritSlots` | 6 |

`skillEditable`은 일반 편집 가능 레코드와 공유 확장 가능 구간에서 정합니다. 정신커맨드 6개만 있는 브라이트도 신규 능력을 직접 추가할 수 있습니다.

**요청**: 파일럿 편집 요청에 `spirits`(여섯 칸의 최종 목록 전체, 순서 있는 `{id, level}` 배열)를 실을 수 있습니다. 없으면 정신커맨드는 그대로입니다. 일반 파일럿은 +23부터 레코드 끝까지, 주인공 습득표는 +0부터 마지막 4바이트 앞까지 쓰며 순서는
여섯 칸, 일곱 번째 이후 쌍(그대로), 특수능력, 종료 쌍 `00 00`, 나머지 0입니다. 필요한 확장은 고정된 편집 가능 구간 안에서만 재배치하고 기존 레코드의 의미값과 불변 머리부를 보존합니다. 같은 목록을 보내면 아무것도 쓰지 않습니다.
화면은 모든 파일럿의 `spirits`를 보내고(고치지 않은 행은 원래 목록), ‘수정 n건’은 칸마다 바뀐 정신커맨드(교체·추가·삭제 각 1)와 바뀐 레벨을 셉니다(`row.spirits`와 열었을 때의 `row.original.spirits` 비교).

**저장 단계의 검증**(`details.field`는 `spirits`, 어긴 요청은 이미지를 만들지 않고 표는 그대로):

| 규칙 | 거부 코드와 `details.reason` |
|---|---|
| 칸은 6개까지(256개를 넘는 목록은 읽지 않고 같은 이유) | `EDITOR_EDIT_INVALID` `spirit-slots` (`limit`, `requested`) |
| 번호는 1~30(원래 있던 쌍은 그대로 둘 수 있음) | `EDITOR_VALUE_OUT_OF_RANGE` `spirit-id` (`spiritId`, `minimum`, `maximum`) |
| 새로 넣거나 바꾼 습득 레벨은 1~99 | `EDITOR_VALUE_OUT_OF_RANGE` `spirit-level` |
| 번호와 레벨은 0~255의 정수 | `EDITOR_VALUE_OUT_OF_RANGE` `byte-value` |
| 같은 번호는 한 번(원래 두 번 있던 번호는 두 번까지) | `EDITOR_EDIT_INVALID` `duplicate-spirit` |

쓴 뒤에는 블록의 바이트와 다시 읽은 여섯 칸·일곱 번째 이후 쌍·특수능력이 계획과 같은지 확인하고 어긋나면 `EDITOR_OUTPUT_INTERNAL`(`read-back`)로 이미지를 만들지 않습니다.
수정한 레코드가 머리 없는 목록 템플릿처럼 읽히게 되면(머리 바이트와 목록 바이트가 짝수 위치에서 우연히 그 모양으로 줄을 서는 경우, 수치나 레벨을 바꿔 생길 수 있음) `EDITOR_EDIT_INVALID`(`reads-as-template`)로 거부합니다. 그런 이미지는 다시 열면 그 레코드를 템플릿으로 보고 편집 범위가 달라져 열리지 않기 때문입니다.

**레코드를 늘리지 않는 이유**(조사, 2026-10-07. 저장소에 넣지 않은 측정 스크립트로 공개 레인 여섯 개를 재었습니다):

- 출처 검사: 개인 수정본의 범위 프로필은 풀린 TSR의 길이를 고정하고, 압축 이어쓰기와 레코드 읽기도 같은 길이와 세그먼트 안의 레코드를 전제로 합니다.

### 기체 구조 능력 잠금 (2026-10-07)

기체가 그대로 가지고 있어야 하는 구조 능력은 **추가·삭제·변경할 수 없습니다.** 잠긴 번호는 `assets/editor-locks.mjs`의 상수 하나
(`LOCKED_UNIT_ABILITY_IDS`)입니다: **11 폭주, 12 슈퍼 모드, 13 버서커 모드, 15 합체, 16 분리, 17 변형, 18 S2기관**(두 게임의 번호가 같고 이름 표만 다릅니다).
요청은 변형·합체·폭주·버서커이고, 같은 성격의 슈퍼 모드·분리·S2기관을 함께 잠갔습니다. 목록을 바꾸려면 이 상수 하나만 고치면 됩니다.
이유 문장(`reason`)은 ‘게임 구조와 묶인 능력이라 안전을 위해 편집을 막았습니다’입니다. **이것은 에디터의 안전 정책이며 게임 내부 동작에 대한 주장이 아닙니다**
(이 번호들을 읽어 동작을 바꾸는 코드는 찾지 못했습니다. 근거는 [EDITOR_FACTS.md](EDITOR_FACTS.md)의 ‘unit-ability-lock’).

**저장 단계가 거부하는 것**(`updateUnitRecords`): 잠긴 능력이 든 칸은 그 칸에 고정됩니다. 판단은 저장된 쌍(번호, 보조값)과 요청한 쌍의 비교이며, 요청 한 건에서 칸 번호 순으로 처음 걸리는 이유 하나를 알립니다.

| 이유 (`cause`) | 뜻 |
|---|---|
| `changed` | 잠긴 칸의 번호나 보조값(조건 플래그 번호)이 바뀜. 삭제(번호 0), 다른 번호로 교체, 다른 칸으로 옮기기(원래 칸이 바뀌므로)가 모두 여기에 든다 |
| `added` | 잠긴 번호가 없던 칸에 잠긴 번호가 생김. 다른 기체에 붙이기, 같은 기체에 두 번째로 붙이기 |
| `hidden` | 잠긴 능력 앞의 칸을 비워(번호 0과 보조값 0) 목록이 거기서 끝나게 함. 게임이 능력 목록을 만들 때 둘째~넷째 칸이 비면 그 뒤를 읽지 않으므로, 칸을 그대로 둬도 읽히지 않게 되는 편집을 막는다. 첫 칸이 비는 것은 목록을 끝내지 않으므로 막지 않는다 |

거부는 `EDITOR_EDIT_INVALID`이고 `details`는 `{ kind: "unit", recordIndex, field, reason: "locked-ability", cause, slot, abilityId }`입니다(`field`는 거부된 칸의 필드 이름 `ability2`·`abilityValue3` 등,
`slot`은 0부터 세는 칸 번호로 `abilityLocks.slots`와 같은 기준이고 `abilityId`는 잠긴 능력 번호). 워커는 이 값을 그대로 보냅니다(토큰 셋과 정수). 거부된 요청은 표를 하나도 바꾸지 않습니다(이 요청의 앞쪽 기체도 되돌립니다).
잠기지 않은 능력(방어 1~4·14, 회피 5~8, HP회복 9·10, 그 밖의 번호)과 잠긴 능력이 든 기체의 다른 칸·다른 수치는 그대로 고칠 수 있습니다.

**행이 알려 주는 것**(화면은 이 값만 보고 잠금을 표시합니다):

| 필드 | 뜻 |
|---|---|
| `abilityLocks.slots`, `abilityLocks.ids` | 지금 잠긴 능력이 든 칸(0~3)과 그 번호. 잠긴 능력이 없으면 둘 다 빈 배열 |
| `abilityLocks.reason` | 위 이유 문장 (모든 행에 있음) |
| `abilityLocks.tampered`, `abilityLocks.issues` | 저장된 쌍이 잠금이 만들 수 있었던 모양이 아닐 때 `true`와 이유 목록: `hidden`(잠긴 능력이 비어 있는 칸 뒤에 있어 목록이 거기까지 읽히지 않음), `duplicate`(같은 잠긴 번호가 두 번), `differs-from-original`(원본 데이터의 배치와 다름) |
| `view.lockedUnitAbilityIds` | 잠긴 번호 전체. 화면은 다른 칸의 선택 목록에서 이 번호들을 뺍니다 |

화면 규칙: 잠긴 능력이 든 칸은 읽기 전용(자물쇠 표시와 이유 문장)이고, 다른 칸의 선택 목록에는 잠긴 번호가 없습니다. 코어가 이 필드를 주지 않으면(예전 코어) 화면은 아무것도 잠그지 않습니다.

**이전 에디터로 저장한 개인 수정본**: 잠금이 없던 에디터가 잠긴 능력을 바꿨더라도 그 이미지는 **열립니다**(출처 검사는 그대로이고, 기체 능력 바이트는 원래 수정 가능 범위입니다).
다만 그 기체의 `abilityLocks.tampered`가 켜지고, 열린 상태가 기준입니다: 잠긴 능력은 지금 든 칸에 그대로 고정되고 새 편집이 그 칸을 건드리면 거부합니다(고치려고 되돌리는 편집도 거부합니다).
이미 가려져 있던 능력은 더 나빠지지 않는 편집만 받고, 앞 칸을 채워 다시 읽히게 하는 편집은 허용합니다. `differs-from-original`은 원본 게임에서 센 배치(`assets/editor-lock-layout.mjs`, 두 게임의 기체 번호와 칸·번호·보조값만의 표)와 비교해서
알아내며, 이 표는 지금까지의 모든 공개 버전과 원본 디스크 두 장에서 같다는 것을 골든 시험이 모든 실제 표와 비교해 확인합니다. 공개 버전이 이 배치를 일부러 바꾸면 표를 같이 고쳐야 합니다.
표는 이름 붙이는 용도(`tampered`)로만 쓰고 편집 허용 여부는 정하지 않습니다. 표가 없는 환경에서는 `hidden`·`duplicate`만 알 수 있습니다.

### 레코드 표시 규칙 (2026-10-07)

이름표는 기체(root11)·파일럿(root12, 약칭 root13)·무기(root14) 모두 **레코드 번호**로 찾습니다. 레코드 +0/+1의
9-bit 값은 기체에서는 맵 아이콘 번호, 파일럿에서는 얼굴 번호이며 이름 키가 아닙니다. 그림 정체성이나 도감 그림으로
이름을 덮어쓰지 않습니다. 무기 이름표는 완결편에서 레코드(1408개)보다 64칸 짧으므로 1344번부터는 이름칸이 없음으로
표시하고 문자열 바이트를 포인터로 읽지 않습니다.

각 행에는 종류(`recordKind`)와 편집 가능 여부(`editable`)가 있습니다.

| 종류 | 뜻 | 편집 |
|---|---|---|
| regular | 일반 레코드 | 가능 |
| unused-filler | 이름이 어디에도 없는 미완성 템플릿(미사용 레코드) | 읽기 전용, 목록에서 기본 숨김(`미사용 레코드 표시 (n)`을 켜면 보임) |
| named-template-stub | 이름은 있으나 수치가 템플릿 기본값인 레코드 | 가능 |
| hero-list-template | 번호 308~311: 머리부 없는 실제 주인공 정신기·특수능력 습득표 | 목록만 편집, 정신기 6칸과 기존 복사 길이 보존 |
| nonstandard-tail | 위 네 습득표 이외의 머리부 없는 목록 | 읽기 전용 |
| alias-group | 한 레코드를 여러 ID가 공유(파일럿 0·1·312~319) — 한 번의 수정이 ID 10개를 바꾼다 | 읽기 전용 |
| hero-slot | 파일럿 302·303: 실행 중 다시 조립하는 자리(확인한 원본 연결은 아래 표) | 읽기 전용 |

미사용 레코드는 완결편 기체 18·파일럿 1·무기 102, F 기체 20·파일럿 28·무기 57입니다. 행 모델에는 남겨 쓰기 경로가 모든
인증된 레코드를 그대로 다시 쓰게 합니다. 화면은 이 행들을 **목록에서 기본으로 숨기고**, 탭 줄 오른쪽의 `미사용 레코드 표시 (n)`을 켠 탭에서만 보여 줍니다
(탭마다 따로, 새로 열 때마다 꺼진 상태). 보이는 미사용 행은 이름 대신 `미사용 레코드`로 표시하고, 이름이 비었지만 능력치가 있는 일반 행은 `이름 없음`이라고 하며 어디에도 ‘이름 미지정’이라는 문구를 쓰지 않습니다.

읽기 전용 행은 화면에서 모든 입력칸·선택칸을 비활성으로 두고, 탭 아래에 `읽기 전용` 표지와 이유 한 줄을 보입니다(눌러 펼치면 설명). 이유는 행의 종류와 `readOnlyReason`을 따릅니다.
쓰기 단계도 원본과 다른 값을 거부합니다(구현됨). 화면의 안내 문구:

- 미사용 레코드: 이름도 쓰임도 없는 빈 레코드.
- 주인공 습득표 #308~311: 능력치와 얼굴 그림이 없으므로 해당 패널을 숨기고 실제 정신기·특수능력만 편집합니다. 이름표의 다른 파일럿 이름을 주인공 이름으로 표시하지 않습니다. 이외의 비표준 목록은 읽기 전용입니다.
- 여러 ID가 공유하는 레코드: 파일럿 0·1·312~319는 한 레코드를 씁니다. 번호 1의 안내가 ‘ID 0–1, 312–319(10개)가 이 레코드 하나를 함께 쓰므로 수정할 수 없습니다’와 같은 ID·이름 목록을 알려 줍니다. 번호 312~319는 목록에 이름과 `공유` 표시로 따로 나오고, 고르면 공유 레코드의 능력치를 읽기 전용으로 보여 줍니다(저장 요청에는 들어가지 않습니다).
- 주인공 자리 레코드(302·303): 게임이 실행 중에 다른 레코드에서 다시 만들어 쓰는 자리입니다. 초기값 100과 자리표시 얼굴 대신 실제 원본을 고르는 버튼을 보여 줍니다. #303의 능력치 원본은 #304~307, 정신기·특수능력 원본은 #308·309이고, #302의 목록 원본은 #310·311입니다. #302의 능력치 연결은 미확인이라고 표시합니다. 이동은 검색·필터를 풀고 해당 입력에 포커스하며 편집 중인 값은 유지합니다. 원본 화면의 `자리로` 버튼으로 돌아옵니다.
- 이름은 있으나 능력치가 기본값인 레코드(named-template-stub): 읽기 전용이 아니며 `미완성 기본값 레코드` 안내만 붙습니다.
- 여섯 칸을 넘는 정신기 범위 쌍(`extraSpirits`, 번호 19의 일곱 번째 쌍): `게임이 읽지 않는 정신기 쌍` 안내로 이름과 레벨만 보여 줍니다(특수능력 칸에는 넣지 않습니다).
- 정신기 목록이 비어 있는 파일럿(`noSpiritInDisc`): 정신커맨드 칸에 ‘원판 데이터에 정신기 없음’만 씁니다. 플레이 가능 여부는 이 데이터만으로 알 수 없으므로 말하지 않고 `Lv`도 붙이지 않습니다.

- 능력 목록의 모양 때문에 코어가 잠근 파일럿(`terminator-level`·`skill-id`·`duplicate-skill`·`too-many-skills`·`unterminated-tail`): 읽기 전용 안내가 특수능력 창과 같은 이유 문장으로 말합니다
  (예: ‘같은 능력이 두 번 들어 있어서’). 화면이 모르는 이유 코드는 일반 문구(‘안전하게 고칠 수 없어 읽기 전용으로만 보여 줍니다’)로 보입니다.

번호 304~307은 실제 능력치 원본으로 편집할 수 있습니다. 빈 초상화 패널과 별도 원본에서 가져오는 정신기·특수능력 패널은 숨기며, `정신·특수` 버튼으로 대응하는 #308·309 습득표를 엽니다.

### 화면과 코어의 계약 (2026-10-07)

특수능력 창은 처음에 이 문서의 계약(행 필드, 요청 모양, 거부 코드)에 맞춰 만든 가짜 행으로 시험했고, 코어는 따로 만들었습니다. 두 쪽을 합친 뒤

### 워커 작업의 수명 (2026-10-07)

워커는 한 번에 확인(`INSPECT`)이나 저장(`EXPORT`) 작업 하나만 돌립니다. 작업은 **살아 있는 동안**(지금 작업이고 중단되지 않은 동안)에만
진행 상황을 알리거나, 열린 세션을 바꾸거나, 결과를 보낼 수 있습니다. 코어 함수는 읽기 사이사이에 중단 신호를 보지만
**마지막 읽기**가 중단 신호보다 늦게 끝날 수 있으므로, 워커가 결과를 보내기 직전에 한 번 더 확인합니다.

- `CANCEL`은 지금 작업의 신호를 중단시키고, 작업이 끝까지 정리되어 `CANCELLED`를 보낼 때까지 지금 작업으로 남깁니다. 마지막 읽기 중에 와도 `INSPECT_COMPLETE`나 `EXPORT_COMPLETE`는 나가지 않고, 열려 있던 이미지의 세션은 그대로입니다.
- `RESET`은 작업을 중단시키고, 지금 작업에서 빼고, 세션을 버리는 일을 한 번에 합니다. 곧바로 다음 `INSPECT`가 와도 `EDITOR_BUSY`가 아니고, 옛 작업은 자기 작업 번호로 `CANCELLED`만 보냅니다(옛 작업이 늦게 세션을 돌려줘도 새 세션을 덮지 못하고, 같은 번호로 새 작업을 열었어도 그 자리를 비우지 못합니다). `RESET` 뒤의 `EXPORT`는 `EDITOR_SESSION_MISSING`입니다.
- 미리보기(`PREVIEW`)는 요청할 때의 세션에 속합니다. 그림을 읽는 동안 세션이 초기화되거나 다른 이미지로 바뀌면 그림 대신 `PREVIEW_ERROR`가 갑니다.
- 결과 메시지를 보낼 수 없으면(복제 오류 등) 그 작업의 오류로 보고하고 열려 있던 세션은 건드리지 않습니다.

### 파일럿 레코드 길이 한도 (2026-10-07)

파일럿 레코드는 머리 23바이트 뒤에 (번호, 레벨) 쌍 목록이 붙은 모양이고, 모든 승인 표에서 25~79바이트입니다. 게임이 쓸 수 있는 가장 긴 목록도
정신커맨드 쌍 7개(칸 6개와 한 레코드의 죽은 일곱 번째 쌍) + 게임이 만드는 특수능력 번호 51개(완결편) + 종료 쌍 = 23 + 2×59 = 141바이트입니다.
그래서 에디터는 레코드 하나가 `MAX_PILOT_RECORD_BYTES`(256바이트, 가장 긴 실제 레코드의 세 배 남짓)를 넘는 표를 **레코드 목록을 만드는 자리에서** 거부합니다
(`EDITOR_TSR_STRUCTURE_UNSUPPORTED`). 읽기·쓰기·별칭·그림 번호·편집 범위 계산이 모두 이 한 곳을 거치고, 쌍을 따라가는 함수(`walkPilotPairs`)도
넘는 범위를 스스로 거부합니다.

한도가 없던 때(읽기 방식을 바꾸면서 예전의 쌍 개수 한도가 사라졌습니다)는 푼 TSR이 최대 8 MiB라는 점만 막아서, 풋프린트가 수 MiB인 레코드 하나를 쌍마다 객체 하나씩 만들며
따라가느라 출처 판정보다 먼저 이 컴퓨터에서 7 MiB 기준 약 1.7초와 힙 약 470 MB를 썼습니다(검토에서 2.9~7.1초, 550~590 MB). 지금은 몇 ms 안에 힙을 거의 쓰지 않고 거부합니다.
기체와 무기에는 이런 한도를 두지 않습니다. 기체는 고정 머리와 항목 16개 이하의 무기 목록만, 무기는 고정 17바이트만 읽으므로 비용이 풋프린트와 무관합니다(시험이 7 MiB 레코드로 확인합니다).
이름 해독은 이미 161바이트에서 끊고, 레코드 표의 칸 수도 4096으로 제한됩니다.

### 읽기 단계 보호 장치 시험 (2026-10-07)

디스크·TSR·레코드 표를 읽는 쪽의 거부 규칙(`if (조건) fail(...)` 120곳, 코어 117곳과 워커 3곳)을 하나씩 꺼 보는 변이 시험(거부 규칙 끄기)을 돌렸습니다.
처음(이 변경 전의 나무, 122곳)에는 51곳만 시험이 잡았고, 나머지는 규칙을 꺼도 시험이 그대로 통과했습니다. 꺼진 상태에서는 깨진 입력이 다른 오류 코드로 거부되거나 그대로 열렸을 것입니다(예: 크기의 두 바이트 순서 복사본이 서로 다른 TSR이 개인 수정본으로 열림).
지금은 **101곳이 죽고 19곳이 살아남으며, 그 19곳은 모두 어떤 입력으로도 거부 조건이 참이 될 수 없는 방어 검사**라 시험으로 죽일 방법이 없는 동치 변이입니다. 코어의 해당 줄 위에 이유를 적어 두었고 종류는 이렇습니다:
- 앞에서 값의 범위가 이미 정해져 있음: 16비트·32비트 쓰기(호출하는 쪽이 검증한 값이나 4비트 네 개로 만든 값, 디렉터리 길이는 16 MiB 이하), 디렉터리·파일 읽기 길이(디렉터리는 읽기 전에 1~32 MiB로 제한, 파일은 1바이트~16 MiB),
  레코드의 시작 위치(설명자 안의 156이거나 반복문이 방금 길이와 비교한 위치), 섹터 번호 곱(위치는 32비트 이하이므로 약 1e13), 압축 참조의 거리(1~8192)와 길이(2~256), 푼 데이터에 쓰는 위치(8 MiB 미만일 때만 다음 토큰을 읽음).
- 구조상 항상 성립함: 루트 표 블록의 끝(시작들이 서로 다르고 정렬되어 있으므로 끝은 다음 시작이거나 데이터 끝), 레코드가 하나도 없는 표(칸 수 2 이상을 앞에서 확인하므로 칸 1이 레코드를 줌), 요청 항목 수(레코드마다 하나씩이라고 앞에서 확인),
  MODE1 섹터의 검사 범위(고정된 두 구간), 섹터 검사값(방금 계산한 값을 같은 코드로 확인), 레코드가 섹터를 넘지 않음(읽기에서 이미 거부), 저장 섹터는 서로 다른 위치이고 모두 2352바이트, 출력 이미지는 조각이 이미지를 빈틈없이 덮음.

죽인 검사마다 깨진 입력 하나로 시험하고 **오류 코드**(겹치는 두 검사가 같은 코드를 낼 때는 **메시지**도)를 확인합니다:
- `tests/editor-iso-guards.test.mjs`(17개): 섹터의 동기 바이트 열두 곳과 모드 바이트, 이미지 안에 있는 섹터(경계 한 바이트), 볼륨 설명자의 종류·식별자·버전, 논리 블록 크기와 두 바이트 순서 복사본의 불일치(같은 필드가 두 번 적히는 크기·위치도),
  루트 레코드, 짧은 레코드·디렉터리 끝을 넘는 레코드·파일 이름 길이, 확장 속성 길이로 늘어나는 위치와 32비트를 넘는 위치, 끼워 읽는 레코드, 섹터 경계를 넘는 레코드와 다음 섹터로 이어지는 디렉터리,
  깊이 16단계(17단계 거부), 크기 0·한도 초과 디렉터리, 레코드 100,000개(100,001개 거부), TSR·FACE·C_ROBOT의 없음·중복·다중 extent·크기 한도·이미지 밖 위치.
- `tests/editor-parser-guards.test.mjs`(22개): 압축 풀기의 잘린 토큰 다섯 가지와 끝 표지만 있는 입력, 8 MiB 한도(바로 아래는 읽히고 정확히 8 MiB는 거부), 저장 형태(푼 데이터 8 MiB 초과), 루트 표의 크기·칸 수·필수 칸 포인터(필수가 아닌 칸은 비어 있는 채로 읽음),
  레코드 표의 크기·포인터·너무 짧은 레코드와 세 읽기 함수의 같은 규칙, 기체 능력 바이트 읽기·쓰기, 열기 서술자(크기, 64자리 소문자 해시, 게임, 토큰), 개인 이미지의 토성 머리글과 제품 번호, 해시 중 잘못된 스트림 조각,
  루트 칸 수가 29 이하인 TSR(열기와 저장 모두), 저장할 세션의 기록 분류, 그림 요청의 세션과 레코드 번호, 요청이 레코드마다 하나씩이어야 한다는 규칙(모르는 번호·반복·부족·초과를 세 저장 함수 모두에서).

깨진 입력을 따라가다 죽은 코드 몇 가지도 정리했습니다. 상대 포인터 표 읽기(`parseRelativeOffsets`)에는 오름차순 확인과 ‘첫 블록과 가장 작은 목표가 같아야 한다’는 확인이 있었지만, 표의 첫 칸은 곧 첫 블록의 위치이고 다른 호출은 모두 별칭을 허용했으므로
두 확인이 참이 될 수 없어서 지웠습니다(동작은 같습니다).

### 기체와 무기의 연결 (읽기 전용)

기체 레코드는 고정 48바이트가 아니라 `50 + 4n`바이트이고, 뒤쪽에 그 기체가 가진 무기 목록(+46 개수, +48부터 4바이트 항목,
`00 00` 종료)이 들어 있습니다. 항목은 무기 번호(11비트), 칸 번호, 탄약 칸, 플래그·추가 투자 표시를 가지며, 무기 번호는
무기 행의 레코드 번호와 같습니다. 에디터는 이 목록을 **고치지 않고 읽기만** 합니다(화면 표시와 무기 검색의 기체 이름 연결은 위 ‘목록과 화면 배치’). 기체 행에는 `weaponList`(저장된 순서의
항목, 칸 번호, 상태 `known`/`inconsistent`/`unknown`), 무기 행에는 `owners`(사용 기체와 칸 번호), `ownerNames`(검색용 기체 이름),
`ownership`(`owned`/`unowned`/`unverified`)이 붙습니다. 개수·종료 표시·길이·무기 번호 범위가 하나라도 맞지 않는 목록은
`unknown`으로 두고 무기를 추측하지 않으며(개수 바이트만 어긋나는 F 기체 한 개는 종료 표시까지의 항목을 `inconsistent`로 보여 주되 `known`으로 올리지 않고 사용 기체로도 세지 않습니다), 게임 화면의 표시 순서와 플래그 번호의 뜻은 확인되지 않았다고 밝힙니다.
레이아웃의 근거와 예외는 [EDITOR_FACTS.md](EDITOR_FACTS.md)의 ‘unit weapon lists’에 있습니다. 목록 바이트는 내보내기에서도
그대로 보존되며 출처 검사도 이전과 같이 이 부분을 불변 해시로 다룹니다.

표시되는 숫자는 게임 데이터의 원시값입니다. 성장 보정과 능력치는 숫자로 편집하고, 지형 적응은 글자로 고릅니다.

지형 적응 등급의 저장값도 정수 그대로입니다. 기체·파일럿은 한 칸이 4비트로 4=A 3=B 2=C 1=D 0=E(화면에 따라 `-`)이고,
무기는 한 칸이 2비트로 3=A 2=B 1=C 0=`-`입니다. 게임 화면은 네 지형을 공·육·해·우 순서로 보여 주지만 데이터 순서는
지상·바다·공중·우주입니다. 대응표와 근거, 파일럿 C·D와 무기 C가 화면으로 확인되지 않았다는 점은
[EDITOR_FACTS.md](EDITOR_FACTS.md)에 있고, 변환 함수는 `assets/editor-grades.mjs`입니다. 바꾸는 기체·파일럿 등급은
0~4여야 합니다(5 이상은 게임이 0%로 계산하고 화면 표시도 확인되지 않았습니다). 이미 5 이상으로 저장된 값을 그대로 두는 것은 허용합니다. 이 제한은 저장 단계(`EDITOR_VALUE_OUT_OF_RANGE`)가
지키고, 화면의 선택 상자는 0~4만 내놓습니다. 전투 능력치가 모두 0인 파일럿은 게임 화면이 지형 칸을 `-`로 보여 준 사례가 있어 글자 표시를 확인하지 못했다([EDITOR_FACTS.md](EDITOR_FACTS.md)).

기체와 파일럿 그림은 사용자가 고른 디스크의 `C_ROBOT.BIN`·`FACE.BIN`에서 레코드가 직접 가리키는 그림
번호(기체의 저장된 graphic 번호, 파일럿의 packed 얼굴 번호)로 읽어 표시합니다. 이름 대조로 그림을 고르거나
행 번호로 보정하지 않습니다. F에서 얼굴이 0인 특정 템플릿 9개는 완결편의 동일 레코드와 F 자체 FACE 파일을
대조해 확인한 참고 초상화를 별도로 표시합니다. 직접 얼굴 번호는 그대로 0이며 화면에도 ‘참고 초상화’로
구분합니다. 주인공 공용 데이터와 머리부 없는 습득표도 고정 얼굴 미지정으로 안내합니다. 나머지 미지정과
읽기 오류는 각각 구분합니다. 기체·파일럿 요청은 독립적으로 관리하고 오래된 선택 응답은 무시합니다.
연결 범위의 수치와 근거·한계는 [이미지 대응 문서](EDITOR_IMAGE_MAPPING.md)에 기록했습니다.
이 이미지를 웹사이트에 따로 싣거나 전송하지 않습니다.

## 제한 사항

에디터는 실행 중인 게임의 메모리에 접근하지 않습니다. 검증한 정품 원본 또는 최신 승인 패치 BIN 안의 `TSR.BIN`을
정적으로 수정해 개인용 BIN/CUE를 만듭니다. 수정값을 게임에서 사용하려면 새 이미지를
에뮬레이터에 다시 열어야 합니다.

새 `TSR.BIN`이 이미지가 정해 둔 자리(아래 ‘저장 공간’)보다 커지면 에디터는 저장을 중단합니다.
디스크 안에서 파일을 옮기거나 이미지 용량을 늘리지 않습니다. 섹터 형식·체크섬·게임
데이터 표 구조를 확인할 수 없는 경우도 저장하지 않습니다.

개인 수정 BIN/CUE는 공개 승인 릴리스나 배포 패치가 아닙니다. 사이트는 ROM, 완성 이미지,
사용자 수정본을 받거나 보관하지 않습니다.

### 원본 선택 후 편집 흐름

정품 원본을 열면 먼저 원본 자체를 검증하고 편집 데이터를 읽습니다. 한글화를 선택하고 편집 또는
저장으로 이동할 때만 기존 원본 확인·희소 패치 검증 코드를 전용 작업 스레드에서 실행합니다. 원본과
결과 전체 해시를 확인한 뒤 중간 결과를 저장하지 않고 에디터 입력으로 전달합니다. 원본 언어를
유지하면 이 패치 단계가 없습니다. 완결편 원본의 CUE는 원본 트랙 위치를 사용하며, 오디오 트랙이
이동한 한글 패치 결과의 CUE 위치와 섞지 않습니다.

수정 TSR이 커진 경우 이미 할당된 마지막 ISO 섹터의 0으로 채워진 padding까지만 사용할 수 있다. 다음 섹터로 확장하지 않으며, padding 검증·압축 roundtrip·EDC/ECC 검증·최종 전체 해시 후에만 결과를 제공한다. 개인 수정본 해시는 공개 릴리스의 해시와 별도로 표시한다.

### 저장 공간 (TSR.BIN 슬롯, 2026-10-07)

게임 데이터 `TSR.BIN`은 디스크 안에서 정해진 자리(슬롯)에 압축된 채 들어 있고, 에디터는 이 자리를 넓히지
못합니다. 슬롯의 크기는 ISO 디렉터리의 파일 길이이고, 그 뒤에 같은 섹터의 0 padding이 있으면 거기까지만
늘릴 수 있습니다. 측정한 공개 이미지의 값은 다음과 같습니다.

| 이미지 | 슬롯(디렉터리 길이) | 마지막 섹터 padding | 원래 압축 데이터 | 슬롯 안 여유 |
|---|---|---|---|---|
| F v0.5 | 202,438바이트 | 314바이트(0) | 199,299바이트 | 3,139 (+314) |
| 완결편 v0.3 c | 215,040바이트(105섹터) | 없음 | 208,718바이트 | 6,322 |
| 완결편 v0.3 a | 215,040바이트(105섹터) | 없음 | 209,406바이트 | 5,634 |

**완결편은 슬롯이 섹터 경계에서 끝나므로 padding이 전혀 없습니다.** 슬롯 안의 남는 바이트는 압축 데이터 뒤의
0뿐입니다. 수정하지 않은 데이터를 에디터의 일반 압축기로 처음부터 다시 압축하면 완결편은 슬롯보다 커서
(c 215,746, a 216,338바이트) 값 하나만 바꿔도 저장할 수 없었습니다. 그래서 저장은 처음부터 다시 압축하지 않고
**이미지에 들어 있는 압축 스트림을 그대로 이어 씁니다.**

- 스트림의 토큰(글자 하나, 앞선 데이터 복사, 끝 표시)을 순서대로 읽어, 수정한 데이터에서도 같은 결과를 내는
  토큰은 원래 비트 그대로 다시 씁니다. 글자 토큰은 새 바이트 값만 바꿉니다.
- 수정한 바이트를 복사 대상이나 복사 원본으로 삼고 있어서 더는 맞지 않는 복사 토큰만 다시 인코딩합니다.
  이웃한 무효 토큰은 한 덩어리로 묶어 더 짧게 나눕니다.
- 수정하지 않은 데이터는 원래 스트림과 바이트까지 같고(앞서 열거한 세 이미지에서 확인), 그 경우 ISO 섹터도 하나도
  다시 쓰지 않아 이미지 전체가 입력과 같습니다.
- 쓰는 방식도 같은 원칙입니다. 압축 결과가 슬롯 안에 들어가면 디렉터리 길이는 원래 값 그대로 두고 스트림 뒤의
  나머지는 0으로 채웁니다. 슬롯보다 길 때만, 마지막 섹터의 padding이 모두 0일 때 그 안에서 디렉터리 길이를 늘립니다.
  내용이 바뀐 섹터만 EDC/ECC를 다시 계산해 씁니다.
- 쓴 뒤에는 결과 이미지에서 디렉터리 길이를 다시 읽고, TSR 섹터 체크섬을 확인하고, 압축을 풀어 수정한 데이터와
  같은지 비교한 다음에야 전체 SHA-256을 계산해 돌려줍니다.
- 저장된 스트림을 이어 쓸 수 없는 경우(압축하지 않은 형식, 해석할 수 없는 스트림, 데이터 길이가 달라진 경우)나 이어 쓴
  결과가 슬롯에 맞지 않을 때는 처음부터 다시 압축한 결과와 비교해 더 짧은 쪽을 씁니다.

**저장이 거부될 수 있는 수정:** 압축 결과가 위 슬롯(또는 0 padding까지)을 넘으면 `EDITOR_TSR_GROWTH_UNSUPPORTED`로
거부하고 이미지를 만들지 않습니다. 화면에는 ‘수정 데이터가 원래 공간보다 큽니다’와 필요한 크기·허용 크기·초과 크기를
한국어로 알립니다. 크기가 늘어나는 정도는 수정한 칸의 개수와 값의 모양에 달려 있습니다.

- 필드 하나를 바꾸면 2~18바이트가 늘고(완결편 c에서 측정: 기체 HP +4, 파일럿 수치 3칸 +12, 무기 공격력 +2,
  세 가지 함께 +18), 무작위 값 300칸은 F v0.5가 +782~871바이트, 완결편 v0.3이 +794~905바이트, 1,000칸은 F가
  +2,421~2,521바이트, 완결편이 +2,457~2,534바이트(다섯 가지 난수 씨앗의 범위)라 보통의 수정은 여유 안에 들어갑니다.
- 값이 서로 다른 칸을 흩어서 많이 바꿀수록 칸당 2~2.5바이트씩 늘어납니다. 무작위 값으로 바꾼 칸의 수가 대략 F v0.5는
  1,500칸, 완결편 a는 2,500칸, c는 3,000칸을 넘으면 슬롯을 넘을 수 있습니다(측정). 모든 칸을 무작위 값으로 바꾸면
  F도 완결편도 거부됩니다(필요 크기 F 220,179, 완결편 c 231,728바이트).
- 같은 규칙으로 모든 편집 칸을 +1씩 올린 경우처럼 바뀐 값이 규칙적이면 압축이 잘 되어 훨씬 적게 늘어납니다(F +272,
  완결편 c +387바이트).
- 파일럿 특수능력 목록의 편집은 칸 하나가 아니라 두 바이트 쌍이 바뀌므로 더 작게 늘어납니다(실제 값, 세 글꼴 변형 모두 같은 범위, 무작위 목록 세 가지 씨앗): 파일럿 1명 +3~5바이트, 5명 +13~28, 25명 +73~84, 100명 +277~338,
  200명 +559~617, 고칠 수 있는 파일럿 전부 +820~864바이트(F 295명, 완결편 310명). 모든 파일럿의 목록을 한도까지(최대 4개) 무작위 능력으로 채워도 F는 +939, 완결편은 +1,047~1,048바이트라 완결편의 여유(c 6,322)와 F의 여유(3,453) 안에 듭니다.
  이 편집만으로는 슬롯을 넘지 않습니다.
- 거부되면 바꾼 칸 수를 줄이거나 일부를 원래 값으로 되돌려 다시 시도합니다. 한 번 만든 수정본을 다시 열어 이어서
  수정하는 경우에도 그 수정본에 들어 있는 스트림을 같은 방식으로 이어 쓰며, 슬롯 크기는 그대로입니다.

이 동작은 합성 디스크로 만든 `tests/editor-export.test.mjs`(재압축, 슬롯·padding·경계 규칙, EDC/ECC, 디렉터리 길이,
출력 해시와 영수증)가 검증하고, 실제 이미지 폴더를 지정하면 `tests/editor-golden.test.mjs`가 같은 확인을 합니다.

기체 특수능력은 레코드 +38/40/42/44의 ID와 +39/41/43/45의 보조 byte가 교차하는 구조입니다(구조 능력 7가지는 위 ‘기체 구조 능력 잠금’처럼 편집할 수 없습니다). 이전 에디터의 연속 ID 저장 오류를 수정했습니다. 기존 잘못 만든 BIN은 자동 보정하지 않으므로 해당 슬롯을 다시 지정해야 합니다. 게임 내에서 모든 능력의 효과가 발생하는지는 별도 조건과 검증이 필요합니다.

### 수정본 재열기 검증 (2026-10-06)

게임 헤더만 맞는 임의 BIN은 허용하지 않습니다. 공개 패치의 전체 SHA-256을 확인한 후 만들어진 에디터 결과는 출력 SHA-256·게임·크기·기반 공개 SHA만 브라우저 로컬 기록에 남깁니다. BIN/CUE나 수정 데이터 자체를 저장하지 않습니다. 이후 선택한 파일의 전체 해시가 이 기록과 일치하고 아래의 기반 범위 검사도 통과하면 자기 출력 이력으로 표시합니다. 기록을 저장할 수 없는 브라우저에서는 현재 세션 기록만 유지됩니다.

모든 개인 수정본은 출력 기록 유무와 관계없이 최신 승인 이미지에 해시로 연결한 프로필의 범위 검사를 거칩니다. TSR 포인터·명칭·스크립트·알 수 없는 byte와 무기 개조 하위 nibble은 불변 해시로 검사합니다. 수정 가능한 기체·파일럿·무기 필드만 mask 처리합니다. 일반 파일럿은 수치 +4~+22와 +23부터 레코드 끝까지의 쌍 블록이며, 별칭 레코드·영웅 슬롯 302·303·알 수 없는 머리 없는 목록·쓰지 못하는 모양의 목록은 불변입니다. 주인공 습득표 #308~311은 `editor-hero-profiles.mjs`가 확인한 기존 48·32·48·32바이트만 추가로 mask 처리하고 마지막 4바이트 0 패딩·주소·길이·정신기 6칸 구조를 별도로 검증합니다. 이 확장 프로필은 최신 승인 a/b/c 6개와 정확한 원판 2개에 각각 고정된 해시를 가지며, 기존 일반 파일럿 수정본도 같은 확장 프로필을 통과합니다. 이전의 좁은 프로필로 재시도하는 예외는 없습니다. 디스크에서는 기존 TSR 할당 섹터의 payload/체크섬과 ISO의 TSR 길이 byte/체크섬만 허용합니다. 게임 코드·그림·음원·섹터 헤더 등 나머지는 기반 이미지와 같은 해시여야 합니다. 할당 범위를 늘리거나 섹터 체크섬이 맞지 않으면 거부합니다.

압축 데이터 뒤의 여백(2026-10-07): 범위 검사는 `TSR.BIN` 할당 섹터 전체를 편집 영역으로 취급하므로, 압축 데이터가 끝난 뒤부터 할당된 마지막 섹터의 끝까지
(디렉터리 길이 뒤의 padding 포함)에 출처를 알 수 없는 바이트를 숨길 수 있었다. 이제 이 구간은 **0이거나, 이전 에디터가 더 짧은 압축 데이터를 앞에 쓰고 남긴
공개 패치의 원래 압축 데이터**여야 한다. 후자는 프로필에 기록한 지문으로 확인한다: 원래 압축 데이터가 끝나는 위치 앞쪽 1024바이트 안의 끝 위치마다, 그 위치에서 원래
압축 데이터의 끝까지의 SHA-256(앞 8바이트)을 적어 두고(`tail`), 새 압축 데이터가 끝난 위치에서 이어지는 바이트가 그 지문과 같고 원래 끝 뒤가 모두 0일 때만 받아들인다.
원본 이미지는 브라우저에 없으므로 지문만으로 확인한다. 그 밖의 바이트가 하나라도 있으면 `EDITOR_TSR_TAIL_FOREIGN`으로 열지 않는다. 이전 에디터가 원래보다 1024바이트보다 더
짧게 쓴 이미지(필드 수천 개를 같은 값으로 바꾼 경우)는 지문이 없어 거부되며 원본에서 다시 만들어야 한다. 현재 에디터가 만든 수정본의 여백은 항상 0이다. F v0.4 a의 이력
프로필은 지문이 없어 0만 허용한다. 지문은 승인 이미지의 `TSR.BIN`에서 다시 계산할 수 있고 실제 파일을 지정한 골든 시험이 확인한다.

기반 공개 버전은 계열(`releaseId`에서 끝의 글꼴 변형 `-a`·`-b`·`-c`를 뗀 이름)이 **정확히 같을 때만** 최신입니다. 접두어 비교가 아니므로 끝 글자만 다른 이전 계열(`…-8` 대 `…-9`),
뒤에 글자가 붙은 계열, 이름 가운데에 변형 표시가 들어 있는 이름은 최신이 아니며 `EDITOR_REVISION_OUTDATED`로 거부합니다(받아들인 이미지, 영수증의 기반, 프로필의 기반 모두 같습니다).

출력 영수증 목록(`customOutputReceipts`)은 **최대 128개**입니다(페이지가 가장 최근 128개만 보관해 보냅니다). 더 길거나, 배열이 아니거나, 구멍이 있는 목록은 일부만 읽지 않고 설명자 전체를
`EDITOR_RELEASE_INVALID`로 거부하며, 이 검사는 이미지의 해시를 계산하기 전에 합니다(예전에는 앞의 128개만 읽고 나머지는 말없이 버렸습니다). 목록이 없거나 `null`이면 영수증이 없는 것입니다.
영수증이 아닌 항목은 하나씩 건너뛰고, 영수증의 다섯 필드(`schema`, `sha256`, `gameId`, `size`, `baseTargetSha256`)는 그 객체 자신의 값만 읽습니다.

에디터가 허용하는 최신 범위 프로필은 F v0.5 a/b/c, 완결편 v0.3 a/b/c입니다(2026-10-07에 위의 범위 정의로 모두 다시 만들었고 F v0.5 b가 추가되었습니다. 이전 에디터가 영웅·별칭 레코드의 수치를 바꿔 만든 수정본은 더 이상 열리지 않습니다). 같은 날 정신커맨드 편집을 위해 파일럿 범위를 정신커맨드 블록 뒤부터에서 +23부터로 넓히고 일곱 프로필의 `decodedMasks`와 `immutableTsrSha256`만 다시 계산했습니다(디스크 쪽 `rawMasks`·`immutableDiscSha256`과 `tail`은 그대로). 계산에는 각 레인의 풀어 낸 TSR을 썼고, 먼저 이전 코드가 저장된 범위와 해시를 그대로 다시 만드는지 확인한 뒤 새 범위를 적용했습니다. 새 범위는 이전 범위를 모두 포함하므로(F 레인마다 2,044바이트, 완결편 레인마다 2,796바이트가 새로 열림) 그 전에 만든 수정본도 그대로 열립니다. 남아 있는 F v0.4 a 프로필은 이전 수정본을 식별하여 차단하기 위한 이력이며 지문(`tail`) 없이 0만 허용하던 동작을 그대로 둡니다. 프로필은 공개 패치를 원본에 적용한 이미지에서 만들었고 그 이미지는 저장소에 넣지 않았습니다. 다른 공개 변형의 정확한 BIN은 공개 전체 해시로 열 수 있으며, 그 세션에서 만든 자기 출력과 기록 없는 수정본도 해당 최신 변형의 고정된 범위 검사를 통과해야 다시 열 수 있습니다. 브라우저 기록은 편집 허용 범위를 넓히지 않습니다. 이전 버전의 BIN은 편집할 수 없으며 자동 업그레이드하지 않습니다. 최신 기반 개인 수정본은 실제 기반 버전을 화면과 다운로드 설명에 표시합니다.

### 명칭 해독 (2026-10-06)

### 통합 에디터 변경 (2026-10-08)

변경 목록과 프리셋은 정신커맨드·탄수·필요 기력·필요 기능·실드·베어내기 값도 함께 저장합니다. 참/거짓 값은 JSON boolean으로 보존합니다. 정신커맨드와 특수능력은 원래 파일럿 레코드의 자리를 공유하며, 프리셋도 두 적용 방식 모두의 합계가 그 자리에 들어가는지 검사합니다.

새 프리셋에는 수정할 수 없는 레코드 머리부의 SHA-256 식별값이 포함됩니다. 머리부 없는 주인공 습득표는 게임·역할·고정 번호·길이·정신기 6칸 계약 태그의 SHA-256을 사용하므로 정신기를 수정한 BIN을 다시 열어도 식별값이 유지됩니다. 테이블 위치나 번역 이름에 의존하지 않습니다. 기존 번호가 식별값과 일치하면 그 번호를 사용하고, 달라졌으면 같은 식별값의 유일한 레코드를 찾습니다. 여러 개이거나 없으면 건너뜁니다. 구조 자체가 바뀐 미래 버전까지 무조건 적용되는 것은 아닙니다. 식별값 없는 기존 프리셋은 번호와 원래 값 비교를 사용합니다. 이전 버전 BIN을 직접 열거나 수정하는 제한은 유지합니다.

허용 범위 밖 입력은 적용되지 않았다고 칸 옆과 상태줄에 안내하고 저장을 막습니다. 다른 레코드나 탭으로 이동하면 마지막 유효한 값으로 돌아갑니다. 구조 능력의 종류·조건 플래그 칸은 잠기며, 앞 칸을 비워 뒤의 구조 능력을 숨기는 선택도 막습니다.
