# C0.11 파일럿 조회: 이전 사적 실행 시험

2026-10-10. 이 문서는 제품 작전 목적 형식에 넣기 전 수행한 단일 조회 시험을 보존한다. 이후 별도 in-place PV01의 제품 연결과 검증은 [제품 계약](EDITOR_PILOT_OBJECTIVE_CONTRACT.md)에 기록했다. 이하의 “제품에 추가하지 않았다”는 문구는 당시 조사 단계의 상태다. 당시에는 파일럿 조건을 제품 compiler·UI·프로필에 추가하지 않았으며 출력 이미지는 저장소 밖에만 있다. 고유 등장 개체의 생존·격추 이력, 조회 부재, 중복·alias의 일반 지원을 주장하지 않는다.

## 시험 입력과 사적 형식

승인 `srwf-final-20261005-v0-3-c` 전체 해시 `0fb10cbf4332f94c865c0e8d0a0c7234f8f6083bdbbb5a06198cebff871d195d`에서 배타적 APFS clone을 만들고 필요한 raw 섹터만 썼다. 사적 출력 해시는 `d725e9d7b10296d613eff47533f5e1d10a4a02d867b37e770ab9ac8a3a52e3f4`, 크기는 521,680,656바이트다. SCEDATA 물리5/선택102만 다시 압축했다. 원본문13,462바이트를 보존하고 헤더 root8/root13을 새 진입부/설명으로 옮겼다. 새 본문13,609바이트, 압축7,656바이트로 원슬롯8,067바이트에 들어갔다.

별도 사적 magic은 `SRWFOP11`이다. 80바이트 trailer의 +8/+12/+16은 원길이/root13/root8, +20은 사적 relocation mode1, +21은 query kind11, +22는 파일럿80의 BE16, +24는 고정 present1이며 나머지는0이다. OB01/OB02/OB03 필드 해석을 확대하지 않았다. 승인 원본문을 직접 대조하고 재생성한 바이트까지 같은지 확인하는 사적 normalizer를 사용했으며, 헤더·query·branch·reserved를 바꾼 11개 위조는 거부됐다. 출처 영수증 없는 제품 inspector는 이 전체 출력의 새 재열기를 `EDITOR_CUSTOM_PROVENANCE`로 거부했다.

원 root4의 CA02@2759, 항목2762는 기체107 가베라테트라 / 파일럿80 시마 가라하우 / 좌표(18,32)다. 현재 TSR 이름과 기록번호로 대조했다. 새 진입부는 원래 두 가드의 destination 및 승리3301·패배3329를 유지한다. 원 아군전멸 조회를 보존하고, 파일럿 조회만 `C0 11 00 50` → **즉시 `F0 00 delta_BE16`**로 연결한다. 미충족 시 새 E9대기와 상대 loop로 돌아간다. 원본문의 명령과 상대참조는 바뀌지 않았다. 이전 callback나 GameSave PC가 원래 본문으로 재진입할 수 있는 relocation의 일반 수명 문제를 이번 한 조회 시험으로 해결했다고 주장하지 않는다.

게임 RAM 주소는 새 query `0x20206CAD`, F0 `0x20206CB1`, 대기E9 `0x20206CB5`, 새 root8 `0x20206C96`이다. F0 operand cell은 `0x20206CB3`이고 원래 승리 `0x202044E5`를 가리킨다. root8 등록 필드는 GameState `0x2020052C`다.

독립 Python 검사에서 변경 섹터는 LBA219479..219483의5개뿐이며 다른 raw 섹터 모두 동일했다. 5개 모두 MODE2 Form1 EDC와 ECC P/Q를 별도 구현으로 통과했다. 디렉터리와 다른102개 물리본문의 압축/해제바이트가 같고 TSR·EXEC·맵도 같았다.

## F0/F1 방향과 피연산자

현재 승인 EXEC의 F0 handler `0x060205B8`, F1 `0x06020620`의 실제 바이트를 기존 실행기로 각각 두 플래그·양방향16변위, 총8경우 실행했다. mode0에서 F0는 VM+37 bit7이0일 때 참 분기하고, F1은 bit7이1일 때 분기한다. 상대변위 기준은 opcode+2의 피연산자 셀이다. 분기는 `F000`, 미분기는 `6002`를 반환하고 VM driver가 총4바이트 다음 명령으로 진행한다. mode1은 플래그 자체를 바꾸므로 사용하지 않는다. C0.11의 +20은 실패 시 stale이므로 수치0 비교를 사용하지 않았다.

## 실제 조회와 원래 승리 처리

`private-pilot-presence-mapclose-final-2` frame162에서 새 query cursor `0x20206CAE`로 C0.11 leaf `0x06024DC0`에 들어왔다. finder `0x060273F8`의 r4는80, 반환 직후 `0x06024DE4`의 r0는73이었다. 실제 actor73은 좌표(18,32), 기체 캐시60, 진영1이며 캐시60의 기체번호는107, 연결 파일럿 캐시60의 번호는80이었다. 파일럿 캐시+6은60이었다.

finder 직전에는 leaf가 VM+37 bit7을1로 초기화했다. 반환 후에는 +20에60을 쓰고 bit7을0으로 만들었다. 바로 다음 F0가 cursor `0x20206CB2`에서 판정을 소비했고, F0 return PC `0x0602060A`에서 r0=`F000`, cursor=`0x202044E5`로 원래 승리에 들어갔다. 그 화면은 브라이트의 원래 승리 대사였다. +20은 관측만 했고 비교 명령으로 사용하지 않았다.

leaf 진입/finder/post-delay C0 return `0x0602419A` 사이 actor1,184 + 파일럿1,536 + 기체3,840 = **6,560바이트 전체**가 같다. 표 전체 해시는 `405ce78d26e432ea3380167a6c2552dcedf6872781931aca427ce6a81b13b7f9`다. 인자 컨텍스트80바이트, r8..r15/PR도 복원됐다. `private-pilot-presence-victory-final-2` frame202에서 원 EC01 cursor `0x202044FF`가 승리 값10을 만들고 VM+37의 mask70이10이었다. 같은 frame의 common ECFF cursor `0x2022203D`는1을 반환했다. 뒤의 `private-pilot-presence-clear34-final-2/native-step-0001.png`는 제34화 ‘프로테아 IV의 위기(전)’까지 완료, 총턴361, 자금1,000,000의 인터미션이다. 여기까지는 원래 승리 action 연결의 단일 실제 경로 근거이며, 새 저장/재로드나 파일럿 조건의 일반 지원 근거가 아니다.

## 실제 반례: 현재 존재하는 파일럿의 없음 조건

별도 `SRWFOA11` 이미지 `5d297460e982748899414f1297e9577c249b1bcbde65e099ea7631f0ae9871ef`는 파일럿80 조회 다음을 F1으로 바꾼 사적 고정 시험이다. 새 승인 원본 clone, 기존 MCA 없는 GameSave33 cold 불러오기, 그 출력 자체의 MCA만 사용했다. 다른 섹터/표/본문은 앞의 시험과 같은 검사로 유지됐고, fresh 제품 inspector는 거부했다.

`private-pilot-absent80-mapclose-final-1` frame162에서 같은 캐시60/actor73이 반환됐고 VM+20은2→60, 판정 bit7은0이었다. F1 return `0x06020672`는 `6002`, cursor `0x20206CB3`로 미분기했다. 바로 뒤 E9 `0x0601F644`에는 cursor `0x20206CB6`로 들어왔고 `0x0601F656`에서 `F000`을 반환했다. E9 helper `0x060209AC`의 실제 동작처럼 VM+0에 재개PC `0x20206CB6`을 저장하고, 인자 컨텍스트의 caller cursor를 복원·스택 칸을 비우며 depth2→1로 만들었다. E9 전후 VM80/인자80의 그 변경을 정확히 대조했고 세 표 전체도 같았다. 즉 이번 실제 배치의 ‘파일럿80 없음’은 승리로 들어가지 않고 생성된 대기로 갔다. 이 한 대기 진입을 모든 callback·저장 재개 수명의 증거로 확대하지 않는다.

## 실제 반례: 표에는 있지만 캐시에 없는 파일럿

현재 승인 TSR의 파일럿159는 기와자 로와우다. 실제 맵의128칸 파일럿 캐시 ID 집합에159가 없음을 전체표로 확인했다. 별도 `SRWFOM11` 이미지 `f78d546f9a78a5c843d5894bcc4f99c58cb9af8f01fad2ac2061dfe8207a7b42`는 C0.11→즉시F0, 다시 C0.11→즉시F1을 배치한 **두 방향 플래그 probe**다. 제품 작전 목적 조합 형식이 아니다. source placement의 시마80/actor73은 맵 연결 대조의 기준이며 이번 요청 ID159와 구분한다.

`private-pilot-missing159-mapclose-final-1` frame162의 두 query에서 finder의 초기 캐시 확인 `0x0602740A`는 r4=`FF`, leaf로의 반환 `0x06024DE4`는 r0=`FF`였다. 둘 모두 파일럿 보정 `0x0602D734`, actor 조회 `0x0602743C`, 결과 store `0x06024E24`에는 들어가지 않았다. 초기 FF 분기가 잘못된 캐시를 읽기 전에 끝나는 실제 경로를 확인했다.

직전 아군 조회의 **VM+20=2가 두 번 모두 그대로 남았다.** 첫 query는 VM+37 bit7만1로 만들었다. 그 다음 F0는 `6002`로 미분기했다. 두 번째 query도 +20=2/bit7=1을 그대로 유지했고 바로 뒤 F1은 `F000`, cursor `0x202044E5`로 원래 승리 대사에 들어갔다. 비어 있는 파일럿 조회를 이전 숫자2와 비교하면 현재 존재처럼 오판할 수 있다는 실제 반례다.

세 query 모두 앞의 존재 시험과 같은 full6,560 pool 해시이고, leaf→post-delay 반환에서 인자80바이트와 r8..r15/PR이 같았다. VM80의 최종 변경 위치는 파일럿80 반례 +23, 첫159 +37, 두 번째159 없음이다. 두 반례는 각9단계의 own-image MCA chain, correct CUE, scheduled RAM poke0을 따로 검증했다. 원자료는 사적 `native-private-pilot-absent80-proof.json`, `native-private-pilot-missing159-proof.json` 및 두 `-owned-chain.json`에 있다.

확정 범위는 완결편의 이번 정상 연결 파일럿80 존재/없음과 초기 미등록159의 flag 경로다. F의 실제 실행, 등록됐으나 actor가 없는 경우, 중복, 연결·보정 alias의 생성/제거/저장 수명, 고유 인물 생존/격추 이력은 여전히 미검증이다. OB01/OB02/OB03 제품 형식과 파일럿 조건 권한은 바꾸지 않았다.

## 인물 이력 조건을 위한 읽기 명령 조사 (2026-10-11)

현재 파일럿 조회의 존재·부재는 과거 등장·도착·격추 이력이 아니다.
그 이력을 별도로 보존하려면 어떤 비트가 해당 시나리오에서 사용 가능한지,
언제 초기화되는지와 게임 저장·재개 때 무엇이 보존되는지를 추가로 확인해야 한다.

승인 완결편 EXEC의 `D0.02` leaf `0x0602118C`를 기존 엄격한 SH-2 실행기로
실행했다. 명시적으로 만든 32바이트 플래그 표에서 번호 0·1·74·166·254·255의
꺼짐/켜짐 12경우와 바로 뒤 `F0`/`F1`의 24분기를 확인했다. 비트 위치는
`GS+0x534+(id>>3)`, 마스크는 `1<<(7-(id&7))`다. 반환은 `6003`이며,
판정은 VM+37의 bit7에 남는다. 플래그 표와 다른 매핑된 비스택 메모리 및
ABI는 보존됐다. VM+20에 일부러 넣은 이전 숫자도 그대로 남으므로 이 명령의
결과를 수치 비교로 해석하지 않는다.

이 검사는 명시적인 합성 메모리에서 승인 코드의 읽기 동작을 확인한 것이다.
실제 게임에서의 격추·도착 판정, 새 이력 비트의 예약, 초기화·저장 수명이나
제품 조건 형식의 확장을 증명하지 않는다. 기존 `C0.12` leaf는 선택된 기체
캐시의 수치에 비율을 적용해 다시 쓰는 명령이므로 읽기 전용 조건 후보에서
제외했다. 해당 필드의 게임상 의미는 별도 연결 근거가 필요하다.

사적 실행기와 보고서는 저장소 밖
`root-person-condition-source-20261011-1/flag-query-cpu.py` 및
`flag-query-cpu-report.json`에 있다. 보고서 상태는
`PASS_SOURCE_CPU_FLAG_QUERY_NOT_NATIVE_GAME`이며 승인 EXEC·실행기·검사 코드의
입력 해시를 포함한다. 신규 미디어·에뮬레이터 실행·제품 권한 변경은 없다.
