# 파일럿 작전 목적 조건: 제품 계약과 검증 범위

2026-10-10. 완결편의 최신 승인 기반 시나리오에서 파일럿 `있음`·`없음` 조건을 기존 승리·패배 조건에 연결한다. 이 조건은 게임이 현재 찾는 파일럿 연결이며 고유 개체의 생존, 사망 또는 격추 이력은 아니다. 원래 대사·플래그·승패 처리와 root8 등록 주소를 보존한다. 조사용 `SRWFOP11` 등과 제품 형식 `SRWFPV01`을 구분한다. 새로운 공개 패치 승인이나 원격 배포가 아니다.

## 대상과 표시

F, 원본 언어 시나리오, root8을 옮기는 경로에는 파일럿 조건을 열지 않는다. 완결편 latest의 기존 in-place 작전 목적만 대상이다. 일반 적·아군 수, 턴 및 기체 종류 조건의 기존 권한은 그대로다.

파일럿 선택은 선택한 BIN에서 실제로 읽은 TSR 표에 묶인다. `statsValid`, regular 독립 레코드, role 없음, alias 없음이 모두 필요하며 ID 1..399 및 실제 표 길이를 확인한다. 전용 슬롯·공유 레코드·비정형 머리·미사용 기록과 302..319는 제외한다. 승인 v0.3-c의 선택 가능 독립 머리는 379개다. 실제 승인 a 이미지도 전체 해시·크기를 확인하고 디렉터리에서 SCEDATA/TSR을 다시 읽었으며, c와 같은 시나리오 바이트·379개 catalog·첫 슬롯 제한을 확인했다. TSR 전체는 글꼴별로 다르다. b의 새 실행은 검사하지 않았다. 같은 이름은 번호를 붙인다. 이 구조 검사는 379명 각각의 모든 등장·퇴각·변형·alias 수명을 게임에서 실행했다는 뜻이 아니다.

작전 목적 조합 지원 19개 본문 중 첫 물리 본문0/선택0의 압축 슬롯은 1,598바이트다. 파일럿80 단일 있음/없음 시험이 각각 1,647/1,646바이트가 되어 들어가지 않는다. 이 고정 슬롯에서는 파일럿 선택을 제공하지 않으며 기존 수·턴·기체 조건은 남긴다. 실제 디렉터리의 물리 번호와 슬롯 크기로 제한하므로 허용된 좌표·보상 편집 또는 OB/DL 복원을 거쳐도 유지된다. 나머지 18개 본문의 단일 있음/없음 36출력은 각 원 압축 공간에 들어갔다. 모든 조건 조합이나 모든 ID의 저장 가능 보증은 아니며, 실제 저장 때 압축 크기를 다시 검사한다.

## 명령과 정규 형식

파일럿 조회는 `C0 11 BE16(id)` 다음 **즉시 mode0 F0(있음) 또는 F1(없음)**로 판단한다. 조회 실패 때 VM+20에 앞선 결과가 남으므로 그 수치를 0과 비교하지 않는다. 숫자 조건과 기체 종류는 기존 전용 조회·비교 경로를 사용한다. 승리·패배 각각 최대3개, 모두/하나라도 충족, 동시 충족 우선순위를 지원한다. 표시 문구는 기존 게임 공간에 맞춰 NFKC 기준18자 이하다.

파일럿 규칙은 별도 tag `0x4000 | (id << 1) | presentBit`이다. OB01/OB02/OB03/DL의 기존 필드 해석을 넓히지 않는다. 예전 형식에 파일럿 tag를 끼운 자료는 거부한다.

PV01 trailer는128바이트이며 magic, 원 길이와 root8/root13, in-place mode0, query family11, 추가 턴 제한,9개 조건 필드, 원래18바이트 구간, **원 본문 전체 SHA-256**, 실제 파일럿 머리 catalog의 SHA-256, reserved0을 담는다. 정상화는 원 본문을 복원한 뒤 전체 확장을 다시 만들어 정확히 비교한다. 사적 metadata 자체가 권한이 되지 않으며, 이후 승인 기반의 기존 불변 프로필 검사가 필요하다. 자체 해시를 새로 맞춘 변조된 원 본문도 이 마지막 검사에서 거부된다. 불변 mask와 기존 프로필 핀은 넓히지 않았다.

TE02 사건 조건은 바깥 wrapper로 유지한다. PV 조건 재편집, 추가 턴 제한 변경, 기존 OB01/OB03·DL로 전환, 조건 완전 제거가 다른 사건 편집을 지우지 않는다. 조건을 완전히 제거한 해제 본문은 원본과 동일하지만 재압축된 BIN의 전체 해시는 달라질 수 있다.

## 저장과 입력 경계

UI→모델→변경 목록→편집값 JSON→BIN/CUE→기록 없는 새 세션의 범위 프로필까지 같은 조건 context를 사용한다. 파일럿 머리 식별은 원4바이트로 고정하며 실제 능력치·정신커맨드·특수능력 변경 후 catalog가 동일한지 검사한다. catalog와 요청은 압축 등 비동기 작업 전에 own data로 복사·동결한다. getter, 중복, 변조 catalog, 다른 게임·레이아웃·표 길이는 거부한다.

JSON 파서는 정규 wire 값을 읽는 데 그친다. 적용 계획은 실제 선택 가능 파일럿 context와 작전 목적 구조 식별을 다시 검사한다. 파일럿 조건이 포함된 한 작전 목적은 전체를 하나로 적용한다. 대상 없음·다른 구조·충돌·skip가 있으면 일부 필드만 적용하지 않는다. 최신 지원 자료 사이를 이름으로 추정해 옮기지 않는다.

미입력 조건은 작업 중 초안이며 출력 데이터에 들어가지 않는다. 새 조건이나 기체/파일럿/숫자 간 대상을 바꾸면 기준값을 비운다. 다른 화면 이동·저장 전에 검증하며 임의 기본 턴은 만들지 않는다. 삭제 후 해당 `조건 추가` 버튼, 복원 후 유효한 우선순위 입력으로 포커스가 돌아온다. 복원은 이전 오류 안내도 지운다. BIN을 재열고 `처음 값`을 누르면 그 BIN을 열었을 때의 조건으로 돌아간다.

편집값 JSON, 게임 내 저장, 에뮬레이터 중간 저장은 서로 다르다. 원4바이트 대기 구간을 교체하므로 **편집 전 BIN의 전투 중 저장을 수정 BIN으로 이어 쓰는 일반 호환성을 보장하지 않는다.** 해당 전투에 들어가기 전의 게임 저장부터 진행한다. 자기 PV 출력의 전투 중 저장·새 부팅 이어하기 시험은 아래 제한된 경로이며, 조건 재편집으로 생성 코드 위치가 바뀐 뒤 옛 중간 저장을 재사용하는 보증도 아니다.

## 실제 게임 실행 범위

정확한 제품 있음 출력 `4b721a…684d`의 별도 home에서 MCA 없는 cold boot로 기존 정상33화 완료 저장(총턴360/자금1,000,000)을 불러왔다. 원 CUE, 구분점 있는 `.%x` 저장 파일명, 해당 이미지 자체에서 만든 MCA만 사용하며 RAM poke·cheat·media-ID override는 없다. 다음전장에서 선택102/진행34/원root8 `202044C3`와 전체13,674B RAM 일치를 확인했다.

실제3회 C011 query의 파일럿80→캐시60→actor73은 즉시F0를 거쳐 새 jump에서 원 Win `202044E5`로 들어간다. 원 EC01→EA→공통ECFF의3회 소비가 결과1로 이어지며 실제34화 완료/총턴361/자금1,000,000 화면을 확인했다. query 전후 actor1,184+파일럿1,536+기체3,840=6,560바이트 전체, 인자80, r8..r15/PR을 대조했고 VM의 조회 결과·판정 플래그 외 부작용이 없다. 이 정확한 제품 출력에서는 새 게임 저장·재로드를 아직 주장하지 않는다.

정확한 제품 없음 출력 `2dd360…0333`은 별도 own home의 MCA 없는 cold boot에서 같은33화 완료 저장을 불러왔다. 선택102·원root8·전체13,674B RAM을 확인했다. 실제3회 C011 pilot80 조회는 현재 존재하는 캐시60/actor73을 찾으므로 즉시F1이 미분기하고 새E9 대기로 간다. E9의 인자 스택 반환·재개PC20206CC5와 다음 재조회를 ordered trace로 대조했다. 같은6,560B 표·인자·ABI를 보존하며 해당 조회 구간에는 원 승리 EC01이 없다. 이 제품 없음 출력에서는 전투 중 저장·coldContinue를 반복하지 않았다.

현재 제품 core/session/export의 파일럿159 없음 출력 `29c575…892a21`도 별도 own home의 MCA 없는 cold boot에서33화 완료 저장을 실제로 불러왔다. 선택102·원root8·전체13,675B RAM이 같았다. 세 실제 조회 때128칸 파일럿 캐시에159는 없고80은 있었다. 조회는 초기 lookup/helper의 FF에서 끝나며 alias 보정·actor 조회·metric 저장 경로에 들어가지 않았다. VM+20은 앞선 결과2를 그대로 남겼지만, 즉시F1은 판정 bit7로 참분기해 생성 jump→원 Win으로 갔다. VM80의 변경은 byte37뿐이고6,560B 표·인자80·ABI는 보존됐다. 원 EC01·EA·공통ECFF를 각각3회 확인했으며 실제34화 완료/총턴361/자금1,000,000 화면까지 이어졌다. 이 검증은 현재 캐시에 등록되지 않은 파일럿의 조회 실패를 안전하게 처리하는 경로이며 격추 이력·alias 전체 수명 또는 새 GameSave/coldContinue 증거로 확대하지 않는다.

별도 in-place PV 사적 prototype 없음80은 전투 중 저장 후 MCA를 모두 지우고 정상 타이틀 `이어하기`로 같은34화 맵·본문·root8을 복원했다. 정상 페이즈 종료에서 다시 C011→즉시F1 불충족→E9 대기를 확인했다. 저장 시 PC가 새E9 재개점이었지만 coldContinue 최종VM+0은0으로 초기화됐으므로 PC가 그대로 복원됐다고 쓰지 않는다. prototype과 제품은 목적 문구가 달라 전체 해시·본문 길이가 다르며, 이 저장 경로를 제품 출력에서 직접 반복한 것으로 표기하지 않는다. 이전 사적 missing159는 조회 실패 때 +20 stale과 F0/F1 반대 방향을 확인한 추가 근거다.

F의 파일럿 조회 실행,379명 전수 등장/alias 수명, 고유 인물 생존·격추 이력, 좌표 도착, 이전 BIN의 전투 중 저장 호환, 임의 실행 중 코드 재편집, 모든 지원 본문·글꼴의 전수 실행은 미확인이다. 페이즈 변경과 신규 증원은 이 형식으로 열지 않는다. 과거 독립 조회 자료는 [조사 기록](EDITOR_PILOT_QUERY_RUNTIME.md)을 참고한다.
