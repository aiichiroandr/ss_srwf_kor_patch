# 기체 종류 조건: 완결편 실행 검증

2026-10-10. 첫 사적 `SRWFOB03` 제안의 실행과 이후 제품의 별도 정규 형식 실행을 구분한 기록이다. 아래 사적 Final 본문 5의 root8 교체 방식은 제품에서 계속 거부한다. 제품은 이 본문의 확인된 기존 조건 진입부와 E9 재개점을 보존하는 mode 0을 사용한다. 게임 파일, 출력 BIN, backup, MCA와 원시 trace는 저장소 밖에만 있다. 공개 릴리스·승인 해시·배포 상태를 변경하지 않았다. 명령 의미와 형식의 근거는 [대상 조회 조사](EDITOR_ENTITY_OBJECTIVE_RESEARCH.md)와 [조건 계약](EDITOR_OBJECTIVE_COVERAGE.md#기체-종류-현재-집계-조건의-별도-형식)에 있다.

## 시험 입력과 조건

최신 승인 완결편 v0.3 c 전체 SHA-256은 `0fb10cbf4332f94c865c0e8d0a0c7234f8f6083bdbbb5a06198cebff871d195d`다. 물리 본문 5 / 선택 번호 102의 승리 조건을 **가베라테트라 종류 존재**, 패배 조건을 기존 아군전멸로 정하고 패배 우선순위를 유지했다. 이는 기체 종류 107의 현재 집계이며 특정 시마의 격추·생존 이력이 아니다.

사적 출력 SHA-256은 `232beb98c23c93eb586c9d63552beca171e039055166025f037ab6f92158639f`다. 원래 본문 13,462바이트의 모든 명령과 상대 참조를 보존하고 header root8·root13만 새 진입부·목적 문구로 연결했다. 확장 본문 13,614바이트, 압축 7,669바이트가 원래 8,067바이트 슬롯 안에 들어간다. 변경한 raw 5개 섹터의 독립 EDC/ECC와 다른 모든 섹터 동일성은 별도로 확인했다. 제품 새 세션은 이 BIN을 `EDITOR_CUSTOM_PROVENANCE`로 거부한다.

기존 조사 홈의 backup을 새 격리 폴더에 복사했지만, 첫 부팅의 저장 파일명 설정에서 확장자 앞 점이 빠져 실제로 읽지는 못했다. 당시 ‘로드 데이터가 없습니다’ 화면 뒤에 타이틀의 ‘시작’으로 들어갔으며, 완결편 새 게임의 33 완료 intermission에서 34화로 진행한 경로다. 기존 GameSave33을 불러온 시험으로 계산하지 않는다. MCA를 모두 제거하고 출력 전체 해시를 확인한 뒤 처음부터 부팅했으며 이후 계측 재개는 **이 출력의 부팅에서 만들어진 MCA만** 사용했다. RAM 쓰기·치트·native media ID 강제는 없었다. 이후 아래의 게임 저장·새 부팅 로드는 그 실행에서 실제 생성한 활성 backup 이름을 명시해 검증했다. 기존 전투 중 저장을 새 BIN에서 호환한다고 주장하지 않는다.

## 실제 조회와 원래 승리 처리

초기 도입부에서 F1 가드가 새 E9로 대기하는 것을 확인했다. 실제 기체 배치와 플레이 화면 이후에는 새 root8 등록 주소 `0x20206C96`을 통해 조회가 실행됐다. 기존 가드를 무시해 도입부의 미등장을 부재 승리로 바꾸는 방식으로 시험하지 않았다.

`private-unit-objective-query-abi-final-1` frame 142의 실제 `C0.0E` 실행에서 다음을 대조했다.

| 항목 | 실제 결과 |
| --- | --- |
| 명령 인수 cursor | `0x20206CAE`, 생성한 `C0 0E 806B`의 하위 명령 위치 |
| native entry / caller 복귀 | `0x06024ADC` → `0x0602419A`, 반환 `6003` |
| 결과 | VM +20 = 1, +37 판정 bit7 = 0 |
| 일치한 출격 개체 | actor 73, unit cache 60, pilot cache 60, 좌표 (18,32), 진영 1 |
| 조회 전후 세 표 | 출격 1,184 + 파일럿 1,536 + 기체 3,840 = **6,560바이트 전체 동일** |
| 부모 문맥 | 인수 문맥 80바이트, r8..r15와 PR 동일 |
| VM 문맥 | 80바이트 중 결과 +20..23과 판정 +37만 예상대로 변경 |

native 필터를 별도의 Python 산식으로 적용한 집계도 1이다. 세 표 전체 SHA-256은 `405ce78d26e432ea3380167a6c2552dcedf6872781931aca427ce6a81b13b7f9`다. 특정 이름이나 출격 슬롯을 결과값으로 임의 대체하지 않았다.

`0x06024B9A`는 RTS **전** 관측점이다. 지연 슬롯 `0x06024B9C`가 r8을 복원하고 SP를 4 증가시키므로 ABI 보존은 caller `0x0602419A`에서 확인했다. RTS 전에 r8이 다르다는 것을 함수의 보존 실패로 계산하지 않았다.

후속 native F3는 결과 +20을 0과 비교해 원래 승리 경로로 분기했다. 원래 브라이트의 승리 대사가 화면에 나왔고, `private-unit-objective-clear-final-1` frame 122에서 원래 `EC01` 인수 `0x202044FF`와 결과 bit `0x10`을 확인했다. 이어 공통 `ECFF` 인수 `0x2022203D`에서 결과 1을 소비했다. 목적 문구만 바꾸거나 새 EC로 원래 사건을 건너뛴 결과가 아니다.

## 게임 저장과 새 부팅

실제 저장 메뉴에서 34화 ‘프론티어 IV의 위기(전)’ 완료를 저장했다. 저장 뒤 intermission에서도 34 완료 / 총 턴 361을 확인했다. 사용 중인 game backup 파일의 SHA-256은 `384182ea7e8aec70e0536d2b8924b2bf8d5b635445d4c49e99af87fee3711852`에서 `f1252b5153c4e636c6ee4c10a534c4adb917354228807edf2001306f0ac72459`로 바뀌었다.

새 격리 폴더에 이 실행의 backup을 복사하고 MCA를 모두 제거했다. 같은 전체 해시의 BIN을 다시 처음부터 부팅하여 타이틀 ‘로드’와 본체 RAM을 선택했고, 저장 목록의 34 완료를 확인했다. 실제 로드 뒤 intermission도 **34 완료 / 총 턴 361**이었다. 저장 뒤 화면과 로드 뒤 화면은 PNG 바이트까지 같고 SHA-256은 `859196ef0c934c59112d5d1351f4c462f9135bd34a953f7a03704d31707c45af`다. 저장 목록을 본 것과 실제 로드를 마친 것을 구분했다.

이는 해당 종류의 **존재 1 → 원래 승리 처리 → 완료 게임 저장 → MCA 없는 새 부팅·로드**라는 한 경로다. 존재 0·부재 조건의 대기와 E9 재조회, 전투 중 저장의 새 조건 재개, F의 대응 실행, 변형·합체·철수·고유 인물 격추 조건, 임의 조합을 이 결과로 통과시킨 것은 아니다. 반대 조건의 사적 출력과 실행을 별도로 조사 중이다.

사적 생성·검증 파일은 `/private/tmp/srwf-scenario-research/`의 `final-private-unit-objective-ob03-plan.json`, `native-unit-objective-proof.py`, `native-unit-objective-proof.json`, `private-unit-objective-*`에 있다. 제품 기능을 열 때는 별도 포맷·정상화·출처·JSON·UI 왕복 계약이 필요하다.

## 반대 조건의 대기와 전투 중 저장 재개

별도 사적 부재 출력 SHA-256은 `fcb06fd59f3314f5f191f2c071063b8114c062b78935f3de68688f234f7b9d45`다. 같은 종류 107의 집계가 1인 실제 맵에서 F2의 부재 조건은 승리로 가지 않고 새 E9로 대기했다. `private-unit-objective-absent-map-final-1`의 frame 362·363·2422에서 독립 집계, 조회 전후 전체 세 표, 인수와 ABI 보존을 확인했다. 원래 EC01 승리 경로는 실행되지 않았다.

실제 전투 중 저장 메뉴로 저장했고, 사용 중인 backup SHA-256은 `97980a2115ce496bbadd143fbad5308478589ac547147bdd4dcb26f76efed882`다. MCA를 모두 제거한 새 부팅에서 타이틀 ‘이어하기’를 선택하여 실제 맵으로 복귀했다. 이후 실제 페이즈 종료와 원래 적군 행동을 진행한 `private-unit-objective-absent-reloaded-phase-final-1` frame 819에서도 생성한 조회 인수 `20206CAE`가 실행됐으며 집계 1 → 부재 불충족 → 새 E9 대기를 확인했다. 조회 전후 6,560바이트는 동일했고, 조회 시 세 표의 SHA-256도 저장 전 조회와 동일했다. 타이틀의 ‘시작’이나 단순 B 입력 화면을 재개 성공 근거로 사용하지 않았다.

`native-unit-objective-absent-proof.py/json`은 **각 주장한 실행 파일에 자체 생성 조회가 존재해야** 통과한다. 이 저장 재개 근거도 제품에서 거부하는 사적 mode 1의 한 실행 경로이며, 제품 mode 0이나 임의 이전 저장의 호환성으로 확대하지 않는다.

## 제품 mode 0의 447 없음(count 0)과 원래 승리

제품 writer로 완결편 물리 본문 5 / 선택 번호 102의 승리 조건을 **447번 기체 없음**, 패배 조건을 기존 아군전멸로 만든 출력 SHA-256은 `a40faa6331e9ae58597c55763dd366c36e2ed7a4dcd04bd2844e08adcfb7c8ea`다. 제품 새 inspector는 출처 기록 없이 `bounded-editor-profile`로 이를 재열었다. mode 0의 원래 root8 `202044C3`를 유지하며 생성한 조회는 `C0 0E 81BF`, 인수 cursor는 `20206CA4`다. 독립 디스크 검사의 변경 섹터는 `219479..219483`의 5개로, 모두 EDC/ECC가 맞고 다른 221,798개 raw 섹터는 승인 입력과 같다.
