# 작전 목적 조건 조합의 지원 범위

## 현재 지원 단위

2026-10-10 기준 최신 승인 F a의 SCEDATA에서 조건 조합을 편집할 수 있는 물리 본문은 **14개**, F완결편 c에서는 **19개**다. 이는 화 수가 아니다. 한 본문을 여러 디렉터리 슬롯이 공유할 수 있고 더미 데이터도 포함된다. 에디터는 선택한 본문의 실제 맵 문맥과 지원 여부를 확인한다.

- F: `0, 11, 14, 18, 23, 25, 27, 30, 33, 34, 39, 41, 44, 47`
- F완결편: `0, 3, 4, 5, 6, 7, 9, 69, 70, 71, 94, 95, 96, 97, 98, 99, 100, 101, 102`

적/아군 인원 수와 현재 턴을 같음·다름·이하·이상으로 비교한다. 승리·패배별 최대 세 조건을 모두/하나라도 충족으로 묶고 동시 충족 우선순위를 정할 수 있다. 기체 종류의 현재 존재·부재를 조합하며, 완결편의 기존 in-place 자료 18개는 일반 파일럿의 현재 존재·부재도 지원한다. 이는 생존·격추 이력을 기록하는 조건이 아니다. 원래 가드와 사건 처리는 사용자 조건보다 먼저 실행될 수 있다.

2026-10-11에는 위 F 14개 본문에 현재 위치 조건을 연결했다. 아군·적군·기타 진영 중 하나를 고르고, 해당 진영의 기체가 지정 칸이나 사각 영역에 한 기라도 있는지 또는 없는지 판정한다. 좌표를 직접 입력하거나 실제 맵에서 선택하며, 미완성 입력은 저장 데이터에 넣지 않는다. 조건 삭제·복원·변경 목록·JSON·BIN 출력·기록 없는 새 세션 검사에 연결한다. 완결편의 위치 조회는 공통 목록과 좌표 상태에 부작용이 있어 아직 허용하지 않는다. 신규 RG01의 실게임 실행 검증은 별도 진행 범위다. [위치 조건의 저장 계약과 검증 한계](EDITOR_REGION_OBJECTIVE_CONTRACT.md)를 참고한다. 임의 이벤트 플래그와 특정 인물의 격추 이력 조건도 아직 지원하지 않는다.

## 두 가지 검증 방식

기존 `SRWFOB01`은 검증된 집계 비교 14바이트와 pending E9 루프 4바이트만 점프로 바꾼다. 기존 가드, 승리·패배 action, 나머지 원문을 보존한다. 덮어쓸 내부를 가리킬 가능성이 있는 상대 참조를 보수적으로 거부한다. 기존 F 10개와 완결편 19개의 지원 및 출력 형식은 유지했다.

새 `SRWFOB02`는 **원래 명령을 한 바이트도 덮어쓰지 않는다.** root 8의 전체 콜백이 아래 형태로 닫힐 때만 새 진입부를 본문 뒤에 붙이고, 헤더의 root 8·13 포인터만 변경한다.

1. `D0 02` 플래그 조회와 `F0/F1` 상대 분기로 된 가드 0~3개.
2. `D3 FC/FB` 인원 수의 0 비교 두 개. 각 분기는 원래 EC01/EC02 결과 action으로 간다.
3. `E9`와 원래 root 8 시작으로 돌아오는 상대 분기.
4. 정확한 `EC 01 EA`와 `EC 02 EA` 결과 action. action에서 E9 재개, 다른 호출, 미해석 명령은 없다.

선언된 root 8의 물리 경계 전체를 확인하며, 다른 곳에 있는 비슷한 바이트를 검색해 권한을 부여하지 않는다. 기존 가드의 실제 목적지도 검증한다. F의 FA/F0 가드는 원래 승리 action으로 바로 분기하고 F1/F1 가드는 pending으로 간다. 새 진입부는 이 차이를 보존한다. 모든 가드를 pending으로 바꾸면 원래 판정이 달라진다.

새 조건의 승리·패배 분기는 원래 EC/EA action에 연결된다. 충족하지 않으면 새 E9에서 반환하고 다음 호출에 새 진입부로 돌아간다. 원래 본문으로의 다른 진입, 상대 참조와 루트 별칭은 그대로 보존한다. 이 방식은 기존 action이 E9로 반환한 뒤 원래 집계 검사로 돌아갈 수 있는 복잡한 콜백까지 허용하지 않는다.

## 저장·복원 계약과 회귀 검사

`SRWFOB02`의 80바이트 trailer에는 원래 해제 길이, 원 root 13, 원 root 8, 추가 턴 제한, 9개 정수 조건 필드를 기록한다. 사용하지 않는 metadata 바이트는 0이어야 한다. 재열 때 두 헤더 포인터를 복원한 뒤 추가 가드·분기·E9 재개·목적 문구·metadata를 모두 다시 생성하고 전체 바이트를 비교한다. 그 결과인 원본문을 기존 불변 출처 프로파일과 대조한다. 정규화 함수만으로 임의 원본문의 출처를 승인하지 않는다.

조건과 추가 턴 제한을 모두 원래 값으로 되돌리면 확장과 두 포인터 변경도 제거하여 원본문 전체가 같아야 한다. 턴 제한만 제거할 때 변경된 조건은 유지하고, 조건이 기본값이면 원본문으로 완전히 복원한다.

독립 명령 실행 모델은 두 게임에서 원문·루트 별칭·다른 원문 진입 보존, 가드의 직접 승리/대기 분기, 동시 승패 우선순위, 새 E9 재개, 새 carrier의 metadata 복원·재편집, 조건/턴 제한의 완전 제거를 검사한다. 위조된 루트·코드·목적 문구·metadata는 거부한다. 기존 `SRWFOB01` 회귀도 유지한다. 이는 에뮬레이터의 실제 세이브 데이터 복원 또는 새 콜백의 실게임 클리어를 확인한 증거는 아니다.

### 실제 F BIN과 브라우저 왕복

F a 전체 입력 SHA-256 `b2a67ed2a409c95de7226d33f2ab934012e93199afb7284bb710c81b6f0223b9`에서 본문 27을 직접 선택했다. UI에서 빈 새 조건의 값을 입력하고 JSON을 저장·복원·불러왔다. 같은 JSON에서 추가 턴 제한 5를 지정한 뒤 UI로 BIN을 출력했다. 출력 SHA-256은 `ede2e8b0f8042c4dfa90109abe88088d5336964c951af60d03b63e829e8e4aa9`이며, 578,512,032 bytes로 입력 길이를 유지했다.

출처 영수증을 주지 않는 새 페이지에서 출력 BIN을 불러와 조건과 제한이 유지되는지 확인했다. 그 페이지에서 조건 값을 다시 바꾸고 ‘처음 값’으로 복원하면 **해당 개인 BIN을 불러온 당시의 값**으로 돌아가는 것도 확인했다. 재편집 출력은 또 다른 새 페이지에서 영수증 없이 열어 승리 2턴 이하, 패배 3턴 이상, 추가 제한 4가 유지되는지 확인했다.

두 추가 조건을 삭제하고 join을 원래 값으로 바꾸며 추가 제한도 0으로 제거한 최종 BIN의 SHA-256은 `e004af95172a04dac70494a8c0c0857ff0839cf8fa0ed1d7f63c76739b1b6447`이다. 독립적으로 다시 불러와 다음을 확인했다.

- 9개의 조건 필드 모두 원래 `criteriaDefaults`와 같고 추가 턴 제한은 0이다.
- `SRWFOB02` 확장이 남아 있지 않으며 root 8·13을 포함한 모든 루트가 복원됐다.
- **SCEDATA의 52개 해제 본문 전체와 모든 루트가 승인 원본과 바이트까지 같다.**
- TSR, SCEDATA 디렉터리, 다른 51개 압축 본문은 승인 원본과 바이트까지 같다.
- 최초 출력과 최종 제거 출력은 영수증 없이 `bounded-editor-profile`로 검사됐다.

최종 전체 BIN이 승인 원본 해시와 같은 것은 아니다. 차이는 본문 27의 압축 토큰에만 있다. 원래 압축 스트림은 6668 bytes, 복원된 스트림은 6366 bytes이며 같은 10736-byte 원본문을 해제한다. 최초 출력과 최종 제거 출력 모두 raw LBA 244851~244854 네 섹터만 바뀌고 나머지 raw 섹터는 전부 동일하다. 독립 Python 구현으로 네 섹터 각각의 EDC와 두 ECC parity를 확인했다. 출력이 원래 게임 데이터·판정으로 복원됐다는 근거와 원래 압축 토큰까지 재현했다는 주장을 구분한다.

1440×1000, 390×844, 375×667, 320×568, 320×330, 740×360, 1280×400에서 총 26개 편집 화면을 캡처·측정하고 입력 오류 표시까지 검사했다. 확인한 화면에서 문서의 가로·세로 overflow, 조건 행 잘림, footer의 viewport 이탈이 없었으며 데스크톱과 모바일 세로 결과도 직접 살펴봤다. 새 `SRWFOB02`의 실제 게임 콜백 실행·게임 내 저장/이어하기 검증은 아직 별도 범위다.

## 계속 지원하지 않는 예

F 본문 28·29의 원래 승리 경로에는 `D3 FD`와 `F3`가 있다. 이 F3의 상대 변위 `FFF9`는 D3가 아닌 **원래 E9**로 돌아간다. root 8 포인터만 바꾸면 그 E9 이후의 원래 분기가 옛 집계 검사로 재개되어 새 조건을 우회할 수 있으므로 새 방식으로 허용하지 않는다. 이전 방식에서 이미 검증된 다른 본문의 유사 명령은 기존 지원 그대로 유지한다.

다른 인물 조회, 좌표 검사, 대사·증원·목적 변경이 섞인 콜백은 명령 길이·실행 분기·부작용·재개 위치를 각각 확인해야 한다. 텍스트나 명령 인수를 상대 분기로 오인할 수 있어 부정 검색 결과만으로 이 제한을 해제하지 않는다.

## 기체 종류 현재 집계 조건의 별도 형식

2026-10-10. `SRWFOB03`은 위 `SRWFOB01/02`의 숫자 조건 의미를 바꾸지 않는 별도 형식이다. 현재 구현한 새 질의는 **기체 종류의 현재 집계 수가 0이 아님 / 0임**이다. 실제 C0.0E의 대상·상태·캐시 연결 필터는 [기체 종류 수명 조사](EDITOR_ENTITY_OBJECTIVE_RESEARCH.md#기체-종류-조회의-연결값과-현재-집계-수명)에 있다. 특정 등장 개체 생존·격추 이력, 파일럿, 임의 진영, 좌표·영역 조건은 이 확장으로 허용하지 않는다. 같은 종류 다른 기체, 미출현·철수·형식 변경·합체 연결·정리 상태에 따라 결과가 달라질 수 있다.

기존 9개 정수 필드와 승리·패배별 1~3개 조건, 모두/하나라도 충족 및 우선순위를 유지한다. 여섯 rule 필드만 기존 정확한 숫자 인코딩과 새 태그의 합집합을 허용한다. 새 rule은 bit15=1, bits14..10=0, bits9..1=기체 종류 번호, bit0=존재1/부재0이다. ID0, 표 밖 번호, 예약 비트와 다른 UInt16 값은 거부한다. 종류 번호는 해당 게임과 실제 TSR root27 레코드 수를 함께 받아 검사하며 최대 F367 / 완결편447이다. 이 편집 인코딩과 VM selector `8000|ID`는 서로 다르다.

조건 컴파일러도 별도 entry point를 사용한다. `C0 0E selectorBE16` 바로 뒤에서 `F3 0`(존재) 또는 `F2 0`(부재)으로 결과 +20을 소비한다. 다른 조회가 그 값을 덮기 전에 각 조건의 분기를 실행한다. 기존 숫자 compiler의 70바이트 한도를 유지하고, 여섯 새 질의를 모두 쓰는 별도 compiler의 최대 크기는 산정한 81바이트다. 게임 목적 문구는 `${ID}번기체있음/없음`으로 만들며 기존 NFKC 18자·실제 폰트 인코딩 검사를 적용한다. 조합 문구가 넘치면 잘라서 다른 조건처럼 표시하지 않고 거부한다.

### OB03의 두 mode와 정상화

- mode0은 기존에 검증한 in-place head14·yield4 hook을 그대로 사용한다. 원래 root8 주소, 가드, 복잡한 승리·패배 사건과 그 재개 주소를 보존한다. 원 head18바이트를 trailer +54..71에 저장한다.
- mode1은 `inspectClosedObjectiveCallback`이 원래 root8 전체를 검증한 경우만 허용한다. 원본문 명령은 그대로 두고 root8·13 헤더만 옮긴다. +54..71은 0이다. 복잡한 action이 원래 집계로 재개할 수 있는 사적 wrapper는 제품 mode1로 허용하지 않는다.

형식의 80바이트 trailer는 magic `SRWFOB03`, 원문 길이 +8, 원래 root13 +12, 원래 root8 +16, mode +20, query kind +21=1, 추가 턴 제한 +34, 기존 9 UInt16 필드 +36..53을 담는다. +22..33, +35, +72..79는 모두 0이다. 새 종류 조건이 없는 OB03은 불필요한 비정규 표현이므로 거부하고, 기존 OB01/02 형식으로 생성한다. mode 선택도 원본문 검사에서 정해지며 metadata 요청으로 바꿀 수 없다.

정상화는 mode에 맞춰 원 헤더·head를 복원하고 모든 루트와 종류·필드·가드·분기·목적·metadata를 재생성해 전체 byte를 비교한다. 그 뒤 원문을 기존 승인 불변 프로파일과 대조하는 출처 흐름은 유지한다. 종류 조건을 숫자 조건으로 되돌리면 기존 OB01/02로 전환되고, 모든 조건·턴 제한을 기본값으로 제거하면 원문 전체가 복원된다. 압축 carrier 마스크나 프로파일 해시를 넓히지 않는다.

### 현재 검증 범위

집중 회귀 21개는 기존 OB01/02의 원래 action·가드·우선순위·재개 검사와 함께, 독립 명령 실행 모델의 종류 중복·연결값·상태·진영·미출현 필터, 모든 65,536개 rule wire 값의 정확한 합집합, 여섯 질의 81바이트, 두 mode·존재/부재·추가 제한0/98·원문 복원·형식 전환을 확인했다. 위조 code·header·mode·예약 byte·저장 head와 잘못된 game/table context는 거부한다.

실제 승인 SCEDATA를 읽어 F14개·완결편19개 지원 본문에서 종류65/107의 존재·부재 **총66개**를 생성·재파싱했다. 모두 exact 정상화·재편집·기존 숫자 형식 전환·기본조건 제거 후 각 원문이 byte 동일했고, `completeNearMatches` 재압축이 원래 슬롯에 들어갔다. F에는 mode0/1이 있고 완결편 19개는 mode0이다. 완결편 물리5의 제품 mode0 시험은 13462→13626바이트, 압축7685≤8067바이트, 원래 root8=3267 유지, 새 root13=13513이다. 그 시험본의 해제 SHA-256은 `84e4f320bf9f92c94138a8194935248c2305fe48e820c7fcbac3386211aa91b7`이다.

기존 사적 완결편 물리5의 **mode1** 실제 해제 출력은 제품 normalizer에서 `EDITOR_OBJECTIVE_INVALID`로 예상대로 거부됐다. 사적 query helper의 실제 실행 증거를 일반 열린 callback relocation 권한으로 사용하지 않는다.

현재 core·preset·archive 연결에 대한 독립 합성 디스크 검사도 두 게임에서 통과했다. 실제 기체 표가 14개인 입력에서 여섯 rule 필드 각각에 ID200을 요청하면 거부하고, writer 옵션의 `unitCount=512`는 검사된 표의 크기를 덮어쓰지 못한다. 편집 요청 자체의 `unitCount` 주입은 알 수 없는 필드로 거부한다. 저장 OB03는 기체 표 문맥이 없거나 0/1/2/513/NaN일 때 거부하고, 올바른 표를 얻은 새 inspector에서는 ID3 출력이 재열린다. preset은 게임별 상한으로 JSON을 먼저 검사한 뒤 적용 대상의 실제 표를 다시 검사하며, 최종 writer도 같은 표로 검사한다. 재현과 결과는 저장소 밖 `objective-coverage-ob03-context-audit.mjs/json`이다. 이는 합성 입력의 API 경계 검사이며 실제 게임 저장 복원 근거가 아니다.

위 66개 검사는 저장소 밖 `objective-coverage-ob03-actual-contract.mjs/json`이며 게임 데이터는 저장소에 포함하지 않았다. 이 절은 해제 본문·형식·슬롯 검사 근거다. **새 제품 mode0의 전체 BIN 출력, 영수증 없는 새 세션 재열기, UI/JSON 왕복, EDC/ECC, 실제 게임 조건·원래 action·게임 저장 복원은 별도 검증으로 남는다.** 사적 OB03 mode1이나 이전 숫자 조건의 native 실행 성공을 이 제품 mode0의 실행 성공으로 계산하지 않는다.
