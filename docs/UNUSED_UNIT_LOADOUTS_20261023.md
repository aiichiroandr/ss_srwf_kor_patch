로컬 웹 에디터의 새 기체 추가는 **능력치 차별화 + 독립 스마트건/리플렉터 인컴 + 제4차식 블러드 템플**을 적용한다. 아래 능력치는 설정상의 역할과 F의 ν건담·F91·빌바인을 참고해 정한 게임용 조정안이며, 삭제된 원래 F 성능표의 복구나 원작의 공식 수치가 아니다. F와 완결편에 같은 기본안을 쓴다. 무개조 기준이며 사용자가 다시 편집할 수 있다.

스마트건은 #475 메가런처를 검증된 빈 무기 레코드에 복제하고 이름·공격 2600·명중 +10·사거리 2–8·EN 30으로 분리한다. S와 Ex-S가 이 독립 스마트건을 공유한다. 리플렉터 인컴은 #474를 별도 복제하고 공격 2400·명중 +30·사거리 2–8·4발·기력 110으로 설정한다. 뉴타입 조건은 추가하지 않는다. 두 독립 무기의 나머지 속성·개조 비용 구분·음성 유형·연출은 각 원본을 재사용한다. **반사 인컴의 빔 반사 궤적은 미구현이며 기존 인컴 연출로 대체한다고 UI에 명시한다.**

두 종류를 만드는 데 빈 무기 레코드 2개를 쓴다(F 최대 31개, 완결편 최대 13개의 기존 복제 공간). 이미 사용한 슬롯은 건너뛰며 원래 무기 수치·명칭을 바꾸지 않는다. Ex-S 추가 중 두 슬롯을 확보할 수 없으면 기체나 무기를 일부만 남기지 않고 전체 계획을 거부한다. 먼저 만든 스마트건이 있으면 재사용하며 재열기 후 사용자가 바꾼 이름·수치도 유지한다. 저장 전 기체 추가를 취소하면 다른 기체가 사용하지 않는 자동 복제 무기만 함께 취소한다.

버전 0/1의 능력치·무장 구성은 유지한다. SRU1 프리셋 필드의 0x8000은 기존 버전 1, 0x4000은 새 버전 2이며 두 비트가 동시에 켜진 기록은 거부한다. 새 기록도 일반 기체 writer와 같은 수치 마스크만 쓴다. 복제·이름·기체 구성은 기존 검증·저장 경로를 함께 쓰며 출처 검증 범위를 넓히지 않는다. JSON은 복제 레코드와 슬롯 연결을 함께 내보낸다. 재열기 후 HP만 고쳐 내보낸 JSON도 독립 스마트건의 이름·수치·복제 선행 조건을 유지한다.

실제 F v0.5 / 완결편 v0.3c에서 다섯 기체 일괄 추가, 원본 무기 보존, 출력 재열기, 무변경 재저장 0B, JSON 재적용의 출력 SHA 일치를 확인했다. 실제 지속 데이터 한도는 그대로 F 401408B / 완결편 458752B다. 기본 다섯 기체 구성 후 F 원래 기체·이름 공유 틈은 **5B**, 완결편 TSR 전체 여유는 **3263B**다. 이외 기존 편집을 더하면 예산을 다시 계산하며, 부족할 때 저장을 거부한다. 각 파일의 여유를 서로 대신 쓸 수 있는 것으로 표시하지 않는다.

검증 출력 해시(F): `e12e07e476b0e12ef51791ec2eb591e46e9c601e34db64eb327bb89ac6bfd49a` / 완결편: `ef4074a9671e84945b4a4170b07ec3ac203928a547ee9af6496ead0f7dba4974`.

완결편 네이티브 전투 시연 진입점으로 MAP 병기를 제외한 **22개 기체/무장 조합**이 공격 종료까지 진행했다. 별도 BIOS·타이틀 콜드부트나 메드나펜을 사용하지 않았다. 새 랜서·S마인·기가블래스터와 스마트건·리플렉터 인컴의 실제 화면도 확인했다. 이는 MAP 실제 발사·전투 중 방패/I필드 발동·장기 자연 플레이를 모두 확인했다는 뜻은 아니다. 헤드리스 브라우저에서도 원본 BIN을 불러와 UI로 5종 추가, 능력치·새 무기명 표시와 오류 없음까지 확인했다. 추출 이미지와 임시 BIN/CUE는 무시된 로컬 build에만 둔다.

## 저장·안전 범위

- 새 목록은 1부터 연속된 독립 개조 칸을 쓴다. 탄약 무기만 1..16의 독립 잔탄 칸을 할당하고, 기체 목록의 이벤트 조건·투자 조건·미해석 상위 비트는 모두 0으로 시작한다. donor의 나중 추가 무장과 숨겨진 조건을 복제하지 않는다.
- Ex-S의 두 인컴은 무기 번호 #474를 공유하지만, 개조 칸은 4/6, 잔탄 칸은 3/4로 분리한다. 세이브 편집기에서 개조 칸 4를 4단·칸 6을 2단으로 따로 저장하고 다시 읽는 테스트를 통과했다. 게임 실행 중 소비·개조 메뉴 동작의 실기 확인을 뜻하지 않는다.
- 기존 `SRU1` 개인 편집본은 유지한다. 프리셋 번호의 상위 bit를 새 구성 버전 표식으로 쓰며, 표식이 없는 기존 구성은 donor 무장·조건을 그대로 유지한다. 새 버전은 예상 기본 슬롯 수·개조 칸·조건 bit·잔탄 칸 범위를 별도로 검사한다.
- JSON의 `construction.loadoutVersion`은 0(기존 donor 복제) / 1(새 설정 응용)을 명시한다. 이 항목이 없는 예전 JSON·worker 요청은 0으로 해석한다. 새 UI의 기체 추가는 1을 명시하며, 기존 구성의 나중 편집을 저장한 JSON은 0을 유지한다. 같은 프리셋 이름이어도 버전이 다른 기체에는 관련 수치·무장 변경을 적용하지 않는다. 적용 전 비교에서 같았더라도 실제 적용 직전에 버전을 다시 확인한다.
- 저장 전 추가를 취소한 뒤 다시 추가하면 새 제안 구성을 사용할 수 있다. 이미 저장된 기체를 자동으로 덮어쓰거나 기존 공유 무기를 전역 변경하지 않는다.
- 기체 헤더의 편집 허용 마스크는 일반 writer와 같게 유지하며, 최근 추가된 기본 격추 EXP(+19)도 같은 범위로 검증한다.

관련 검증: 5종 UI 추가·취소, JSON 적용과 BIN 동일성, 두 게임의 재열기, donor 추가 무장·조건 차단, 구버전/새버전 혼합 재열기, 잘못된 헤더·조건·잔탄 칸 거절, 공유 인컴의 독립 세이브 개조 칸. 실제 승인 BIN은 메모리에서 출력·재열기하며 원본 파일을 덮어쓰거나 새 전체 BIN을 디스크에 남기지 않는다.

2026-10-23 결과: construction/restoration/preset-export 관련 **23개 테스트 통과**. 버전 없는 예전 JSON은 두 게임에서 donor 무장·조건을 재현하고, 명시적인 버전 0 구성과 출력 BIN 바이트가 같음을 확인했다. 버전이 다른 같은 프리셋과 비교 이후 바뀐 구성의 종속 편집은 차단했다. 실제 F v0.5c는 #348/349/350/351/354, 완결편 v0.3a는 #430..434에 5종을 한 번에 구성했다. 양쪽 모두 메모리 출력의 표준 `bounded-editor-profile` 재열기에 성공했고, 위 무기 번호·그래픽·새 구성 표식·조건 없는 슬롯·탄약 칸이 일치했다. 게임 실행·개조 메뉴·공격 연출을 이 결과로 검증했다고 표현하지 않는다.
