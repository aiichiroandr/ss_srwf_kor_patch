# 카트리지 세이브 에디터

2026-10-25 출력 보강: 기존 payload 체크섬·블록 체인·재파싱 검사를 통과한 후, 전달할 gzip 결과를 실제로 다시 풀어 압축 전 컨테이너 전체와 비교한다. 짝홀 배치 및 미편집 패딩도 포함한다. 포인터 이설이나 저장 블록 확장 기능을 새로 넣은 변경은 아니다.

같은 날 실제 ROM·세이브 복합 편집에서, 화면의 이름 조회가 전체 저장 목록을 반복 해석해 대량 조작이 수분 동안 느려지는 문제를 확인했다. 이제 원본 또는 편집이 확정된 불변 payload의 모델을 재사용한다. 수정 중인 임시 버퍼는 캐시에 넣지 않으며, 새 편집·복원·글리프 맵 교체는 각각 올바른 스냅샷을 반환한다. 실제 완결편 세이브 3슬롯의 이름·기체 추가·개조·파츠·레벨 등 UI 조작 495회를 수정 후 37.1초에 완료했고, 수정 전 출력과 전체 바이트가 동일했다. 별도로 F 36슬롯·완결편 56슬롯의 82,226회 편집을 각각 한 번에 출력·재열기하고 gzip/인터리브·전체 복원을 확인했다. 로컬 증거는 `build/editor-batch-qa/`에 보관한다.

ROM 에디터에서 아직 저장하지 않은 미사용 기체 구성은 세이브 추가 목록에서 제외한다. 먼저 해당 ROM을 저장하고 다시 열어 실제 레코드를 확인한 뒤, 같은 세이브를 이어 편집할 수 있다. 이번 검수에서도 S건담·Ex-S건담·서바인·즈와우스·블러드 템플을 이 경로로 추가했다.

ROM 검증을 마친 뒤 **F/F완결편 롬에딧 열기** 아래의 **세이브 에디터 열기**에서 백업 RAM 전체 파일을 열고 저장 슬롯을 선택한다. 검증한 ROM과 같은 게임의 저장 슬롯만 표시한다. 파일은 브라우저 메모리에서만 처리하며 업로드하지 않는다. 수정본은 원래 이름에 `-edited`를 붙여 다운로드한다. 에뮬레이터를 종료하고 기존 파일을 백업한 다음, 수정본의 이름을 원래 이름으로 바꾸어 적용한다. 스테이트를 불러오면 편집 전 메모리로 돌아갈 수 있으므로 게임의 일반 불러오기를 사용한다.

## 지원 범위

- Ymir의 raw 백업 RAM, FF/데이터 교대 인터리브, Mednafen/RetroArch Beetle Saturn의 raw 또는 gzip 백업 RAM. 포장 형식과 크기를 유지한다.
- 32 KiB 내장 메모리, 512 KiB / 1 MiB / 2 MiB / 4 MiB 백업 RAM. 블록 크기는 각각 64 / 512 / 512 / 512 / 1024 바이트.
- 이름이 `SROBOT_F_XX` 또는 `SROBOTFC_XX`인 **0x1600 바이트 일반 저장**의 자금, 파일럿 레벨, 다음 레벨까지 EXP, 기체 5종 개조, 무기별 개조, 장착 파츠.
- 검증한 ROM의 모든 기체 레코드에서 선택·검색해 추가한다(빈 ID 0, 이미 보유한 ID 제외). 별도 형태·적 기체·미사용 레코드도 선택할 수 있다. 단쿠가(유형6), 콤바트라V(유형8), 슈퍼건담 계열(유형9), 겟타 계열(유형4)은 필요한 구성 기체를 함께 추가하고 저장 칸 링크를 만든다. 기존 구성 기체가 있으면 재사용한다. 링크를 포함한 전체 추가에 공간이 부족하면 아무것도 쓰지 않는다. 새 기체는 원칙적으로 미탑승·무개조·파츠 없음, ROM 기본 HP/EN이며 기존 구성 기체의 탑승 정보를 합체 본체에 연결할 수 있다. 선택 가능하다는 것이 해당 적/미사용 기체의 아군 운용·탑승·변형 이벤트까지 검증했다는 뜻은 아니다.
- 제4차 연동 직후에도 BIN 저장·재열기 없이 추가 기체를 세이브에 넣을 수 있다. 세이브를 열기 전에 현재 편집 요청으로 메모리상의 BIN을 만들고, 같은 기반의 검사기로 다시 읽어 얻은 기체 표를 사용한다. 이 검사는 편집 중인 ROM 세션을 바꾸지 않으며, 완료한 출력과 표는 같은 요청의 BIN 저장에서 재사용한다. 세이브 다운로드 직전에도 현재 출력 표를 확인한다. 세이브에 새로 넣은 기체의 식별·복구 프리셋·변형 구조가 이후 ROM 편집에서 없어지거나 바뀌면 다운로드를 거부하고 변경 내용은 남긴다. 추가 기체를 사용하려면 그 편집 상태의 BIN/CUE와 수정 세이브를 함께 저장해야 한다.
- 기체 삭제·교체, 파일럿 추가, 스테이트, BUP 단일 저장 내보내기, 0x3150 중단 저장 편집은 지원하지 않는다.
- 장착 파츠는 ROM의 장착 가능 칸(1~4칸)에만 쓴다. 미장착 파츠 재고는 변경하지 않는다.
- 기본 개조 상한은 F 5단, 완결편은 저장된 해금 비트에 따라 5/10단이다. 완결편의 ‘69화 이전에도 10단 개조 해금’을 선택하면 해당 저장의 해금 비트도 설정한다. 선택만으로 모든 기체를 10단으로 바꾸지는 않는다. ‘불러온 해금 상태 유지’는 원본의 해금 비트만 복원하며 이미 편집한 단수는 낮추지 않는다. 전체 처음 값은 추가 기체까지 모두 복원한다. 기존 상한 초과 값은 열기만으로 잘라내지 않는다.
- 같은 게임의 ROM 에디터가 열려 있으면 해당 세션의 이름을 사용한다. ROM이 없거나 게임이 다르면 ID를 표시한다. 저장 칸 번호와 파일럿/기체 ID를 구분한다.
- 여러 저장을 편집할 수 있으며 변경 목록과 전체 복원을 제공한다. 레벨 편집은 레벨 바이트만 바꾼다. EXP, 기존 성장 관련 데이터, 격추 수 등을 자동으로 재계산하지 않는다.
- **이름·자금·개조 → 이름·애칭:** 주인공 풀네임·주인공 애칭·애인 풀네임·애인 애칭을 각각 독립적으로 편집한다. 풀네임은 종료 문자 포함 14바이트, 애칭은 6바이트다. **기체 이름**은 완결편에서 주인공 기체 한 형태 또는 세 형태를 각각 편집하며, 형태별 본문 10바이트이며 종료 문자는 ROM 이름 칸에 따로 있다. 빈 기체명은 게임의 기본 이름을 사용한다. 다른 보유 기체의 공통 ROM 이름을 바꾸는 기능은 아니다.
- 현재 글자표에 없는 현대 한글은 기존 추가 글리프 경로로 연결한다. 추가 글리프를 사용하면 세이브와 수정 ROM을 함께 저장해야 한다. 칸의 바이트 한도를 확장하지 않는다. 기존 기본 이름이 짧은 네이티브 코드에서 긴 한글로 표시되는 경우, 표시된 값을 그대로 두면 원래 코드를 보존한다.

기존 패널, 목록, 검색, 입력, 변경 내역 스타일을 사용한다. 레이아웃은 `assets/editor-runtime.css`에서 관리한다.

## 바이트 계약과 근거

Saturn 컨테이너: `BackUpRam Format` 서명. 레코드 시작 블록 표식 `80 00 00 00`. 블록 기준 +4 이름 11바이트, +0x1A 날짜 BE32, +0x1E 길이 BE32, +0x22부터 BE16 블록 목록(0 종료). 후속 블록은 +4부터 이어진다. 블록 리스트 자체가 다음 블록으로 넘어가는 경우도 지원한다. 모든 활성 레코드의 체인을 검사하여 중첩, 순환, 예약 블록 참조, 범위 초과를 거부한다. 서명은 기존 Mednafen 파일 호환을 위해 첫 64바이트 반복을 검사한다.

출처: [Ymir backup_ram.cpp](https://github.com/ymir-emu/Ymir/blob/8cdf0a530ec1927f44bf3cd02c6ab51a586c4407/libs/ymir-core/src/ymir/sys/backup_ram.cpp)의 `kSizes`, `kBlockSizes`, `ReadBlockList`, `BuildFile`, `CheckInterleaved`; [Beetle Saturn backup.c](https://github.com/libretro/beetle-saturn-libretro/blob/d0d841784845da0278a9a49554cc4cc01597ee2c/mednafen/ss/cart/backup.c)의 `GetNVInfo`, `CART_Backup_Init`. 게임 필드 근거는 로컬 F/FIN 정적 분석과 기존 검증된 백업 RAM 파서를 재사용했다.

0x1600 일반 게임 저장 기준:

| 필드 | 오프셋 | 형식 |
|---|---:|---|
| 체크섬 | 0 | BE32, `[4, 0x15FC)` 바이트 합 |
| 자금 | 0x0A | BE24 |
| 기체 목록 | 0x100 | 128칸 × 30바이트, 앞 BE16 ID |
| 파일럿 목록 | 0x1000 | 128칸 × 12바이트 |
| 파일럿 ID | 칸 +0 | BE16, 0은 빈 칸 |
| 파일럿 레벨 | 칸 +2 | u8 |
| 다음 레벨까지 EXP | 칸 +4 | BE16 |
| 주인공 풀네임 / 애칭 | 0x3C / 0x4A | 14 / 6바이트 게임 문자열 |
| 애인 풀네임 / 애칭 | 0x50 / 0x5E | 14 / 6바이트 게임 문자열 |
| 완결편 주인공 기체명 | 0x64 / 0x6E / 0x78 | 형태별 본문 10바이트; ROM +10의 FF가 종료 문자 |

FIN 원본 EXEC SHA-256 `b0d2c1b597ebd4d792383a0f9708fc79a360d41c18e1c731665c31c3acbdb3ac`. SH-2 `0x0602DAF0..0x0602DB50`은 128칸/12바이트, +2 레벨/+4 EXP 접근을 확인한다. `0x0602D7B4` 생성 루틴에서 +2에는 전달받은 레벨을, +4에는 TSR root30의 레벨별 EXP를 쓴다. `0x06034588`의 로드는 0x1500바이트 단위/파일럿 영역을 복사한다. 자금 BE24는 `0x06035B3E..0x06035B62`에서 복원한다. F·FIN 실제 카트리지 레코드에서도 크기, 체크섬, ID/레벨/EXP 구조를 대조했다. 세이브 에딧 후 게임 내 성장·인계 전체 흐름의 검증을 뜻하지 않는다.

체크섬이 틀린 저장은 읽기 전용이다. 출력은 원본 복사본의 지정 필드와 해당 체크섬만 변경하며, 다시 컨테이너를 파싱하여 모든 저장의 페이로드를 대조한다. 무변경 출력은 gzip 헤더까지 포함하여 입력과 완전히 같다. 수정 시 gzip 압축 표현은 달라질 수 있으나 해제한 다른 저장·헤더·빈 공간은 보존한다.

### 이름 저장·복원 계약과 확인 (2026-10-25)

FIN `06035CC0..06035D6C`는 payload +0x34부터 인물 선택/이름 48바이트와 +0x64부터 기체명 3×10바이트를 복원한다. 런타임 프로필의 풀네임/애칭은 +0x4DC/+0x4EA 및 +0x4F0/+0x4FE다. `06036018..0603617E`는 이 문자열을 root12/root13의 주인공 #303·애인 #302 이름에 복원한다. F의 대응 저장 복원 `06031710..060317A0`와 이름표 복원 `06031A10..06031BEA`에서도 같은 인물 이름 경계다.

완결편 `0603622A..060363A2`는 프로필 +0x4D6의 bit0(저장 +0x36)을 검사해 0이면 기체 #0xDD 한 이름, 1이면 #0xDE/#0xDF/#0xE0의 세 이름을 복원한다. 기체명 프로필 주소 +0x504/+0x50E/+0x518이 저장 +0x64/+0x6E/+0x78에 대응한다. 다른 진행 플래그로 형태 수를 추정하지 않는다. F에서는 기체명 쓰기를 거부한다. 기체명 전체가 기본값이면 저장의 이름 묶음을 0으로 둔다. 한 형태만 바꿀 때는 나머지 형태의 기본 이름 본문을 검증한 ROM에서 가져와 함께 기록한다. 첫 형태가 비어 있으면 게임이 모든 형태의 이름 복원을 건너뛰며, 복원 시에는 세 이름을 모두 복사하기 때문이다. 기본 이름은 별도의 +10 종료 FF가 있는 11바이트 ROM 이름 칸에서만 가져오며, 구조가 다르면 쓰기를 거부한다. 이름 본문은 10바이트(한글 5글자)까지 쓸 수 있고, 기체 수치·진행 플래그는 바꾸지 않는다.

F 원본 EXEC의 두 구간(144·474바이트)과 실제 승인 완결편 v0.3a EXEC의 두 구간(172·944바이트)이 기존 정적 역어셈블 결과와 바이트 단위로 같음을 확인했다. Final 기본 애칭은 저장된 얼굴과 정확한 6바이트 지문으로 판독하며, 원래 00/FF 패딩과 기존 한글 애칭을 구분한다. 근거의 코드 구간 해시는 로컬 `build/save-name-qa/static-contract.json`에 기록한다.

실제 F 36슬롯·완결편 56슬롯의 이름 424항목을 메모리 복사본에서 편집 → 출력 → 재파싱했다. 체크섬·파일럿/기체·개조/파츠·인물 선택·진행도·일시를 보존하고, 전체 복원 결과는 입력과 같으며 원본 파일도 그대로다. 이 실제 완결편 파일의 형태 수는 모두 한 형태다. 세 형태의 독립 편집·비활성 칸 쓰기 거부는 정적 분기와 합성 저장 검사로 확인했다.

백그라운드 브라우저에서는 제품의 실제 ROM 검증 후 56슬롯 파일을 열고 네 인물 이름과 기체명을 편집한 다운로드를 다시 읽었다. 1440×900·430×932·375×667에서 각 입력칸이 보이고 문서 넘침이 없으며, 애칭 길이 초과의 저장 차단과 탭 이동 시 오류 유지, 추가 글리프 애칭의 재열기, 전체 복원을 확인했다. 콜드부트·게임 로드·새 ROM 출력은 하지 않았다. 로컬 근거는 `build/save-name-qa/`다.

## 검증

`node --test tests/save-core.test.mjs`는 분산된 블록, 블록 목록의 경계 통과, 다른 게임 보존, 체크섬, 복원, malformed 입력 거부, gzip 중첩, 인터리브, 각 크기 및 출력 재파싱을 검사한다. 합성 저장만 저장소에 포함한다.

## 기체 및 개조 해금 정적 근거 (2026-10-22)

단위는 저장 페이로드 오프셋이다. 기체 행의 시작은 `0x100 + slot*30`이다.

| 필드 | 행 상대 위치 | 인코딩 |
|---|---|---|
| HP 개조 | +3/+4 | `(BE16(+3) >> 7) & 15` |
| EN 개조 | +4 | `(byte >> 3) & 15` |
| 장갑 개조 | +4/+5 | `(BE16(+4) >> 7) & 15` |
| 한계 개조 | +5 | `(byte >> 3) & 15` |
| 운동성 개조 | +5/+6 | `(BE16(+5) >> 7) & 15` |
| 무기 개조 | +7..14 | 16칸, 짝수 인덱스 상위 nibble / 홀수 하위 nibble |
| 장착 파츠 | +17..20 | ID 0 없음, 1..22 파츠 |

FIN `0602FC34..0602FD68`가 저장 행을 작업 구조체로 풀고, `0602FD7A`, `0602FE06`, `0602FE70`, `0602FEDA`, `06030128`에서 각각 한계/장갑/HP/운동성/EN 개조 단수를 읽어 누적한다. F의 대응 unpack 구간 `0602BEF8`부터 324바이트는 동일하다. F 원본 EXEC SHA-256은 `a7e9a648641d728dcf6f60a778d6a1e5ccfebc77c92a0d3fd64cbcd5f19db409`.

무기 슬롯은 FIN `060319B0..060319BA`, F `0602DBC8..0602DBD2`에서 ROM 무기 목록의 첫 BE16을 11비트 우측 이동하고 15로 마스킹한다. FIN `06031F68` / F `0602E0DC`의 동일한 함수가 작업 구조체 +6부터 nibble을 읽는다. 저장 행 +7부터 이 영역으로 복사된다. ROM에서 알려진 무기 슬롯만 편집한다.

파츠 수는 ROM 기체 +25의 bits 4..5에 1을 더한 값이다(FIN `06030432..0603044A`, F `0602C798..0602C7B0`). FIN `06030498..060304AE` / F `0602C7FC..0602C812`가 저장 행 +17+칸에서 파츠를 읽고 효과 함수로 넘긴다. FIN `0603059C..06030688`은 0..22 파츠 ID별 효과를 적용한다.

완결편 해금은 페이로드 `0x9C`의 `0x08` 비트다. 로드 `06035DD2..06035DEA`가 payload +0x94부터 64바이트를 low RAM +0x534에 복원하므로 +0x9C가 +0x53C에 대응한다. 메뉴 `0607CFEC..0607D026`이 +0x53C의 0x08 비트로 두 개조 상한을 5/10으로 정한다. 표시 화수나 내부 시나리오 번호를 추정해 판정하지 않는다. 편집 시 해당 비트와 체크섬만 바꾸며 나머지 진행 정보는 보존한다. 이 비트의 모든 사용처나 실제 게임 화면을 검증했다는 뜻은 아니다.

기체 추가는 FIN `06031040` / F 대응 `0602D288`의 기본 행 초기화를 참고한다. 빈 행 30바이트를 초기화하고 ID, 아군 상태 +2=0x40, 미탑승 +15=0xFF, 연결 없음 +16=0xFF, 파츠/개조 0, +26=0xFF, HP +22/EN +24를 쓴다. 실제 기존 F 세이브의 일반 아군 행과도 대조했다. FIN `060325C4`의 ROM +7 분기에 따라 유형6은 본체 다음 4개 3형태 묶음에서 한 형태씩, 유형8은 다음 5개 구성 기체, 유형9는 ID2/3/4의 연결을 만든다. 유형4는 3개 형태를 기본 형태 저장 칸에 연결한다. 해당 저장 칸 번호를 +16에 쓰며, 기존 기체의 링크 변경도 diff에 표시한다. 생성·추가 후 이벤트 정리, 변형·합체·탑승·게임 화면의 동작은 사용자 실행 검증 대상이다.

합성 데이터로 기체 추가, 비트 보존, 개조 단수 전 범위, 무기 nibble, 파츠, 조기 해금, 복원, 출력 재파싱을 검사한다. ROM·실제 세이브는 저장소에 포함하지 않는다.

## 저장 슬롯 정보와 선택 UX

선택한 저장의 클리어 화수·시나리오 제목·주인공 이름·저장 일시를 상단 요약에 표시한다. 슬롯 선택 항목과 접을 수 있는 카드 목록에도 진행도·이름·일시를 표시한다. 기본 파일명을 식별 보조 정보로 유지한다.

- 클리어 화수는 payload +5의 값에서 1을 뺀 값. FIN `06071F80..06071F8E`, F `0606B5AC`의 동일 코드가 이를 화면에 넘긴다. 0은 미확인으로 표시한다. 내부 다음 시나리오 번호(payload +6)를 화수로 사용하지 않는다.
- 완료 제목은 payload +7을 사용자 ROM의 TSR root22 제목 인덱스로 읽는다. FIN `06071F90..06071FAE`가 직접 root22를 참조한다. 경로별 화수를 제목 번호에서 추정하지 않는다.
- 주인공 이름은 payload +0x3C의 14바이트 게임 문자열. FIN 로드 `06035CE2..06035D28`가 payload +0x34를 low RAM +0x4D4로 옮기며, `06036040..060360A4`가 +0x4DC의 이름을 파일럿303 이름표에 복원한다. 실제 F 클리어 저장에서도 이름을 대조했다. 문자 경계의 FF 종료와 EB..F5 두 바이트 문자를 처리한다. 불명 문자는 해독 불가로 표시하며 ROM의 기본 이름으로 덮어 추정하지 않는다.
- 저장 일시는 파일 시스템 수정일이 아닌 백업 RAM 레코드의 날짜다. [Ymir BackupFileHeader](https://github.com/ymir-emu/Ymir/blob/8cdf0a530ec1927f44bf3cd02c6ab51a586c4407/libs/ymir-core/include/ymir/sys/backup_ram_defs.hpp)는 1980-01-01부터의 분으로 정의한다. 시간대 정보가 없으므로 브라우저 현지 시각으로 변환하지 않고 ‘게임기 시계 기준’을 명시한다. 0 또는 범위 밖 날짜는 미기록/확인 불가로 표시한다. 편집·내보내기는 이 메타데이터를 변경하지 않는다.

## 실제 데이터 기준 UI 개선 (2026-10-22)

실제 완결편 카트리지의 일반 저장 56개를 읽고, 56개 모두 주인공 이름을 해독했다. 완결편 주인공 이름은 일반 명칭표가 아닌 `FINAL_PILOT_NAME_MAP`을 사용한다. 실제 슬롯 36은 69화 클리어 / 사상누각 / 미나 라이클링 / 게임기 시계 2026-08-28 09:24이며, 파일럿 73명·기체 70기다. 입력 세이브는 저장소 밖에 보관하며 원본과 작업용 복사본의 전체 SHA-256이 같음을 확인했다. 실제 사용자 파일의 경로나 바이너리를 사이트 코드에 넣지 않는다.

- 파일럿 / 보유 기체 / 자금·개조 해금 탭으로 편집 대상을 나눈다.
- 기체 상세는 기체 개조 / 무기 개조 / 장착 파츠로 묶는다. 기체 추가는 펼쳐서 사용한다.
- 슬롯 선택은 제목·화수·이름 검색과 슬롯순 / 최근 저장순 / 진행순 정렬을 제공한다.
- 데스크톱은 목록·상세를 나란히, 모바일은 목록→상세→목록 전환으로 표시한다. 저장 버튼은 하단 고정 영역에 둔다.
- 목록의 탑승 파일럿과 주인공 이름은 현재 저장을 기준으로 표시한다. ROM의 기본 주인공 이름을 그대로 쓰지 않는다.

승인 v0.3 a ROM의 전체 해시 검증 후 실제 세이브를 브라우저에 열어 데스크톱 및 iPhone 16(393×852) 배치를 확인했다. 실제 세이브의 값을 바꾸거나 게임을 실행한 검증은 아니다.

## 개조 칸·그림·입력 검증 (2026-10-22)

기체의 HP/EN/장갑/운동성/한계 및 무기 개조는 10칸의 막대로 표시한다. 저장의 현재 한도가 5단이면 뒤 5칸은 잠금 무늬로 표시하며, 한도 밖의 클릭은 쓰지 않는다. 칸 클릭, ±, 방향키, Home(0단), End(현재 한도)를 지원한다. 이미 한도를 넘은 원본 값은 경고 색으로 보존한다. 기체 상세는 기체 개조/무기 개조/강화 파츠 탭으로 나눈다.

검증한 ROM 세션의 기존 C_ROBOT/FACE 미리보기 경로를 재사용하여 기체 그림과 탑승 파일럿 초상화를 표시한다. 파일럿 탭에서는 해당 파일럿이 탄 기체를 함께 표시한다. 미탑승은 빈 상태로 표시하며 주인공은 아래에 확인한 저장의 얼굴 번호를 사용한다. 추출한 그림은 저장소에 포함하지 않는다.

### 파일럿 목록과 저장된 주인공 얼굴 (2026-10-23)

파일럿 목록의 기존 52px 행 안에 32px 초상화를 넣는다. 현재 페이지의 얼굴만 요청하고 상세와 같은 세션 캐시를 사용한다. 페이지나 ROM 세션이 바뀐 뒤 도착한 이전 응답은 버린다. 목록 높이·페이지 수를 초상화 때문에 늘리지 않는다.

일반 저장의 주인공 #303 얼굴은 `BE16(payload +0x34) >>> 7`, 슬롯 #302 얼굴은 `BE16(payload +0x38) >>> 7`이다. 두 필드는 읽기 전용이다. FIN `0602AE24..0602AE72` / F `06027CD8..06027D26`가 복원된 선택 정보 +0x4D4를 7비트 우측 이동해 #303 머리부의 9비트 FACE 번호에 쓴다. #302는 FIN `0602ADA4..0602ADF2` / F `06027C58..06027CA6`가 +0x4D8을 같은 방식으로 읽는다. 0·게임별 FACE 범위 밖 값은 표시하지 않으며 ROM의 자리표시 얼굴이나 이름 검색 결과로 대체하지 않는다.

#303 이름은 기존 +0x3C의 14바이트, #302 이름은 +0x50의 14바이트를 같은 문자열 디코더로 읽는다. 이름이 미기록이거나 문자 경계를 해독할 수 없으면 일반 슬롯명으로 표시한다. 실제 완결편 BCR의 슬롯 01·36에서 #303 얼굴 317을 읽어 미나 초상화 표시를 확인했다. 이 연결은 이름·얼굴 선택을 편집하는 기능이 아니다. 관련 코어·워커·세이브 UI·주인공 원본 테스트 77개가 통과했으며, 375×667에서도 목록 52px와 창 내부 무스크롤 배치를 확인했다. 실제 게임 실행 검증은 하지 않았다.

레벨 1~99, 자금 0~9,999,999, EXP 0~65535 범위의 정수만 쓴다. 자금은 게임이 불러오기 목록에 7자리 칸으로 그리며 10,000,000 이상이면 그 화면에서 멈춘다(2026-11-04 실측, 게임도 격추 자금을 더할 때 9,999,999로 묶는다: 완결편 0x06053E6C). 바꾸는 값만 이 범위에 묶고, 이미 저장에 들어 있던 값은 그대로 둘 수 있다. 세이브 검사는 9,999,999를 넘는 자금을 오류로 보이고 정리 버튼이 9,999,999로 낮춘다. EXP 범위는 저장 필드의 표현 범위이며 게임 성장 규칙 전체를 검증했다는 뜻은 아니다. 개조 한도, 실제 무기 연결 칸, ROM의 파츠 장착 칸과 파츠 ID도 쓰기 단계에서 확인한다. 잘못된 숫자는 해당 항목 옆에 오류를 표시하고 수정본 저장을 막는다. 탭이나 슬롯을 옮겨도 오류 입력을 기억하며 수정 또는 변경 취소로 해제한다.

원본 FIN 디스크의 기체 그림에서 능력치 목록에 연결되지 않은 이미지 13개를 별도로 추출해 확인했다. 시각상 S건담은 C_ROBOT 이미지 305, Ex-S건담은 306, 서바인은 308, 즈와우스는 309에 해당한다. **이 번호는 저장에 넣는 기체 ID가 아니다.** 현재 파싱된 기체 이름·능력치 레코드에서는 대응 ID를 확인하지 못했으므로 이 네 기체의 추가 지원을 주장하지 않는다. 샤아의 다른 버전 초상화 역시 기체 추가와 별개다. 그래픽만 있는 더미를 운용하려면 ROM 쪽의 기체·무기 정의를 구성하고 연결하는 별도 작업이 필요하다. 일반/미사용 기체 레코드 전체 목록과 빈·미완성 레코드 전용 필터는 제공한다.

`tests/save-upgrade-bar.test.mjs`는 5단/10단에서의 클릭·키보드, 잠긴 값 쓰기 거부, 읽기 전용, 기존 초과 값 보존, 숫자 범위 검증을 확인한다. save-core/save-metadata/editor-ui-modes와 함께 실행한 관련 테스트 37개가 통과했다. frontend-contract/editor-worker 통합 회귀 테스트 107개도 통과했다. 실제 512 KiB/56슬롯 카트리지를 브라우저에 열어 그림 표시, 숫자 오류 표시, 탭 전환 후 오류 유지와 다운로드 차단을 확인했다. 실제 슬롯 36의 풀아머백식개(저장 칸 6) HP 개조 6단 및 빔라이플 개조 7단을 브라우저에서 지정하고 다운로드한 결과가 두 항목만 편집한 예상 출력 바이트와 완전히 일치했다. 56개 저장을 재파싱했으며 원본 SHA-256도 유지했다. 모바일도 본문을 페이지로 나누며 헤더/저장 버튼을 고정한다. 게임 실행은 하지 않았다.

데스크톱(901px 이상)은 창 바깥 여백을 줄이고, 기체 그림/초상화를 228px 묶음으로 제한해 기체명·상세 탭 옆에 배치한다. 개조는 항목명/단계 칸/현재 단수를 한 줄에 표시한다. 저장 정보와 슬롯 탐색, 데이터 탭과 기체 추가는 각각 같은 행을 사용한다. 상세 영역과 목록은 페이지로 넘기며 변경 내역은 저장 버튼 위에 펼친다. 모바일 배치는 별도 미디어 규칙을 유지한다.

## 스크롤 없는 페이지 탐색 (2026-10-22)

세로로 항목을 찾아 내려가는 편집 흐름을 페이지 탐색으로 대체했다. 파일럿/기체 목록, 저장 슬롯 카드, 개조/무기/파츠, 변경 내역에 이전·다음 버튼과 페이지 번호를 제공한다. 목록과 슬롯은 표시 공간에 맞춰 개수를 계산하고, 상세 항목은 실제 렌더링 높이로 페이지를 나눈다. ResizeObserver로 화면 크기가 바뀔 때 다시 나누며, 원본 ID·선택 기체·편집값은 페이지와 분리하여 유지한다. 기체 추가를 열면 목록 대신 추가 화면을 표시한다. 스크롤바만 감추고 항목을 남겨 두는 방식이 아니며 모든 항목을 페이지로 접근할 수 있다.

`tests/save-pages.test.mjs`는 페이지 경계/필터 후 보정/가변 높이/좁은 화면에서 항목 보존을 확인한다. `tests/save-ui-pages.test.mjs`는 선택 유지, 무기 개조값의 페이지 왕복 유지, 탭 전환 후 입력 오류의 저장 차단, 전체 복원을 확인한다. save-core/save-metadata/save-upgrade-bar/editor-ui-modes와 합계 41개, frontend-contract 87개가 통과했다.

자금과 개조 해금은 각각 하위 탭으로 나누어 짧은 화면에서도 두 패널을 세로로 이어서 찾지 않도록 했다. 모바일 높이 740px 이하는 파일/저장 선택 행과 기체 그림 높이를 줄이고, 주인공·화수·저장 시점은 계속 표시한다.

실제 56슬롯 카트리지로 데스크톱 일반 배율과 iPhone SE 375×667을 확인했다. 데스크톱에서 목록 다음 페이지로 이동해도 빌바인 선택이 유지되며, 7개 무기도 두 페이지로 모두 접근했다. 저장 슬롯 카드는 표시 영역에 맞춰 8개씩 7페이지로 나눴다. 375×667에서는 개조 5종을 한 항목씩 5페이지로 표시하고 마지막 한계 개조까지 스크롤 없이 이동했다. 실제 세이브 SHA-256은 유지했다.

## 강화파츠 장착 한도: 검토만 수행 (2026-10-22)

사용자 지시에 따라 한도 확장 기능은 구현하지 않았다. ROM 기체 +25의 bits 4..5는 0..3이며 실제 장착 수는 +1한 1..4다. 세이브의 30바이트 기체 행에는 +17..+20 네 개 파츠 ID가 있다. FIN 원본 `06030432..0603044A`가 ROM에서 얻은 수를 작업 구조체에 설정하고 `06030498..060304C8`이 그 수까지만 저장 행의 파츠를 읽어 효과 함수에 전달한다. 따라서 원래 1~3칸인 기체에 세이브의 남는 칸만 채워도 해당 루틴의 적용 수는 늘지 않는다. 기본 구조의 장착 최댓값은 4칸이며 5칸 이상은 저장 구조/게임 코드의 별도 확장 문제다.

승인 FIN v0.3 a 디스크의 실행 파일 `/0`에서 `06030432..0603044E`, `06030498..060304CA` 바이트가 원본 EXEC와 동일함을 확인했다. 세이브 에디터는 기존 ROM 장착 한도 검증을 유지한다. 이는 파츠 보유 재고 수량의 최댓값을 뜻하지 않는다. 재고 수량 상한은 이번 결론에서 확정하지 않았다.

## 창 축소 시 배치 격리

세이브 창 루트에서 ROM 에디터 전용 `editor-data-panel` 클래스를 제거했다. 이 클래스의 중간 너비/낮은 높이용 grid 규칙 때문에 세이브 창 헤더가 왼쪽 열로 배치되던 오류였다. 세이브 전용 테마 변수와 flex 루트를 사용하며, 목록의 `editor-panel-body` 공용 배치 클래스도 제거했다. 짧은 데스크톱 창에서는 그림·이름 영역 높이를 줄여 레벨/EXP 입력과 안내가 잘리지 않도록 했다.

반응형 확인: 사용자와 같은 약 967×570 창, 약 793×570 중간 너비, 약 693×570 경계 아래 너비에서 실제 세이브를 열었다. 좁은 영역은 목록/상세 전환을 사용하고, 저장 정보는 한 행이 전체 너비를 점유하지 않도록 세로 정보 묶음으로 정리했다. 파일럿 상세는 기체 탭/페이지 행을 예약하지 않아 입력·안내 영역을 확보한다. 이 수정은 파츠 슬롯 확장 기능을 추가하지 않는다.
