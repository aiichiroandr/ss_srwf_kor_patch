# F / F완결편 에디터: 조사와 막힘 대응

이 문서는 2026-09-23 작업 로그에서 실제로 발생한 반복을 줄이기 위한 지침이다. 모델의 성능을 보장하는 프롬프트가 아니다. Luna 계열은 에디터 작업 시작 전과 막혔을 때 반드시 읽는다. 다른 모델도 같은 절차를 권장한다.

## 먼저 지킬 완료 단위

기존 구현을 재사용한다. 한 항목은 **원본 데이터 읽기 → 실제 명칭/레코드 연결 → UI 표시 → 입력 유지 → diff → reset → 출력 재파싱**까지 이어져야 완료다. 캡처만 얻었다고 데이터 쓰기까지 검증됐다고 하지 않는다. 배포는 별도 요청 사항이다.

- `assets/editor-core.mjs`: 디스크/TSR 파싱, 레코드와 쓰기.
- `assets/editor-worker.mjs`: 브라우저 작업 전달.
- `assets/app.mjs`: 선택/입력/이미지/diff/reset/output.
- `assets/editor-runtime.css`: 게임 화면 내부 배치의 단일 수정 위치. `style.css` 끝에 보정 규칙을 계속 추가하지 않는다.
- `docs/LOCAL_EDITOR.md`, `tests/editor-core.test.mjs`: 현재 동작과 회귀 근거. 문서와 구현이 다르면 실제 코드를 확인한다.
- `manifest/releases.json`: 승인 이미지 식별 기준. 검사 통과를 위해 검증 완료 플래그를 조작하지 않는다.

## 오늘 로그에서 확인한 낭비와 대체 방법

2026-09-23 작업 로그에서 관찰한 사례다. 여러 모델/인용문이 섞여 있으므로 전체 호출 수를 특정 모델의 성과로 집계하지 않는다.

## 역공학: 한 번에 하나의 검증 가능한 질문

1. 찾는 값/레코드/게임 버전을 한 문장으로 적는다. 예: ‘한 파일럿의 베어내기 명칭과 습득 레벨은 어떤 포인터에서 읽는가?’
2. 기존 해석기·TSRViewer·분석 스크립트에서 같은 용어/offset을 찾는다. 새 추측 파서를 먼저 만들지 않는다.
3. 원본 바이트 주소, endian, 길이, 참조 기준, 종료 조건을 함께 기록한다. **디스크 raw offset / ISO logical offset / 압축 해제 TSR offset / 런타임 RAM 주소**를 섞지 않는다.
4. 이름이 다른 레코드 2개 이상에서 검증한다. F에서 성공해도 F완결편에 동일 offset을 가정하지 않는다.
5. 쓰기는 구조/길이 보존과 재파싱까지 확인한다. 모르는 byte는 그대로 보존한다. 모르는 필드 이름을 임의의 게임 효과로 단정하지 않는다.
6. 두 번 같은 시도가 실패하거나 10분간 새 근거가 없으면 멈추고 ‘가설 / 관찰 / 반증 / 다음 최소 probe’를 네 줄로 적는다. 검색 범위를 넓히기 전에 기존 자산 위치와 좌표계를 재확인한다. 다른 확정 항목은 계속 구현한다.

VM 명령 길이를 재는 경우 반환값 하위 비트만 길이로 쓰지 않는다. 원래
디스패처는 opcode를 따로 보관하며 커서는 opcode 다음을 가리킨다. leaf가
자체적으로 커서를 옮길 수 있고, 다음 opcode의 선읽기도 포함된다. A8.06/07/10은
실제 연속 디스패치 커서 차이5/3/4바이트로 확인했다. C4.15처럼5000계열
반환값으로 상대 표를 고르는 명령은 고정 길이 뒤로만 전진시키지 말고,
원래 선택식의 범위와 모든 표 셀·목표를 별도로 추적한다.

51.01의 네 입력 결과 표와51.02의 메뉴 선택 결과 표도 구분한다. 실제
51.02는 저장 메뉴에서500F까지 도달하며 항상 두 선택지인 것이 아니다.
확인된 두 선택문의 표 크기를 다른 메뉴에 그대로 적용하지 않는다.
EE.02는 다음 opcode를 저장한 뒤 부모 문맥으로 복귀하고 나중에 다시
들어올 수 있다. E7.03과 같은 영구 종료나 즉시 fallthrough로 처리하지 않는다.

시나리오 번호만 바꾼 일반 세이브는 그 지점의 자연 진입을 보장하지 않는다.
F 내부 슬롯63은 슬롯16의 우회 선택에서 세계지도 상태를 유지한 채 바로
이어진다.63만 직접 불러오면 원본 F와 완결편 양쪽에서 같은 카메라 대기에
걸리지만, 원래16의 선택을 거치면 완결편에서도 맵·목적문·중단 재개가 된다.
실패 시 먼저 원본의 같은 진입 조건과 실제 직전 호출을 비교한다. 이 결과를
모든 시나리오 직접 불러오기가 불가능하다거나 이식이 모두 정상이라는
주장으로 확대하지 않는다. E7.02의 목적문 임시 포인터도 Continue 직후에는
0일 수 있으므로 해당 메뉴의 원래 재등록 이후에 비교한다.

F와 완결편의 수치 A/B에서 같은 세이브 payload를 쓰면 이름의 문자 코드는
같은 글자로 표시되지 않을 수 있다. 동일 숫자·진행 상태 비교와 실제 이름
표시 검수를 구분한다. 원본 비교 파일에서만 이름이 깨졌다면 두 게임의
제품 문자 코덱으로 먼저 확인한다. 별도 표시 검수 사본은 F 세이브 편집기의
이름 쓰기를 사용해 네 이름 칸과 체크섬만 다시 쓰고 편성·진행 바이트를
보존한다. 실제 완결편 출력이 정상인 사례를 폰트 그림 결함으로 오판하거나
기존에 증명한 동일 payload 비교 파일을 덮어쓰지 않는다.

맵 저장/Continue의 액터 신원을 원시4바이트 그대로 비교하지 않는다.
액터+3에는 진영과 임시 선택 비트40이 함께 있다. 신원·좌표·진영을 따로
비교하고 원시 전체도 별도로 대조한다. F63·F57의 실제 Continue에서는
첫 액터의 선택 비트만 해제됐다. 이 한 비트를 근거로 다른 차이까지
무시하지 않는다. 원본 F/완결편을 비교할 때 새 적의 HP·EN이 다르면
두 ROM의 실제 기본 기체 레코드와 시나리오 개조치를 먼저 대조한다.
현재 F 연결은 기존 완결편/에디터 레코드를 유지하며 F 밸런스를 가져오는
기능은 아니다. 기존 보유 행 보존과 새로 생성한 적의 기본값 차이를 구분한다.

## 재사용할 분석 자산과 알려진 구조

F용·완결편용 로컬 분석 프로젝트와 구 도구(`SRWF_TSRViewer.exe`, `research/tips.utf8.txt`)는 저장소 밖 작업자의 로컬 폴더에 있다. 위치는 저장소에 기록하지 않으므로 작업자에게 확인하고, 파일이 없으면 상위 폴더의 파일명 목록부터 찾는다.

- 모듈 공용 헬퍼: 바이트 배열 비교·DataView·hex/base64 변환·SHA-256 digest·시나리오 본문의 14개 root 읽기는 `assets/editor-bytes.mjs`, 자기 소유 속성 조회와 복사는 `assets/editor-own.mjs`를 쓴다. 모듈마다 사본을 새로 만들지 않는다(`tests/editor-bytes.test.mjs`가 사본을 거부한다).
- raw sector는 2352 bytes, user payload는 +16에서 2048 bytes. ISO extent는 logical LBA다.
- TSR 상대 포인터는 **포인터 셀 자신의 주소 + signed BE32 변위**. F완결편은 backward pointer/alias가 있으므로 root 순번을 물리 정렬 순번으로 바꾸지 않는다. 영역 끝은 다음 물리 unique offset으로 경계 처리한다.
- 현재 해석: root27 유닛,28 파일럿,29 무기. 명칭 root11 유닛,12 파일럿,13 파일럿 약칭,14 무기,16 정신기,17 파일럿 특수능력,18 기체 특수능력. 새 버전은 파서 근거로 다시 확인한다.
- **이름 키 = 레코드(포인터 셀) 번호.** 기체·파일럿·무기 이름표 모두 같다. 레코드 +0/+1의 9-bit 값은 기체에서 맵 아이콘 번호, 파일럿에서 얼굴 번호이며 이름 키가 아니다(0은 고정 얼굴 없음이며 합법이다). 무기 이름표는 완결편에서 레코드보다 64칸 짧다. 이름이 비어 있다는 사실만으로 미사용 레코드라고 하지 말고 이름표×레코드 수치 템플릿 교차로 판정한다.
- 기체 능력 ID는 record+38/40/42/44, 보조 byte는 +39/41/43/45. TSRViewer robotstructlist의 반복문은 ID와 보조 byte를 교대로 읽는다. 보조 byte는 효과의 크기가 아니라 조건 플래그 번호다(0 = 항상, 아니면 그 이벤트 플래그가 켜진 동안만; 근거는 `docs/EDITOR_FACTS.md`의 unit-ability-aux).
- 기체 레코드는 `50 + 4n`바이트의 가변 길이다. +46 = 무기 항목 수 n, +47 = 탄약 칸 수, +48부터 4바이트 항목 n개, `00 00` 종료. 무기 번호는 `((e0&7)<<8)|e1`로 무기 레코드 번호와 같다(TSRViewer의 `robotstructlist`, `robotbytesupdate`, `robotload`가 출처). 읽기는 `assets/editor-weapon-links.mjs`, 교체·추가 계획은 `assets/editor-loadout.mjs`이다. 추가 시 `editor-unit-storage.mjs`는 검증용 논리 뷰에서 기체 표를 TSR 끝으로 옮긴다. F·완결편 출력은 `editor-unit-compact.mjs`가 원래 기체 영역에 다시 저장하고, 승인된 미사용 슬롯의 정확히 같은 빈 레코드만 공유한다. 실제 기체끼리는 공유하지 않는다. 완결편 `SRUCMP03`(원래 영역)·`SRUCMP04`(원래 포인터 표를 유지하고 넘치는 완전 레코드만 한도 안의 TSR 꼬리에 저장; 옛 형식), `SRUCMP05`(마지막 꼬리 레코드 다음 0000 반워드 보호), F `SRUCMP02`의 가변 길이 메타데이터(옛 완결편 `SRUCMP01`도 읽음)로 논리 뷰를 손실 없이 복구한 뒤 기존 불변 해시를 대조한다. F·완결편 CD 원본 적재 주소는 0x0028d800이며 그 앞 섹터도 덮는다. 지속 데이터는 F 401,408B, Final 458,752B로 끝 0x0028d000을 적용한다. F 원래 설치기 꼬리는 그대로 보존하며 새 편집 공간이 아니다. 실제 F v0.5의 F06 메타데이터는 root27 안 빈 공간에 둔다. F 무기명·추가 글자 기록과 기체 복원 prefix도 SRFAUX01로 같은 틈에 저장하고 실제 root11/root14 이름 포인터만 변환한다. 논리 staging 버퍼를 게임의 새 꼬리 공간으로 내보내지 않는다. 재열기에서는 물리 배치를 되돌린 뒤 기존 이름·글자·기체 canonical 및 불변 해시 검사를 유지한다. 과거 460,800B 및 0x002b1800 출력 한도는 안전하지 않았다. F 설치기는 TSR 재전개마다 실행하며 재사용하지 않는다. F의 원래 root40은 0x0028d800을 넘어가므로 완결편 경계를 F에 적용해서도 안 된다. F·완결편 글자 기록은 동일 검증 내용을 `SRWGLY02` 이진 형식으로 작게 저장하며 옛 `SRWGLY01`도 읽는다. 한도 안에 들어가지 않는 출력은 거부한다. 표시 순서와 플래그 번호의 뜻은 확인되지 않았다.
- 지형 적응: 기체(+26)와 파일럿(+9)은 4비트 넷(지상·바다·공중·우주 순), 무기(+11)는 2비트 넷이다. 화면 순서는 공·육·해·우이고 글자는 `assets/editor-grades.mjs`(기체·파일럿 4=A..0=E, 무기 3=A..0=-). 파일럿 C·D와 무기 C는 화면으로 확인하지 못했다.
- 파일럿 기본부23 bytes, +5..8 성장 nibble, +9..10 지형, +11 격투, +12 사격, +13 명중, +15 회피, +17 SP, +19 기량, +21 반응(+17/+19/+21은 게임 상태창의 Lv50 값과 대조해 확인했다. 이전의 tech/cnt/mp 순서는 틀렸다). +23부터 (ID, 레벨) 쌍. 게임의 두 스캔은 모두 ID가 0인 첫 쌍에서 끝난다(`00 01`·`00 00` 모두 종료). 정신기는 ID 1..31 중 앞의 6쌍만 칸이 되고(이름은 1..30) 31 초과는 건너뛴다. 특수능력은 ID 32 이상(F 32..81, 완결편 32..83)이며 이름은 root17의 ID−32 연결을 쓴다. 레벨 99 초과는 이벤트 플래그(레벨−100).
- 레코드 길이 필드는 없다. 레코드 끝은 다음 unique 시작 오프셋이다. 번호 308..311은 머리부 없는 주인공 습득표(여섯 정신기 쌍, 스킬 쌍, `00 00`, 0 패딩)이며 수치 파일럿이 아니다. #303은 능력치 #304..307과 목록 #308·309에서 재조립하고 #302의 목록은 #310·311에서 가져온다. #302의 능력치 공급원과 선택 비트의 성별·역할 의미는 미확인이다. #304..307은 능력치만 편집하고 목록은 실제 공급 습득표에서 편집한다. 습득표는 길이 52·36·52·36바이트와 정신기 정확히 6개를 고정하며 마지막 4바이트 0 패딩은 편집·재배치 예산에서 제외한다. 제품 writer 출력의 승인 실행 코드 복사·등록과 전체 BIN 재열기는 검증했으며 전체 게임·생일 후속 재설정까지 검증한 것은 아니다. 셀 0·1·312..319는 한 레코드를 공유한다. 파일럿 #19의 일곱 번째 정신기 범위 쌍은 게임이 읽지 않는다.
- 성장 nibble은 레벨당 증가량이 아니라 성장 종류다. 바이트별로 +5 격투/사격, +6 명중/기량, +7 회피/반응, +8 SP/미확인(뷰어 구조체의 attshot·hittech·agicnt·mindnazo; 에디터가 ‘동조’라 부르는 하위 nibble의 뜻은 확인하지 못했다). +7의 하위 nibble은 반응의 성장 종류다: 게임이 레벨 99로 만든 기술자에서 반응 상승량이 nibble 값 0, 1~2, 3에 따라 79, 72, 68이다. 상태창 근거(Lv50): SP = +17 + 76(4명), 기량 = +19 + 49(3명), 반응 = +21 + 35~37(3명), 격투·사격 = +11·+12 + 49, 명중·회피 = +13·+15 + 98.
- **성장 nibble ≠ 베어내기 같은 특수능력**. 성장 공식 확인 없이 ‘레벨당 +n’으로 설명하지 않는다.
- 구 TSRViewer의 정신기 경계(ID 47)와 특수능력 21쌍 상한은 게임 규칙이 아니라 뷰어의 제약이다. 표시·쓰기·출처 범위는 모두 게임의 규칙(`pilotPairLayout`: 맨 앞의 ID 1..31 쌍이 정신기 블록이고 그 뒤 ID 32 이상이 능력 목록)으로 정의한다. 일반 파일럿의 신규 특수능력은 정신기 6칸과 기존 항목을 보존한다. 길이가 모자라면 승인 레이아웃으로 고정한 연속 편집 가능 구간 안의 확정 0 패딩만 모아 재배치하며, 잠긴 레코드 주소·바이트와 전체 TSR 길이·다른 루트는 고정한다. 개인 수정본 재열기는 승인 배치로 정규화한 불변 해시 검증을 거친다. 구현과 예산 경계는 `docs/LOCAL_EDITOR.md`의 ‘파일럿 특수능력 추가·삭제’와 `docs/EDITOR_FACTS.md`의 pilot-skill-write에 있다. 정신기 블록 뒤에 정신기 ID가 다시 나오는 레코드처럼 어느 목록에도 넣을 수 없는 모양은 잘못 보여 주지 않고 거부한다. 미확정 ID는 읽기 전용으로 둔다.
- 일본 자료의 특정 보정/연인 보정 설명은 ROM 주소 근거가 아니다. 특정지원 명칭이 존재하는 것과 인물별 방향/거리/보정 테이블을 찾은 것은 구별한다.
- 그림을 record index로 매핑했다면 **이름·그림·수치가 같은 기체인지** 별도 확인한다. 이미지가 잘 렌더링됐다는 사실만으로 연결이 맞는 것은 아니다.

## 실제 화면과 비교하는 방법

기준은 저장소 밖에 있는 로컬 실기 참조 캡처(파일럿 능력 화면 등)다. 이 저장소에는 포함하지 않는다. 원본 전체330×240과 내부 패널 crop 좌표계를 구분한다. 현재 웹 내부289×222 비율을 전체330×240이라고 보고 오차를 계산하지 않는다.

패널 경계→글자 baseline/실제 ink bounds→그림 불투명 영역→선택영역 순으로 측정한다. CSS font-size만 비교하지 않는다. Lv99 런타임 수치를 ROM 기본 능력치와 직접 일치시켜서는 안 된다.

초록 경계는 원래 한 띠 안에 밝은 가로선 두 개가 있다. 이것을 중복으로 오인해 지우지 않는다. 문제는 인접 패널의 전체 띠 두 개 또는 부모+자식 프레임이 겹치는 것이다. 공유 경계는 한 패널만 소유하게 한다. 현재 SVG는 재구성 자산이며 ROM에서 추출한 원본이라고 부르지 않는다. 실제 자산을 쓰려면 사용자 BIN에서 세션 내 추출한다.

390×844,433×844,desktop에서 긴 이름·최대 숫자·수정/reset 버튼을 확인한다. 숨겨서 문제를 없애지 않는다. 목록/상세 전환으로 편집 정보에 접근할 수 있어야 한다.

## 반복 사용 가능한 브라우저 probe

`scripts/editor-probe.cjs`는 실제 로컬 BIN을 선택해 해시 검증 후 세 화면을 desktop/390/433에서 캡처하고 HP 수정·focus·reset을 확인한다. 목록에서 상세 화면으로 돌아온 뒤 기체·파일럿 그림이 유지되는지, 740×360에서 각 상세 페이지가 재계산 후에도 선택과 버튼 focus를 유지하는지도 검사한다. CLI의 `--playwright`와 `--browser`는 설치된 경로를 넣는다. 설치/다운로드를 자동으로 하지 않는다.

```sh
node scripts/editor-probe.cjs --bin=/absolute/approved.bin --out=/absolute/capture-dir --game=srwf-f --playwright=/absolute/node_modules/playwright --browser=/absolute/browser
```

F완결편은 `--game=srwf-final`로 별도 실행한다. 보고서에는 status/errors/각 화면 크기/가로 overflow가 남는다. **이 probe는 export 바이트, 모든 입력, 폰트 유사도를 검증하지 않는다.** 그 검증은 별도 항목으로 남긴다. 실패하면 failure.png와 report.json부터 읽고 무작정 timeout을 늘리지 않는다. proprietary BIN/캡처/추출 자산은 저장소에 추가하지 않는다.
