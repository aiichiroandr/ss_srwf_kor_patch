# 기존 합류·배정 명령의 네이티브 의미 — 2026-10-23

C7의 존재나 파일럿/기체 번호만으로 ‘신규 합류’라고 부르면 초기 편성, 하차, 링크 변경, 삭제와 조회까지 혼동한다. 이 문서는 최신 승인 F/완결편의 EXEC `0`을 읽고 기존 SH-2 재컴파일 소스와 literal 값을 대조해 좁힌 의미다. 임의 실행 코드나 새 VM 명령을 제품 writer에 추가하지 않았다. 합류 catalog는 확인된 instruction 경계의 원래 명령을 읽으며, 미확정 명령은 opcode와 원래 operands로 남긴다.

주소는 모두 런타임 SH-2 주소다. F dispatch C1=`060281DC`, C2=`0602B168`, subtable C1=`060B2AB8`, C2=`060B2B98`; 완결편 dispatch C1=`0602B328`, C2=`0602EA84`, subtable C1=`060B9048`, C2=`060B913C`다. 각 subhandler는 VM 피연산자 커서의 첫 byte를 subcommand로 읽는다.

위 명령의 길이는 실제 반환과 커서 쓰기를 함께 확인한 범위다. cache 번호는 파일럿/기체 데이터 번호와 다르고, 하차·삭제 명령은 없는 cache index나 변형·합체 연결에 관한 원래 가정을 갖는다. 이 표를 근거로 임의 호출을 앞 시나리오에 복제하는 쓰기 권한을 만들지 않는다.

C1.04의 F helper는 `060263D4`, 완결편은 `0602A0FC`다. 완결편 handler에는 기체 ID3에 배정했을 때 기존 기체 ID2의 파일럿 index도 동기화하는 `0602B6A2..0602B6E8` 분기가 추가돼 있다. 일반적인 pilot→unit 배정만으로 전체 부작용을 설명할 수 없다.

C1.02 뒤의 cache clear는 F `0602A360` / 완결편 `0602D90C`다. C1.03의 전체 초기화 helper F `0602A330` / 완결편 `0602D8DC`는 0..127을 반복해 이 clear를 호출한다. clear는 firstword=0, 일부 flags 해제, 연결 byte=FF, 기본 기력50 등 원래 cache 초기값을 쓴다.

여러 명령이 호출하는 F `0601F430` / 완결편 `06020998`은 전역 byte의 bit80을 세우고, F `0601F41C` / 완결편 `06020984`는 같은 bit를 지운다. 이것만 하는 존재 조회를 ‘배정’으로 분류하지 않는다. bit의 후속 조건 해석과 VM+20 숫자 반환도 구분한다.

## 게임별 차이와 미확정 항목

- C1.0E는 F handler76줄과 완결편35줄로 구조가 다르다. 단순 번호·길이 일치로 완전히 같은 동작을 부여하지 않는다.
- C2.12의 F subtable 값은 `0602E2DC`이고 원래 반환6006은 총7바이트 형태다. 완결편은 `0602F718`에서 pilot ID→배정 기체 조회→기체 제거 helper를 호출하며 총4바이트다. Final catalog의 길이와 의미를 F에 복사하면 안 된다.
- C1.01/0D/0F/11/12/14/15, 완결편 추가16/17, C2.01/02/05/06/07/08/09/0A/0C/0D/0F/10 및 추가13/14는 원래 handler와 길이 후보를 확보했지만 이 문서가 모든 게임 효과의 분류를 끝낸 것은 아니다. 기존 C7/C2.06의 pair 생성 근거는 별도 합류 연구와 결합한다. 모르는 필드·부작용을 친숙한 게임 효과로 임의 명명하지 않는다.
- 사적 `addrbook_20260912/vm_opcodes.json` 중 Final 프로젝트에 있는 파일은 이름에 final이 없어도 실제 C1/C2 handler가 완결편 주소였다. 경로 이름 대신 파일의 exec hash와 실제 dispatch 주소를 확인한다.

## F C0 위치 조회 번호의 독립 재확인

승인 F v0.5-c 전체 이미지 SHA-256
`75555116f784115e7104c593fd990491ae182b9493d9f159201e17b3e3d88202`를
실파일에서 확인하고, 이 이미지의 EXEC `0`만 메모리에서 읽었다. 이 해시는
승인 build 문서의 target pin과 같다. 주 dispatch cell
`060B21BC + C0 * 4 = 060B24BC`의 값은 `06022244`다. 이 handler는
현재 커서의 subcommand byte에4를 곱해 literal `06022268`의 table
`060B2944`를 직접 조회한다. subcommand에서1을 빼는 조정은 없다.

| F 명령 | 실제 table cell | handler | 길이와 좁힌 의미 |
|---|---|---|---|
| C0.0C | `060B2974` | `060228B8` | roster cache와 기체·파일럿 속성을 순회하는 별도 선택 질의다. 사각형 좌표4개를 읽는 handler가 아니다. 전체 의미는 이 확인 범위에서 명명하지 않는다. |
| C0.0E | `060B297C` | `06022B9C` | 반환 `6003`, 전체4바이트. 기존 기종 조회는 bit15 경로에서 low9 기체 종류로 현재 map actor 목록을 모은 뒤 unit cache +16이 FF인 항목을 센다. 결과는 VM+20이다. |
| C0.0F | `060B2980` | `06022C80` | 반환 literal `06022D4E = 6007`, 전체8바이트. BE16 selector와 x0/y0/x1/y1 네 byte를 읽어 양 끝을 포함하는 현재 위치 사각형을 검사한다. |
| C0.10 | `060B2984` | `06022D68` | 반환 `6003`, 전체4바이트. 파일럿 cache +2 level을 VM+20으로 읽는 별도 조회다. 이 주소를 C0.0F라고 부르면 table 인덱스가 어긋난다. |
| C0.11 | `060B2988` | `06022E14` | 반환 `6003`, 전체4바이트. full16 파일럿 ID→배정 기체→현재 map actor 조회를 거친다. 이 경로의 성공 predicate는 미출격 파일럿까지 포함하는 전체 roster 존재 조회가 아니다. |

C0.0F는 `06026C90`으로 selector에 맞는 actor 목록을 모으고 각16바이트
actor의 +0/+1 좌표를 비교한다. selector -5/-4/-3은 helper의 원래
분기에서 각각 mask1/2/4로 이어진다. count를 VM+20에 쓰고0이 아니면
원래 predicate bit를 지운다. 실제 EXEC에서 해당 table cell, handler
첫 명령, selector·좌표의 +1..6 인수 읽기, `6007` literal 등 원시 SH-2
word9개를 재컴파일 소스와 직접 대조했다. C0.11의 숫자 반환은 존재할 때
파일럿 cache +6 word를 VM+20에 쓰지만, 기존 존재 조건은 이 숫자가
아닌 바로 뒤 F0/F1 predicate 분기를 사용한다.

따라서 이번 독립 정적 확인으로는 기존 F RG01의 C0.0F, 기종 조건의
C0.0E 또는 현재 map 파일럿 조건의 C0.11을 다른 번호로 바꿀 근거가
없다. 기존 개인 편집본의 metadata 의미도 변경하지 않는다. 이 확인은
새 게임 실행이나 전체 조건 검사의 반복이 아니며, 원래의 조건 지원
범위를 확대하지 않는다. 게임 파일·원시 코드·추출 자료는 저장소에 넣지 않았다.
