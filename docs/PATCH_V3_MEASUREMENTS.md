# `srwf.sparse-byte-delta.v3` 측정 기록

[`PATCH_FORMAT_V3.md`](PATCH_FORMAT_V3.md)의 설계 근거가 된 수치입니다. 규범 문서가 아니며 형식 규칙은 그쪽이 우선합니다.
모든 크기는 byte이고, 파일 크기는 실제 인코더가 낸 파일의 정확한 값입니다. **측정하지 못한 것**은 9절에 모았습니다
(실제 정품 원본, 휴대 기기, Firefox·Safari).

## 2. 측정 방법

- 입력: 저장소 `3cb5e69`의 실제 승인 payload 여섯 개(`patches/srwf-f-2026092* v0-5-a/b/c`, `v0-4-a/b/c`). 각 파일의 SHA-256은
  `receipts/*.acceptance.json`의 `patchSha256`과 같습니다.
- 인코더: `encode_v3.py`, 표준 라이브러리만. CPython 3.11.15, zlib 1.3(런타임 1.3), **level 9, `memLevel` 9, `wbits` 15, 기본 strategy**,
  타임스탬프 없음. 같은 입력에서 항상 같은 bytes가 나옵니다(CLI와 라이브러리 출력이 byte 단위로 같음을 확인).
- 라운드트립: `roundtrip_v3.py`가 독립 디코더로 풀어 승인된 v1의 `(offset, length, targetBytes)` 목록과 변형마다 record 단위로 비교했고 여섯 릴리스
  모두 일치했습니다(7절). Node 교차 검증(`check_v3.mjs`)은 같은 payload를 `DecompressionStream`으로 풀어 같은 `recordSetSha256`을 냅니다.
- 속도: Node 22.22.2, Linux, 4 vCPU 공유 VM(부하 평균 0.8~2.8이라 실행마다 10~20% 흔들림). 브라우저 수치는 Chromium 141(headless
  Playwright, module Worker, 디스크 기반 `File`)에서 속도·메모리 분석이 측정한 것이며 **합성 578,512,032-byte 원본**(모든 record byte가 원본과
  다르게 고친 의사 난수 이미지)을 썼습니다. 정품 원본은 이 환경에 없습니다.
- "압축 분석", "속도·메모리 분석", "보안 분석"은 v3 설계 전에 세 방향에서 따로 한 실측입니다. 인용한 수치는 그 출처를 밝혔습니다.

## 4. 설계 선택의 근거가 된 실험

### 4.1 body 배치 (같은 데이터, 같은 zlib 설정, F v0.5 / F v0.4)

| 배치 | v0.5 body 압축 | 채택 대비 | v0.4 body 압축 | 채택 대비 |
|---|---:|---:|---:|---:|
| 채택: set별 `GAP`·`LEN` column, 그다음 data 영역 | 22,151,839 | +0 (+0.00%) | 20,461,598 | +0 (+0.00%) |
| data 영역을 앞에 둠 | 22,154,672 | +2,833 (+0.01%) | 20,465,056 | +3,458 (+0.02%) |
| set마다 `GAP`·`LEN`·`DATA`를 이어 붙임 | 22,153,107 | +1,268 (+0.01%) | 20,462,436 | +838 (+0.00%) |
| 압축 분석의 순서(공통 `DATA`를 맨 끝) | 22,151,790 | -49 (-0.00%) | 20,462,580 | +982 (+0.00%) |
| `LEN`을 1 byte + 255 escape로 | 22,138,984 | -12,855 (-0.06%) | 20,449,403 | -12,195 (-0.06%) |
| (gap, len)을 record별로 섞음 | 22,302,556 | +150,717 (+0.68%) | 20,601,954 | +140,356 (+0.69%) |
| 채택 배치, zlib level 6 | 22,202,596 | +50,757 (+0.23%) | 20,517,162 | +55,564 (+0.27%) |

배치 사이의 차이는 모두 ±0.7% 안입니다. 합의한 기준(차이 2% 미만이면 가장 단순한 디코더)에 따라 **모든 값을 LEB128 하나로 통일한 column 배치**를 채택했습니다.
interleaved가 가장 커서(+0.68%) 버렸고, 1-byte `LEN`(−0.06%)은 디코더에 분기를 더할 만큼의 이득이 아닙니다.

압축기 구현에 따른 차이도 배치 차이와 비슷합니다. Node(Chromium zlib)로 같은 v0.5 body를 level 9, `memLevel` 9로 압축하면 22,099,427 bytes로
CPython zlib 1.3의 22,151,839보다 0.24% 작습니다(속도·메모리 분석 측정, 두 body는 byte 단위로 같음을 확인). 그래서 압축기는 형식이 아니라
생성기의 재현 조건으로만 고정합니다. level 6은 level 9보다 0.23% 큽니다.

### 4.2 압축 분석의 부가 실험 (F v0.5, CPython zlib 1.3, 공통 대상 bytes 36,525,326 B 단독)

| 실험 | 크기 |
|---|---:|
| zlib level 1 / 3 / 6 / 9 | 23,395,281 / 22,693,914 / 20,969,472 / 20,936,279 |
| level 9, `memLevel` 8 | 20,955,411 |
| level 9, `Z_FILTERED` / `Z_RLE` / `Z_HUFFMAN_ONLY` | 21,373,995 / 29,137,293 / 29,894,228 |
| level 9, window 16 KiB / 4 KiB (32 KiB가 20,936,279) | 23,641,022 / 27,100,868 |
| record 길이별로 stream을 둘로 나눔(≤16 / >16) | 20,650,358 (−1.4%) |
| 길이 1·2 record가 전체의 약 32%, 길이 ≥128이 61,962개, 최대 2,052 | – |
| gap이 정확히 1 byte인 비율 | 88.5% |

결론은 level 9, 기본 strategy, 32 KiB window입니다. 길이별 분할은 −1.4%(2% 미만)이고 stream이 늘어 디코더가 복잡해져 채택하지 않았습니다.
Zopfli(인코더 쪽 전용, 출력은 여전히 zlib)는 A0에서 −1.69%였으나 외부 패키지가 필요하고 인코딩이 40~90 s 걸려 채택하지 않았습니다.

### 4.3 채택하지 않은 추가 압축 (압축 분석 측정, 인코더·zlib 동일 조건)

| 구성 | F v0.5 그룹 | v1 대비 | F v0.4 그룹 | v1 대비 |
|---|---:|---:|---:|---:|
| 합의한 방향만(v3와 같은 계열, 헤더 211 B) | 22,139,484 | 10.60% | 20,448,092 | 10.65% |
| 위에 CD 섹터 EDC/ECC 재생성(`ECC2352`)을 더함 | 16,845,600 | 8.07% | 15,338,152 | 7.99% |
| 위 대신 자체 장거리 중복 제거 단계(`LZ`, window 4 MiB)를 더함 | 17,537,027 | 8.40% | 16,645,636 | 8.67% |
| 둘 다 더함 | 12,794,075 | 6.13% | 12,202,557 | 6.36% |
| (참고) 제1자 LZMA 디코더를 허용했을 때의 body, 사전 64 MiB | 16,276,312 | – | – | – |

- 변경 바이트의 87.5%는 게임 데이터이고 12.5%는 CD Mode 1 섹터의 EDC/P/Q 패리티(섹터 내용의 함수)입니다. `ECC2352`는 이 패리티를 디코더에서 다시 계산합니다.
  다만 원본 섹터 내용에 의존하므로 **원본 이미지 없이 무손실 검증을 할 수 없고** 실측 증거는 일부 섹터(v0.5 181개, v0.4 208개, 불일치 0)뿐입니다.
- 게임 데이터 bytes의 약 61%는 이전 bytes를 32 KiB~1 MiB 뒤에서 반복합니다(deflate window 밖). `LZ`는 이를 자체 구현 단계로 걷어 냅니다. 원본 없이 검증할 수 있지만
  합의한 "zlib만" 방향을 넘습니다.
- 두 그룹 합계는 합의한 방향 42,587,576 → `ECC2352` 32,183,752 → 둘 다 24,996,632입니다. 사이트 `.srwfp` 총량은 약 108 / 97 / 90 MB가 되므로 현재 v3의
  107 MB에서 더 줄여도 1 GB 한도에는 영향이 없습니다. **권고: 별도 형식(`SRWFKP4`)의 소유자 결정 사항으로 남깁니다.**

## 5. SHA-256 처리량 (이 VM, Node 22.22.2, 1 MiB × 256, 3회 중 최고)

| 구현 | 처리량 | 578,512,032 B 한 번 | 원본 + 결과 |
|---|---:|---:|---:|
| `assets/sha256.mjs` (현재) | 84.3 MiB/s | 6.5 s | 13.1 s |
| 빠른 드롭인(8라운드 unroll, Int32Array 스케줄, 다중 블록 compress) | 115.4 MiB/s | 4.8 s | 9.6 s |
| `node:crypto`(네이티브, 브라우저 Worker에서 스트리밍 불가) | 387 MiB/s | – | – |

속도·메모리 분석의 추가 측정: Chromium에서 현재 구현 93~96 MB/s, 드롭인 137~140 MB/s(1.45배). 드롭인은 `node:crypto` 대비 14,678건(길이 0..700 전부, 55/56/63/64/65/119/120/127/128 경계 ±1,
1 MiB, 0·0xFF 채움, 임의 분할 4,000건, 200 MB + 37 B)에서 비트 일치했고 기존 33개 패치 테스트가 그대로 통과했습니다. WASM(`clang -O3` 스칼라)은 148~151 MB/s로 이득이 작고
현재 CSP(`script-src 'self'`, `wasm-unsafe-eval` 없음)에서 Chromium이 `WebAssembly.instantiate`를 거부합니다. 소스 해시를 중첩 Worker로 옮기면 Chromium에서 11 s → 7.5 s(1.4배)이지만
복사·역압·중단 처리가 늘고 단일 코어 기기에서는 이득이 없습니다. 결과 해시는 첫 변경 offset(47,306)부터 원본 해시와 상태가 갈라져 재사용할 수 없습니다.

| v1의 JS DEFLATE 구조 스캐너를 v3 body에 돌릴 때 | 3.4~3.8 s(v1 body에서는 11.7 s) | 보안 분석, 속도·메모리 분석 |
| 메모리: 파싱 후 상주 / 파싱 중 최대 | 약 66 MB / 약 110 MB (v1: 약 240 MB) | 속도·메모리 분석 |
| Chromium RSS 증가, 적용 | v3 +207 ~ +218 MB, v1 +335 MB | 속도·메모리 분석 |
| 모바일 다운로드 캡처 창 | 여섯 릴리스 모두 4개 창 46,137,344 B(44 MiB), v1과 동일 | 속도·메모리 분석 |

- 파싱과 적용 전체가 두 번의 전체 이미지 SHA-256(원본 + 결과)에 90% 이상 묶여 있어, 형식을 더 바꿔도 시간은 거의 줄지 않습니다. 해시 구현이 남은 유일한 큰 지렛대이며
  형식과 독립입니다(5절).
- `DecompressionStream('deflate')`의 다중 stream 동작(속도·메모리 분석, Node 22.22와 Chromium 141): 하나의 zlib stream 안에서 sync/full flush로 구간을 나눈 입력은 이어서 풀리고, 두 stream을
  이어 붙이거나 뒤에 쓰레기를 붙이면 `TypeError`로 거부됩니다. 반면 CMF가 512-byte window를 선언하고 거리 5000을 쓰는 stream은 양쪽 모두 **받아들입니다**. 따라서 v1의
  "window 밖 거리 금지"를 지키던 것은 JS 스캐너뿐이었고, v3는 `CMF = 0x78` 고정 규칙으로 같은 성질을 형식에서 보장합니다.

## 8. 검증기 시간

현재 저장소 `python3 scripts/verify_repo.py`는 이 세션에서 **431 s(7분 11초, `PATCH_FORMAT_V3.md`를 추가한 상태에서 통과: 165개 파일, `node --test` 110건도 통과)**가 걸렸습니다(v1 payload 약 465 MB의 순수 Python DEFLATE 스캔이 대부분). v1 payload 한 개(69.6 MB)의 Python DEFLATE 검사는 68.4 s입니다. 변환 뒤에는 남는 v1·v2 payload(64.6 MB)의 스캔이 대부분이므로 약 65~100 s로 추정되며,
