# 시나리오 에디터 조사와 구현 범위

2026-10-11. 이 문서는 로컬 에디터 작업 기록이며 새 패치 릴리스의 승인·배포 기록이 아니다. 게임 실행 검증은 별도로 수행해야 한다. 실제 BIN과 추출 파일은 저장소 밖에만 둔다.

## 현재 구현: 강화파츠 격추 보상

TSR root 32에는 48개의 선택 번호가 있고, 실제 물리 레코드에는 `[파츠 번호, 확률]` 쌍과 종료 표지가 들어 있다. F는 물리 레코드 26개 중 25개, 완결편은 31개 중 30개를 편집할 수 있다. 여러 선택 번호가 한 레코드를 공유할 수 있다. 에디터는 이 공유를 유지하고 현재 들어 있는 1~2개 쌍만 수정한다. 새로운 쌍을 삽입하거나 빈 레코드의 크기를 늘리지는 않는다.

- 파츠 번호 1~22, 각 확률 0~100%, 합계 최대 100%.
- 남은 확률은 보상 없음이다. 합계 0%도 허용한다.
- 에디터의 처음 값 복원, 변경 목록 이동, 편집값 JSON 저장·불러오기, BIN 반영을 연결했다.
- 보상은 기체 기본 능력이 아니라 시나리오의 각 등장 배치가 선택하는 공통 추첨 설정이다. 각 후보는 함께 지급되는 슬롯이 아니라 하나의 결과로 추첨되며, 남은 확률은 보상 없음이다.
- 화면에서는 내부 ‘보상 표’ 번호 대신 실제 파츠명·확률을 표시한다. 기체·파츠·확인된 화수와 제목으로 검색하고, 확인된 적용 등장 수와 사용 기체를 항상 표시한다. 사용 기체에서 해당 초기·증원 배치로 이동해 그 기체의 보상 구성을 선택할 수 있다.
- 구성 선택기는 작은 화면에서 첫 파츠와 확률·나머지 후보 수를 표시하고, 아래 입력칸에서 전체 파츠명과 각 확률을 확인한다. 같은 파츠 ID를 두 후보로 설정한 경우 간결한 선택 문구의 확률만 합산하고 저장된 두 후보는 그대로 보존한다. 잘못 입력한 확률도 처음 값으로 복원할 수 있다.
- F와 완결편의 원본 TSR 이름 표 모두 파츠 21을 `リペアキットＳ`로 표시한다. 현재 승인 완결편의 해당 이름은 다른 안내 문장으로 연결되어 있어, 에디터에서 그 문장만 ‘리페어 키트 S’로 표시한다. 승인 파일의 문자열·포인터는 수정하지 않는다.

실행 파일의 직접 읽기 근거:

| 내용 | F | F 완결편 |
| --- | --- | --- |
| 보상 선택 함수 | `0x0602D3F8` | `0x060311B0` |
| TSR root 32 조회 | `0x0602D42A..434` | 동일한 2단계 상대 포인터 조회 구조 |
| 누적 확률 계산 | `0x0602D44C..470` | 같은 루프 구조 |
| 부족한 확률에 보상 없음 추가 | `0x0602D472..488` | 같은 조건·100 임계값 |
| 1~100 추첨값과 누적값 비교 | `0x0602D48A..4C2` | 같은 비교 구조 |

완결편 기체 생성 경로 `0x06027544 → 0x06030F70 → 0x06031040 → 0x060311B0`에서 선택한 파츠가 런타임 기체 레코드에 들어간다. 따라서 격추 때마다 다시 추첨한다고 설명하지 않는다. 이미 생성된 기체의 저장 데이터에는 기존 결과가 남을 수 있다. F 생성 호출 경로도 추가 대조 대상이다.

개인 이미지 재열기 검증 범위를 최신 승인 a/b/c 여섯 개와 정확한 원본 두 개에서 확장했다. 기존 프로파일로 각 캐시 TSR의 변경 불가 영역 해시와 편집 범위를 먼저 확인한 뒤 보상 쌍 바이트만 추가한다. 선택 포인터·공유 관계·항목 수·종료 표지는 변경 불가 영역에 남긴다. 이전 편집 프로파일도 계속 검사하며, 이전 승인 릴리스의 편집 허용 여부는 기존 최신 계열 제한을 따른다.

검증:

- 합성 데이터: 잘못된 포인터·종료 표지·확률·항목 추가·별칭 번호·중복 요청을 거부하고, 요청 전체를 검증한 뒤에만 쓰는 것을 검사.
- F/완결편 합성 디스크: 보상 두 곳 변경, 독립 섹터 EDC/ECC 검사, 프로파일 재열기, JSON 재적용의 BIN 해시 일치.
- 실제 최신 F a/완결편 c: 화면에서 보상 두 곳 변경, JSON 다운로드, BIN 생성, 브라우저 세션을 새로 만든 뒤 개인 BIN 재열기와 값 일치 확인.
- 데스크톱 및 모바일 세로 입력: 합계 초과 거부, 유효값으로 수정, 초점 유지, 변경 목록에서 보상 입력칸으로 이동 확인.
- 실제 게임에서 파츠 획득 여부는 아직 실행해 확인하지 않았다.

## SCEDATA: 섹터 형식부터 구분

최신 F a의 SCEDATA는 MODE1 섹터에 있다. 최신 완결편 c의 SCEDATA는 MODE2 Form 1 섹터에 있다. TSR 전용 MODE1 추출을 완결편 SCEDATA에 사용하면 매 섹터의 8바이트 부헤더가 데이터에 섞이고 실제 데이터 끝 8바이트가 빠진다.

초기 잘못된 추출은 빈 첫 슬롯과 조기 LZ 종료를 만들었다. 이를 다중 압축 스트림 가설로 해석했으나, 실제 섹터의 mode=2와 중복 부헤더를 확인한 뒤 가설을 폐기했다. 임의 스트림 이어붙이기, END 해석 변경, 엔디언 변경은 제품 코드에 넣지 않았다.

올바르게 읽은 완결편 c SCEDATA:

- 길이 1,106,799 바이트.
- SHA-256 `8902db80ae5aeecc11902adcfc5fc0ebe7bcfb216eb63e5ea01da23fc8081b6b`.
- 디렉터리 1,600 바이트, 논리 선택 번호 200개, 공유를 제외한 압축 본문 103개.
- 전체 해제 본문 합계 1,962,133 바이트. 각 본문의 14개 상대 포인터가 본문 내부를 가리킴을 확인했다.
- 시작·끝 포인터는 두 셀 각각이 아니라 8바이트 항목의 시작을 기준으로 계산한다. F와 구별하여 읽는다.

기존 자료에 `4310b9e...`로 적힌 완결편 SCEDATA는 이번 잘못된 MODE1 방식의 추출과 일치했다. 원본 게임 파일의 해시라고 재사용하지 않는다. SCEDATA 저장 기능은 섹터 형식별 체크섬·공유 디렉터리·압축 공간·재읽기를 구현한 뒤 연결해야 한다.

## 현재 구현: 공용 지형 효과

기체의 지형 적응, 무기의 지형 적응, 맵 타일의 지형 효과는 서로 다른 데이터다.

게임의 지형 팝업(F `0x06067D64`)은 TSR root 34의 하위 표 3에서 지형마다 두 보정값을, 하위 표 4에서 회복값 두 개를 읽는다. F의 해당 표는 각각 240바이트(120개), 완결편은 288바이트(144개)다. 회복 화면의 실제 표제는 ‘회복/HP/EN’으로 확인했다. 두 번째 회복 바이트는 표시 단계에서 `0x7F`로 마스킹하므로 상위 비트를 회복량으로 덮어쓰면 안 된다.

전투 계산까지 대조한 결과, 하위 표 3의 첫 바이트는 명중 계산값의 배율, 둘째는 방어를 뺀 피해 계산값의 배율이다. F `0x0604C54C..568`에서 첫 바이트를 읽어 `0x0604C9FE..1A`에서 100으로 나눠 적용한다. F `0x0604BECC..BF06`에서 둘째 바이트를 읽어 `0x0604C168..18E`에서 적용한다. 완결편의 대응 조회는 `0x060520A6`와 `0x06051A1C`다. 지형 적용 여부를 검사하고 미적용 상태에서는 100을 사용하므로 모든 기체 상태에 무조건 적용된다고 설명하지 않는다. 피해의 최솟값 등 나머지 전투 규칙은 그대로다.

화면의 ‘회피 보정/방어 보정’은 `100 - 저장 배율`로 표시하고 저장한다. 예를 들어 저장값 75는 보정 25%다. 허용 범위는 0~100%이며 기존 데이터의 범위를 넓혀 음수나 100% 초과 보정을 쓰지는 않는다.

F `0x060701DA..20E`와 완결편 `0x06076B76..BAA`에서 하위 표 4의 HP 바이트와 EN 하위 7비트를 다른 회복 원인에 더한다. F `0x060702B0..352`에서는 최대 HP/EN의 비율을 계산해 현재 값에 더하고 최대치에서 제한한다. 공중 상태·특수능력·그 밖의 소비 상태 때문에 화면의 지형 회복량과 실제 총 회복량이 다를 수 있다. EN 상위 비트는 F `0x0606FA30..6C`, 완결편 `0x060763CC..408`에서 별도 조건으로 검사하고 위치 상태를 저장하는 데 쓰인다. 이 비트의 모든 의미가 닫힌 것은 아니므로 편집하지 않고 보존한다.

‘지형 효과’ 탭에 네 입력칸을 한 줄로 놓았다. 기존 변경 목록 이동, 처음 값 복원, 편집값 JSON 저장·불러오기와 BIN 쓰기를 연결했다. F 120개/완결편 144개 지형 번호에 적용하며, 같은 이름이어도 서로 다른 번호는 합치지 않는다. 이름이 해석되지 않으면 번호를 표시한다. 같은 번호를 쓰는 모든 맵에 영향을 준다는 설명을 제공한다.

최신 승인 6개와 원본 2개에서 원래 프로파일의 해시를 먼저 확인하고 지형 보정/HP 바이트와 EN 하위 7비트만 변경 가능 범위에 추가했다. 기존 일반/보상 전용 개인 BIN 프로파일도 유지한다. 지형 이름·상대 포인터·개수·EN 제어 비트는 변경 불가 영역에 남는다.

검증: 합성 F/완결편 디스크에서 배율 변환, EN 제어 비트 보존, 요청 전체의 원자적 거부, 수정하지 않은 지형·바이트의 동일성, 독립 EDC/ECC 검사와 프로파일 재열기를 통과했다. 실제 최신 F a/완결편 c에서도 지형 두 개를 수정해 BIN 저장 후 새 브라우저에서 모든 지형 값을 대조했다. 데스크톱과 320/390px 모바일 화면, 키보드가 열린 높이 330px에서 입력/저장 버튼의 경계를 검사했다. 실제 게임에서의 지형 효과 변경은 아직 실행해 확인하지 않았다.

## 시나리오·맵 저장과 편집 화면 — 초기 구현 기록

이 절의 초기 배치 전용 개수와 경로는 최초 구현 기록이다. 현재 등장·턴 조건의 확장 범위는 문서 마지막의 ‘기존 등장·증원과 턴 조건 구현’을 따른다.

`editor-scenario-archive.mjs`는 SCEDATA 디렉터리, 본문 공유, 14개 셀 기준 상대 포인터, 명시적 압축 종료와 뒤의 0 채움을 검사한다. 압축 본문의 원래 위치와 공간, 해제한 길이, 루트 포인터를 유지한다. 원래 압축 공간에 들어가지 않는 수정은 거부한다. 원본 완결편은 최신 패치본과 달리 MODE1 섹터에 있으며 끝 포인터도 끝 셀 기준이다. 최신 완결편은 MODE2 Form 1과 항목 시작 기준이다. 파서는 승인/원본 식별에 따라 두 디렉터리 형식을 명시적으로 구분한다. 논리 아카이브 바이트만으로 섹터 모드를 추정하지 않는다.

초기 배치의 쓰기는 `editor-deployments.mjs`에서 제한한다. 루트 4의 실제 시작에서 확인한 명령 경계를 따라가며, 미해석 명령·분기·공통 스크립트 호출에 도달하면 멈춘다. 바이트 패턴 검색으로 배치 위치를 정하지 않는다. CA02의 12바이트 항목 중 X/Y와 격추 보상 선택 번호만 편집한다. 기체·파일럿 번호, 레벨, 업그레이드, 이벤트 상대 포인터, 묶음 선택 번호, 항목 수와 종료 표지는 그대로다. CA01은 확인한 4바이트 간격으로 건너뛰며 편집 대상으로 삼지 않는다. CA01의 C0 모드 값은 단순 맵 좌표가 아니기 때문이다.

- 현재 범위: F의 물리 본문 52개 중 29개에서 390대, 완결편 103개 중 54개에서 744대. 최신 a/b/c와 원본에서 같은 수의 초기 배치를 확인했다. 전체 증원·등장 이벤트를 모두 편집한다는 뜻은 아니다.
- C4 sub0의 맵 선택과 해당 MAP_MAP 첫 상태의 실제 사각형을 연결한다. 좌표는 X `0..너비-1`, Y `0..높이-1`이다. 맵 대응을 확인하지 못한 항목은 읽기 전용이다.
- 보상 선택 번호는 TSR root 32의 0~47 또는 255(보상 없음)다. 255의 우회 분기는 F `0x0602D420..424`, 완결편 `0x060311D8..DC`에서 확인했다. 파츠를 보장하려면 선택한 표의 파츠/확률을 함께 설정해야 한다.
- 논리 시나리오 선택 번호는 화수가 아니다. 같은 본문을 공유하는 번호도 있다. 제목·분기·화수 매핑 전에는 번호 0을 ‘1화’처럼 표시하지 않는다.

`editor-map-archive.mjs`는 F 111개/완결편 127개 맵과 F 21개/완결편 24개 그래픽 묶음을 읽는다. 맵 항목에는 SC01 압축 상태 두 개가 있으며, 두 상태의 사각형 크기가 항상 같지는 않다. 상태의 전환 조건은 아직 화면 명칭으로 확정하지 않았다.

타일 사각형 시작은 해제 헤더의 BE32(+4)에서 4를 빼고 짝수 위치로 맞춘 값, 너비/높이는 +10/+11이다. 타일은 BE16의 하위 10비트다. 방향/제어를 담은 상위 6비트와 사각형 뒤의 다른 데이터는 보존한다. 그래픽 묶음의 해제 데이터 +512에는 타일 1,024개의 지형 번호가 있다. 실제 로더 F `0x0605528C`/완결편 `0x0605AF64`와 변환기 F `0x06048B18`/완결편 `0x0604E3C4`에서 이 연결을 대조했다. 그래픽 묶음의 원본 팔레트·그림 데이터는 편집하거나 배포하지 않는다.

MODE1과 MODE2 Form 1의 별도 섹터 체크섬 경로를 추가했다. MODE2에서는 중복 부헤더와 Form 1 표시를 확인하며, ECC 계산 시 주소 헤더를 임시 0으로 처리하고 원래 값으로 돌린다. 데이터 기록은 파일의 길이·위치·마지막 섹터 패딩을 유지한다.

개인 수정본 검사는 `editor-scenario-profiles.mjs`의 최신 승인 6개 및 정확한 원본 2개로 확장했다. 각 전체 이미지 SHA와 기존 TSR/디스크 프로파일을 먼저 확인해 생성했다. 압축 영역을 허용하되, 별도의 해제 데이터 해시로 배치의 허용 바이트와 타일 하위 10비트만 마스킹한다. 디렉터리·본문 공유·맵 헤더·나머지 시나리오 코드·방향 비트·그래픽 묶음은 검증 대상에 남는다. 원본 완결편의 작은 디스크와 최신 계열의 확장 디스크도 각각 식별한다. 기존 일반/보상/지형 전용 프로파일은 유지한다.

코어/워커 저장 경로는 배치·타일과 기존 TSR 수정을 한 BIN에 반영할 수 있다. 합성 F/완결편 디스크에서는 세 종류의 동시 수정, 반복 편집, 원본 완결편 재열기, 잘못된 좌표·타일·요청/중단 거부를 검사했다. 체크섬이 맞는 시나리오 코드/기체 ID 변경과 타일 방향 변경도 개인 수정본으로 받아들이지 않는 것을 검사했다. 실제 최신 F a/완결편 c에서는 배치 한 곳과 타일 한 곳을 함께 변경해 BIN을 파일로 저장하고 새 Blob으로 열었다. 두 경우 모두 별도 출력 영수증 없이 확장 프로파일로 재열렸고, TSR은 그대로였으며 변경한 세 섹터를 독립 EDC/ECC 계산으로 확인했다.

**시나리오/맵 화면·변경 목록·처음 값 복원·편집값 JSON 저장/불러오기까지 연결했다.** F a/완결편 c 실제 BIN에서 화면의 좌표·격추 보상·타일을 변경하고 JSON 저장 → 처음 값 복원 → JSON 재적용 → BIN 출력 → 새 브라우저 작업 스레드에서 출력 영수증 없이 재열기를 확인했다. 새 파일의 좌표·보상 선택·타일이 바뀐 값과 일치했고 개인 수정본으로 식별됐다. 실제 게임에서 배치·타일 수정이 적용되는지는 실행해 확인하지 않았다.

화면은 `시나리오` 탭(좁은 화면은 `맵`)이다. 초기 배치 데이터·맵·두 상태를 따로 고른다. 기체를 고른 뒤 X/Y 또는 선택 칸으로 이동하며, 격추 보상 표/보상 없음도 고를 수 있다. 타일 선택은 같은 맵의 MAP_BANK가 연결하는 1,024개 ID와 지형 명칭으로 한다. 타일 적용·연속 칠하기·선택 칸 처음 값·해당 지형 효과 이동을 제공한다. 지도는 **사용자가 연 BIN의 실제 타일 그림**을 기본 팔레트로 보여준다. 진영·이동 가능성이나 실행 중의 밤/날씨/애니메이션을 재현하지 않는다. 두 상태를 임의로 ‘변경 전/후’라고 이름 붙이지 않는다.

1440×1000, 390×844, 375×667, 320×568, 320×330에서 측정했다. 남은 높이에서 맵·입력값을 최대한 함께 놓으며, 짧은 화면만 맵/편집값으로 나눈다. 입력값도 기존 `packMeasuredGroups`로 실제 높이를 재어 필요한 수만큼 나누고 입력 초점과 변경 목록의 이동 대상을 유지한다. 가로 넘침과 페이지의 불필요한 세로 스크롤을 확인했다. 로컬 캡처·보고서는 저장소 밖 `/private/tmp/srwf-scenario-carrier-live/ui-f-final/`, `ui-final-final/`에 있다.

배치 프리셋의 식별 값은 변경을 허용한 바이트를 제외한 본문 해시·공유 시나리오 번호·배치 위치로 만든다. 타일 프리셋은 변경 불가 맵 데이터·그래픽 묶음 해시·맵/상태/좌표를 묶는다. 다른 구조의 원본/패치본에 이름이나 동일 오프셋만으로 적용하지 않고 건너뛴다. 같은 계열에서 재편집하는 JSON 왕복은 지원한다. 맵은 수정/조회한 칸만 행으로 만드는 sparse 모델을 써서 휴대폰에 모든 맵 셀의 가변 객체를 만들지 않는다. 최대 20,000칸 편집을 담을 수 있게 JSON 상한을 8 MiB로 늘리고, 배치/타일 항목 수·문자열·좌표·필드·식별 정보·값 범위는 별도로 제한한다.

## 작전 목적 조건 조합 검토

요청 범위는 승리·패배 조건의 추가와 조합이다. 목적 문구만 바꾸는 기능으로 대체하지 않는다.

기존 완결편 목적 번역 자료에는 다음 유형이 있다: 전멸, 특정 기체 격파, 턴 제한, 특정 지점/영역 도달, 시설 침입 저지, 특정 기체의 모함 격납, 특정 기체 격파 **또는** 특정 진영 전멸. 이 목록은 표현·설계 사례이며 해당 조건의 기계 명령을 모두 해석했다는 증거는 아니다.

지금 직접 확인한 것은 범용 VM의 조건 플래그와 분기 기능이다:

- F E7 sub0/sub1은 플래그 번호를 검사하는 `0x0601FF70`을 부른다. 플래그 검사 결과에 따라 선택 문맥의 상위 조건 비트를 설정한다.
- E7 sub2는 이 조건 비트를 보고 상대 포인터를 설치한다. 기존 조사에서는 목적 표시 자료의 참조 소유자로 사용되었다. 이것만으로 승패 판정이라고 단정할 수 없다.
- F0/F1(`0x0601F1BC`, `0x0601F224`)은 조건 비트를 검사해 부호 있는 16비트 상대 위치로 분기한다.
- F3/F4(`0x0601F2E0`, `0x0601F334`)는 문맥 값과 16비트 상수를 비교하여 분기한다.
- 해당 값에 실제 턴 수·진영 잔존 수·기체 생존·좌표가 어떻게 들어가는지는 추가 조사 대상이다.

에디터 설계는 승리와 패배를 분리하고, 각 조건 묶음에 ‘모두 만족/하나라도 만족’을 둔다. 예를 들어 ‘5턴 이내에 A 기체가 목표 구역에 도달하고 B 기체가 생존’은 승리의 AND 묶음으로, ‘6턴 진입 또는 B 기체 격추’는 패배의 OR 묶음으로 표현할 수 있다. 이는 제안 문법이며 현재 BIN에 쓰는 구현은 아니다.

### 사용자 화면과 조건의 의미

처음에는 기존 승리·패배 조건을 한 화면에서 읽게 하고, ‘조건 추가’를 누른 뒤 조건에 필요한 입력만 펼친다. 논리식 기호를 직접 입력하게 하지 않는다. 조합은 ‘모두 충족’과 ‘하나라도 충족’으로 표현하며, 깊은 중첩은 기본 화면에 넣지 않는다. 고른 조건에서 자연어 목적 문구를 자동으로 만들고 실제 판정과 함께 저장해야 한다.

| 사용자가 원하는 목적 | 작성할 조건 | 판정에서 반드시 구별할 것 |
| --- | --- | --- |
| 적 전멸 | 승리: 지정한 적 진영의 잔존 수 0 | 미등장 증원과 철수 기체, 진영 변경, 판정 활성화 시점 |
| 아군 전멸 | 패배: 아군 진영의 잔존 수 0 | 미출격 아군과 모함 격납 기체, 증원 대기 상태 |
| 5턴 안에 클리어 | 기존 승리 조건 + 제한 시점 초과 시 패배 | 플레이어 턴 시작/종료와 적 턴 종료 중 엔진이 실제 검사하는 시점 |
| 5턴 안에 목표 위치로 이동 | 승리: 대상 기체의 목표 칸/영역 도달 + 제한 | 현재 그곳에 있음과 한 번이라도 도달했음, 실제 맵 범위와 진입 가능성 |
| 특정 인물을 죽이지 않기 | 패배: 해당 등장 기체 격추 | 아직 등장하지 않음·철수·모함 격납을 격추로 오인하지 않을 것 |
| A 격파 또는 적 전멸 | 승리 묶음의 OR | 같은 프레임에 승리·패배 조건이 함께 참인 경우의 우선순위 |

대상은 전체 기체 능력치 표의 이름만으로 선택하면 안 된다. 같은 기체 형식의 적이 여러 대 등장할 수 있으므로 해당 시나리오의 등장 개체·진영·증원 묶음까지 식별해야 한다. 출격/증원 경로가 연결되지 않은 대상은 새 조건의 피연산자로 쓰지 않는다.

‘죽이지 않기’는 완료 순간의 생존 여부만 확인하는 것과 다르다. 목표 기체가 격추된 사건을 패배로 연결해야 한다. ‘도달’도 현재 좌표 검사와 도달 이력 저장이 다르므로, 실제로 확인한 이벤트/플래그 저장 방식에 해당하는 선택지만 제공한다. 기한 문구는 엔진의 판정 시점과 맞춰 생성한다. 지원할 수 없는 조건·중첩·디스크 공간 초과는 구체적인 이유와 함께 저장을 거부하고 기존 조건을 유지한다.

게임 반영을 열기 위한 요건:

1. 각 기본 조건의 실제 소비 함수·필드·비교 방향·판정 시점을 F/완결편에서 확인한다.
2. 기존 시나리오의 실제 명령 경계와 승리·패배 전환 경로를 추적한다. 목적 문구 검색이나 바이트 패턴 검색만으로 기록 위치를 정하지 않는다.
3. 기체/파일럿 ID, 실제 맵 좌표 범위, 증원 전후의 진영 판정, 미출격 기체, 턴의 시작/종료 시점, 동시에 승패가 참인 경우의 우선순위를 정의한다.
4. 조건 AST를 검증된 명령만으로 컴파일하고, 상대 분기·본문 공유·압축 후 디스크 공간·런타임 본문 공간을 검사한다. 보장하지 못하는 추가·중첩은 저장 단계에서 거부한다.
5. 화면 목적 문구와 실제 판정 코드를 함께 생성하며, BIN 재열기에서 같은 조건 트리를 복원한다.
6. 기존 조건 유지/변경을 최소 두 시나리오에서 검사하고 실제 게임에서 경계 사례를 실행한다.

현재 조건 조합 작성/저장은 **미구현**이다. 판정 연결이 확인되지 않은 조건을 선택 가능한 버튼으로 먼저 노출하지 않는다. 자유 문장으로 임의 조건을 만들어 게임에서 작동한다고 약속하지 않는다.

| SCEDATA root 8 등록/호출 | 공용 TSR root 0의 스크립트가 E8 FF08로 현재 시나리오 root 8을 선택, E8 FFF3로 게임 상태 +0x52C에 등록. 이후 E8 FFFE로 등록한 스크립트를 호출 | 모든 맵에서의 검사 타이밍과 목적 변경 이벤트의 순서 |

완결편의 실제 root 8 사례에는 진영 집계 두 개, 0과의 비교, EC01/EC02 및 EA가 연결되어 있다. 따라서 수치 조건과 분기를 조합하는 기반은 관찰했다. 다만 콜백을 호출하는 공용 게임 루프, 전멸 처리의 제외 상태, 최종 클리어/게임오버 소비처까지 연결해야 사용자가 읽는 조건과 실제 판정이 같다고 보장할 수 있다. 현재 출처 검사는 모든 분기·결과 명령을 변경 불가 영역에 남겨 둔다.

다음 구현의 우선순위는 기존 단순 전멸 목적의 완전한 판정 경로를 먼저 닫고, 턴 제한·특정 등장 개체·지점/영역 조건을 차례로 추가하는 것이다. 조건 추가 공간은 압축 후 크기뿐 아니라 해제 본문의 사용 가능 영역과 다른 명령의 참조까지 확인해야 한다. 공간이 없으면 이벤트를 삭제하거나 알 수 없는 빈 바이트를 덮어 조건을 넣지 않는다.

### 검토 결론과 저장 범위

조건 조합의 후보 구현은 고정된 기본 조건을 AND/OR 분기로 컴파일하는 방식이다. ‘N턴 안에 목표 칸 도달’은 승리의 도달 조건과 패배의 시간 초과 조건을 같이 생성한다. ‘특정 기체를 죽이지 않기’는 해당 등장 개체의 격추 사건을 패배로 연결한다. 목적 문구는 이 구조에서 생성해야 한다. 임의 자연어를 게임 코드로 해석하는 기능은 제안하지 않는다.

현재 추가 조건을 안전하게 쓰는 템플릿은 **0개**다. 기본 집계/분기 명령을 관찰한 것과 사용자 조건이 실제 승패로 이어지는 것은 별개다. 현재 저장기는 배치 좌표·보상 선택·타일만 허용하며 root 8 및 승패/턴/이벤트 명령은 변경 불가 영역이다. 따라서 이번 검토는 조건 생성 기능을 구현·실행 검증했다고 주장하지 않는다. 기본 조건 소비처를 닫은 뒤 승인 프로파일의 검증 범위와 조건 컴파일/역파싱을 같이 추가해야 한다.

## 실제 맵 그림 표시 (2026-10-10)

`editor-map-graphics.mjs`는 사용자 BIN에서 검증해 읽은 MAP_BANK 데이터만 해독한다. 게임 그림이나 팔레트 파일을 사이트에 넣지 않는다. 워커가 전달하는 묶음별 읽기 전용 데이터는 기본 팔레트 512바이트, 패턴명 8,192바이트, 맵 캐릭터 픽셀 32,768바이트다. 두 묶음에서 최대 512개 타일씩 캐시하므로 캐시의 RGBA 픽셀은 약 1 MiB 이하다. BIN 내 그림/팔레트와 출처 검사 범위는 수정하지 않는다.

좌표는 **해제 MAP_BANK 상대 오프셋**이다. 기본 팔레트는 `0..511`, 1,024개 타일의 네 BE16 패턴명은 `1536..9727`, 1,024개 8×8 4bpp 캐릭터는 `11264..44031`이다. 게임 로더 F `0x0605544C..74`, 완결편 `0x0605B124..14C`가 이 범위를 복사한다. 뒤의 별도 512개 캐릭터 업로드(44,032부터 16,384바이트)는 주 맵 타일 패턴의 하위 10비트가 가리키는 범위에 포함하지 않는다. 구 뷰어의 시작값 11,328을 그대로 쓰지 않았다.

F의 맵 표시 초기화 `0x06054BBA..BC4`는 첫 캐릭터 영역을 VDP2 VRAM `0x25E00000`으로 지정하고, `0x06054DD0..DE4`는 1워드 패턴명 설정을 사용한다. 패턴명의 하위 10비트는 캐릭터, 10/11비트는 H/V 반전, 상위 4비트는 기본 팔레트의 16색 묶음을 선택한다. 각 픽셀은 상위 nibble부터 읽고 BE16 RGB555의 R/G/B 각 5비트를 기존 그림 해독기와 같은 8배 값으로 표시한다.

맵 칸의 10/11비트는 네 사분면 순서를 각각 `[1,0,3,2]`, `[2,3,0,1]`로 바꾸고, 각 패턴명의 자체 반전 비트와 **OR**한다. XOR로 반전을 취소하지 않는다. 근거는 F `0x06048B3E..BA0`, `0x06048D72..DF4` 및 완결편 대응 변환기 `0x0604E3C4`다. 타일을 바꿔도 원래 칸의 반전/제어 비트는 기존 저장기가 보존한다.

맵에는 선택 칸과 초기 배치 점을 겹쳐 보여주고, 교체할 타일 선택 옆에 그림을 보여준다. 지형 효과 화면은 해당 지형 번호가 실제 맵에서 쓰인 타일 예시 네 개까지 보여주며 누르면 그 맵/상태/좌표로 이동한다. 타일 적용, 처음 값 복원, JSON 재적용은 같은 모델의 값을 그려 즉시 반영된다.

표시는 기본 팔레트의 정적 맵 미리보기다. 게임은 런타임 `game state + 0x59D`의 상위 두 비트로 다른 팔레트를 선택하기도 하며, 이 상태의 시나리오 조건·시간 변화는 아직 자동 재현하지 않는다. 선택한 두 맵 상태의 전환 조건 역시 추정하지 않는다. 실제 에뮬레이터 화면과 픽셀 단위 일치 검증을 완료했다고 주장하지 않는다.

검증: 실제 최신 F a의 21개 묶음/222개 맵 상태와 완결편 c의 24개 묶음/254개 맵 상태를 모두 해독했다. 두 게임 각각 맵 0·2·40·70은 별도 원시 픽셀 복원 스크립트와 RGB 바이트가 일치했다. 합성 그림 테스트는 nibble 순서, RGB555, 상위 팔레트·마지막 캐릭터, H/V 사분면 반전과 자체 반전의 OR, 잘못된 범위 거부, 공유 맵/편집 후 그림과 지형 예시 연결을 검사한다. 합성 BIN 왕복에서는 읽기 전용 그림과 원래 반전 비트의 동일성도 확인했다. 전체 Node 테스트는 777 통과/99 기존 건너뜀/0 실패였고 최종 변경 관련 108개가 통과했다. 실제 F/완결편 브라우저에서 맵 그림, 타일 미리보기·변경·복원, 지형 예시 이동을 클릭했다. 데스크톱 및 390×844·375×667·320×568·320×330에서 페이지 넘침이 없었으며 F의 짧은 화면은 잘못된 입력 안내까지 검사했다. 캡처/보고서는 저장소 밖 `/private/tmp/srwf-scenario-research/graphics-ui-f-final/`, `graphics-ui-final-fixed/`, `graphics-all-maps.json`에 있다.

## 초기 적군·턴/페이즈 이벤트·증원 범위 확인 — 구현 전 조사 (2026-10-10)

현재 좌표 저장 범위는 root 4 초기화 경로에서 명령 경계를 따라 도달한 CA02 항목뿐이다. 초기 적군 전체나 후속 증원을 전수 지원한다고 표시하지 않는다. 현재 지도 점도 진영 색을 뜻하지 않는다. F 390개/완결편 744개의 편집 가능한 항목에는 여러 등장 묶음 선택값이 있으며, 선택값을 즉시 아군/적군 이름으로 바꾸지 않는다.

CA02 처리 함수는 F `0x060242B8`, 완결편 `0x06026810`이다. F에서는 선택 byte를 보존하고 항목마다 좌표·ID·보상·상대 이벤트 참조·강화값을 읽어 `0x060256BC`로 전달한다. 선택 byte의 하위 2비트와 나머지 비트가 서로 다른 인수로 나뉜다(`0x060243BE..06024404`). 따라서 전체 byte 하나만 보고 진영을 단정할 수 없다. 게임이 같은 등장 명령을 실행한다는 근거와 해당 시나리오에서 어떤 조건/시점으로 호출되는지의 근거는 분리한다.

턴 값 후보를 만드는 D4 sub0은 F `0x06024778..78A`, 완결편 `0x06027050..7062`에서 게임 상태 +16을 1비트 오른쪽으로 이동해 조건 문맥 +20에 저장한다. D4 sub1은 +14의 word 조회/설정이며, 이를 적군/아군 페이즈라고 이름 붙이지 않는다. 실제 턴 증가와 페이즈 전환 소비처, 콜백 호출·1회 실행 플래그, 이벤트에서의 맵 변경 경로는 추가 확인 대상이다.

후속 편집의 구분은 (1) 기존 초기 출현 좌표, (2) 기존 증원의 좌표, (3) 기존 사건의 발동 턴/페이즈/플래그, (4) 새 사건·새 등장 개체 추가다. 기존 증원도 실제 콜백 시작·분기/호출 경계·맵 문맥을 따라 도달한 등장 목록만 좌표 편집 대상으로 삼아야 한다. 전체 본문에서 CA02 바이트를 검색해 증원이라고 라벨하거나 변경 허용 마스크를 늘리지 않는다. 신규 항목은 압축 공간 외에 해제 본문 공간과 상대 참조를 확인해야 한다. 이번 범위 확인에서 저장기·출처 프로파일·이벤트 UI를 변경하지 않았다.

UI 방향은 기존 맵 위의 등장 묶음 선택을 초기/후속 사건 선택으로 확장하고, 선택한 묶음의 기체만 표시하는 것이다. 발동 조건과 좌표는 같은 편집 영역에서 연결한다. ‘3턴 아군 시작’ 같은 문구는 실제 콜백 시점이 확인된 경우에만 생성하며, 분석되지 않은 사건을 임의 턴 라벨로 보여주지 않는다.

## 기존 등장·증원과 턴 조건 구현 (2026-10-10)

`editor-scenario-events.mjs`는 root 4와 root 5의 시작점에서 검증된 명령 길이와 실제 분기 목적지를 따라간다. CA02 바이트 검색으로 항목을 추가하지 않는다. 각 루트의 다음 경계, 본문 안 상대 참조, 항목 종료, 명령 내부로 진입하는 분기, 경로 수 상한을 검사한다. 미해석 명령과 공통 스크립트 호출에서는 그 경로의 분석을 멈춘다. E9의 재개 이후를 초기 배치라고 표시하지 않으며, 동일한 등장 목록에 여러 맵 문맥이 도달하면 좌표 편집을 잠근다.

D4 sub0은 game state +16의 byte를 오른쪽으로 1비트 이동해 VM context +20에 저장한다. F2/F3/F4/F5는 이를 각각 `=`, `≠`, `≤`, `≥`로 BE16 상수와 비교한다. 분기 상대 위치는 첫 피연산자 주소를 기준으로 계산한다. 턴 입력은 **D4 sub0 바로 뒤의 비교 명령 연쇄**에만 허용하며, 다른 명령을 지나온 문맥 값은 턴이라고 추정하지 않는다. 값이 1~99이고 모든 도달 경로에서 같은 턴 조회가 확인된 조건만 쓰기 대상으로 한다.

F0/F1은 피연산자가 0이면 4바이트 분기이고, 0이 아니면 2바이트 조건 설정이다. 고정 4바이트로 처리하지 않는다. E9는 루트를 끝내는 표지가 아니라 다음 호출에 이어 실행할 위치를 저장하는 반환이다. E8의 FF04/FF05는 각각 SCEDATA root 4/5를 선택하고, FFF1/FFF2는 문맥을 game state +524/+528에 저장하며, FFFC/FFFD는 저장된 문맥을 호출한다. 공통 TSR root 0 / group 2 / sequence 8은 root 5를 등록한다. 실제 재개는 턴 종료 확인 뒤 적군 행동에 들어가기 직전의 별도 루틴에서 수행된다. 초기 조사에서 이를 아군 시작으로 해석한 것은 잘못이었다. 현재 root 5의 확인된 묶음은 ‘적군 시작’으로 표시한다. root 4는 맵 준비와 새 아군 턴 시작에 함께 쓰여 후속 등장만으로 페이즈를 단정하지 않는다. D4 sub1의 +14 word를 페이즈로 사용하지 않는다.

CA02 선택값의 하위 2비트는 생성 함수의 형식/진영 인수다. ‘상위 비트가 진영’이라는 초기 가설은 기각했다. F `0x060243F6..FC` / 완결편 `0x0602694E..54`의 마스크 3 인수는 유닛 초기화 F `0x0602D2E4..EC` / 완결편 `0x0603109C..A4`에서 유닛 byte +2의 bit 3~4에 들어간다. 이후 개체 생성 F `0x060253C0..D2` / 완결편 `0x06029C3E..50`가 이를 개체 byte +3의 bit 1~2로 옮기며 D3가 바로 그 2비트를 진영 집계에 쓴다. 상위 선택 비트의 기타 속성은 보존하며 모두 이름 붙이지 않는다. UI의 점 색상은 선택 상태만 뜻한다. 초기 적군도 좌표 편집 목록에 포함되지만 초기 적군 전체를 지원한다고 표시하지 않는다.

최신 승인 a/b/c 여섯 개와 정확한 원본 두 개에서 이 구조를 확인했다. 완결편의 3개 읽기 전용 항목은 기존 ID/좌표와 맵 대응 조건을 통과하지 않아 쓰기 범위에서 제외한다. 초기 목록 중 진영 상위 코드 1인 항목은 F 75개/완결편 668개다. 이 숫자는 확인된 CA02 경로의 관측치이며 전체 적군 수나 게임 화면 진영 검증의 대체가 아니다.

기존 시나리오 탭의 선택 순서는 데이터 → 등장/턴 조건 → 맵이다. 선택한 묶음의 기체만 같은 실제 그래픽 맵에 표시한다. 턴 조건은 같은 입력 영역에 두고 숫자를 변경하면 묶음 이름도 갱신한다. 필요한 턴 조건이 여러 개면 그 조건을 선택할 수 있다. 등장 목록과 연결되지 않은 확인된 턴 비교도 독립 항목으로 표시하며 빈 좌표 입력은 숨긴다. 플래그·비교 방식·한 번 실행하는 처리·대사·순서는 보존한다는 설명을 제공한다. 시나리오 데이터 번호를 플레이 화수로 표기하지 않는다.

### 저장·식별·검증

CA02의 X/Y·보상 선택 byte와 턴 비교 상수의 **하위 byte만** 변경 허용한다. 턴 상수의 상위 byte, 비교 opcode, 분기 목적지, 다른 명령·기체 ID·상대 참조·항목 수는 해제 데이터의 불변 해시에 남는다. `srwf.editor-scenario-scopes.v2`의 해시를 인증된 여덟 입력에서 다시 생성했다. 압축 본문 공간과 해제 길이는 늘리지 않으며, 들어가지 않는 편집은 전체 출력을 거부한다. 좌표와 턴의 동시 변경은 같은 본문을 한 번 압축해 쓰고 MODE1/MODE2 Form 1 체크섬을 갱신한다.

`events`는 version 1 프리셋의 선택 배열이다. 본문 불변 해시·공유 번호·명령 위치를 묶은 `event:1:` 식별값이 일치해야 적용한다. 이벤트의 이름이나 비슷한 오프셋으로 다른 구조에 이전하지 않는다. 이전 좌표 전용 프리셋의 식별값은 인증된 옛 본문 해시를 같은 배치 위치에 묶은 별칭으로만 허용한다. 처음 값 복원, 변경 목록의 해당 칸 이동, JSON 저장/불러오기, 반복 BIN 편집을 연결했다.

합성 F/완결편 디스크에서 분기 연쇄·반대 조건·문맥 오염·명령 내부 분기·잘못된 요청·상위 상수 byte 변경 거부와 좌표/턴 동시 출력, 독립 EDC/ECC 검사, 출력 영수증 없는 재열기를 검사했다. 실제 최신 F a와 완결편 c에서는 기존 후속 등장 한 곳의 턴과 좌표를 함께 바꿔 해제 데이터의 허용 byte만 바뀌었고 TSR이 그대로임을 확인했다. 바뀐 SCEDATA 섹터는 F 1개/완결편 5개였으며 별도 EDC/ECC 계산을 통과했다.

실제 F/완결편 화면에서도 턴 입력·복원, 좌표 변경, JSON 다운로드 → 초기화 → JSON 적용 → BIN 만들기 → 새 세션에서 출력 영수증 없이 재열기를 통과했다. 데스크톱 1440×1000과 모바일 세로 390×844·375×667·320×568·320×330에서 맵/입력 화면을 실측했다. 낮은 가로 화면 740×360·844×390·1280×400도 추가 검사했다. 둘이 들어가는 화면은 함께 두고, 짧은 화면만 맵/입력값을 나눠 실제 높이로 입력 그룹을 구성한다. 넓지만 낮은 화면에서는 맵 옆의 입력값만 나눈다. 한 페이지면 입력 페이지 화살표를 숨긴다. 740×360에서 여섯 탭을 세로로 놓을 때 저장 줄이 밀리던 문제는 시나리오 화면의 탭을 한 줄로 배치해 고쳤다. 오류 안내가 뜬 경우에도 페이지 넘침과 아래 저장 줄 겹침을 검사했다. 나뉜 입력 페이지를 모두 순회하며 각 입력칸이 정확히 한 번 나타나고 패널 밖으로 잘리지 않음을 확인했다. 등장 기체가 없는 독립 턴 조건에서는 빈 좌표/보상 칸이 숨겨지고 턴 편집·복원이 되는 것도 F/완결편에서 확인했다.

전체 `npm test`와 `python3 scripts/verify_repo.py`를 통과했다(파이썬 43개). 마지막 Node 전체 검사는 784 통과/99 기존 건너뜀/0 실패였으며, 이후 배치 조정 관련 91개도 통과했다. 캡처와 실제 BIN 보고서는 저장소 밖 `/private/tmp/srwf-scenario-research/events-ui-export-f/`, `events-ui-export-final/`, `events-all-pages-f/`, `events-all-pages-final/`, `/private/tmp/srwf-scenario-carrier-live/events-report.json`에 있다. 캡처는 게임 실행의 증거로 사용하지 않는다. 프로파일 인증에 사용한 임시 전체 이미지 사본 세 개(약 1.68 GB)는 검사 후 삭제했다.

### 남은 범위

페이즈를 다른 콜백으로 옮기는 기능, 플래그/조건 추가·제거, 신규 이벤트·신규 등장 개체, 철수, 작전 목적 조건 조합은 제공하지 않는다. 공통 호출과 미해석 경계를 넘는 실행 경로, 콜백의 보존 상태와 상대 참조를 먼저 확인해야 한다. 압축 공간의 남은 0 byte만으로 해제 본문에 새 명령을 넣을 수 있다고 판단하지 않는다. 현재 실행 경로·해제 공간·상대 참조를 모두 확인한 신규 이벤트 템플릿은 0개다. 실제 게임에서 수정한 턴에 증원이 등장하는지와 좌표 이동 결과는 아직 에뮬레이터로 검증하지 않았다.


## 추가 턴 제한: 기존 판정 뒤에만 붙이는 목적 조건 (2026-10-10)

`editor-scenario-deadlines.mjs`는 기존 root 8을 교체하지 않는다. 확인된 플래그 가드 0~3개, D3 FB/FC 인원 수의 0 비교 두 개, E9와 root 8 시작으로 돌아오는 상대 분기가 연속으로 있는 진입부만 지원한다. 바꿀 네 바이트의 내부를 목적지로 삼을 가능성이 있는 상대 참조는 보수적으로 거부한다. 이 부정 검사는 바이트 검색으로 변경 권한을 부여하는 기능이 아니다. 이 검사로 F의 두 후보를 제외했다. 기존 승리·패배 경로와 대사·플래그·클리어 처리는 그대로 실행된다. 아직 승패가 정해지지 않아 기존 E9에 도달했을 때만 별도의 D400/F5 검사로 들어간다. 제한 N은 N+1턴부터 추가 패배이며 0은 추가 조건 제거다. 기존 승패 결과가 먼저 결정되면 그 결과를 유지한다.

주요 실행 근거:

- D3의 FB/FC/FD는 진영 마스크 1/2/4로 바뀐다. 조건 명령은 F `0x06024714` / 완결편 `0x06026FEC`에서 r7=0으로 인원 수 함수 F `0x06026C90` / 완결편 `0x06028834`를 호출한다. r7=0은 목록 경로 F `0x06026DBC..E3E` / 완결편 `0x0602897C..9FE`를 사용하며 기체 상태 `0x20000008`을 제외한다. r7≠0의 스칼라 경로 F `0x06026E40..EAE` / 완결편 `0x06028A00..A6E`는 `0x60000008`을 제외한다. D3가 스칼라 경로를 쓴다는 초기 해석은 분기·지연 슬롯 대조로 기각했다. 각 비트의 모든 발생 사유는 아직 설명하지 않는다.
- D400은 game state +16 byte를 오른쪽으로 1비트 이동한 현재 턴을 읽는다. 카운터는 99에서 제한되므로 추가 제한은 1~98만 허용한다. +14 word나 +6 시나리오 번호를 페이즈라고 표시하지 않는다.
- EC 1/2는 문맥의 결과 비트를 설정한다. EC FF 소비처와 공통 목적 검사 함수, TSR root 0의 1E 분기까지 대조했다. F `0x3EB`의 1/2 결과는 각각 클리어/실패 경로로, 완결편 `0x403`도 같은 구분으로 연결된다. 완결편을 `0x401`로 잘못 잡지 않는다.
- SCEDATA 해제 본문의 실제 RAM 시작은 F `0x20211800`, 완결편 `0x20203800`이며, 다음 활성 작업 버퍼는 각각 `0x20219800`, `0x2020C800`이다. 원본 실행 파일과 최신 패치 파일의 상수 및 캐시 초기화를 대조한 0x8000/0x9000 범위를 넘으면 거부한다. 이 근거를 다른 게임 파일의 가변 크기 허가로 사용하지 않는다.
- root 13의 E702/E703은 목적 문구의 표를 반환한다. 표는 32비트 이름 포인터가 아니라 두 개의 BE16 자기 상대 포인터다. F `0x0606B45C` / 완결편 `0x06071E30`에서 승리·패배 문구를 순서대로 읽는다. 기존 승리 문구는 유지하고 패배 문구에 ‘또는 N+1턴 이상’을 붙인다. 사용자 BIN에 있는 한글 글꼴의 확인된 글자만 사용한다. 일본어 원본의 목적 문구는 이 템플릿의 대상이 아니다.

추가 코드는 원래 본문 뒤에 붙고 root 8 포인터는 유지한다. root 13 포인터와 기존 E9/분기 네 바이트만 정해진 형태로 바뀐다. 끝의 24바이트 `SRWFDL01` 메타데이터는 원래 해제 길이/목적 루트/제한값을 기록한다. 재열 때 원래 형태를 복원한 뒤 추가 코드·포인터·문구·메타데이터를 전부 재생성해 바이트 단위로 비교한다. 정확히 일치하는 확장만 제거해 기존 v2 불변 프로파일과 비교하므로 기존 인증된 여덟 프로파일 해시를 바꾸지 않는다. 임의 코드, 원래 불변 바이트, 텍스트, 분기, 예약 바이트, 압축 뒤의 불명 데이터는 허용하지 않는다.

압축 공간은 원래 디렉터리와 물리 범위를 유지한다. 기존 토큰 재사용이 실패하면 가까운 2바이트 참조까지 찾는 LZ 경로로 다시 압축한다. F 20개/완결편 19개 물리 본문에서 가장 큰 제한값 98까지 원래 압축 범위에 들어가는 것을 확인했다. 이 수에는 더미/공유 데이터가 포함된다. 맵과 사건이 확인되어 시나리오 선택 목록에 나타나는 데이터에서만 UI로 고른다. 확인되지 않은 맵을 이전 시나리오의 맵으로 대신 표시하지 않는다.

UI의 기존 사건 선택 목록에 ‘작전 목적 · 추가 턴 제한’을 넣었다. 추가 제한과 기존 승리/패배 문구를 표시한다. 넉넉한 화면에서는 실제 맵과 함께 표시하고, 작은 높이에서는 실측한 그룹 높이로 넘치는 내용만 페이지로 나눈다. 변경 목록 이동, 처음 값 복원, v1 JSON의 선택 항목 `objectives`, BIN 저장과 재열기를 연결했다. 목적 JSON은 같은 불변 본문과 같은 정확한 위치의 식별값이 있어야 하며 이름이나 다른 위치로 옮겨 적용하지 않는다.

검증: 합성 F/완결편에서 기존 승리·패배 우선순위, 제한 직전/직후, 가드, 재개/재편집/제거, 다른 좌표·턴 편집과의 합성, 잘못된 입력 및 체크섬을 다시 계산한 위조 이미지 거부를 확인했다. 실제 최신 F a/완결편 c에서 BIN 출력 후 파일을 새로 열어 전체 SHA-256과 독립 EDC/ECC, 기존 불변 프로파일, TSR 미변경, 재편집·제거를 확인했다. 실제 브라우저에서도 클릭→JSON 저장/복원→BIN 저장→이전 출력 영수증 없는 새 창 재열기를 통과했다. 두 게임에서 1440×1000, 390×844, 375×667, 320×568, 320×330, 740×360, 1280×400을 측정했고 가로/세로 문서 overflow와 브라우저 예외는 없었다.

### 실행/문구 표시 조사에서 구분한 관측과 가설

목적 표시용 함수의 메뉴 번호 30이라는 가설은 기각했다. 30은 내부 창 리소스 번호이며 실제 53 명령의 메뉴 함수는 F 초기화 `0x060559E4..EA`가 +96에 넣는 24다. 사적 RAM 관측에서 첫 루트 13 실행 전에 이 메뉴를 강제로 호출한 두 시도는 검은 화면만 얻었다. RAM 포인터/문구 쓰기 성공은 확인했지만 실제 목적 창의 가시성이나 수정된 게임의 정상 플레이 증거로 삼지 않는다. 후속 검사에서는 E702가 VM 반환 스택을 꺼내므로 이미 실행 중인 FFFB를 바꾸어도 현재 호출은 바뀌지 않는 것을 확인했다. 제어 파일은 읽기 커서를 유지하므로 덮어쓰기 대신 명령을 추가해야 했다. 원래 반환 위치의 저위 RAM 코드만 사적으로 바꾼 최소 검사에서 53 메뉴 24와 목적 소비 함수 `0x0606B45C` 진입을 실제 기록했다. 문구 표가 추가 제한 98의 생성 문자열을 가리키는 것도 확인했으나, 3450/3700 프레임 캡처는 여전히 검은 화면이었다. 따라서 소비 함수 진입을 표시 성공으로 확대하지 않는다. 다음 최소 검사는 정상 맵에서 목적 메뉴를 열고 텍스트 복사/렌더러의 반환과 UI 작업 상태를 함께 기록하는 것이다. 목적 문구 길이 상한은 보수적인 편집 제한이며 실제 글자별 픽셀 폭의 전수 실측 근거로 주장하지 않는다. 추가 턴 제한이 정상 플레이 중 실제 게임오버를 일으키는지 역시 아직 실행 검증하지 않았다.

D4 dispatch의 sub 0~10을 F와 완결편 EXEC0에서 대조했다. sub 0은 +16 byte를 1비트 이동한 턴 조회이고, sub 1은 +14 word 조회/설정이다. sub 2/3은 해당 카운터를 변경하며 두 게임의 길이/처리가 같지 않다. sub 5(F `0x060248CC`, 완결편 `0x06027208`)는 +16의 하위 bit를 보존하고 턴을 1로 초기화한다. sub 7/8은 +10 word와 +12 byte로 된 24bit 값을 더하거나 빼고, sub 9는 그 값에 `0x10624DD3`를 곱한 상위 값에서 6bit 이동한 결과를 조회한다. 이를 페이즈로 오인할 수 없다. sub 10(F `0x06024A58`, 완결편 `0x06027394`)도 별도의 상태 조회 경로다. 이 조사만으로 적군/아군 페이즈를 읽는 부작용 없는 VM 명령은 확보하지 못했다.

- 가설: D4의 다른 subopcode로 현재 페이즈를 조회할 수 있다.
- 관찰: 조사한 sub 0~10에는 턴·다른 카운터의 읽기/쓰기가 섞여 있고, 턴 byte의 하위 bit를 보존하는 초기화는 있다.
- 반증: 카운터 변경·초기화 명령과 주소가 비슷하다는 이유로 조회/페이즈 조건을 만들 수 없다.
- 다음 최소 probe: 공통 TSR의 아군/AI 경로가 +16의 하위 bit를 실제로 어떻게 변경·소비하는지와 root 4의 재개 호출 시점을 대조한다. 진영 판정과 콜백 보존이 증명되기 전까지 페이즈 이동 UI/쓰기는 열지 않는다. 신규 증원의 74칸 할당 실패 문제도 계속 미해결이다.

### 콜백과 C4 상태 명령 추가 대조 (2026-10-10)

E8의 등록과 재개를 두 실행 파일에서 다시 대조했다. F `0x0601E18A..1AE` / 완결편의 대응 경로는 FFF1/FFF2/FFF3에 각각 game state +0x524/+0x528/+0x52C의 스크립트 위치를 저장한다. F `0x0601E222..276`의 FFFC/FFFD/FFFE는 반환 스택에 호출 이후 위치를 넣고 해당 저장 위치를 VM의 현재 명령 위치로 읽는다. 페이즈 번호를 받는 명령이 아니므로 이 인수만 바꾸어 기존 사건의 페이즈를 이동할 수 있다고 판단하지 않는다.

공통 TSR root 0에서 FFFC/FFFD의 원시 호출 후보는 F `0x4CAC`/`0x4C12`, 완결편 `0x4F48`/`0x4E56`에 있다. 0A의 자기 상대 BE32 호출 처리(F `0x06017A00..4E`, 완결편 `0x06017E94..EE2`)도 대조했다. 앞선 좁은 01/03 검색은 공통 루트의 이러한 호출을 놓친다. 이 주소들은 root 0 세그먼트 상대 오프셋이며 SCEDATA나 EXEC0 오프셋이 아니다. 원시 상대 참조 발견은 전체 명령 경계·도달 순서·진영을 증명하지 않으므로 쓰기 권한을 늘리지 않았다.

C4 sub 0/1/2/3/4/5/8/14/17/19의 직접 상태 접근도 두 실행 파일에서 대조했다. 예를 들어 sub 2(F `0x06027334`, 완결편 `0x0602A47C`)는 game state +8의 상위 2bit를 설정하고, sub 14(F `0x0602788C`, 완결편 `0x0602A9B0`)는 +6 byte를 문맥 +20으로 읽는다. 인접 상태 명령이라는 이유로 맵 로드나 페이즈 조회로 명명하지 않는다. C0 sub 25(F `0x060233B4..432`, 완결편 `0x0602543C..4BA`)는 FF 슬롯을 건너뛰고 특정 진영/상태의 개체를 찾아 상태 bit를 지우므로, 부작용 없는 빈 출격 슬롯 조회 후보에서도 제외했다.

### 공통 TSR 호출 순서와 페이즈 표시 정정 (2026-10-10)

**root 5의 ‘아군 시작’ 표시는 잘못됐으며 ‘적군 시작’으로 고쳤다.** 블록 적재 때 root 5를 등록하는 시점과 등록된 콜백을 재개하는 시점은 다르다. 기존 완결편 원본의 공통 TSR 국면 지도와 실제 최신 승인 F a/완결편 c의 root 0 명령 경계를 대조했다. 턴 종료 확인 뒤의 32비트 상대 호출은 root 5 재개·재개점 저장·작전 목적 검사·적군 행동 경로로 이어진다. 적군 처리 뒤 턴 증가와 새 아군 턴 경로는 root 4를 재개한다.

아래 값은 모두 **압축 해제한 TSR root 0 세그먼트 상대 오프셋**이다. SCEDATA 본문 오프셋이나 EXEC0 런타임 주소와 섞지 않는다.

| 확인 지점 | F | F완결편 |
| --- | --- | --- |
| 턴 종료 확인 뒤 0A 호출 → 적군 경로 | `0x03E6 → 0x4BDB` | `0x03FE → 0x4E19` |
| E8 FFFD → FFF2, root 5 재개·저장 | `0x4C12 / 0x4C15` | `0x4E56 / 0x4E59` |
| 적군 경로 뒤 D4 sub 2 턴 증가 | `0x4C63` (2바이트) | `0x4EAD` (3바이트) |
| 새 턴 호출 → 새 아군 턴 루틴 | `0x0282 → 0x4C95` | `0x02BE → 0x4F17` |
| E8 FFFC → FFF1, root 4 재개·저장 | `0x4CAC / 0x4CAF` | `0x4F48 / 0x4F4B` |
| 맵 준비 때 root 4 경로 호출 두 곳 | `0x0210 / 0x0275 → 0x4CA9` | `0x022D / 0x02A9 → 0x4F45` |

완결편의 이전 조사에서 쓰던 전체 TSR 좌표는 root 0 시작 `0xA4`를 더한 값이다. 원본의 적군 루틴 `0x4EBD..4FBB`, 새 턴/root 4 루틴 `0x4FBB..5006`, 턴 종료 확인 호출 주변 `0x0491..04D0`은 최신 승인 c 입력에서도 같은 바이트였다. 기존 국면 해석을 현재 버전에 옮길 때 이 동일성을 확인했다. 재귀 분석 도구의 일부 스위치 표 길이는 첫 분기 목적지로 추정한 값이므로 이를 모든 분기의 완전한 쓰기 권한으로 삼지 않는다.

root 4는 맵 준비 때도 호출된다. E9 이후라는 사실만으로 모든 root 4 사건을 ‘아군 시작’으로 표시하지 않는다. 현재 root 4의 정확한 페이즈는 빈 값으로 두며, 초기/후속 등장과 확인된 턴 조건을 표시한다. root 5의 확인된 턴 조건과 등장 묶음에는 ‘적군 시작’을 표시한다. 이 수정은 표시에 쓰는 메타데이터이며 명령·콜백·출력 바이트의 편집 범위를 늘리지 않는다.

검증: 페이즈 메타데이터와 출력 재파싱·화면 계약을 포함한 관련 시험 114개가 통과했다. 실제 최신 F a/완결편 c 입력에서 턴 수정→JSON 저장→처음 값 복원과 수정된 묶음 이름을 확인했다. 두 게임 각각 1440×1000, 390×844, 375×667, 320×568, 320×330의 맵/편집값/입력 오류 상태 15개에서 문서 넘침과 브라우저 예외는 없었다. 이 화면 확인을 게임 실행 검증으로 대신하지 않는다.

페이즈 이동의 다음 최소 검사는 E9 반환 후 FFF1/FFF2가 저장하는 **독립적인 두 재개점**을 보존하는 컴파일 형태다. 원래 콜백을 중첩 호출한 뒤 E9를 하나 붙이는 방식은 전역 재개점을 덮을 수 있으므로 사용하지 않는다. 원래 등장보다 빠른 페이즈로 기체를 옮길 때도 개체의 최대 점유가 늘 수 있어 신규 증원과 같은 할당 안전성 검사가 필요하다. 페이즈 이동·신규 증원 쓰기는 아직 열지 않았다.

### 특정 인물 조건의 D3 후보 — 쓰기 권한 없음

D3의 양수 선택값도 추가 대조했다. F `0x06024722`는 피연산자를 signed byte로 읽고 `0x06026C90`에 전달한다. 양수 경로 `0x06026D98..DB8`은 128칸 캐시의 식별 word 검색(`0x0602A3E0`)과 연결 보정(`0x0602A194`)을 거친 뒤 개체 집계의 비교 키를 얻는다. 따라서 양수를 곧바로 기체 레코드 번호나 출격 슬롯 번호로 표시할 수 없다. 캐시 종류·연결 상태·격추 후 수명과 실제 인물 식별의 대조가 더 필요하다.

두 버전의 실패 처리도 같지 않다. 완결편 `0x0602894A..958`에는 보정 뒤 FF 값과 비교 키 0을 걸러 0을 반환하는 분기가 있다. F의 대응 `0x06026DA6..DBC`에는 같은 FF 결과 검사가 없으며, 검색 함수는 못 찾으면 FF를 돌려준다. F의 연결 보정 함수가 받는 FF 입력과 뒤의 캐시 접근을 확인하지 않고 ‘없는 인물은 0명’이라고 가정하지 않는다. 이 양수 선택값을 특정 기체의 생존/도착 조건이나 빈 출격 슬롯 조회로 추가하지 않았다. 다음 최소 검사는 실제 배치된 두 인물과 미출격/격추 상태에서 캐시 식별·조회 결과를 각각 대조하는 것이다.

- 가설: C4 상태 조회나 C0의 개체 검색으로 페이즈 또는 신규 출격의 여유를 확인할 수 있다.
- 관찰: C4는 서로 다른 상태 byte/word를 읽거나 쓰고, C0 sub 25는 점유 개체를 검색하며 상태를 변경한다. 공통 콜백의 호출에는 0A 자기 상대 BE32 경로도 있다.
- 반증: 상태 필드의 위치나 FF 검사만으로 페이즈 의미·빈 슬롯 수·콜백의 한 번 실행을 보증할 수 없다.
- 다음 최소 probe: 공통 TSR의 두 재개 호출에 도달하는 0A 호출 경계와 반환 경로를 먼저 확정하고, 해당 단계의 선택 개체 진영을 실제 소비 함수와 연결한다. 원래 콜백 보존과 신규 개체 할당 안전성은 각각 별도의 조건으로 유지한다.

### 기체 생성 분류와 추가 할당 경로 (2026-10-10)

최신 승인 F a/완결편 c의 실행 파일에서 아군 기체 생성 함수 F `0x060259A4` / 완결편 `0x0602782C`를 대조했다. 기체 캐시의 식별 word로 TSR root 27 레코드를 찾아 **레코드 +7의 `(byte & 0x78) >> 3`**을 분류값으로 사용한다. +7은 현재 수치·특수능력 편집이 바꾸는 범위 밖이다. 먼저 기본 개체를 한 번 할당하고, 분류값 1~9의 자기 상대 signed word 분기 표를 사용한다. 표 기준은 F `0x06025A8C` / 완결편 `0x06027914`이다. 명령으로 해석할 수 없는 표와 상수 구간을 선형 명령 목록에서 제외해야 한다.

빈칸 조회 후보도 구분했다. 완결편 `0x0602A39C..A3CE`는 74칸에서 첫 byte FF를 찾아 인덱스 또는 FF를 반환하는 읽기 전용 경로다. 그러나 현재 확인한 참조는 네이티브 할당 함수 내부의 호출이며, 이를 부작용 없는 VM 조건으로 호출하는 경로는 확보하지 못했다. F `0x060251EC` / 완결편 `0x06029A8C` 전체 함수는 개체 초기화와 할당을 수행하므로 조회 명령처럼 부를 수 없다.

실행 파일 끝에 조회 코드를 붙이는 후보도 제외했다. F EXEC0 끝 `0x060B6970`부터 `0x060D12A4`, 완결편 `0x060BD1E0`부터 `0x060D86E4`는 시작 코드가 지우는 BSS이며 실제 전역 변수가 사용한다. 빈 파일 끝이나 0바이트를 안전한 실행 코드 공간으로 간주하지 않는다. 다른 코드 공간의 사용·실행 수명이나 개인 이미지 출처 검사는 새로 증명해야 하며 제품의 네이티브 쓰기 범위를 늘리지 않았다.

### 정상 부트의 캡처 범위 재확인 (2026-10-10)

### 정상 맵의 선택 누락과 출력 BIN의 목적 표시 (2026-10-10)

완결편의 신규 게임에서 실제로 들어가는 첫 맵은 SCEDATA 선택 번호 102, 물리 본문 5, 맵 인덱스 56이었다. 이 번호를 플레이 화수로 표시하지 않는다. root 4의 `16 03` 뒤에 `C4 00 39` 맵 선택이 있다. 기존 배치 판독의 짧은 선형 경로는 앞 명령에서 멈춰 시나리오의 맵을 비워 두었지만, 별도의 검증된 이벤트 판독은 초기 등장 묶음과 맵을 이미 읽고 있었다. 그 결과 정상 맵의 편집 항목이 화면에서 누락됐다.

RAM 쓰기는 사용하지 않았다. 읽기 전용 관측에서 시나리오 헤더의 root 13 word가 원래 `0x1A1F`에서 출력의 `0x34A7`로 바뀌었고, E702 소비 경로의 VM 위치도 새 목적 코드에 진입했다.

승인 BIN에서 만든 에뮬레이터 중간 저장 상태를 출력 BIN에 바로 재사용한 초기 시도에는 원래 SCEDATA가 RAM에 남아 있었다. 따라서 해당 시도는 수정본의 실행 증거에서 제외한다. 출력 BIN의 cold boot 또는 그 출력에서 생성한 상태를 이어 쓰고, 실제 로드된 본문의 헤더/코드를 대조해야 한다. 정상 표시 확인은 위 완결편 두 문구에 한정하며 조건에 따른 승패 실행과 구분한다. 아래 후속 검사에서 해당 완결편 패배 조건의 게임오버를 확인했다. F의 수정 문구 표시와 신규 증원의 할당 안전성을 이 표시 검사로 증명하지 않는다.

이 단계의 읽기 전용 관측은 완결편 D4 00의 반환 위치 `0x06027064`에서 추가 조건 코드의 VM 위치 `0x20206CA1`와 집계값 1을 기록했다. 실제 일반 메뉴도 `턴 수 1`로 표시됐다. 당시에는 턴 조회만 확인했으므로 게임오버 성공으로 기록하지 않았다. 게임 UI가 입력을 처리하는 간격보다 짧은 3프레임 버튼 입력은 일부 메뉴 이동에서 누락됐고, 버튼을 10~24프레임 유지한 후에야 빈 칸의 일반 메뉴를 다시 열었다. 아래 후속 검사는 이 수정본의 확인된 1턴 메뉴 상태에서 페이즈 종료를 실행했다.

### 추가 턴 조건의 정상 게임오버 확인 (2026-10-10)

위와 같은 출력 BIN과 정상 부트에서 만든 상태를 사용해, 일반 메뉴의 페이즈 종료 확인창을 거쳐 적군 행동을 진행했다. 자동 확인 입력은 이후의 결과 창까지 넘길 수 있으므로 그 실행의 마지막 `턴 수 1`만으로 성공이나 실패를 판단하지 않았다. 최종 검사는 입력을 종료 직전까지 동일하게 재생한 뒤 마지막 A 입력(4350프레임, 2프레임 유지)을 끝으로 멈췄다. RAM 수정 없이 5505프레임까지 실행했다.

- 4359프레임까지 추가 코드가 조회한 턴은 1이었다. 같은 조건 평가에서 아군 집계 1, 적군 집계 14를 읽었다. 원래 아군 전멸과 적군 전멸은 모두 충족하지 않았다.
- 4362프레임에 D4 02의 원래 턴 증가 경로가 raw 턴 byte를 2에서 4로 바꿨다. D4 00 조회는 이 값을 한 비트 이동하여 2를 반환한다.
- 4365프레임에 추가 조건의 VM 위치 `0x20206CA1`가 턴 2를 읽고 원래 패배 명령 `0x20204502`(인수 위치)에 들어갔다. 원문 `0xD01`의 `EC 02 EA`를 그대로 사용했으며, 네이티브 `0x06020236`에서 패배 상태 bit `0x20`의 쓰기를 확인했다.
- 4700프레임 PNG에 게임의 `GAME OVER` 창이 표시됐다. 이후 턴 초기화 입력은 없었고, 출력 BIN의 전체 SHA-256도 위의 웹 다운로드 결과와 다시 일치했다.

따라서 이번 근거는 **완결편 v0.3 c 기반, 선택 번호 102/물리 본문 5의 아군 생존 상태에서 ‘2턴 이상’이 실제 패배를 일으킨 한 경로**를 증명한다. 조건 문구만 바뀐 것을 실행 성공으로 계산하지 않았다. 원문 승리 처리, 다른 시나리오와 모든 비교/결합/동시 우선순위, F의 자연 플레이, 신규 이벤트·증원과 페이즈 변경까지 전수 실행한 근거로 확대하지 않는다. 실제 BIN·컨트롤러 계획·MCA 출처 해시·실행 trace·PNG와 그 해시를 저장소 밖의 사적 검증 기록에 보관했다.

이 완결편 실행에서 턴 byte의 하위 bit는 아군 1턴과 적군 행동 중 모두 0이었다. 따라서 그 bit를 현재 아군/적군 페이즈 조회로 쓰는 후보는 이번 관측과 맞지 않는다. 이 관측을 F의 동일 필드 의미로 일반화하지 않는다.

### 신규 이벤트의 대화 진입점 조사 (2026-10-10)

기체를 생성하는 명령과 별도로 B1 이벤트 진입점을 F/완결편에서 대조했다. 핸들러는 F `0x0601BA2C`, 완결편 `0x0601BFC8`이다. 각각 공통 호출 보조 함수 `0x0601B91C` / `0x0601BEB8`를 사용해 VM 문맥 +68의 호출 깊이를 늘리고 피연산자 커서 +4를 반환 위치로 저장한다. 바로 텍스트를 렌더링하는 명령이 아니라 **TSR root 0 안의 스크립트 group 2, entry 3**을 호출한다. 첫 TSR root 0 조회를 빼고 공개 이름 세그먼트 root 2를 같은 표로 읽으면 잘못된 위치를 얻는다.

현재 최신 입력의 공통 스크립트 진입 위치는 F TSR 전체 `0x4532`(root 0 상대 `0x448E`), 완결편 `0x49C6`(상대 `0x4922`)이다. 이 관측만으로 새 대화 이벤트 쓰기를 허가하지 않는다. 호출자 피연산자의 문구/인물 참조, 공통 UI 경로의 부작용·복귀와 최대 호출 깊이, 한 번 실행하는 콜백의 재개 보존을 더 확인해야 한다. 다음 최소 조사는 이 실제 진입점에서 기존 네이티브 유래 해석기로 공통 UI 경로를 추적하는 것이다. 해석되지 않은 명령을 건너뛰어 완료된 호출 그래프로 표시하지 않는다. 신규 증원의 74칸 할당 안전성 문제와 페이즈 변경은 별도 미완료 항목으로 유지한다.

완결편의 이 진입점을 기존 해석기로 따라간 결과는 명령 12개, B5 미해석 지점 1개, 겹침 0개였다. 미해석 지점을 건너뛰지 않았다. B5 네이티브 진입점은 F `0x0601BBC8` / 완결편 `0x0601C164`이다. 래퍼는 전역 UI 상태의 bit 7로 공통 스크립트 entry 1/2를 고르고, 커서 보정 0으로 기존 호출 보조 함수를 사용한다. 뒤의 `04`를 subopcode 4로 dispatch하는 래퍼가 아니므로 `B5.04`라는 가정으로 길이를 정하지 않는다. 준비 함수 F `0x0601C630` / 완결편 `0x0601CBFC`의 경로도 서로 다르다. 다음 최소 조사는 두 준비 함수와 공통 entry 1/2의 전체 인수·UI·복귀 계약이며, 아직 문구/인물 인코딩이나 새 이벤트 쓰기 권한은 확보하지 않았다.

### 출격칸 조회 함수의 사적 네이티브 실험 (2026-10-10)

새 증원의 74칸 할당 검사를 위해 직접 작성한 SH-2 조회 함수를 저장소 밖에서 시험했다. 기존 VM dispatch 표 F `0x060B21BC` / 완결편 `0x060B869C`의 256개 포인터에는 NULL 칸이 없다. FC를 포함한 여러 명령이 공유하는 기본 핸들러는 F `0x0601789C` / 완결편 `0x06017D30`이며 `F000`을 반환한다. 이 반환은 원래 VM의 진행 경로에 속한다. 기본 핸들러라는 사실을 ‘기존 게임에서 사용하지 않는 안전한 명령 번호’의 증거로 삼지 않는다.

조회 함수는 네이티브 할당기와 같은 표 포인터 F `0x060B207C` / 완결편 `0x060B855C`에서 16바이트 간격의 74칸을 읽고, 각 칸의 첫 byte가 FF인 경우만 센다. 아군/적군 수나 생존 판정으로 빈칸을 추정하지 않는다. 결과 쓰기는 VM 상태의 +20 값 한 곳이며, 세 레지스터의 임시 보존에 12바이트 스택을 사용한다. 기존 SH-2 디코더를 이용한 별도 실행 검사에서 각 게임 331가지 상태·빈칸 위치를 시험했다. 모든 칸이 FF이면 74, 모든 칸이 사용 중이면 0이고, r1..r15를 보존했다. 이는 조회 함수 검사이며 전체 증원 명령의 용량 안전성 검사가 아니다.

사적 디스크 실험은 정확한 최신 승인 입력의 전체 SHA-256을 먼저 확인하고, ISO 실행 파일 `0`(분석 자산의 이름은 EXEC0)의 FC 포인터 네 바이트와 선택한 SCEDATA 본문만 바꿨다. F SCEDATA는 MODE1, 완결편은 MODE2 Form 1이었다. 동일한 사용자 데이터 쓰기 함수로 EDC/ECC를 재생성하고 압축 해제 결과를 다시 대조했다. **이 실행 파일 수정은 에디터의 쓰기 권한·출처 검사·승인 릴리스에 추가하지 않았다.** 생성 코드, 변경 BIN, 캡처와 MCA는 저장소 밖에만 있다.

F 물리 본문 1의 원래 C4.0F 명령 네 바이트를 사적 분기 래퍼에서 그대로 실행하고 원래 다음 명령으로 복귀하는 실험은 콜드 부팅으로 호출을 확인했다. 입력은 F v0.5 a 기반이고 출력 SHA-256은 `a51d47e023d7c101487acd6c959a28b7e92bdbce7000e9506c2bdafdbc8c3fde`다. 7663프레임에 `0x202151A0`의 직접 작성한 코드에 들어가, 실제 표 `0x20201AA0`의 74칸을 모두 읽고 빈칸 74를 VM 값에 썼다. 반환 `6000`, PR과 r1..r15, 실제 RAM의 코드 바이트를 trace로 대조했으며 이후 원래 맵·대화가 진행됐다. 해제된 본문 14,880바이트와 압축본 7,501바이트는 각각 기존 RAM 경계와 7,820바이트 슬롯 안에 들어갔다. 이전 F 본문 24의 RAM 끝 고정 배치는 압축 슬롯을 141바이트 초과하여 출력 전에 거부했다.

완결편 물리 본문 5/선택 번호 102에서도 같은 조회 함수를 실제로 호출했다. 출력 SHA-256은 `40221d385316518d50f7d30b8c0ee360b0f1cc4924ce0fd804743236fd0e677b`이며, 콜드 부팅으로 그 출력의 코드를 읽은 뒤 같은 출력에서 만든 MCA만 이어 사용했다. 원래 입력의 에뮬레이터 MCA를 새 실행 파일 위에 재사용하지 않았다. 2393프레임에 `0x2020C780`에 들어가 실제 표 `0x20201AA0`의 74칸에서 읽은 FF를 모두 확인하고, VM +20에 74를 쓴 뒤 `6000`으로 복귀했다. PR과 r1..r15를 보존했으며 원래 맵·대화가 이어졌다. 출격 표의 첫 256바이트는 진입/결과 저장/복귀 때 같았다. 당시 peek 도구가 256바이트로 제한한 결과를 표 전체의 스냅샷 비교라고 확대하지 않는다. 표 밖 쓰기 제한은 전체 생성 코드와 별도 SH-2 실행 검사로 대조했다. 완결편 해제 본문 36,864바이트와 압축본 7,939바이트는 각각 0x9000 RAM 경계와 8,067바이트 슬롯에 들어갔다.

실행 파일 변경은 Mednafen의 이미지 식별 값도 바꿨다. 완결편 콜드 부팅에서는 이전 조사에서 게임 자체가 작성한 backup RAM만 실제 새 식별 값의 파일명으로 복사하여 로드했고, 원본 backup의 해시를 기록했다. 게임 식별 값을 강제로 지정하거나 RAM을 고치지 않았다. 향후 기능 구현은 이 저장 데이터 호환성 영향도 처리해야 한다. 현재 에디터로 두 실험 BIN을 새로 검사하면 모두 `EDITOR_CUSTOM_PROVENANCE`로 거부한다. 사적 실험의 성공을 일반 개인 편집 이미지의 신뢰 근거로 등록하지 않았다.

이 근거는 **F와 완결편의 빈 초기 출격 표를 각각 조회한 실행**까지만 증명한다. 네이티브에서 빈칸이 0일 때의 생성 중단, 실제 새 기체의 생성·콜백·반복 방지, 다른 시나리오에서의 코드 상주와 기존 FC 동작 보존, UI·JSON·BIN·새 세션 출처 검사는 아직 완료되지 않았다. 다음 단계는 코드를 보유하지 않은 다른 장면에서 FC가 잘못된 위치를 실행하지 않는 상주·호출 계약을 정하는 것이다. 임의 코드 쓰기를 허용하는 범용 EXEC0 마스크로 이 문제를 우회하지 않는다.

상주 위치의 다음 조사 후보로 두 입력의 초기 프로그램(IP) 헤더를 확인했다. 선언된 길이는 모두 0x1800이고, 해당 프로그램의 0x1780..0x1800은 원문에서 0이다. 완결편의 위 실제 실행에서는 RAM `0x06002000`에 같은 IP 식별 헤더가 있었고 `0x06003780`의 128바이트도 0이었다. **한 시점에 0이라는 관측은 사용하지 않는 메모리의 증거가 아니다.** 이 조사 시점에는 그 자리에 코드를 쓰지 않았다. 이후 사적 시험은 아래에 구분한다. 로딩·기존 참조·스택/버퍼·장면 전환 수명과 원래 FC 명령의 호환 반환을 더 확인해야 한다. EXEC0 EOF를 늘려 BSS에 코드를 넣는 방법은 계속 사용하지 않는다.

### 태그를 구분하는 IP 조회 함수의 사적 시험 (2026-10-10)

위험한 전체 EXEC0 허용 마스크를 추가하지 않고, 저장소 밖에서만 IP 위치의 호출 계약을 시험했다. FC 뒤의 네 바이트가 직접 정한 `FQ01` 태그일 때만 조회하며 `6004`를 반환한다. 태그가 다르면 원래 FC의 `F000`을 반환하고 VM 결과를 바꾸거나 출격 표를 읽지 않는다. 기존 SH-2 디코더로 각 게임의 조회 331가지, 첫 네 바이트 중 하나가 다른 태그 1,020가지, 피연산자의 네 정렬을 검사했다. 모두 PR과 r1..r15를 보존했고, 조회 이외의 코드·표 쓰기는 없었다. 이는 원래 VM 호출자의 T 처리와 한정된 함수 검사이며 범용 호출 ABI의 보장이 아니다.

알려진 EXEC0의 IP 범위 PC 상대 32비트 참조는 F `0x06080D44`, 완결편 `0x0608720C`의 `0x06002000` 한 개씩이었다. 실제 경로의 F `0x06080E3C` / 완결편 `0x06087304`는 기존 스택을 저장하고 r15를 그 주소로 바꾸는 함수다. 이 알려진 스택은 IP 아래로 자라며 `0x06003780`을 직접 스택으로 쓰지 않는다. PC 상대 참조 검사나 이 함수만으로 계산된 주소 참조·DMA·다른 버퍼 사용까지 없다고 단정하지 않는다.

F 사적 출력 SHA-256 `fd70c0235979b2ff42c1f5530f9f052dcbf2b1b8de84b03505f615f68c7f190e`는 원래 IP의 0x1780..0x1800에 직접 작성한 128바이트, FC 포인터 네 바이트, 물리 본문 1의 사적 래퍼만 변경했다. IP 선언 길이와 비어 있는 원문 128바이트를 먼저 검증하고 세 영역 모두 EDC/ECC와 재읽기를 확인했다. SCEDATA는 원래 14,741바이트에서 14,754바이트로 늘었고 압축본 7,440바이트는 기존 7,820바이트 슬롯 안에 들어갔다. 시나리오 RAM 끝까지 패딩하지 않았다.

콜드 부팅의 7663프레임에 `0x06003780`을 두 번 호출했다. 첫 호출은 태그 없는 FC이며 출격 표를 읽지 않고 VM 결과를 보존해 `F000`으로 복귀했다. 두 번째는 `FQ01`이며 실제 표 `0x20201AA0`의 74칸을 읽고 VM +20에 빈칸 74를 쓴 뒤 `6004`로 복귀했다. 두 호출 모두 PR과 r1..r15가 일치하고 RAM의 코드 128바이트가 직접 작성한 함수와 같았다. `0x06003780..0x060037FF` 변경 감시는 BIOS가 IP를 읽은 438프레임의 25개 쓰기만 관측했다. **이 감시는 해당 주소 별칭만 포함하며 다른 별칭·DMA까지의 무쓰기를 증명하지 않는다.** 같은 출력에서 만든 MCA를 이어 사용한 후 원래 맵의 기체 그림과 배치도 표시됐다. 이 F 호출에서는 출격 표 전체 1,184바이트의 전후 스냅샷을 얻지 않았으므로 전체 표 비교로 기록하지 않는다.

완결편 사적 출력 `aab0c0a28829ecda3a9c79f207c344b1054643bb3c6805adf677c1d979bf04f9`도 같은 세 영역만 바꿔 압축·체크섬·재읽기를 통과했다. 원래 13,462바이트에서 13,475바이트로 늘었고 압축본 7,584바이트는 기존 8,067바이트 슬롯 안에 들어갔다. 해당 출력의 콜드 부트로 만든 MCA만 이어 사용했고, 저장 확인창을 벗어나 실제 시나리오 대화를 진행한 뒤 4042프레임에 태그 없는 FC와 `FQ01`을 각각 호출했다. 전자는 VM 결과 보존·표 읽기 0·`F000` 복귀, 후자는 실제 표 `0x20201AA0`의 74칸 조회·빈칸 74·`6004` 복귀를 확인했다. PR과 r1..r15, 함수 128바이트도 대조했다. 별도 256바이트 이하 peek 다섯 개를 합쳐 출격 표 1,184바이트가 진입과 복귀 때 같으며 조회한 74개 첫 byte와도 일치함을 검증했다. 같은 장면의 새 함수 영역 감시에는 쓰기가 없었고 이후 원래 맵의 기체 배치가 표시됐다. **이 결과는 다른 시나리오나 메모리 별칭·DMA까지의 상주 안전성 근거가 아니다.** 두 출력 모두 실제 제품의 새 검사에서 `EDITOR_CUSTOM_PROVENANCE`로 거부됐다. 승인 릴리스나 제품의 BIN 쓰기 권한에 등록하지 않았다.

사적 실행의 backup 파일은 기존 조사에서 게임이 만든 복사본이다. 격리된 에뮬레이터의 backup 파일명 규칙만 기존 복사본의 이름으로 지정했고, 실제 이미지 식별 값과 MCA 식별 값은 강제하지 않았다. 제품의 저장 데이터 호환성 문제를 해결한 근거로 계산하지 않는다. 남은 단계는 다른 시나리오에서의 수명, 빈칸 0일 때의 생성 차단과 실제 한 번만 생성하는 콜백이다.

### 생성 직전의 세 할당 표 검사와 프레임 경계 (2026-10-10)

CA02 핸들러 F `0x060242B8` / 완결편 `0x06026810`은 12바이트 항목마다 일반 생성 함수 F `0x060256BC` / 완결편 `0x06027544`를 한 번 호출한다. 이 함수는 파일럿 캐시, 기체 캐시, 출격 개체 순서로 할당한다. 각 표에서 최대 한 칸씩 필요하며 출격 표만 확인하면 앞의 두 캐시가 부족한 경우를 놓친다. 합체 부품을 추가로 할당하는 CA00의 아군 생성 함수와 이 일반 생성 함수를 동일하게 취급하지 않는다.

| 표 | 칸 수 / 간격 | 빈칸 판정 | 포인터 전역 F / 완결편 |
| --- | --- | --- | --- |
| 출격 개체 | 74 / 16바이트 | 첫 byte `FF` | `0x060B207C` / `0x060B855C` |
| 파일럿 캐시 | 128 / 12바이트 | 첫 BE word `0000` | `0x060B208C` / `0x060B856C` |
| 기체 캐시 | 128 / 30바이트 | 첫 BE word `0000` | `0x060B2088` / `0x060B8568` |

F5의 참 분기는 `F000`을 반환하여 현재 VM 호출을 끝낸다. F4의 거짓 분기는 `6004`로 같은 호출 안에서 다음 명령을 실행한다. 따라서 ‘여유 조회 → F5 참 분기 → 다음 프레임 생성’은 그 사이 원래 게임 처리가 빈칸을 사용할 수 있다. 사적 증원 컴파일러는 `FC FQ02 → F4 (여유 ≤ 0이면 대기) → CA02`로 바꿨다. 여유가 있을 때 조회·비교·생성을 같은 호출에서 실행하고, 없으면 양보한 뒤 다시 조회한다. 이는 확인된 VM 반환 계약을 반영한 연구 코드이며 브라우저에서 가져오지 않는다.

직접 작성한 FQ02 SH-2 함수는 `0x06003700`의 256바이트 후보 영역에서 세 표의 빈칸 수 중 최솟값을 VM +20에 쓴다. 코드 170바이트와 0 패딩 86바이트이며 원문 IP의 선언 길이 `0x1800`과 마지막 `0x100`바이트가 0인 것을 먼저 검사했다. 다른 태그는 원래 FC의 `F000`을 반환하고 세 표와 VM 결과를 건드리지 않는다. 기존 디코더를 사용한 별도 실행 검사에서 각 게임의 조회 840가지, 태그 불일치 1,020가지, 피연산자 정렬 네 가지가 통과했다. 결과 외 쓰기는 임시 스택 16바이트이며 PR과 r1..r15를 보존했다.

게임 메뉴에서 저장을 선택해 ‘세이브 완료’를 확인했다. 이 실행에서 사용하는 게임 backup 파일의 SHA-256은 저장 후 `f9d2979777b5a70e6d4b550d3c8692395a18b456008c8611948f28c08ee098aa`로 바뀌었다. 저장소 밖의 새 격리 폴더에 이를 복사하고 MCA를 모두 제거한 상태를 검사한 뒤, 같은 전체 해시의 BIN을 처음부터 부팅했다. 타이틀의 ‘이어하기’로 실제 게임 저장을 읽었으며, 이전 실행의 MCA를 새 부팅에 불러오지 않았다. 이후 관측을 위한 재개는 이 새 부팅에서 만들어진 MCA만 사용했다. RAM 쓰기·치트와 native media ID 강제는 없었다.

게임 저장 직후와 새 부팅·이어하기 뒤에 각각 입력 없는 5프레임 관측을 했다. 턴 byte는 양쪽 모두 6, 즉 턴 3이었다. game state +0x524/+0x528/+0x52C의 세 재개점과 출격·파일럿·기체 표 전체 6,560바이트가 바이트 단위로 같았다. 추가된 출격 59번의 기체/파일럿 캐시 연결도 유지됐다. 해당 기체의 AI는 생성 시 시작점 `0x20203A24`에서 플레이 중의 재개점 `0x20203A4E`로 진행한 상태였으며 이 값까지 복원됐다. 재개점의 원래 상대 분기는 같은 시작점으로 돌아간다. AI의 시작 주소가 플레이 내내 고정된다고 가정하지 않는다.

복원된 게임에서 다시 턴 종료 메뉴를 선택했다. 3턴 적군 시작의 실제 VM 읽기는 생성 이후 완료 루프에 진입했고, E9와 E8 FFF2는 다시 `0x20206CBD`를 저장했다. 이 콜백 동안 세 표는 그대로였으며 새 여유 조회·F4·CA02·일반 생성 함수의 호출이 없었다. 로그 한도에 걸리지 않았다. 따라서 **이 완결편 경로의 1턴 미생성 → 2턴 한 기 생성 → 게임 저장 → 새 부팅·이어하기 → 3턴 미생성**을 확인했다.

이 근거는 동일한 사적 BIN과 관측한 원래 출격 조합에 한정된다. 편집을 다시 한 다른 BIN에서 옛 게임 저장을 재사용하는 호환성, F 대응 실행, 모든 원래 할당의 최대 점유, 다른 장면에서의 함수 상주, 제품 UI·JSON·출처·출력 권한은 증명하지 않는다. 격리 실험의 backup 파일명 규칙은 기존 조사용 이름을 계속 사용했으며 일반 에뮬레이터의 저장 파일명 호환성을 해결한 근거가 아니다. 신규 증원은 제품에서 계속 거부한다.

### F의 기존 후속 콜백 보존과 추가 호출의 문맥 (2026-10-10)

F 최신 a 입력의 전체 SHA-256을 다시 확인하고, 기존 SCEDATA·해제 TSR 분석 사본이 해당 BIN의 ISO 파일에서 읽은 바이트와 같은지 대조했다. 물리 본문 1의 root 5는 해제 주소 2544..2813이며 빈 콜백이 아니다. 기존 판독기는 턴 5·6의 비교 조건과 2575의 CA02 목록에서 무사이개/ＤＣ병사 항목을 읽는다. 2595의 E1.11 및 2759의 BF.09에서 해석을 멈춘다. 따라서 이 root 5를 빈 루프로 대체해 F 증원 검증을 통과시킨 것으로 계산하지 않는다.

F 본문 1과 완결편 본문 5의 root 1/3/7은 모두 104를 가리키며, 그곳은 444바이트의 실제 스크립트다. 원시 TSR 바이트에서 E8 FF07이 안 보인다는 관측은 root 7이 미사용이라는 권한이 아니다. 56..103의 헤더 뒤 데이터에도 0 값과 60..80으로 돌아오는 상대 참조가 있다. 이 영역을 별도 콜백 포인터나 상태 저장 공간으로 쓰는 것은 아직 허가하지 않는다.

완결편 E8의 FF00..FF0F 경로는 `0x0601F5C0..610`에서 선택한 스크립트 위치를 VM 문맥 +0에 넣는다. 선택만으로 별도 스크립트가 호출되는 것은 아니다. FFF9의 `0x0601F4C8..4E8`은 실제 반환 위치를 문맥 +68의 스택에 넣고 선택한 스크립트를 호출한다. 이 호출은 부모의 조회값·판정 플래그를 별도 보관하지 않는다. 새 호출을 원래 페이즈 처리에 추가할 때에는 원래 root 4/5의 저장 재개점뿐 아니라 부모 문맥 소비도 보존해야 한다.

E1.11의 공통 entry 17 경로를 기존 해석기로 추가 조사했다. 완결편 TSR 전체 0x7F6C에서 시작하며, 0x7F71의 85.13은 네이티브 `0x0605D7B4..7EE`의 두 반환값 5002/5004로 정확히 두 상대 분기를 선택한다. 첫 목적지까지의 거리를 표 길이로 추측하지 않았다. 두 경로의 다음 미해석 지점은 0x7F89의 38과 0x8251의 1E이며, 이를 건너뛰어 원래 할당 전체를 확인했다고 하지 않는다. 다음 최소 검사는 F의 이 기존 콜백 명령·상대 참조·복귀와 추가 호출의 부모 문맥 계약을 확정하는 것이다.

### 기존 배치의 읽기 전용 표시 확장 (2026-10-11)

기존 편집 판독기는 미해석 명령에서 멈추므로 F 기본 제1화의 편성 기체 9개, Super 제1화의 배치 자료, 완결편의 일부 출격 위치가 목록에 나타나지 않았다. 새 판독기는 **출처 검증이 끝난 뒤 화면용 자료만 보강**한다. 원래의 편집 가능 항목, 해제/디스크 쓰기 마스크, region context, 개인 편집본의 출처 범위와 writer lookup은 그대로다. 신규 증원을 만드는 권한이나 추가 좌표의 쓰기 권한을 주지 않는다.

완결편의 읽기 전용 수에는 기존 좌표·맵 대응이 닫히지 않은 CA02 3개도 포함된다. 기존 판독기의 초기 / 사건 항목은 F 427 / 148, 완결편 810 / 287 그대로다. 추가 표시 중 root4의 호출·재개 전 구간은 F 54개, 완결편 45개이며, 나머지 F 1,089개와 완결편 1,963개는 **등장 시점이 닫히지 않은 시나리오 배치**로 분류한다. root4라는 이유만으로 첫 턴이나 유일한 초기 실행을 주장하지 않는다. F 기본 제1화의 CA01 9개는 명시 맵 선택 뒤, E1.11 호출 전에 있어 맵과 연결된다. 호출 뒤 추가 CA02는 목록에서 확인할 수 있어도 맵·턴을 추정하지 않는다.

CA01의 항목 끝 BE16은 런타임 편성 참조이며 고정 기체·파일럿 번호가 아니다. 모드 `00/40/80`은 `X & 63`, `Y & 63`을 편성 조회·배치 함수에 전달한다. `C0`는 두 바이트를 묶은 참조를 별도 함수에 넘기므로 직접 X/Y를 표시하지 않는다. CA00은 선택한 출격 기체의 순서에 따라 2바이트 위치 목록을 소비한다. 실제 기체·파일럿·보상은 이 목록에서 만들지 않는다. 저장된 좌표는 **출격 목표 위치**다. 배치 함수가 점유된 칸을 피하는 위치 탐색을 호출하므로 실제 최종 위치와 항상 같다고 단정하지 않는다.

실제 승인 EXEC의 CA01 호출 직전 조각을 게임별 X/raw-Y 전체 65,536조합에서 실행했고, CA00은 실제 자료의 범위인 0..63의 X/Y 4,096조합에서 실행해 전달 인수를 대조했다. F는 CA01 `0x060241DA` → 편성 배치 `0x060258E8` / packed 처리 `0x06026134`, CA00 소비 `0x0605F96E`에서 같은 편성 배치로 이어진다. 완결편은 CA01 `0x06026732` → `0x06027770` / packed 처리 `0x06027F6C`, CA00 소비 `0x06065CFA`가 대응한다. 이 검사는 실제 게임을 새로 플레이한 근거가 아니라 승인 EXEC의 정확한 명령 조각과 인수 경계 검사다.

새 고정 길이 문법은 실제 모든 본문의 root4/root5 그래프에서 도달한 피연산자로 다시 실행했다. F 3,975회 / 독립 네이티브 실행 1,378회, 완결편 7,187회 / 2,801회에서 미해석 경로·잘못된 길이·범위 초과가 0이었다. 런타임 상태에 따라 분기하는 native leaf도 분기별로 검사하며, 읽는 피연산자 바이트가 전부 같은 경우만 결과를 재사용한다. 완결편 `EE.03`은 네 표본에서 간접 점프가 닫히지 않아 문법에서 통째로 제외했다. 새로운 leaf의 길이가 닫혀도 맵이나 시점 보존은 증명하지 않으므로 둘 다 해제한다. 뒤의 명시 `C4.00`은 맵만 다시 연결하며 시점은 계속 미확인으로 둔다. 같은 root 안의 `03/04` 호출·복귀 경계만 제한적으로 따르고, root 밖의 호출 목적지는 추적하지 않으며, 확인된 복귀점 뒤에서는 맵·시점을 다시 추정하지 않는다. 경계 충돌이나 탐색 한도 초과는 해당 본문의 추가 표시를 폐기한다. 명령을 찾으려고 본문 중간을 바이트 검색하지 않는다.

현재 표시 판독기의 미해석 지점은 F 93개, 완결편 241개다. F에서는 `CF.01`, `88.00`, `68.28`, `EE.0F` 등이 남고, 완결편은 이들 외 `C0.16`, `BD.00`, `80.06`, 제외한 `EE.03` 등이 남는다. 완결편에서 표시 행이 없는 물리 본문은 `1, 2, 69–71, 87, 88, 91, 94–102`다. 해당 root는 대기 루프나 공통 처리로 이어지며, 표시 행이 없다는 사실을 실제 적·아군이 없는 장면이라는 뜻으로 쓰지 않는다. 다른 root·공통 스크립트·게임의 편성 상태 전체를 해석한 결과가 아니며, 조건부 경로의 모든 항목이 한 번에 출현한다고 주장하지 않는다.

CA02의 최초 진영은 `groupSelector & 3`이다. F `0x060242B8` → 일반 생성 `0x060256BC` → 기체 캐시 초기화 `0x0602D288` → actor 할당 `0x060251EC`, 완결편 `0x06026810` → `0x06027544` → `0x06031040` → `0x06029A8C`에서 같은 값이 기체 캐시 +2의 bits3..4, actor +3의 bits1..2로 전달된다. raw group과 원래 캐시/actor flags를 바꾼 게임별 4,096조합의 정확한 native 조각 검사와 기존 배치·화면 대응 근거로 0 아군 / 1 적군 / 2 기타 진영을 표시한다. 3 및 CA00/CA01은 미확인이다. 2를 중립으로 단정하거나 이후 사건에 따른 진영 변경을 반영했다고 하지 않는다.

F 정품 원본도 별도로 조사했다. canonical 이미지 SHA-256 `c198a93007d46161abe769b6f579f01cae89e23737c0a2ff38ec314d43b3adf8`, 실제 EXEC SHA-256 `a7e9a648641d728dcf6f60a778d6a1e5ccfebc77c92a0d3fd64cbcd5f19db409`를 확인하고 52본문의 신규 고정 leaf 3,975회 / native 실행 1,375회에서 실패 0을 확인했다. 같은 원본 EXEC로 CA01 65,536조합과 CA00 4,096조합을 다시 검사했고, 좌표·진영·CA02 생성 관련 조각도 승인 F와 바이트 동일했다. **완결편 canonical 원본의 동일 검사는 완료하지 못했다.** 완결편 원본 및 그 원본에서 만든 개인 BIN에서는 이번 추가 표시만 닫고 기존 검증된 판독·편집·저장 범위를 유지한다. 최신 승인 한글패치 계열과 그 개인 편집본은 추가 표시를 사용한다.

실제 승인 전체 BIN에서 F 본문 1의 기존 사건 좌표·보상 선택과 완결편 본문 3의 기존 초기 좌표·보상 선택을 TSR root32 보상표 수정과 함께 저장했다. 독립 Node SHA-256 검사 뒤 receipt 없는 새 세션에서 두 출력 모두 `bounded-editor-profile`로 다시 열렸다. 변경된 해제 바이트는 각 본문 X와 보상 선택 두 곳, root32의 파츠 한 곳뿐이었다. 모든 추가 읽기 전용 행, 나머지 본문·TSR root, 기존 scopes, 원본 세션·원본 파일이 보존됐다. 읽기 전용 행의 쓰기는 거부됐고, 재열기 뒤 무변경 저장은 같은 Blob과 같은 전체 해시를 반환했다. 출력은 게임 파일을 저장소에 넣지 않고 메모리에서 검증했다.
