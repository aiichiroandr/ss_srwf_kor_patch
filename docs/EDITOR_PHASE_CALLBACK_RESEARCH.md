# SCEDATA root 4 / 5 콜백 호출·재개 조사

2026-10-10. 최신 승인 F v0.5 a와 F완결편 v0.3 c의 EXEC0 / 압축 해제 TSR을 대조했다. 첫 조사에서는 기존 네이티브 trace만 재검토했고, 후속 완결편의 실제 관측은 마지막 절에 따로 기록했다. 게임 바이트·UI·편집 범위를 변경하지 않았다. 추출 파일·실행 trace·메모리·저장 상태는 저장소 밖에만 둔다.

**root 4는 새 아군 턴 경로뿐 아니라 맵 준비 경로에서도 사용한다. root 4에 코드를 넣었다는 사실만으로 ‘아군 시작마다 한 번’ 실행되는 새 사건을 보장할 수 없다.** 확인된 root 5 재개 경로는 턴 종료 확인 이후 적군 처리 경로다. root 4 / 5는 각각 별도 재개 위치를 보존하며, 초기 등록과 실제 호출은 서로 다른 명령이다.

## 좌표·근거 범위

- 아래 `0x4xxx` 등의 공통 스크립트 좌표는 **압축 해제 TSR의 root 0 세그먼트 상대 오프셋**이다. 두 게임 모두 root 0 시작은 전체 압축 해제 TSR `0xA4`다. SCEDATA 본문 번호·게임 화수·EXEC0 주소가 아니다.
- `0x060xxxxx`는 EXEC0의 SH-2 런타임 주소, `0x202xxxxx`는 해당 trace의 실제 RAM 주소다. RAM 주소를 다른 부팅에 고정 적용하지 않는다.
- TSR 포인터는 포인터 셀 주소에 signed BE32 변위를 더해 해석했다. 그룹 번호나 물리 순번을 화수로 바꾸지 않았다.
- 현재 조사에서 확인한 공통 경로를 열거한다. 원시 바이트 검색이나 부분 디코더 결과를 전체 게임의 완전한 간접 호출 그래프로 주장하지 않는다.

### E8 FF04 / FF05: 루트 선택

E8는 `CTX[0]`에서 BE16 피연산자를 읽는다. root 4 / 5를 호출하는 명령에 아군·적군을 뜻하는 별도의 네이티브 `r4` 인수가 있는 구조가 아니다. **핸들러 진입 때 남아 있는 r4 / r5 값**을 콜백의 인수로 해석하지 않는다.

FF04 / FF05 경로는 `gameState[6] << 8 | rootIndex`를 구성한다. 상위 바이트를 `RESUME + 31`에 기록하고, 상위 값이 0이 아니면 현재 SCEDATA 포인터와 하위 루트 번호로 root를 조회한다. 상위 값 0에는 별도의 공통 컨테이너 조회 경로가 있다. 반환된 시작 위치를 `RESUME[0]`에 넣는다. 따라서 `gameState + 6`의 선택 번호와 현재 SCEDATA 적재 문맥도 보존해야 한다. 이 선택 번호를 화수나 페이즈라고 표시하지 않는다.

이 **선택**만으로 root 본문을 실행하지 않는다. 뒤의 FFF1 / FFF2가 재개 슬롯에 저장하고, 나중의 FFFC / FFFD가 그 슬롯을 읽어 실행한다.

### E8 FFF1 / FFF2: 독립 재개점 저장

- FFF1은 전역 `RESUME[0]`을 `gameState + 0x524`에 저장한다.
- FFF2는 전역 `RESUME[0]`을 `gameState + 0x528`에 저장한다.
- 같은 구현의 FFF3는 root 8의 재개 위치를 `gameState + 0x52C`에 저장한다.
- 저장 직전 PC에서 `r0 = 0x524 / 0x528 / 0x52C`, `r1 = 저장할 재개 주소`, `r2 = game state 주소`다. 이 시점의 레지스터는 실제 쓰기 대상과 값을 확인하는 근거로 사용할 수 있다.
- 핸들러 결과는 `0x6002`이며 BE16 인수를 소비한다. E8 전체 명령은 3바이트다.

저장 슬롯은 분리되어 있지만 그 슬롯으로 옮기기 전의 `RESUME[0]`은 공유한다. root 8 등 다른 콜백의 E9가 이 전역 값을 변경하는 동안 이미 저장된 `+0x524` / `+0x528`이 그대로 남는 것을 F trace에서도 확인했다.

### E8 FFFC / FFFD: 저장된 문맥 호출

FFFC는 `+0x524`, FFFD는 `+0x528`의 주소를 `CTX[0]`으로 읽는다. 호출 전에는 피연산자 커서에 2를 더한 **E8 다음 명령 위치**를 VM 반환 스택에 넣고 `CTX + 0x44`의 byte 깊이를 증가시킨다. 스택 셀 주소는 `CTX + 4 + 4 × 이전 깊이`다. 호출 꼬리에서는 `RESUME + 37`의 상위 nibble을 지우고 결과 `0xF000`으로 디스패처에 돌아간다. 그 nibble의 게임 의미는 이번 조사에서 확정하지 않았다.

| 분기 | F | F완결편 |
| --- | --- | --- |
| FFFC: root 4 슬롯을 호출 | `0x0601E222` | `0x0601F4EA` |
| FFFD: root 5 슬롯을 호출 | `0x0601E23C` | `0x0601F504` |
| 공유 슬롯 읽기 / CTX 쓰기 | `0x0601E272 / 0x0601E276` | `0x0601F53A / 0x0601F53E` |

이 명령 자체는 새 턴 여부·한 번 실행 여부를 판정하거나 콜백마다 새 전역 문맥을 만들지 않는다. 호출 원인과 재개 위치를 구별해야 한다. 스택 범위 검사의 존재는 확인하지 않았으므로 임의의 중첩 호출을 추가하지 않는다.

### E9: 다음 호출에 이어 실행할 위치를 저장하며 복귀

주 E9 핸들러는 helper에 `r4 = 0`을 전달한다. 디스패처가 opcode를 이미 소비했으므로 이 helper에서 다음과 같이 처리한다.

1. `RESUME[0] = CTX[0] + r4`, 즉 E9 바로 뒤의 위치를 기록한다. 실제 쓰기는 F `0x0601F44E`, 완결편 `0x060209B6`이다.
2. `CTX + 0x44`의 깊이를 하나 줄인다.
3. 해당 깊이의 반환 스택 셀을 읽어 `CTX[0]`으로 복귀한다.
4. 사용한 반환 셀을 0으로 지운다. 주 핸들러는 `0xF000`을 반환한다.

**E9는 루트의 끝을 뜻하는 종료 표지가 아니다.** 뒤의 코드가 다음 호출에 이어 실행될 수 있다. 인접 EA 핸들러는 같은 helper 뒤에 전역 재개 주소를 0으로 지우므로 E9를 EA로 바꾸는 것도 같은 동작이 아니다.

0A도 같은 반환 스택을 사용한다. 0A 명령의 4바이트 피연산자 셀을 기준으로 signed BE32 변위를 더해 목적지를 계산하고, 피연산자 커서 +4를 반환 위치로 저장한다. 전체 명령은 5바이트다. 공통 스크립트의 **0A 호출 복귀 위치**와 root 콜백 내부의 **E8 다음 위치**를 혼동하면 호출 이유를 잘못 분류하게 된다.

## 공통 TSR에서 확인한 경로

[기존 공통 국면 조사](EDITOR_SCENARIO_RESEARCH.md)의 좌표를 최신 승인 입력에서 다시 대조했다. 원시 E8 검색은 두 게임 각각 아래의 8곳을 찾았다. 검색 결과 자체는 명령 경계·모든 분기의 도달 가능성을 보장하지 않는다.

| 역할 | F root 0 상대 | 완결편 root 0 상대 |
| --- | --- | --- |
| 초기 root 4 선택 → 저장 | `0x47A4` FF04 → `0x47A7` FFF1 | `0x4D4D` FF04 → `0x4D50` FFF1 |
| 초기 root 5 선택 → 저장 | `0x47AA` FF05 → `0x47AD` FFF2 | `0x4D53` FF05 → `0x4D56` FFF2 |
| root 5 재개 → 새 재개점 저장 | `0x4C12` FFFD → `0x4C15` FFF2 | `0x4E56` FFFD → `0x4E59` FFF2 |
| root 4 재개 → 새 재개점 저장 | `0x4CAC` FFFC → `0x4CAF` FFF1 | `0x4F48` FFFC → `0x4F4B` FFF1 |

초기 선택·등록은 root 0 그룹 2의 sequence 8, F 시작 `0x4759` / 완결편 `0x4CF6` 안에 있다. 이번 선형 디코더는 그 진입부터 F `0x4771` / 완결편 `0x4D1A`의 미해결 C0.05에서 멈췄다. **진입에서 등록 명령까지의 모든 분기 순서를 이번 도구로 재증명한 것은 아니다.** 네이티브 E8의 선택·저장 계약과 그 구간에 있는 실제 피연산자는 별도로 대조했다.

| 공통 경로 | F 호출 → 목적지; 복귀 | 완결편 호출 → 목적지; 복귀 | 이번 재확인 범위 |
| --- | --- | --- | --- |
| 맵 준비의 첫 root 4 wrapper 호출 | `0x0210 → 0x4CA9`; `0x0215` | `0x022D → 0x4F45`; `0x0232` | 각 맵 준비 진입에서 이 0A까지 실제 EXEC0로 명령 경계 확인 |
| 맵 준비의 다른 root 4 wrapper 참조 | `0x0275 → 0x4CA9`; `0x027A` | `0x02A9 → 0x4F45`; `0x02AE` | 기존 국면 지도와 최신 원시 상대 참조 일치; 이번 선형 도구는 앞의 미해결 switch에서 멈춤 |
| 새 아군 턴 루틴 호출 | `0x0282 → 0x4C95`; `0x0287` | `0x02BE → 0x4F17`; `0x02C3` | 기존 국면 지도·최신 상대 참조 일치. F 실제 trace의 호출 복귀 위치도 일치 |
| 턴 종료 확인 뒤 적군 루틴 호출 | `0x03E6 → 0x4BDB`; `0x03EB` | `0x03FE → 0x4E19`; `0x0403` | 기존 국면 지도·최신 상대 참조 일치. F 실제 trace의 호출 복귀 위치도 일치 |

F 새 아군 루틴 진입 `0x4C95`에서 wrapper `0x4CA9`, E8 FFFC / FFF1까지는 이번 네이티브 선형 디코딩이 미해결 없이 이어졌다. 완결편 새 아군 루틴은 `0x4F31`의 EE에서 도구 한계에 도달했으므로 같은 수준의 새 전체 경계 증명으로 표시하지 않는다. 완결편 대응 wrapper와 기존 원본 국면 구간이 최신 승인 c에서 바이트 단위로 같다는 앞선 조사 근거는 유지한다.

첫 조사만으로는 두 맵 준비 참조가 한 맵 시작에서 모두 실행되는지 확정하지 못했다. 마지막 절의 후속 완결편 한 경로에서는 두 참조가 모두 실행되는 것을 관측했다. 이를 F와 모든 맵의 ‘항상 두 번’이라는 규칙으로 확대하거나, 위 참조 외의 간접 경로가 없다고 주장하지 않는다.

공통 적군 처리 뒤의 턴 증가 명령은 F `0x4C63`의 D4 sub2(2바이트), 완결편 `0x4EAD`의 D4 sub2(3바이트)다. `D4 00`은 game state +16 byte를 한 비트 오른쪽 이동한 턴 조회다. +16의 하위 bit나 +14 word를 진영·페이즈로 판정하는 근거는 없다. 초기 준비와 실제 턴 콜백의 구별에 단순히 `턴 >= 2`만 사용하지 않는다.

## 기존 F 실행 기록의 실제 관측

재사용한 세 기록은 동일한 승인 입력 기반 개인 편집 BIN의 네이티브 실행이며 게임 RAM 직접 수정이 없다. 이미 만들어진 저장 상태에서 이어 실행한 **제한된 창**이다. 변경 없는 승인 BIN의 초기 부팅·모든 맵·모든 턴 호출 횟수를 검증한 것으로 확대하지 않는다.

세 계획은 E8 진입 `0x0601E0DC`, E9 진입 `0x0601E37C`, 슬롯 쓰기 직전 `0x0601E1AE`를 실제 watch했다. 각 기록에는 `CTX` 앞 24바이트, `RESUME` 80바이트, game state +0x524부터 16바이트가 있다. 이 지점의 game state 앞 32바이트는 수집하지 않았으므로 콜백 진입마다 raw 턴 byte를 직접 확인한 것은 아니다.

| 기록 | 전체 PC hit / 한도 | root 4 호출·저장 | root 5 호출·저장 | 관측 범위 |
| --- | --- | --- | --- | --- |
| `native-fcomposed-phase1-f-1` | 221 / 250 | 각각 1회 | 각각 1회 | 적군 루틴에서 다음 아군 루틴까지 |
| `native-fcomposed-phase2-f-1` | 91 / 250 | 창 안에서 관측 없음 | 각각 1회 | root 5의 다음 대기점까지; 이후 root 4 부재를 주장하지 않음 |
| `native-fcomposed-phase4-f-1` | 173 / 250 | 각각 1회 | 창 안에서 관측 없음 | 이미 진행 중인 적군 처리에서 다음 아군 루틴까지 |

세 보고서는 정상 종료, timeout 없음이다. hit 한도에 도달하지 않았다. phase1에는 전체 E9 / 공통 슬롯 쓰기가 각각 17회, phase4에는 각각 15회 있지만 상당수는 root 8 경로다. **이 합계를 root 4 호출 횟수로 세면 안 된다.**

phase1의 공통 root 0 RAM 시작은 `0x2022B0A4`다. E8 피연산자 커서와 바깥 0A 반환 위치가 최신 TSR의 독립된 두 좌표와 함께 일치한다.

| 순번 / 프레임 | 실제 관측 |
| --- | --- |
| 0 / 432 | FFFD 진입 커서 `2022FCB7`, root 0 명령 `4C12`, 바깥 반환 `2022B48F = root0 + 03EB`; +528은 `20215195` |
| 33~35 / 432 | root 5 E9 뒤 FFF2; 전역 재개 `202151C7`; 쓰기 직전 r0=`528`, r1=`202151C7`, r2=`20200000` |

## 기존 완결편 기록이 증명하는 범위

`native-enemy-once-phase1-advance-final-2`와 `native-enemy-once-all-command-final-1`의 계획은 E8 / E9 / 콜백 슬롯 쓰기를 watch하지 않았다. 해당 trace에 콜백 PC가 없다는 사실을 ‘호출 0회’로 해석하지 않는다.

`native-enemy-once-turn3-global-final-1`, `native-enemy-once-save-reload-global-final-1`는 E9와 저장 PC를 watch했지만 해당 제한 창에 hit가 없었다. E8 진입은 watch하지 않았다. 이 기록들만으로 root 4의 시작 시점이나 횟수를 계산할 수 없다.

`native-enemy-once-reloaded-phase3-final-1`은 실제 새 부팅·이어하기 후의 기존 저장 상태에서 이어 관측한 창이다. 게임 RAM 직접 수정 없음, 정상 종료, timeout 없음이며 전체 10 PC hit 중 다음 두 쓰기와 두 E9를 관측했다.

## root 4를 새 아군 시작 사건의 host로 쓰기 위한 계약

현재 확인한 구조는 **후보 host**의 근거다. 아래 항목을 충족하기 전까지 새로운 아군 시작 사건 쓰기를 열 근거는 아니다.

1. **초기와 새 턴 구별:** 맵 준비 호출, 첫 아군 턴, 적군 처리 뒤 새 아군 턴의 실제 호출 순서와 횟수를 두 게임에서 확인한다. 같은 턴 메뉴 재진입이 콜백을 다시 부르는지도 측정한다. 루트 번호나 확인되지 않은 상태 bit로 추정하지 않는다.
2. **원래 root 4 재개 유지:** 원래 E9 뒤 위치·상대 분기·기존 등장/대사/플래그 처리를 보존한다. root 4와 root 5, root 8의 독립 슬롯을 함께 대조한다.
3. **전역 재개점 덮어쓰기 방지:** ‘원래 root를 중첩 호출 → 추가 사건 → 새 E9’만 이어 붙이면 원래 E9가 남긴 재개점이 새 E9 위치로 바뀔 수 있다. 원래 재개 문맥과 추가 사건의 완료 상태를 명시적으로 보존하는 컴파일 형태부터 검증한다. 현재 엔진에 새 재개 슬롯이 있다고 가정하지 않는다.
4. **한 번 실행 / 저장 후 재개:** 실행 완료를 저장하는 방법과 저장·새 부팅·이어하기 뒤의 완료 상태를 확인한다. 기존 게임 플래그의 빈 번호를 추측해 쓰지 않는다. 시작 시각만 맞는 조건과 한 번 실행되는 사건은 다르다.
5. **생성 안전성:** 사건이 기체를 생성하거나 원래 등장보다 빠르게 옮기면 최대 점유·복합 기체 추가 할당·원래 출격 슬롯 충돌을 별도로 확인한다. 콜백 타이밍 확인은 생성 안전성 검증을 대신하지 않는다.

## 첫 조사에서 정한 다음 최소 실행 계획

이미 설치된 네이티브 기록 도구를 재사용하고, 각 창은 별도의 저장소 밖 디렉터리에 짧게 기록한다. 첫 단계는 **변경 없는 최신 승인 두 게임의 읽기 전용 타임라인**이다. 아래 지점 외에 무차별 opcode watch를 넣지 않는다.

- E8 진입, FFFC / FFFD의 슬롯 읽기 뒤 공유 꼬리, E9 helper의 재개 저장 전·후, FFF1 / FFF2의 실제 슬롯 쓰기를 watch한다. 진입에서는 CTX의 BE16 피연산자로 명령을 구별하고, 저장 PC에서는 r0 / r1 / r2로 대상을 구별한다.
- 각 hit에서 CTX 앞 `0x48`바이트(반환 셀과 깊이 포함), RESUME 앞 `0x28`바이트, game state 앞 32바이트와 +0x524부터 12바이트, game state / SCEDATA 포인터 전역을 읽는다. 원래 콜백과 새 콜백을 섞지 않도록 현재 스크립트 주소의 소속도 기록한다.
- 현재 선택 번호, 실제 raw 턴, 바깥 0A 복귀 위치, VM 반환 깊이, 불러온 맵 문맥으로 호출을 분류한다. 이전 trace의 `202xxxxx` 주소를 고정하지 않고 현재 포인터와 실제 root를 기준으로 계산한다.
- 맵 첫 진입의 준비 경로 → 첫 아군 메뉴 → 턴 종료 확인 → 적군 콜백 → 턴 증가 → 다음 아군 메뉴를 한 창씩 관측한다. 각 콜백에서 같은 턴 몇 번 실행됐는지 센다. 두 맵 준비 참조의 상호 배타성은 실제 분기 기록으로 결정한다.
- 같은 아군 턴에서 메뉴 열기·닫기, 아군 대기, 그리고 아군/적군의 E9 대기점에서 저장 → 프로세스 종료 → 새 부팅 → 게임 이어하기를 각각 확인한다. 전후 +524 / +528 / +52C, 반환 문맥, 생성 개체와 완료 상태를 비교한다.
- 타임라인이 일치한 뒤 생성 없는 최소 사건 하나로 초기 호출 오실행·같은 턴 재호출·다음 턴 실행·저장 후 중복 실행 여부를 검증한다. 콜백 보존과 출력 재파싱을 확인한 다음에만 실제 증원 후보를 별도 검사한다.

다음 계획의 핵심 반증 조건은 ‘초기 맵 준비에서도 새 사건 실행’, ‘같은 턴 두 번 실행’, ‘원래 root 4 / root 5의 재개 주소 소실’, ‘이어하기 후 재실행’이다. 하나라도 발생하면 해당 컴파일 형태를 지원하지 않는다.

## 도구 한계와 막힘 대응 기록 — 첫 조사

- 가설: root 4 호출은 언제나 새 아군 턴 시작이고 한 턴 한 번이다.
- 관찰: 승인 공통 TSR에는 맵 준비 참조와 새 턴 참조가 함께 있다. 실제 F의 제한된 두 창에서 새 턴 쪽 root 4 호출·독립 재개점 저장을 각각 한 번 확인했다.
- 반증: 초기 호출과 저장 후 반복 재개를 구별하지 않은 ‘root 4 = 아군 시작’ 가정은 사용할 수 없다. 전체 E9 hit 수에도 root 8이 섞인다. 완결편 대응 호출의 실제 횟수는 현재 재사용 기록에 없다.
- 다음 최소 probe: 전체 CFG 디코더 한도를 계속 늘리는 대신, 위의 실제 반환 위치·상태·슬롯 쓰기를 짧은 읽기 전용 타임라인에서 관측한다. 원시 후보를 명령으로 건너뛰거나 미해결 길이를 추측하지 않는다.

기존 원본 grammar와 최신 EXEC0 기반 디코더를 모두 재사용했지만 C0 / switch / EE의 부분 해석에서 한계에 도달했다. 선형 명령 경계 확인, 원시 상대 참조, 실제 런타임 관측은 서로 다른 근거다. 이 문서는 그 차이를 유지하며 페이즈 이동·신규 아군 시작 사건의 구현 또는 검증 완료를 선언하지 않는다.

## 후속 완결편 실제 관측 — 동일 후보의 root 4 / root 5 경계

기존 완결편 once 후보 **정확히 같은 이미지**에서 생성한 저장 상태와 실제 패드 계획을 재사용했다. 대상 이미지 SHA-256은 `f903aeff0f464075aaf7073e490d86cd6ea8303011d1a2a1f21e127099a74790`다. 이 값은 승인 원본의 해시가 아니라 이번 개인 편집 후보의 전체 이미지 해시다. 다른 이미지에서 만든 승인 저장 상태를 이 이미지에 이식하지 않았다.

이 후보의 실제 물리 본문 5(선택 번호 102)의 root 4 `0xAAB..0xCBF`, 532바이트는 승인 입력에서 추출한 같은 물리 본문과 바이트 단위로 같다. root 4 SHA-256은 `9007b6efa8a5ed8e0767f7c0dbd5b4f2c11e79c90348c3263beaeab925cf7b93`이며, 비교 근거는 `N-root4-original-byte-proof.json`이다. 선택 번호 102를 물리 본문 102나 화수로 바꾸어 비교하지 않았다.

전용 wrapper는 각 source의 전체 이미지 해시, 단 하나의 own MCA와 그 해시를 실행 전에 검증하고 종료 뒤 다시 검증했다. 원 source MCA·이미지는 모두 불변이었다. 매 실행은 별도 home과 고유 `phase-root4-final-*` 출력 폴더를 사용했다. RAM 직접 수정·치트·미디어 식별값 강제 변경은 없고, 패드는 기존 계획의 실제 버튼 입력만 재사용했다. 이 결과는 네이티브 후보 한 경로의 근거이며 원본 승인 이미지의 전체 게임 검증이 아니다.

### 같은 초기 1턴의 실제 root 4 두 호출

`initial-map-1`에서 raw 턴은 계속 2였다. root 4 안의 D4 조회도 1을 반환했다. 이 한 실제 맵 진입에서는 기존의 두 준비 참조가 배타적이지 않았고, **게임 조회 1턴에 root 4를 두 번 호출**했다.

| 4896 / 22 | FFFC, 앞의 E9 다음 위치 `20204382` 재개, 깊이 2 | `2021D352 = root0 + 02AE`, 맵 준비 0A `02A9`의 복귀 | 호출 전 `20204382` |
| 5532 / 24~28 | root 4 E9 → 전역 쓰기 → FFF1, 깊이 1 | 같은 바깥 반환 셀 유지·내부 셀 소거 | `2020441A` 저장 |

두 호출의 내부 반환 셀은 모두 `20221FEF = root0 + 4F4B`이며, 재개 wrapper는 동일한 공통 E8 FFFC / FFF1이다. +528=`202044BF`는 6005프레임 창의 모든 hit와 전후 MCA에서 불변이었다. 이 흐름의 +524는 **루트 시작 → 첫 초기 재개점 → 후속 초기 재개점**으로 바뀐다. 매 호출을 독립적인 새 ‘아군 시작’으로 세거나 루트 시작으로 되돌리는 형태는 원래 준비를 훼손할 수 있다.

이는 ‘root 4는 한 턴 한 번 호출된다’는 가정의 실제 반증이다. 모든 맵이 같은 초기 호출 횟수나 스크립트 모양을 갖는다는 증거는 아니다.

### 다음 아군 턴의 실제 root 4 체인

`new-player-1`에서 2877프레임 D4 턴 증가 경로 뒤의 raw 값은 4였다. 3166프레임의 root 4 안 D4 조회는 **2**를 반환했다. 따라서 아래 호출은 원시 값 4인 **게임 조회 2턴**의 새 아군 턴이다. 이를 ‘4턴’으로 부르지 않는다. 화면 메뉴의 턴 숫자를 이 새 창에서 직접 캡처한 것으로도 주장하지 않는다.

- 순번 197, `0601F612`: decoded r5=`FFFC`, CTX 현재=`2020441A`, 깊이=2, 반환 셀=`2021D367`와 `20221FEF`, +524=`2020441A`, +528=`20206C9E`.
- 순번 199~201: 주 E9 → helper 전역 쓰기. `RESUME[0]`이 `202044E2`에서 `2020441A`로 바뀐다.
- 순번 202~203: FFF1 진입·실제 +524 쓰기, r0=`524`, r1=`2020441A`, 깊이=1. 내부 반환 셀은 0으로 지워졌고 바깥 셀 `2021D367`은 유지됐다.
- 두 반환 주소로 공통 root 0 시작을 독립 계산하면 `2021D367 - 02C3 = 20221FEF - 4F4B = 2021D0A4`다. 해당 RAM의 root 0 `4F48 / 4F4B`도 실제 FFFC / FFF1 명령이었다.
- 6005프레임 창의 모든 관측에서 +528=`20206C9E`가 유지됐고, 전후 MCA의 +524도 `2020441A`였다. root 8 호출 16회와 그 슬롯 쓰기를 root 4 횟수에 포함하지 않았다.

### 같은 게임 2턴의 적군 시작 root 5 체인

`enemy-boundary-1`은 raw 4인 2턴 종료 확인 뒤의 실제 A 입력이다. 319프레임에 decoded FFFD → E9 → FFF2를 한 번 관측했다.

- 호출 시 CTX=`20206C9E`, 깊이=2, 반환 셀=`2021D4A7`와 `20221EFD`다.
- E9 helper가 전역 재개를 `20206CBD`로 바꾼 뒤 FFF2는 깊이 1에서 +528에 같은 주소를 저장했다. 내부 반환 셀은 지워지고 바깥 셀은 유지됐다.
- `2021D4A7 - 0403 = 20221EFD - 4E59 = 2021D0A4`이며 실제 RAM 명령도 FFFD / FFF2였다.
- +528은 `20206C9E → 20206CBD`, +524=`2020441A`는 전체 창에서 불변이다. raw 턴은 계속 4이고, 이 805프레임 창에는 root 4 호출이 없었다.

**root 4의 새 아군 턴 호출과 root 5의 적군 시작 호출은 같은 게임 조회 2턴에 각각 존재한다.** 두 호출은 반환 위치·독립 슬롯으로 구별된다. 턴 숫자만으로 아군/적군을 구별할 수 없다는 직접 근거다. 적군 처리의 모든 지연·저장 상태에서 root 4가 언제나 호출되지 않는다는 보증으로 확대하지 않는다.

### 부모 문맥 비교와 남은 한계

전체 CTX 읽기는 +20 word / +37 byte / +68 depth와 반환 셀을 포함한다. 위 두 체인에서 E9의 깊이 2 → 1, 내부 셀 소거, 바깥 반환 셀 유지가 확인됐다. RESUME +20은 실제 D4 등의 결과로 바뀌며, +37 상위 nibble은 E8 호출 처리에서 지운다. 이 정상 명령의 변화를 문맥 손상으로 분류하거나, +37 값을 페이즈 번호로 이름 붙이지 않는다.

같은 턴 무입력 805프레임에서 CTX 100, game state 32, 슬롯 16, 루트 표 56은 전후 바이트 단위로 같았다. 알려진 RESUME 값·+20 / +37 / +68도 같았다. **RESUME 100바이트 전체는 같지 않았다:** +50 / +51만 바뀌었으며 이번 조사에서 그 필드의 의미는 확정하지 않았다. 콜백 호출이 없다는 사실을 모든 메모리가 정지했다는 뜻으로 해석하지 않는다.

이번 후속 산출물 `N-new-callback-observations.json`과 `N-callback-bounded-proof.json`에는 실제 callsite별 `summaryNativeCallback`, 전후 MCA·이미지 검증, 모든 사건의 raw 턴·슬롯·반환 문맥이 있다. 결정적인 trace SHA-256은 초기 맵 `9d955ffcb644b216047cf46cb8f89cbb29db3fce46496263d4a291316f8ab7e2`, 새 아군 `84eb85a6cc0f5bf3ee278c88e7f1e365964c8cb55ef4c1454496b1b6f54ae28a`, 적군 경계 `954d81915ba129281c08cd69a4ee0cdc16bb3967e9d42dca69bc65e6f9091920`이다.

이 근거로 완결편 한 실제 경로의 초기 두 호출, root 4 / root 5 분리와 새 턴 콜백 계약을 추가 확인했다. 다른 맵·분기의 최초 타임라인, 초기 호출을 배제할 조건, 모든 같은 턴 입력 경로, 새 root 4 사건의 완료 상태·cold Continue, 신규 생성 최대 점유는 아직 검증하지 않았다. 따라서 아군 시작 사건을 새로 쓰는 권한이나 페이즈 이동 UI를 열지 않았다.

## 후속 조사: 페이즈 이동·새 조건 사건의 닫힌 host

목표는 **원래 본문과 재개·부모 문맥을 보존하며 특정 사건을 옮기거나 더할 수 있는 완전히 닫힌 템플릿의 존재 여부**다. 빈 영역 검색이나 콜백 번호만으로 쓰기 범위를 넓히지 않는다. 이번에는 승인 BIN의 전체 SHA-256을 다시 확인하고, 해당 BIN의 ISO에서 읽은 SCEDATA가 기존 조사 사본과 정확히 같은지도 대조했다. 새 실험 BIN·RAM 변경·게임 실행은 만들지 않았다. 제품 코드·UI는 수정하지 않았다.

| 입력 | 전체 BIN SHA-256 | SCEDATA SHA-256 | 고유 물리 본문 |
| --- | --- | --- | --- |
| F v0.5 a | `b2a67ed2a409c95de7226d33f2ab934012e93199afb7284bb710c81b6f0223b9` | `26a3c66a55987323b2c47dd5214f9a2267c724d53f48ca79b16ebc538b091671` | 52 |
| 완결편 v0.3 c | `0fb10cbf4332f94c865c0e8d0a0c7234f8f6083bdbbb5a06198cebff871d195d` | `8902db80ae5aeecc11902adcfc5fc0ebe7bcfb216eb63e5ea01da23fc8081b6b` | 103 |

저장소 밖 `phase-host-research-20261010-1`에 승인 추출 동일성·루트 경계·기존 이벤트 판독 결과를 기록했다. `approved-host-inventory.json`, `static-callback-cfg.json`, `host-candidate-summary.json`, `minimal-final-root5-native.json`이 이번 읽기 전용 결과다. 기존 SCEDATA carrier / 이벤트 판독기와 기존 EXEC 유래 `scedis` 문법을 재사용했다. 일반 문법의 명령 경계가 이어졌다는 결과는 현재 두 게임의 모든 네이티브 동작·외부 호출·간접 참조가 닫혔다는 증거가 아니다. 특히 F는 완결편 문법과 달라 이미 확인한 D4.02 / BF.09 예외만 적용했고, 모르는 명령을 넘기지 않았다.

### 실제 빈 콜백과 초기화 뒤 대기 루프

여기서 ‘빈 콜백’은 다음 물리 루트까지 정확히 4바이트이며, E9 다음의 상대 분기가 같은 E9로 돌아오고, 다른 선언 루트가 그 영역을 공유하지 않는 경우다. E9 자체가 재개 주소를 저장하므로 실행 동작까지 없는 0 패딩이라는 뜻은 아니다.

| 구조 | F | 완결편 | 해석 범위 |
| --- | --- | --- | --- |
| 독립된 빈 root 4 | 0 | 2 | 완결편 물리 본문 1·2만 해당 |
| 독립된 빈 root 5 | 15 | 48 | 적군 콜백의 좁은 구조 후보; 실제 실행 가능한 15·48개 맵이라는 뜻이 아님 |
| 기존 root 4 안의 단순 E9 대기 루프 | 15 | 54 | 초기화나 후속 사건 이후의 기존 대기점; 루트 전체가 빈 것은 아님 |

완결편의 빈 root 4 두 본문에는 현재 판독상 맵·배치·턴 조건이 없다. 물리 본문 1은 선택 번호 1..73이 같은 자료를 공유하고, 본문 2는 선택 74다. 이를 74개의 새 아군 사건 삽입 지점으로 계산하지 않는다. 현재 실제 맵 선택 대상으로 연결된 빈 root 4 host를 발견한 것은 아니다.

기존 원시 상대 참조의 **거부 전용** 검사에서도 빈 root 5 중 F 1개·완결편 6개에 내부를 가리키는 가능성이 나왔다. 데이터가 명령처럼 보인 오탐일 수 있으므로 실제 incoming 참조라고 선언하지 않는다. 반대로 이 검사에서 후보가 없다는 사실도 알려지지 않은 간접 소비자가 없다는 증명은 아니다. 이 후보들은 닫힌 host로 허용하지 않는다.

단순 E9 대기 루프가 있는 root 4는 F 15개·완결편 54개이며, 앞선 실제 모델 QA에서 맵 연결이 있는 것은 각각 15개·52개다. 이 숫자는 **기존 재개점 구조의 수**다. 초기 몇 번째 호출에 그곳으로 들어가는지, 첫 턴에서 바로 반복하는지, 저장 후 어디로 재개하는지는 각 본문별로 확인해야 한다. 게임 화수·새 사건 지원 수·네이티브 도달 가능성으로 표시하지 않는다.

### 실제 첫 완결편 맵의 root 4는 빈 host가 아니다

물리 본문 5 / 선택 102의 원래 root 4는 `0xAAB..0xCBF`, 532바이트다. 앞 절의 원래 바이트 동일성 및 실제 두 초기 호출과 대조하면 다음처럼 이어진다.

- 첫 E9 `0xB81` 뒤 `0xB82`는 도입 대사·추가 CA02·기존 E1 호출 등을 계속 실행한다. 첫 E9 뒤를 ‘초기화 완료’로 취급하지 않는다.
- 두 번째 E9 `0xC19` 뒤 `0xC1A`는 원래 D4 조회 `0xC12`로 돌아간다. `0xC14`의 F2는 **게임 조회 턴 3과 같음**을 검사한다.
- 3턴 분기의 `0xC1D..0xCBE`에는 대사·CA00·E1·플래그 조회와 원래 E9 대기점으로 돌아가는 분기가 있다. 이 구간을 빈 완료 루프로 대체하면 원래 사건을 버린다.

실제 새 아군 2턴 관측에서 `+524 = 2020441A`는 해제 본문 `0xC1A`에 해당했고, 원래 3턴 조건이 불충족하여 같은 재개점을 다시 저장했다. **저장된 주소가 그대로였던 관측은 빈 코드의 증거가 아니다.** 확인한 실제 경로에서 원래 조건을 재검사한 결과다. 3턴 사건 전체를 이번 후속 조사에서 새로 실행한 것으로 주장하지 않는다.

### 가장 작은 기존 조건 사건: 완결편 본문 9

물리 본문 9 / 선택 106의 root 5 `2790..2805`는 15바이트, 5명령이다. 현재 승인 EXEC에서 각 명령의 길이·분기·E9 재개를 다시 확인했으며 이 다섯 명령에는 구체 실행기의 미해결 경로가 없다.

1. `2790` D4.00: game state +16을 오른쪽 한 비트 이동한 게임 턴을 조회한다.
2. `2792` F3: 조회값이 4와 **다르면** `2801`로 건너뛴다. ‘4턴 외에 플래그를 켠다’는 조건으로 뒤집어 표시하지 않는다.
3. `2797` D0.00: 조회 턴 4일 때 기존 이벤트 플래그 250을 켠다.
4. `2801` E9: `2802`를 저장하고 원래 부모로 반환한다.
5. `2802` 상대 분기: 다음 root 5 호출에서 `2790`부터 다시 검사한다.

이는 **작은 반복 조건 사건**의 실제 문법이다. 실행 완료를 따로 보존하는 한 번 실행 템플릿이 아니다. 같은 턴에 다시 부르면 같은 플래그를 다시 켤 수 있으며, 플래그 OR 쓰기의 반복이 새 임의 동작의 반복 안전성을 보장하지 않는다.

D0.00의 현재 네이티브 경로는 `06021124..0602114C`에서 BE16 인수 250을 `060216D0` helper로 넘긴다. helper는 game state `+0x534 + (250 >> 3)`, 즉 **+0x553의 bit 0x20**을 OR한다. 외부 시프트 helper의 실제 선택 경로도 대조했다. 이 플래그는 같은 본문의 root 8 시작 `2805`에서 D0.02로 이미 읽으며, 그 뒤 조건 분기·C1.02·CA02 처리로 이어진다. **250을 새 사건용 비어 있는 플래그로 재사용할 수 없다.** root 5의 시점을 바꾸면 독립 슬롯 `+52C`로 돌아가는 기존 root 8 사건의 조건 시점도 바뀔 수 있다. 이번 정적 소비 확인을 그 root 8 사건의 실제 실행 검증으로 대신하지 않는다.

문맥 주소도 구분했다. 완결편 D4.00의 실제 쓰기 `06027062`는 **RESUME `060C6B60` +20 = `060C6B74`**다. F3는 이 공유 값을 읽으며 두 분기의 반환 코드는 각각 `F000` / `6004`다. CTX `060C6D70`의 +20과 같은 주소가 아니다. E9는 RESUME[0]과 CTX의 +68 깊이·반환 셀을 바꾸고, RESUME +20을 부모의 이전 값으로 되돌리지 않는다. 따라서 새 조회를 추가했을 때 부모의 조회값이 원래대로 남는다는 주장은 별도로 증명해야 한다. 기존 도구의 `effects` 목록은 커서 유래 쓰기만 일부 기록하므로, 절대 메모리 쓰기와 실제 네이티브 명령도 함께 대조했다.

### 가능성을 닫는 기준과 현재 결론

**원래 본문을 보존하면서 특정 턴 사건만 다른 페이즈에 옮기거나 새 조건 사건을 삽입할 수 있는 완전히 닫힌 범용 템플릿은 아직 확인하지 못했다.** 구조상 후보는 찾았다. 실제 Final 빈 root 5의 완료 재개점 실험과 F의 두 원본 사본 합성은 후보의 일부 계약을 이미 증명했다. 아래 차이가 남아 있으므로 제품 활성화나 신규 쓰기 권한으로 사용하지 않는다.

## 좁힌 사적 후보: 원래 적군 턴 사건의 조건만 확장

다음 단계에서는 페이즈 이동이나 새 동작을 만들지 않고, **완결편 물리 본문 9 / 선택 106의 기존 플래그 250 사건에 턴 조건만 조합**하는 별도 사적 후보를 만들었다. 이 선택 번호를 실제 화수로 표시하지 않는다. 승인 본문 SHA-256은 `d874925d9b8878b60ca52a7fe080aa73f16344d6955d3a01a02eabb496ecb575`다. 제품 코드·UI·개인 편집 허용 형식에는 연결하지 않았다.

### 후킹·네이티브 쓰기·원본 복원 계약

- 원래 F3 `2792..2796`만 3바이트 상대 분기와 0 패딩 2바이트로 바꾸고, 본문 끝에 조건 검사 코드를 붙인다. 기존 D4.00 `2790`, 플래그 동작 `2797`, E9 `2801`, 저장 재개점 `2802`, 14개 선언 root 및 원래 root 8 소비 코드는 그대로다.
- 새 코드는 기존 목적 조건 컴파일러의 분기 생성만 재사용한다. 허용 명령은 D4.00 / F2·F3·F4·F5 / 상대 분기 01뿐이다. 별도 0A·E9, 플래그·기체 생성·네이티브 helper·승리 처리·새 콜백 슬롯이 없다. 조건 충족은 원래 `2797`, 불충족은 원래 `2801`로 재합류한다.
- 새 조회는 **턴 조회만** 반복한다. 현재 승인 EXEC에서 F2~F5의 양쪽 네이티브 경로에는 절대 메모리 쓰기·외부 호출이 없고, 스크립트 커서만 바뀐다. D4.00이 마지막으로 남기는 RESUME +20은 원래 D4.00과 같은 게임 턴이다. 이 정적 footprint는 실제 콜백·부모 재개 대조를 대신하지 않는다.
- 원래 본문의 14개 root에서 기존 문법의 successor / 코드 단위 / gosub를 따라 967명령·463상대 포인터를 확인했다. 미해결·범위 밖·겹침은 없고, 교체하는 5바이트 안으로 들어오는 선언 root나 해독된 상대 참조도 없다. 별도의 거부 전용 원시 참조 검사도 내부 후보를 찾지 못했다. 그대로 보존한 E1 7개와 BF.00 1개의 외부·간접 소비 의미까지 모두 해독했다는 뜻은 아니다.

사적 형식 `SRWFTE01`은 기존 OB03 / SP01과 별개다. 80바이트 메타데이터에 원래 길이·후킹 위치·root 5·생성 코드 길이·결합 방식·최대 3개 턴 조건·승인 본문 SHA-256과 0 예약 바이트를 기록한다. 정규화는 승인 길이로 잘라 원래 F3 5바이트를 복원하고 SHA-256을 확인한 뒤, 같은 조건으로 재생성한 전체 바이트가 정확히 같을 때만 성공한다. 기존 편집이 섞인 본문·다른 글꼴·다른 본문을 허용한 형식은 아니다.

정적 사적 검사는 `turn >= 4 AND turn <= 4`, `turn = 4 OR turn = 5`, `turn >= 3 AND turn <= 7 AND turn != 5` 세 조합에서 각 256개 턴 값을 대조했다. 원본 보존과 정확한 정규화·재생성도 통과했다. 조합별 메타데이터 80개 단일 바이트 변조와 생성 코드 39 / 39 / 49개 단일 바이트 변조는 거부했다. 이 결과는 조건 분기와 형식 검증이며, 의미가 달라진 두 조합을 실제 게임에서 실행한 증거는 아니다.

### 기존 게임 저장에서의 실제 도달 준비와 한계

기존 저장 파일은 읽기 전용으로 검사했다. 프로젝트의 BKR 9,717개를 파일 SHA-256으로 226개로 합쳐 확인했으며, 원래 크기 0x1600에 checksum이 맞는 `SROBOTFC_02`의 진행 바이트는 `[37,105,104]`, payload SHA-256은 `615abe35d093765239c0a7267b286eba9d36524f4a84b97e85390ce3247384a4`였다. 그 원 BKR SHA-256은 `202009affbe2ee0aab462f142c7a769b47495b2e4b8710df9a962421884b69df`다. 최신 승인 이미지에서 생성된 저장이라는 출처는 확인되지 않았다. 이름 확장 실험으로 길이·내용이 바뀐 저장은 이 경로에서 제외했다.

최신 승인 c public-reference 홈의 원래 외장 BCR에는 별도의 `SROBOTFC_04`가 있다. 크기 0x1600·checksum 유효, 진행 바이트 `[38,106,105]`, payload SHA-256 `fd8def78f2cd5dd9f5fd9f687db6b84a3ea339da56a0f6de3d456c257599104a`, 원 BCR SHA-256 `7f842287b96c93b3ba16a906c626e2a1026a734be57e5693dd6eaa6ba260d445`다. 저장의 숫자·SCEDATA 번호만으로 화면의 완료 화수나 실제 도달을 단정하지 않는다.

이 원 BKR / BCR 바이트를 hash-pin하고, 승인 BIN과 사적 후보 각각 **별도 홈에서 MCA 없는 cold**로 저장 목록부터 확인했다. 저장 파일명은 `%f.%m.%x`로 확장자 앞 점을 포함한다. 현재 native `MakeFName`에서 소문자 `%m`은 hash만, 대문자 `%M`은 필요할 때 hash 뒤 점까지 포함한다. 첫 시도의 `%f.%M.%x`는 실제 `hash..bkr`를 만들어 원 저장을 읽지 못했으므로, `cold-1`과 그 후속 own MCA를 저장 불러오기·게임 도달 근거에서 제외했다. 새 `cold-2`는 올바른 이름으로 MCA 없이 다시 시작해 실제 원 외장 저장을 읽었다.

원 저장은 수정하지 않으며, MCA는 해당 이미지로 실제 생성한 own MCA만 후속 관측에 사용한다. RAM·미디어 ID·stage 변경은 사용하지 않는다. 성공하더라도 이전 릴리스 전체 저장 호환성의 보증으로 확대하지 않는다. 아래 실제 관측은 기존 저장에서 해당 본문으로 들어가는 제한된 경로의 근거이며, 페이즈 이동이나 새 조건 사건 지원 완료가 아니다.

다음 스테이지는 실제 인터미션 UP → A로 선택했고, 같은 A 도입 입력에서 첫 root 4 호출 두 번의 진입을 대조했다. 첫 `FFFC`는 창 프레임 2198, 커서 `20204107`, 부모 반환 `2021D2D6`, 내부 반환 `20221FEF`였다. 최초 E9 / FFF1은 프레임 2278에 `+524 = 20204254`를 저장했다. 다음 `FFFC`는 프레임 2874, 커서 `20204254`, 부모 `2021D352`, 내부 `20221FEF`로 들어가 실제 전함 출격 선택에서 기다렸다. 원본·후보의 이 두 호출과 슬롯·부모 문맥은 같았다. 후속 `story2-1` 창 프레임 1249의 두 번째 E9 / FFF1은 `+524 = 202042E3`를 저장했다. 원래 전함 선택·도입 처리는 두 이미지에서 같은 부모·슬롯으로 끝났다.

출격 선택에서는 START와 A가 완료시키지 않았고, B 뒤 C 단발이 넬아가마 선택 표시와 잔여 `1기 → 0기`, `이대로 좋습니까?` 확인을 만들었다. 확인 `예`에서 C 단발로 정상 도입 대사가 이어졌다. 실제 패드 입력·화면 변화로 기록하며, 추측한 컨트롤러 의미나 게임 메모리 수정으로 이 단계를 대체하지 않았다. 화면·추출 데이터는 저장소 밖에만 둔다.

위 채택된 각 창은 native 정상 종료, timeout 없음, hit 한도 미도달, trace close를 확인했고, 입력 전체 BIN과 원 MCA의 SHA-256을 재개 전후 확인했다. trace의 예약 RAM 변경 수는 0이고 미디어 ID override도 없다. 원 BKR / BCR은 바이트 그대로 별도 홈에 복사했으며 다른 이미지의 MCA를 쓰지 않았다.
